# 트러블슈팅 기록

문제를 **해결한 직후**에 쓴다. 나중에 쓰면 실제 출력을 잃고 기억으로 쓰게 되어 어긋난다 (CLAUDE.md 4.1절 — *"오류 메시지는 실제 출력을 복사한다"*).

## 언제 쓰나

| 쓴다 | 쓰지 않는다 |
|---|---|
| 빌드·기동·외부 연동이 실패해 복구했다 | 오타 수정 |
| 원인 찾는 데 10분 이상 걸렸다 | 테스트 1건 실패 → 바로 고침 |
| **문서·라이브러리 설명과 실제 동작이 달랐다** | 이미 검토서에 상세히 적은 것 → 한 줄 + 링크만 |
| **오류 없이 조용히 잘못되던 것**을 잡았다 | 설계 판단 변경 (그건 정정 이력) |
| 같은 실수를 두 번째 했다 | |

**조용히 잘못되는 유형은 반드시 쓴다.** 소리를 내며 죽는 건 다음 사람도 바로 안다. 조용한 건 기록이 없으면 몇 주를 헤맨다.

## 어디에

`docs/internal/검토서_트러블슈팅.md` **한 파일에 누적**한다. Phase별로 나누지 않는다 — 유지보수 담당자는 "어느 Phase였나"가 아니라 "이 증상이 뭐였나"로 찾는다.

- 파일이 없으면 아래 머리를 붙여 만든다
- 있으면 **1절 색인 표에 한 줄 추가** + **말미에 항목 추가**. 기존 항목은 고치지 않는다
- 번호는 `T-001`부터 순번. 재사용하지 않는다

## 형식 (이 순서 그대로)

```markdown
## T-0NN · <증상을 한 줄로> · YYYY-MM-DD

| 항목 | 내용 |
|---|---|
| **증상** | 사용자가 보는 것. **실제 출력을 그대로** |
| **환경** | Phase, 브랜치, OS, 관련 버전 |
| **원인** | 진짜 원인. "~인 것 같다"면 그렇게 쓴다 |
| **조치** | 무엇을 바꿨나. 커밋 해시 |
| **재발 방지** | 코드·테스트·검사·문서 중 무엇으로 막았나. 없으면 "없음 — 이유" |
| **확인 방법** | 다음 사람이 같은 증상인지 판별하는 명령 1~2줄 |
| **관련** | 검토서·요구사항·보류 결정 링크 |

### 왜 이런 일이 생겼나
(2~5줄. 다음 사람이 같은 함정을 피하려면 원인의 **구조**를 알아야 한다)
```

**"재발 방지"가 비어 있으면 그 항목은 미완이다.** 기록만 하고 막지 않으면 같은 일이 난다. 막을 수 없다면 왜 못 막는지 적는다 — 그것도 정보다.

## 파일 머리 (최초 생성 시)

```markdown
# 검토서 — 트러블슈팅 기록

- 용도: 유지보수 담당자가 "이 오류 본 적 있나"를 찾는 곳
- 규칙: 해결 직후 기록. 실제 출력 인용. 기존 항목은 고치지 않고 새 항목으로 정정
- 작성: `.claude/skills/troubleshoot/SKILL.md`에 따라 메인이 직접

## 1. 색인

| # | 증상 | 원인 한 줄 | 일자 | Phase |
|---|---|---|---|---|

## 2. 항목
```

## 쓰고 나서

1. `pnpm verify:docs` — 링크·경로 확인
2. 색인 표와 항목 번호가 맞는지 확인
3. 그 Phase의 `P*_검토서_SelfReview.md`가 있으면 "발견 사항"에서 `T-0NN`을 참조한다. 두 곳에 상세를 중복해 쓰지 않는다 — 검토서는 링크, 상세는 여기
