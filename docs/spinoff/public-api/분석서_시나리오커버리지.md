# 분석서 — 사용자 시나리오로 본 API 커버리지

- 작성일: 2026-10-02 / 작성 LLM: Claude Opus 5.5
- 물음 (사용자 원문): "현재 전체기능을 api 로 커버 가능한지 사용자 경험 시나리오 base 로 분석해"
- 기준 시나리오: [`windows체험판_기능점검표.md`](../../guide/shortcut/windows체험판_기능점검표.md) 1~19절의 점검 항목 120개 — 원 저장소가 "모든 기능을 화면에서 한 번씩"으로 쓴 목록이라 이것을 사용자 경험의 전수 목록으로 썼다. 세부는 [`사용자가이드.md`](../../guide/사용자가이드.md)
- 대조한 것: 화면용 API 97개 경로(`apps/api/src` 컨트롤러 전수)와 공유 스키마(`packages/shared/src/schemas.ts`)

## 0. 결론

**에이전트가 할 만한 일은 지금 API로 거의 전부 된다. 다만 그대로 열면 LLM 에이전트가 실제로는 쓰기 어렵거나 사람의 작업을 망가뜨리는 곳이 둘 있다(G1·G2).** 이 둘을 v1에서 풀어야 "커버한다"고 말할 수 있다.

| 판정 | 항목 수 | 뜻 |
|---|---|---|
| ○ 된다 | 79 | 지금 경로를 그대로 v1로 옮기면 같은 결과 |
| △ 되지만 모자람 | 15 | 경로는 있으나 에이전트가 쓰기에 형식·안전이 모자람 → G1~G5 |
| ✕ 경로 없음 | 2 | 화면만 하는 일 (텍스트·마크다운 복사) → G1이 함께 푼다 |
| — 제외 (사용자 결정) | 15 | 계정 흐름 11, 실시간 편집 4 |
| · 해당 없음 | 9 | 화면 조작 자체(접기·넓게 보기·단축키·붙여 넣기·인쇄·서버 끄고 켜기) |

## 2. 모자람과 제안

| # | 모자람 | 왜 문제인가 | 제안 (v1에서) |
|---|---|---|---|
| **G1** | **본문 형식이 ProseMirror JSON뿐이다** — 페이지·댓글을 쓰려면 JSON 트리를 만들어야 하고, 읽어도 JSON이다. 텍스트·마크다운 변환은 화면에만 있다 | LLM 에이전트는 마크다운을 잘 쓰고 JSON 트리는 자주 틀린다(허용 목록 밖 노드 → 400). 2차 개발자도 편집기 스키마를 알아야 한다. 점검표 4·9·11·12절과 LLM 붙여 묻기가 여기 걸린다 | 읽기: `format=json\|markdown\|text` (공유 함수 `pageMarkdown`·`pageText` 재사용 — 이미 A등급). 쓰기: `{ format: "markdown", body }`를 받아 **서버가 문서 JSON으로 바꾼 뒤 지금의 검증을 그대로** 거친다 — 마크다운→문서 변환은 새 A등급 순수 함수(`packages/shared`, 테스트 먼저). 왕복(문서→마크다운→문서)이 같은지를 성질 시험으로 본다 |
| **G2** | **실시간 편집 중인 페이지에 REST로 저장하면 사람들의 저장 전 입력이 버려진다** — 협업 방은 정본이 앞서 있으면 상태를 버리고 연결을 닫는다(`apps/api/src/pages/collab/collab.gateway.ts` 926행). 지금 화면에서는 같은 페이지를 REST로 저장할 일이 드물어 드러나지 않았다 | 에이전트는 사람이 편집하는 중에도 쓴다. 에이전트의 저장 한 번이 사람의 몇 초~몇 분 치 입력을 **조용히** 지운다 | (가) 방이 열려 있으면 409 `PAGE_BEING_EDITED` — 에이전트가 기다렸다 다시 한다 (나) 방을 먼저 저장(flush)하고 그 버전을 기준으로 409 판정 — 에이전트는 바뀐 기준 버전을 받는다. **추천 (가)** — 단순하고 사람의 입력을 절대 건드리지 않는다. 결정 요청 |
| **G3** | 관리 기능의 토큰 사용 — 비밀번호 초기화가 임시 비밀번호를 돌려준다. 세션 강제 종료·정지가 토큰을 끊지 않는다(토큰이 없던 때의 설계) | 토큰이 새면 그것으로 다른 계정을 넘겨받는다. 정지한 사람의 에이전트가 계속 돈다 | 비밀번호 초기화는 토큰으로 열지 않는다(화면 전용). 세션 강제 종료·정지·비밀번호 변경이 그 사람의 토큰을 **함께** 폐기한다. 관리 기능은 `admin` scope(계획서 Q4) |
| **G4** | 빵부스러기·조상 경로 전용 경로가 없다 | 트리 전체를 받아 계산해야 한다 — 큰 공간에서 무겁다 | 페이지 읽기 응답에 `ancestors`(id·제목) 더하기 — v1 응답에만 |
| **G5** | 그림 넣기 — 첨부를 올린 뒤 그 첨부 주소를 문서의 그림 노드에 넣어야 한다. 주소 모양이 문서화돼 있지 않다 | 에이전트가 주소를 지어내면 400(이미지 출처는 내부 첨부만) | 첨부 응답에 문서에 넣을 주소(`src`)를 싣고 API 사용가이드에 예를 둔다. G1의 마크다운 쓰기에서는 `![이름](첨부 주소)`를 받는다 |

## 3. 커버리지 판정

- **G1·G2를 풀면** ○가 79 → 93(△ 12개 + ✕ 2개)이고, **G3·G4까지 풀면 96** — 남는 것은 사용자가 뺀 15개와 화면 조작 9개뿐이다(120 − 15 − 9 = 96) → **"전체 기능을 API로 커버한다"고 말할 수 있다.**
- G3은 커버리지가 아니라 **안전**의 문제다 — 풀지 않고 열면 안 된다.
- G4·G5는 편의다. 없어도 되지만 에이전트의 호출 수와 실수를 줄인다.

## 4. 이 분석이 보지 않은 것

- 응답 시간·빈도 — 에이전트는 사람보다 자주 부른다. 빈도 제한 값은 설계서에서 실측으로 정한다.
- 점검표에 없는 기능 — 점검표가 전수라는 가정에 기댔다. 사용자가이드 27절 "화면에 아직 없는 것"은 API에도 없다.
- 실제 호출 — 이 분석은 코드와 문서를 읽은 것이다. 이 서버에 아직 Node가 없어 돌려 보지 못했다(계획서 8절 위험 1).
