## 2. 실측 — "상태 벡터로 판정하면 안 된다"

작성자 오염(FR-802)을 고치는 방법으로 **① 적용 전후의 상태 벡터 비교**와 **② Yjs의 `update`
이벤트**를 놓고 재 봤다. ①이 간단해 보였다.

```
빈 문서 전체상태 적용: update이벤트 0회 상태벡터변화=false
이미 아는 상태 되돌려받음: update이벤트 0회 상태벡터변화=false
글자 추가:            update이벤트 1회 origin=["member-A"] 상태벡터변화=true
순수 삭제:            update이벤트 1회 origin=["member-A"] 상태벡터변화=false   ← 여기
```

**①을 골랐으면 "지우기만 한 편집"이 저장되지 않았다.** 상태 벡터는 만들어진 항목의 시계만
담고 삭제는 담지 않는다. ②로 갔다.

앞의 두 줄이 문제의 원인이기도 하다 — 화면은 접속 직후 자기 빈 문서를 한 번 보내는데, 서버가
**`MSG_UPDATE`를 받았다는 사실만으로** 작성자를 바꾸고 있었다.

## 4. 실제로 동작시켜 확인한 것

### 4.1 컨테이너 + nginx 경유 WebSocket (TLS 검증 **켠 채**)

`NODE_EXTRA_CA_CERTS=deploy/certs/cert.pem`로 사내 CA를 신뢰시키고 `rejectUnauthorized`는
건드리지 않았다 (7절).

```
로그인 OK
페이지 28e30185-dbff-4216-8f7d-65143e65b18a
✅ 같은 Origin — 연결됨
✅ 초기 상태 수신 55바이트
— 다른 Origin: 거부 401
— Origin 없음: 거부 401
```

`https://evil.example.internal`을 `Origin`으로 보내면 401, 아예 없어도 401이다 (FR-806).

### 4.2 하트비트와 즉시 파기

```
✅ 연결됨. 35초 동안 하트비트를 본다 (WF_COLLAB_PING_MS 기본 30000)
  ping 1회 (02:49:49)
✅ 하트비트 1회 — nginx proxy_read_timeout 300s보다 자주 온다
강제 종료를 부른다 (user=5cb80026-…)
  응답 201
✅ 편집 연결이 즉시 끊겼다 — code 1008 "세션 파기"
```

**관리자가 강제 종료를 누른 그 순간 편집 연결이 끊겼다.** 주기를 기다리지 않는다 (FR-805).

### 4.3 혼자 오래 열어 두기

nginx `proxy_read_timeout 300s`가 끊는지 본다. **혼자 있고 아무것도 치지 않는다** — 여럿이면
서로의 글자가 오가서 이 시험이 성립하지 않는다.

```
✅ 390초(6.5분) 동안 혼자 열어 두었는데 끊기지 않았다. 서버 ping 13회
```

390초 / 30초 ≈ 13이라 ping이 빠짐없이 갔다. **하트비트가 없던 Phase 6에서는 300초에 끊겼다** —
편집 화면에 "연결이 끊겼다"가 뜨고, 그 뒤에 쓴 것은 아무에게도 가지 않았다.

## 7. 확인하지 못한 것

- **실연동은 여전히 없다.** 사내 IdP(보류 11)·사내 메일(보류 18) 둘 다 모의로만 확인했다.
- **재판정 주기의 실제 지연을 운영에서 재지 않았다.** 기본 5분이고, 그 5분은 "Crew에서 빠진
  사람이 계속 쓸 수 있는 최대 시간"이다. 세션을 끊는 동작은 즉시라 여기 해당하지 않는다.
- **동시 편집자를 많이 놓고 재지 않았다.** 매초 DB 질의를 없앤 것(코드 리뷰 13)의 효과를
  숫자로 보여 주지 못한다. 보류 14(쓰기·고장 상황 측정)에 함께 둔다.
- **`taskList` 제거가 기존 문서를 거부하는지**는 개발 DB 25건에서 0건임을 확인한 것이 전부다.
  운영 데이터는 아직 없다(반입 전).
- 6.5분 유지 시험은 **이 호스트의 nginx 설정**(`proxy_read_timeout 300s`)에 대한 것이다.
  폐쇄망의 앞단에 다른 장비가 있으면 그쪽 유휴 타임아웃을 따로 봐야 한다.
