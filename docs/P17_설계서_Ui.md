# P17 설계서 — Ui (Windows 체험에서 나온 개선 — F-010)

Phase 17은 사용자가 Windows 묶음(F-009)을 써 보고 적은 개선 열 가지(`docs/기능백로그.md` F-010)를 한다. 조각으로 나눠 끝낸 것부터 적는다 —
비밀번호 변경 화면(1·9번), 편집기와 댓글의 쓰는 칸(4·5번), 시스템 관리자 아이디 찾기 안내(7번), 비밀번호 초기화 요청 알림과 모든 화면의 알림 영역(8번).
화면 전면(2·3·6번)과 감사 로그 레벨(10번)은 그 조각을 할 때 이 문서에 더한다.

- 요청 원문: `docs/prompts/phase17/scope.md`
- 요구사항 번호: **FR-1800**, 비기능 **NFR-170**부터
- 선행: [`docs/P4_설계서_Admin.md`](P4_설계서_Admin.md) C절(알림함) · [`docs/P1_설계서_Auth.md`](P1_설계서_Auth.md) FR-208·209a(계정 찾기 — 같은 모양의 응답) ·
  [`docs/P11_설계서_Ops.md`](P11_설계서_Ops.md) D.1(관리의 우열 — 위임까지 본다) · [`docs/P13_설계서_Readiness.md`](P13_설계서_Readiness.md)(비밀번호 변경·정지)
- 구조: [`docs/설계서_Architecture.md`](설계서_Architecture.md)

> **첫 판 2026-09-28** — 끝낸 조각(1·9, 4·5, 7, 8)을 적었다. 2·3·6은 참고 자료(Confluence·웹어워드코리아 2025 수상작)를 조사해 우리 근거로 이 문서의 새 절에

## A.1 묻지 않고 정한 것 — 근거와 되돌릴 조건 (8번)

| # | 정한 것 | 근거 | 되돌릴 조건 |
|---|---|---|---|
| 1 | 초기화 요청은 그 사람을 **관리할 수 있는** 활성 관리자·시스템 관리자에게만 간다 — `canManageUser` 한 곳 | 알림을 받고도 초기화 단추가 막히면 쓸모가 없다. 관리의 우열(위임까지 — P11 보안 검토 1)을 다시 구현하면 사용자 관리 화면과 어긋난다 | — |
| 2 | 알림은 **넣은 아이디와 email이 활성 계정과 맞을 때만** 만든다. 응답은 그대로 같다(FR-208·209a) | 맞지 않은 요청까지 알리면 누구나 관리자의 알림함을 채울 수 있다. 맞지 않은 요청은 감사로그(`auth.password.recover`, `found: false`)에 있다 | — |
| 3 | 응답은 알림을 **기다리지 않는다**(NFR-170) | 맞을 때만 쓰기가 하나 더 붙는다 — 기다리면 걸린 시간이 "그런 계정이 있다"를 말한다 | — |
| 4 | 읽지 않은 같은 요청이 있으면 또 만들지 않는다(FR-1802). 확인과 쓰기 사이를 잠그지 않는다 | 로그인하지 않은 경로라 되풀이할 수 있다(IP별 제한이 있어도 쌓인다). 동시에 둘이 오면 같은 알림이 두 개 생길 수 있다 — 해가 없어 잠그지 않는다 | 같은 알림이 겹쳐 보인다는 보고가 오면 부분 유일 색인을 둔다(마이그레이션) |
| 5 | 누가 초기화하면 그 사람의 요청 알림은 받은 사람 **모두에게서** 읽음이 된다(FR-1803) | 둘이 같은 요청을 받아 둘 다 초기화하면 먼저 전한 임시 비밀번호가 쓸모없어진다 | — |
| 6 | 관리자에서 내려가면 초기화 요청 알림은 목록에도 안 읽은 수에도 없다(FR-1804) — 지우지 않는다 | 누가 초기화를 요청했는지는 관리자의 일이다. 다시 올라가면 그대로 보인다 | — |
| 7 | 알림 영역은 **화면 맨 위 오른쪽의 한 줄**이다 — 화면 위에 떠 있지 않는다(펼친 목록만 뜬다). 스페이스 목록 머리말의 **알림 (N)** 링크는 뺐다 | 떠 있으면 각 화면 오른쪽 위의 단추를 가린다. 같은 수를 두 곳에 두면 한쪽이 늦게 센다 | 화면 전면(2·3·6번)이 머리말을 새로 짜면 거기로 옮긴다 |
| 8 | 안 읽은 수는 **화면을 옮길 때와 30초마다** 다시 묻는다(`NOTIFICATION_POLL_MS`). 서버가 밀어 주지 않는다 | 동시 세션이 수십이면 1초에 몇 번이다. 밀어 주려면 알림마다 WebSocket 경로가 하나 더 필요하다 | 알림이 늦다는 보고가 오면 간격을 줄이거나 밀어 주는 길을 만든다 |

## B. 요구사항

| # | 요구사항 | 확인 |
|---|---|---|

## C. 데이터·API (8번)

- **마이그레이션 없음.** `notifications.kind`는 `text`이고 CHECK가 없다(`0004_admin`), `page_id`·`actor_id`는 비울 수 있다(`0008`). 종류는 `NOTIFICATION_KINDS`(`packages/shared/src/constants.ts`)가 정한다 — 초기화 요청은 `password.reset.request`, `actor_id`가 요청한 사람, 페이지·댓글은 없다.
- `NotificationView`에 `actorUsername`을 더했다 — 초기화 요청일 때만 싣고 멘션은 `null`이다(부른 사람의 아이디를 새로 내보내지 않는다).
- 경로는 그대로다(`GET /api/notifications`·`unread-count`, `POST :id/read`·`read-all`). 목록·안 읽은 수·모두 읽음이 FR-1804의 조건을 같이 쓴다(`NotificationsService.visibleKinds`).
- 만들기: `NotificationsService.notifyPasswordResetRequest` — `AuthService.recoverPassword`가 맞는 계정일 때 기다리지 않고 부른다. 읽음: `NotificationsService.resolvePasswordResetRequests` — 사용자 관리의 초기화(`UsersController.resetPassword`)가 같은 트랜잭션에서 부른다.

## D. 화면 (8번)

- `apps/web/src/components/NotificationBell.tsx` — 모든 화면의 알림 영역(`App.tsx`가 경로들 위에 둔다). 로그인하지 않았거나 비밀번호를 바꿔야 하면 그리지도 묻지도 않는다.
- `apps/web/src/components/NotificationText.tsx` — 알림 한 건의 글. 알림함과 알림 영역이 같이 쓴다.
- `apps/web/src/pages/admin/AdminUsersPage.tsx` — 주소의 `?q=`를 찾기 칸에 넣는다(알림의 링크).
- `apps/web/src/pages/FindAccountPage.tsx` — 요청 뒤의 말: "아이디와 email이 맞으면 관리자의 알림에 간다" — 맞지 않아도 같은 말이다.

## H. 남는 것

- 확인과 쓰기 사이를 잠그지 않아 동시 요청은 같은 알림을 둘 만들 수 있다(A.1-4).
- 알림 영역은 탭이 가려져 있어도 30초마다 묻는다. 지금 규모에서 무시할 만하다.
- 관리할 수 없게 된 관리자(대상이 뒤에 그 관리자가 못 하는 위임을 받았다)에게도 받은 알림은 남는다 — 초기화 단추는 그때의 판정으로 막힌다(사용자 관리가 까닭을 말한다).
