명령: `pnpm release:bundle` → `pnpm release:verify <경로>`.

| 항목 | 실측 |
|---|---|
| 묶음 만들기 시간 | **7.4초** (NFR-51 목표 5분) |
| 묶음 크기 | **264MB** · 파일 9개 |
| `images.tar` | 264MB (이미지 3종) |
| app 이미지 | **389MB** (8.2절 예산 400MB 이하 — **통과**) |
| postgres:17 | 641MB |
| nginx:1.27-alpine | 73MB |
| SBOM | CycloneDX 1.5 · 부품 **199개** |
| 라이선스 목록 | 201줄 |
| 매니페스트 | `version=0.1.0` · `gitSha` · `builtAt` · `image=` 3줄 |

### 2.1 검사가 실제로 잡는지 확인했다 — **세 가지를 일부러 깨뜨려 봤다**

```
$ pnpm release:verify .local/release/2026-09-22
[verify] 통과 — 필수 8개 · 체크섬 8개 일치
```

그다음 `MANIFEST.txt`를 **한 글자 고치고** 다시 돌렸다.

```
[verify] 실패 — 1건
  MANIFEST.txt: 체크섬이 다르다
```

그다음 `MANIFEST.txt`에서 `version=` 줄을 지웠다 → `매니페스트에 version가 없다`.
그다음 `images.tar`를 치웠다 → `필수 파일이 없다`.

셋 다 되돌린 뒤 다시 `통과 — 필수 9개 · 체크섬 8개 일치`.
**통과하는 것만 보면 그 검사가 아무것도 안 하고 있어도 모른다.**

> 자체 점검이 이 검사에서 **두 구멍**을 찾았다. ① 가장 중요한 `images.tar`가 **필수 목록에
> 없었다** — 체크섬 목록에 우연히 들어 있는 것으로만 간접 확인됐다. ② `parseManifest`의
> 호출자가 테스트뿐이어서 FR-603("버전·sha가 없으면 거부")이 **실제로는 강제되지 않았다** —
> 매니페스트를 파싱하지 않고 그냥 출력했다. 둘 다 고친 뒤 위처럼 확인했다.

### 2.3 `env.template`은 compose에서 뽑는다

처음에는 개발용 `.env.example`을 그대로 썼다. 그래서 **compose가 요구하는 키가 빠지고**
(`WF_PG_PASSWORD`·`WF_HTTPS_PORT`·`WF_APP_IMAGE`) compose가 읽지도 않는 개발 키
(임베디드 DB 경로·테스트 DB URL·모의 OIDC)가 들어 있었다 — 작업자가 채워도 아무 효과가
없고, 정작 채워야 하는 것은 목록에 없다.

지금은 **`deploy/compose.yml`이 실제로 참조하는 변수**를 뽑는다. `build:` 블록 안은
위치로 빼낸다(사내 프록시는 빌드용이고 폐쇄망에서는 채울 이유가 없다). 목록이 코드와
어긋날 수 없고, 손으로 관리하는 이름 목록도 없다.

실측: **19개.** 전부 `WF_*`이고 빌드용 프록시 셋은 빠졌다.

체크섬 형식은 `sha256sum`과 호환한다 — 폐쇄망에 우리 스크립트가 없어도
`sha256sum -c SHA256SUMS`로 검사할 수 있다.

### 2.2 `docker load` 리허설과 마이그레이션

**우리 이미지만 지우고 tar에서 되살렸다.** 공유 서버라 `postgres:17`·`nginx:1.27-alpine`은
건드리지 않았다 — tar 안에 있는 것만 확인했다.

```
$ docker rmi workfluence-app:latest
$ docker load -i .local/release/2026-09-22/images.tar
Loaded image: workfluence-app:latest
Loaded image: postgres:17
Loaded image: nginx:1.27-alpine
```

되살린 뒤 기동 → `/api/health` **200**, `{"status":"ok","db":"ok"}`.

**반입 절차서의 마이그레이션 명령을 그대로 돌렸다.** 이 서버에 Node가 없다고 가정하고,
이미지 안의 것만 쓴다.

```
$ docker compose -f compose.yml --env-file .env run --rm api node dist/db/migrate.js
[migrate] /app/api/drizzle → postgres://***@postgres:5432/workfluence
[migrate] 7개 마이그레이션 적용 상태
```

한 번 더 돌려 같은 출력을 확인했다 (멱등). 이미지 안에 `dist/db/migrate.js`와
`drizzle/*.sql`이 함께 들어 있어 **저장소 없이도 마이그레이션이 된다** — 이 경로가
성립하는지는 이번에 처음 확인했다.

> 중간에 한 번 실패했다. 내가 앞서 `0006`을 **psql로 손수 적용해** 제약은 생겼는데
> journal에는 없는 상태였고, 마이그레이션이 `MergeWithExistingConstraint`로 거부했다.
> 손으로 적용한 것을 되돌린 뒤 정상 동작했다. **마이그레이션 러너 밖에서 스키마를
> 건드리면 journal이 어긋나고, 그 뒤 정상 경로가 깨진다.**

> **확인 못 한 것**: 진짜 폐쇄망(인터넷 없음)에서의 `docker load`. 이 서버는 프록시 뒤지만
> 인터넷이 있다. 다만 `docker load`는 네트워크를 쓰지 않으므로 차이가 날 여지는 작다.

## 3. 백업·복원 (FR-610 ~ FR-617)

| 항목 | 실측 |
|---|---|
| `pnpm backup:create` 시간 | **3.7초** (현재 데이터 규모) |
| 출력 | `마이그레이션 6개 · users 1 · spaces 2 · pages 2 · page_versions 2 · attachments 2 · comments 1 · audit_events 182 · notifications 0` |
| 위치 | `.local/backups/<UTC 시각>/` (인자로 변경 가능) |
| 방식 | `pg_dump -Fc` + 첨부 디렉토리 |

### 3.1 복원 리허설 — 실제로 지우고 되살렸다 (FR-617)

**두 번 했다.** 첫 리허설은 api를 멈추지 않고 돌렸고, 그래서 아래 결함을 통과시켰다.

볼륨 `deploy_postgres_data`와 `deploy_attachments`를 **실제로 지우고** 백업에서 복원했다.

| 확인 | 결과 |
|---|---|
| 모든 테이블 행 수 | 백업 시점과 **전부 일치** |
| 첨부 파일 | **서로 다른 sha256 덩어리 수**로 비교해 일치. 행 수가 아니라 덩어리 수로 보는 이유는 같은 파일을 여러 곳에 붙이면 행은 늘고 파일은 안 늘기 때문이다 |
| 복원 후 기동 | `/api/health` 200 |
| **비어 있지 않은 대상에 복원** | **거부한다.** 운영 데이터를 실수로 덮어쓰지 않게 만든 장치다 |

### 3.2 첫 리허설이 놓친 것 — 복원이 절반만 되고 되돌릴 수도 없었다

자체 점검이 찾았다. `backup-restore.ts`가 첨부를 `docker compose exec api tar`로 풀었는데,
**복원 절차의 첫 단계는 "api를 멈춘다"**(`운영가이드_장애대응.md` 7.18절)다. `exec`는
떠 있는 컨테이너에만 붙으므로 그 뒤에 부르면 실패한다 — **DB는 이미 복원됐고 첨부만 빠진
상태**로 예외가 나고, 다시 돌리면 "비어 있지 않다"로 거부되어 첨부를 되살릴 길이 없다.

첫 리허설이 통과한 이유는 **문서가 정한 순서를 따르지 않았기 때문**이다. api를 멈추지
않고 돌렸다. 절차서를 만들었으면 **그 절차서대로 리허설해야 한다.**

`run --rm --no-deps`로 바꿨다 — 새 컨테이너를 띄우므로 api가 떠 있든 멈춰 있든 같게
동작하고, 볼륨 이름을 손으로 적지 않아도 compose가 같은 마운트를 붙인다. 백업 쪽도
같은 이유로 함께 고쳤다.

### 3.3 두 번째 리허설 — **문서 순서 그대로** (2026-09-22)

| 단계 | 결과 |
|---|---|
| ① api가 살아 있는 상태에서 백업 | 통과. `audit_events 183` |
| ② `stop api nginx` | — |
| ③ **멈춘 상태에서 백업** | **통과.** 고치기 전에는 여기서 깨졌다. `audit_events 184` |
| ④ 볼륨 `deploy_postgres_data`·`deploy_attachments` 삭제 | — |
| ⑤ postgres만 띄우고 **api 없이 복원** | **통과.** 행 수 8개 표 전부 일치, 첨부 덩어리 1 = 디스크 파일 1 |
| ⑥ 전체 기동 | `/api/health` 200, 세 서비스 `healthy` |

### 3.4 행 수 대조를 "하한"으로 바꿨다

백업은 행 수를 **덤프보다 먼저** 센다. 주석은 그것을 "하한"이라고 설명했는데 복원 쪽은
**완전 일치**를 요구했다 — **주석과 코드가 반대말을 하고 있었다.**

주간 백업은 서비스가 도는 채로 뜨므로 로그인 하나만 끼어도 `audit_events`가 늘어난다.
완전 일치를 요구하면 **복원이 다 끝난 뒤에** 그것을 불일치로 보고 예외를 던지고, DB는
이미 비어 있지 않아 다시 시도할 수도 없다. 지금은 **모자란 것만 실패**로 보고, 넘치는
것은 "백업 도중 들어온 쓰기"로 알려 준다.

> NFR-52(빈 볼륨 복원 10분 이내)는 현재 데이터 규모에서 분 단위에 못 미친다.
> **운영 규모에서 다시 재야 하는 수치다** (10절).

## 4. 부하 측정 → 보류 6 판정 (FR-620 ~ FR-623)

명령: `pnpm load:test`. 대상은 **컨테이너 스택**(nginx → api → postgres)이고 TLS 검증을
켠 채로 재었다(`NODE_EXTRA_CA_CERTS`). 합성 페이지 5,000건, 합성 계정 1개로 50세션.

```
동시 50세션 × 10회 — 표본 2000개, 오류 0개
```

| 단계 | p50 | p95 | max |
|---|---|---|---|
| 스페이스 목록 | 191ms | 574ms | 667ms |
| 검색 (한글 2글자 "회의") | 433ms | **602ms** | 742ms |
| 알림 수 | 173ms | 359ms | 588ms |
| 감사로그 | 84ms | 216ms | 572ms |

**가장 느린 단계의 p95 602ms < 1,000ms · 오류 0건** → NFR-50 통과.
**보류 6을 닫는다 — 앱 서버를 이중화하지 않는다.**

측정에 쓴 합성 계정·스페이스·페이지 5,000건은 **지웠다** (FR-622). 정리 후 `users 1 · pages 2 · spaces 2`.

### 4.1 이 측정의 실제 결과물은 숫자가 아니다

부하 측정이 **결함 둘을 찾았다.** 둘 다 요청을 한 번에 하나씩 보내면 드러나지 않는다.

| # | 결함 | 증상 | 기록 |
|---|---|---|---|
| 1 | 트랜잭션 안에서 풀에 **두 번째 연결**을 요청 | 동시 로그인이 풀 크기(10)에 닿자 **앱 전체가 영구히 멈췄다.** 오류도 로그도 없다. CPU 0.19%, DB를 안 타는 경로는 18ms에 응답 | T-026 |
| 2 | `@UseGuards`의 가드가 provider와 **다른 인스턴스** | 로그인 제한 환불이 **한 번도 동작한 적이 없었다.** 성공 로그인 21번째부터 429 | T-027 |

그리고 **자체 점검이 같은 계열의 결함 셋을 더 찾았다.** 셋 다 측정으로는 안 드러났다.

| # | 결함 | 왜 측정으로 안 드러났나 |
|---|---|---|
| 3 | 요청 제한 청소가 **호출한 쪽의 창**으로 모든 키를 판정 | 로그인(60초) 트래픽이 가입(600초) 예산을 리셋한다. 부하 측정은 **로그인만** 던졌으니 서로 다른 창이 섞이는 상황이 없었다 |
| 4 | `changeRole`이 트랜잭션 안에서 `this.db`로 센다 (T-026 잔존) | 역할 변경은 부하 시나리오에 없다. 읽기만 재면 쓰기 경로의 같은 결함은 안 보인다 |
| 5 | 복원이 절반만 되고 되돌릴 수도 없다 | 3.2절 |

3번은 회귀 테스트 2건을 뒀다 — 짧은 창 요청이 긴 창 예산을 건드리지 않는지, 그리고
자기 창이 지나면 정상적으로 풀리는지. 4번은 전수 조사를 **위치로** 다시 돌려
`tx`를 받는 메서드 안에서 `this.db`를 쓰는 곳이 하나도 없음을 확인했다.

1번 수정은 두 겹이다. ① 조회 도우미에 `tx`를 넘긴다. ② 풀에 `connectionTimeoutMillis`
10초와 `idle_in_transaction_session_timeout` 30초를 걸어 **새는 곳이 또 생겨도 멈추지 않고
실패**하게 했다 (`packages/shared`의 `DB_POOL`).

회귀 테스트는 **고친 코드를 되돌려 실제로 실패하는 것을 확인했다.**

| 테스트 | 무엇을 본다 |
|---|---|
| `auth.integration.spec.ts` — "동시 로그인이 연결 풀을 잠그지 않는다" | 테스트 풀(4)의 두 배를 동시에 던져 20초 안에 전부 돌아오는지. 되돌리면 20초를 넘겨 죽는다 |
| `rate-limit.guard.spec.ts` — "가드 인스턴스가 달라도 같은 예산을 본다" | 가드 **둘**이 한 저장소를 공유하는지. 예전 구조에서는 실패한다 |

컨테이너 실측: 성공 로그인 **50회(10개씩 다섯 묶음) 전부 201**. 고치기 전에는 21번째부터 429였다.

## 5. 자동 기동 (FR-624)

공유 서버라 재부팅할 수 없다. 설계서 C절의 대안 절차로 확인했다.

| 확인 | 명령 | 결과 |
|---|---|---|
| 도커가 부팅 시 뜨는가 | `systemctl is-enabled docker` | `enabled` (`is-active`: `active`) |
| 세 서비스에 재시작 정책이 있는가 | `docker inspect` | 셋 다 `unless-stopped` |
| 세 서비스에 헬스체크가 있는가 | `docker compose ps` | 셋 다 `(healthy)`. **nginx에는 없어서 이번에 넣었다** |
| 정책이 실제로 되살리는가 | `workfluence-app` 이미지 + `--restart unless-stopped`로 곧 죽는 컨테이너 | `RestartCount` **0 → 6 (35초)**. 확인 후 삭제 |

### 5.1 처음 쓴 두 방법은 아무것도 확인하지 못했다 (T-025)

| 방법 | 결과 | 왜 |
|---|---|---|
| `docker kill workfluence-api` | 되살아나지 않는다 | 도커가 `kill`도 **"사람이 멈춤"으로 기록**해 정책을 건너뛴다 |
| 컨테이너 안에서 `kill -9 1` | 아무 일도 없다 | 커널이 **네임스페이스 안에서 PID 1로 보낸 신호를 무시**한다. 오류도 안 난다 |

**두 명령 모두 종료 코드 0으로 끝났다.** `RestartCount`를 안 봤다면 "자동 기동 확인 완료"로
적었을 것이다 — 한 번은 정책이 안 걸린 줄 모르고, 한 번은 죽인 적도 없으면서.

> **확인 못 한 것**: **실제 재부팅.** 공유 서버라 할 수 없다. 반입 당일 절차에 넣었다
> (`docs/운영가이드_반입.md`). 위 확인은 재부팅과 **같지 않다.**
