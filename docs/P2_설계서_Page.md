# 2. 스페이스

## 2.1 접근 컨텍스트

서비스는 스페이스 행·내 멤버십·멤버 수를 모아 `spaceAccess()`에 넘기고 결과만 쓴다.
**판정을 서비스에 다시 쓰지 않는다** — Phase 1의 가드와 같은 규칙이다.

```
context(spaceId, principal) → { space, membership, memberCount, access }
  access.canRead  == false → 404 (403이 아니다. 존재 자체를 알리지 않는다)
  access.canWrite == false → 403
```

> **읽을 수 없는 스페이스는 404다.** 403을 주면 "그 스페이스는 있다"가 새어 나간다.
> Phase 1의 계정 열거 방지와 같은 판단이다.

## 2.2 마지막 owner 보호 (FR-312)

owner가 하나뿐이면 제거도 강등도 막는다. 주인 없는 팀 스페이스는 아무도 Crew를 바꿀 수 없어
관리자만 손댈 수 있는 상태가 된다. 마지막 root 보호(FR-233)와 같은 종류의 잠금 방지다.

## 2.3 개인 스페이스 자동 생성 (FR-309)

사용자 승인 트랜잭션 **안에서** 만든다. 따로 두면 승인은 됐는데 스페이스가 없는 계정이 생긴다.

# 3. 페이지

## 3.1 버전과 충돌 (FR-322, FR-323)

```
저장 요청 { title, content, baseVersionNo }
  → 트랜잭션 시작
  → SELECT ... FOR UPDATE  (같은 페이지의 동시 저장을 줄 세운다)
  → locked.current_version_no != baseVersionNo → 409 + 현재 버전 번호
  → page_versions에 nextNo 추가 (append-only)
  → pages.current_version_no = nextNo
```

**409만으로는 부족하다.** 두 요청이 같은 `baseVersionNo`로 동시에 들어오면 둘 다 검사를
통과하고 같은 `versionNo`를 쓰려다 unique 위반으로 죽는다. `FOR UPDATE`가 줄을 세운다.

**화면은 덮어쓰기 버튼을 주지 않는다** (FR-343). 최신을 불러와 다시 편집하게 한다. 덮어쓰기를
한 번 허용하면 남의 저장을 지우는 것이 정상 동작이 된다.

## 3.2 복원 (FR-325)

과거 버전의 내용으로 **새 버전을 만든다.** 되돌리는 것이 아니라 앞으로 붙이는 것이다.
그래야 "언제 무엇으로 되돌렸는지"가 이력에 남는다.

## 3.3 트리 (FR-326 ~ FR-328)

부모를 따라 올라가며 본다 — 자기 자신을 만나면 순환, 다른 스페이스면 거부, 깊이 한도를 넘으면
거부. 깊이가 10이므로 최대 10회 조회다.

판정 자체(무엇이 순환인가·한도를 넘었나)는 A등급 순수 함수로 빼고, 조회는 서비스가 한다.

| 화면 흐름 | C | E2E: 스페이스 생성 → Crew → 페이지 작성·편집 → 충돌 → 복원 |
