## 4. 브라우저 — E2E

새 빌드(`pnpm build`)를 호스트 `:3100`에 띄우고 `pnpm test:e2e`(대상은 `E2E_BASE_URL`로 `:3100`) — **36 통과 · 실패 0 · 건너뜀 0 (2.7분).** (마지막 실측으로 채운다)

- **관리자가 건 중지는 권한을 받은 주인만 푼다**(Phase 15의 흐름)에 Crew 칸을 더했다 — 관리자가 중지한 뒤 주인의 공간 화면에 "관리자가 중지한 스페이스라 Crew를 바꾸지
  못한다 — 관리자에게 부탁한다. 다시 쓰게 되면 주인도 바꾼다."가 보이고 **아이디로 Crew 추가** 칸이 없다 → 관리 권한을 받은 주인이 **다시 쓰기**로 푼 뒤 그 칸이 돌아온다.
- 권한을 받은 뒤 새로 고치면(다시 쓰기 전) Crew 칸에 "관리자가 중지한 스페이스라 Crew를 바꾸지 못한다 — 스페이스 관리의 다시 쓰기로 먼저 풀면 바꾼다."가
  보이고 넣기 칸이 여전히 없다(병합 전 검토 반영).
- 첫 실행에서 한 건(멘션 → 알림함 → 휴지통 복원 → 라벨)이 페이지 **삭제**와 댓글 **삭제**를 함께 잡아 실패했다 — Phase 3부터의 흔들림이다(T-071). 셋째 단계가 저장
  전 댓글 칸의 글자로 통과하던 기다림을, 댓글 POST의 응답과 저장된 댓글의 삭제 단추를 기다리게 고쳤다.

## 9. 확인하지 못한 것

- **경합을 브라우저로** — E2E는 관리자의 중지와 주인의 Crew 변경이 겹치는 순간을 지나지 않는다. 통합 시험이 앞의 일을 커밋 전에 붙잡아 두고 본다(NFR-161).
- **반대 방향의 write skew**(설계서 L — 상태 바꾸기가 자기 자리를 옛 값으로 읽는다) — 시험하지 않았다. 결과가 더 엄격한 쪽이라 남는 것으로 적었다.
- **잠금의 비용** — Crew 변경마다 공간 행을 나눠 잠근다. Crew 변경끼리는 기다리지 않고 상태 바꾸기만 줄을 선다. 동시 부하로 재지 않았다(Crew 변경은 드물다 —
  보류 14에 더할 때).
- **Windows에서** — F-006의 러너(`.github/workflows/windows.yml`)를 Phase 16 코드로 돌리지 않았다. F-009(받아서 푸는 묶음)를 만들 때 같이 본다.
