# 운영가이드 — 운영 이관

> **누가 읽는가.** 이 시스템을 **매일 돌보는 사람**이다. 개발을 몰라도 읽힌다.
> 반입 당일의 절차는 [`docs/운영가이드_반입.md`](운영가이드_반입.md)에, 장애가 났을 때는

## 0. 이 시스템이 무엇으로 되어 있나 — 세 덩어리

```
    사람 ──[HTTPS]──▶ nginx ──▶ app(워크플루언스) ──▶ PostgreSQL
                       │            │                   │
                    인증서       첨부 파일            문서·사용자
                                 (attachments)      (postgres_data)
```

컨테이너 셋이 한 서버에서 돌고, **데이터는 컨테이너 밖 볼륨 둘**에 있다.
컨테이너는 지워도 다시 만들면 되지만 **볼륨 둘은 지우면 끝이다.** 백업이 그 둘을 지킨다.

| 이름 | 무엇 | 지워지면 |
|---|---|---|
| `workfluence-nginx` | 바깥에서 들어오는 HTTPS를 받아 앱에 넘긴다 | 접속만 안 된다. 데이터는 안전 |
| `workfluence-api` | 실제 앱. 화면도 여기서 준다 | 접속만 안 된다. 데이터는 안전 |
| `workfluence-postgres` | 문서·사용자·이력·감사기록 | **복구 불가.** 백업에서 되살려야 한다 |
| 볼륨 `deploy_postgres_data` | 위 데이터베이스의 실제 파일 | **복구 불가** |
| 볼륨 `deploy_attachments` | 사람들이 올린 첨부 파일 | **복구 불가** |

## 1. 매일 — 3분

아침에 한 번, 아래 한 줄만 본다.

```bash
docker compose -f deploy/compose.yml --env-file deploy/.env ps
```

**셋 다 `Up`이고 `(healthy)`여야 한다.** 하나라도 다르면 장애대응 가이드로 간다.

`(healthy)`가 붙는 이유는 세 컨테이너가 **스스로 자기 상태를 보고하도록** 만들어 뒀기
때문이다. nginx는 자기 자신에게 HTTPS로 물어보므로, **인증서가 만료되면 여기서 먼저
빨개진다** — 사람이 접속해 보기 전에 알 수 있다.

그다음 앱이 실제로 답하는지 본다.

```bash
curl -sk https://localhost:8443/api/health
```

`{"status":"ok","db":"ok",...}`가 나와야 한다. `db`가 `ok`가 아니면 앱은 살아 있고
데이터베이스가 문제다 — 둘을 나눠 알려 주려고 따로 표시한다.

## 2. 매주 — 10분

### 2.1 디스크를 본다

```bash
df -h /
```

**여유가 5GB 아래로 내려가면 그 주에 조치한다.** 첨부 파일과 데이터베이스가 같은
디스크를 쓰므로, 차면 **글을 저장하는 것부터 실패한다.** 차고 나서 늘리는 것보다
차기 전에 보는 것이 싸다.

### 2.2 백업을 뜬다

```bash
pnpm backup:create
```

데이터베이스 전체와 첨부 파일을 한 덩어리로 묶어 `.local/dumps/` 아래에 날짜 이름으로
남긴다. **끝나면 파일 개수와 크기를 출력한다** — 그 숫자를 보고 넘어간다. 조용히 끝나는
백업은 백업이 아니다.

> **백업 주기를 왜 주 1회로 잡나.** 문서 위키의 하루치 손실은 "다시 쓰면 되는" 종류다.
> 반면 첨부까지 포함한 백업은 용량이 크다. 주 1회를 기본으로 하고, **큰 작업(대량
> 편집·마이그레이션) 직전에는 반드시 한 번 더 뜬다.** 그때가 실제로 잃을 수 있는 시점이다.

### 2.3 백업을 다른 곳으로 옮긴다

```bash
ls -lh .local/dumps/
```

**같은 서버에만 있는 백업은 백업이 아니다.** 서버가 죽으면 백업도 같이 죽는다.
옮길 곳은 조직이 정한 보관 위치다. 옮긴 뒤 원본을 지울지는 그 위치의 용량에 따른다.

## 3. 매월 — 20분

### 3.1 복원을 **실제로** 해 본다

백업 파일이 있는 것과 되살아나는 것은 다른 이야기다. 한 달에 한 번, 마지막 백업이
정말 열리는지 본다.

```bash
pnpm backup:restore .local/dumps/<날짜>
```

> **주의.** 이 명령은 **비어 있지 않은 대상을 거부한다.** 운영 볼륨을 실수로 덮어쓰지
> 않게 만들어 둔 것이다. 그래서 운영에서 그냥 돌리면 "비어 있지 않다"며 멈춘다 —
> 그것이 정상이다. 복원 연습은 **시험용 서버에서** 한다. 운영에서 하려면 진짜 장애가
> 났을 때뿐이고, 그때는 장애대응 가이드가 순서를 알려 준다.

### 3.2 지울 것을 지운다

```bash
pnpm trash:purge
pnpm audit:purge
```

휴지통에서 보존 기간이 지난 것과, 보존 기간이 지난 감사기록을 실제로 지운다.
**둘 다 무엇을 몇 건 지웠는지 출력한다.** 보존 기간은 관리 화면에서 바꿀 수 있고,
감사기록은 90일보다 짧게 내려가지 않는다 — 추적을 없애는 길을 막아 뒀다.

### 3.3 인증서 남은 기간을 본다

```bash
openssl x509 -in deploy/certs/cert.pem -noout -enddate
```

**만료 한 달 전에 재발급을 요청한다.** 만료되면 아무도 접속하지 못하고, 그때 발급을
시작하면 며칠이 걸린다. 새 인증서에도 SAN이 있어야 한다 (반입 가이드 3절).

## 4. 사람이 요청해서 하는 일

| 요청 | 하는 일 | 어디서 |
|---|---|---|
| 새 사용자를 넣어 달라 | 가입 요청을 승인한다 | 관리 화면 → 사용자 |
| 비밀번호를 잊었다 | 초기화한다. 임시 비밀번호는 **화면에 한 번만** 보인다 | 관리 화면 → 사용자 |
| 계정이 잠겼다 | 잠금을 푼다 | 관리 화면 → 사용자 |
| 지운 문서를 살려 달라 | 휴지통에서 되살린다 | 휴지통 |
| 검색 결과가 이상하다 | 색인을 다시 만든다 (`pnpm search:reindex`) | 명령 |
| 업로드 용량을 늘려 달라 | **두 곳을 같이 고친다** — 관리 화면의 정책값과 `deploy/nginx.conf`의 `client_max_body_size` | 화면 + 파일 |

> 마지막 줄을 조심한다. 앱 쪽만 올리면 **앱은 받겠다고 하는데 nginx가 막는다.**
> 사람에게는 "업로드 실패"만 보이고 앱 기록에는 아무것도 안 남는다. 그래서 둘이
> 어긋나면 `pnpm verify:docs`가 실패하도록 해 뒀지만, 그 검사는 개발 쪽에서 돈다 —
> 운영에서 고칠 때는 **사람이 두 곳을 기억해야 한다.**

## 5. 하지 말 것

| 하지 말 것 | 왜 |
|---|---|
| `docker compose down -v` | `-v`가 **볼륨을 지운다.** 데이터가 사라진다. 컨테이너만 내리려면 `-v` 없이 |
| `docker system prune` / `volume prune` | 이름을 보지 않고 지운다. 다른 것까지 사라진다 |
| 데이터베이스에 직접 붙어 고치는 것 | 감사기록이 남지 않고, 값 집합 제약에 걸려 어차피 거부되는 것이 많다. 화면으로 한다 |
| 운영에서 `pnpm db:migrate`를 아무 때나 | 배포 절차의 명시적 단계다. 새 버전을 올릴 때만, 백업을 뜬 뒤에 |
| 앱 로그를 지우는 것 | 용량이 문제면 `docker logs`의 보관 설정을 바꾼다. 감사기록은 로그가 아니라 데이터베이스에 있다 |

## 6. 로그를 어디서 보나

앱 로그는 컨테이너 표준 출력에 **한 줄에 하나씩 JSON으로** 나간다.

```bash
docker compose -f deploy/compose.yml --env-file deploy/.env logs --tail 100 api
```

**비밀번호·토큰·세션 번호·문서 본문은 로그에 없다.** 일부러 안 넣는다. 사용자는
사람이 읽을 수 없는 번호로만 나온다.

**"누가 무엇을 했나"는 로그가 아니라 감사기록에서 본다.** 관리 화면 → 감사로그다.
로그는 시스템이 어떻게 돌았는지를, 감사기록은 사람이 무엇을 했는지를 보여 준다.
감사기록은 **고치거나 지울 수 없게** 데이터베이스가 막아 두었다.

> 중앙 로그 수집 장치는 두지 않았다 (보류 8). 수집기가 생기면 앱을 고치지 않고 붙일
> 수 있게 표준 출력 JSON으로 남겨 둔 것이다.

## 7. 연락 경로

| 무엇 | 누구에게 | 무엇을 들고 |
|---|---|---|
| 접속이 안 된다 / 컨테이너가 안 뜬다 | 먼저 장애대응 가이드를 본다 | `docker compose ps` 출력과 `logs --tail 100` |
| 데이터가 사라졌다 / 복원이 필요하다 | **바로 개발 담당** | 마지막 백업 날짜, `df -h /`, 언제부터 이상한지 |
| 인증서·방화벽·DNS | 사내 인프라 담당 | 오류 화면 그대로 |
| 사내 인증(IdP)으로 로그인이 안 된다 | IdP 담당 + 개발 담당 | 로그인 시각과 사용자 아이디. **비밀번호는 절대 옮기지 않는다** |
| 새 기능을 원한다 | 개발 담당 | 원하는 말 그대로. 요약하지 않는다 |

> **구체적인 이름과 연락처는 이 문서에 적지 않는다.** 이 저장소는 공개돼 있다
> (CLAUDE.md 12.3절). 이관받는 조직이 **자기 쪽 문서에** 표의 "누구에게" 칸을 채운다.

## 8. 무엇을 확인하지 못했나

정직하게 남긴다.

| 확인 못 한 것 | 왜 |
|---|---|
| **실제 재부팅 후 자동 기동** | 개발 서버가 다른 프로젝트와 공유하는 인스턴스라 재부팅할 수 없다. 대신 도커가 부팅 시 뜨도록 설정돼 있는 것과, 컨테이너가 죽으면 되살아나는 것을 따로 확인했다 (`P5_검증기록_Release`). **반입 당일에 한 번은 실제로 재부팅해 본다** |
| **사내 인증(IdP) 실연동** | 개발 서버가 사내 IdP에 나갈 수 없다. 모의 서버로만 확인했다 (보류 11) |
| **운영 규모의 데이터** | 부하 측정은 합성 문서 5,000건으로 했다. 실제 문서가 쌓인 뒤 한 번 더 본다 |
| **첨부 바이러스 검사** | 넣을 자리만 만들어 두었다. 사내 보안 정책이 요구하면 그 자리에 끼운다 (보류 3) |
