## 0. 먼저 — 이 문서의 명령은 두 종류다

**운영 서버에는 Node도 pnpm도 저장소도 없다.** 반입 묶음에는 컨테이너 이미지와 설정만
들어 있다 ([반입 가이드](운영가이드_반입.md) 0절). 그래서 이 문서의 명령은 두 종류로 나뉜다.

| 종류 | 어디서 도는가 |
|---|---|
| `docker`·`openssl`·`df` 같은 기본 도구 | **운영 서버에서 바로 된다.** 일상 점검·백업·월간 정리가 전부 이쪽이다 |
| `pnpm <무엇>` | **저장소와 Node가 있는 곳에서만 된다.** 개발·빌드 서버가 그렇다 |

**월간 정리(휴지통·감사로그)와 검색 재색인도 운영 서버에서 된다** (Phase 13). 그 명령이 앱 이미지 안에 들어 있고, compose의 **`tools`**
— 앱 이미지로 한 번 돌고 끝나는 작업 칸 — 로 부른다. 백업·되살리기는 10절에 `docker`만으로 하는 방법을 적었다.
`pnpm backup:create`·`pnpm backup:restore`는 그 일의 기준 구현이고 출력에 행 수 대조까지 붙어 있어, **저장소가 있는 곳에서는
그쪽이 낫다.**

> **`docker` 명령은 모두 묶음을 푼 디렉토리에서 친다.**
>
> ```bash
> cd ~/workfluence/deploy
> ```
>
> 반입 가이드 1절대로 **`deploy`라는 이름으로** 풀었다는 전제다 — compose는 디렉토리 이름으로 "어느 설치인가"를 알아보고 그 설치의 볼륨
> (`deploy_postgres_data`·`deploy_attachments`)을 붙인다. **다른 디렉토리에서 치면** `docker compose ps`가 아무것도 보이지 않고, `tools`는
> **비어 있는 새 볼륨**을 붙인다 — 첨부 백업이 빈 채로 오류 없이 끝난다. 개발 서버에서는 저장소의 `deploy` 디렉토리가 같은 자리다.
> `pnpm` 명령은 저장소의 맨 위 디렉토리에서 친다.

## 1. 이 시스템이 무엇으로 되어 있나 — 세 덩어리

```
    사람 ──[HTTPS]──▶ nginx ──▶ app(워크플루언스) ──▶ PostgreSQL
                       │            │                   │
                    인증서       첨부 파일            문서·사용자
                                 (attachments)      (postgres_data)
```

컨테이너 셋이 한 서버에서 돌고, **데이터는 컨테이너 밖 볼륨 둘**에 있다.
컨테이너는 지워도 다시 만들면 되지만 **볼륨 둘은 지우면 끝이다.** 백업이 그 둘을 지킨다.

| 이름 | 무엇 | 지워지면 |
|---|---|---|
| `workfluence-nginx` | 바깥에서 들어오는 HTTPS를 받아 앱에 넘긴다 | 접속만 안 된다. 데이터는 안전 |
| `workfluence-api` | 실제 앱. 화면도 여기서 준다 | 접속만 안 된다. 데이터는 안전 |
| `workfluence-postgres` | 문서·사용자·이력·감사기록 | **복구 불가.** 백업에서 되살려야 한다 |
| 볼륨 `deploy_postgres_data` | 위 데이터베이스의 실제 파일 | **복구 불가** |
| 볼륨 `deploy_attachments` | 사람들이 올린 첨부 파일 | **복구 불가** |

`tools`는 이 표에 없다 — 늘 떠 있는 컨테이너가 아니라, 표 만들기·월간 정리·첨부 백업·메일 시험을 할 때만 `run --rm tools …`로 한 번 돌고
지워진다.

**데이터베이스 계정이 둘이다** (Phase 13).

| 계정 | 누가 쓰나 | 할 수 있는 것 |
|---|---|---|
| `workfluence_app` (앱 계정) | 기동 중인 앱(`workfluence-api`) | 표를 읽고 쓰기만. **표를 만들거나 지우지 못하고, 감사기록은 넣고 읽기만** 한다 |
| `workfluence` (소유 계정) | `tools`, 그리고 `docker exec workfluence-postgres …`로 붙는 사람 | 전부 |

앱 계정과 그 권한은 표 만들기(`tools`의 `migrate.js`)가 만들고 맞춘다 — 여러 번 쳐도 같다. 나뉘었는지는 반입 가이드 7.2절의 명령으로
본다. 기동 중인 앱에는 소유 계정 비밀번호와 첫 root 비밀번호가 넘어가지 않는다.

## 2. 매일 — 3분

아침에 한 번, 아래 한 줄만 본다.

```bash
docker compose -f compose.yml --env-file .env ps
```

**셋 다 `Up`이고 `(healthy)`여야 한다.** 하나라도 다르면 장애대응 가이드로 간다.

`(healthy)`가 붙는 이유는 세 컨테이너가 **스스로 자기 상태를 보고하도록** 만들어 뒀기
때문이다. nginx는 자기 자신에게 HTTPS로 물어보므로, **인증서가 만료되면 여기서 먼저
빨개진다** — 사람이 접속해 보기 전에 알 수 있다.

그다음 앱이 실제로 답하는지 본다(`8443`은 `.env`의 `WF_HTTPS_PORT` — 비웠으면 8443).

```bash
curl -sk https://localhost:8443/api/health
```

`{"status":"ok","db":"ok",...}`가 나와야 한다. `db`가 `ok`가 아니면 앱은 살아 있고
데이터베이스가 문제다 — 둘을 나눠 알려 주려고 따로 표시한다.

## 3. 매주 — 10분

### 3.1 디스크를 본다

```bash
df -h /
```

**여유가 5GB 아래로 내려가면 그 주에 조치한다.** 첨부 파일과 데이터베이스가 같은
디스크를 쓰므로, 차면 **글을 저장하는 것부터 실패한다.** 차고 나서 늘리는 것보다
차기 전에 보는 것이 싸다.

### 3.2 백업을 뜬다

운영 서버에서는 **10.1절**의 명령으로 뜬다 — 데이터베이스 덤프와 첨부 파일을 `~/workfluence/backups/` 아래에 시각 이름으로 남긴다.

저장소가 있는 곳에서는 이것이 같은 일을 하고 행 수까지 적어 둔다.

```bash
pnpm backup:create
```

데이터베이스 전체와 첨부 파일을 한 덩어리로 묶어 `.local/backups/` 아래에 시각 이름으로
남긴다. 다른 곳에 두려면 경로를 인자로 준다 (`pnpm backup:create /백업/둘/곳`). **끝나면 파일 개수와 크기를 출력한다** — 그 숫자를 보고 넘어간다. 조용히 끝나는
백업은 백업이 아니다.

> **백업 주기를 왜 주 1회로 잡나.** 문서 위키의 하루치 손실은 "다시 쓰면 되는" 종류다.
> 반면 첨부까지 포함한 백업은 용량이 크다. 주 1회를 기본으로 하고, **큰 작업(대량
> 편집·새 버전 들여오기) 직전에는 반드시 한 번 더 뜬다.** 그때가 실제로 잃을 수 있는 시점이다.

### 3.3 백업을 다른 곳으로 옮긴다

```bash
ls -lh ~/workfluence/backups/
```

(저장소에서 `pnpm backup:create`로 뜬 것은 `.local/backups/` 아래에 있다.)

**같은 서버에만 있는 백업은 백업이 아니다.** 서버가 죽으면 백업도 같이 죽는다.
옮길 곳은 조직이 정한 보관 위치다. 옮긴 뒤 원본을 지울지는 그 위치의 용량에 따른다.

> **백업을 두는 곳의 쓰기 권한을 좁게 잡는다.** 백업 묶음 안에는 "복원한 뒤 무엇이
> 몇 건이어야 하는가"를 적은 파일이 함께 있다. 그 파일을 고칠 수 있는 사람은
> 복원 결과를 속일 수 있다 — 그래서 묶음 안의 모든 파일에 지문(체크섬)을 걸어 두었고,
> 복원은 **지문이 걸려 있지 않은 파일이 있으면 아예 거부한다.** 그래도 백업이 놓인
> 곳 자체를 아무나 고칠 수 있으면 방어가 한 겹 줄어든다. **읽기는 넓게, 쓰기는 좁게.**
> 이 지문은 `pnpm backup:create`로 뜬 묶음에 있다. 10.1절로 뜬 백업에는 없으니, 옮기기 전에 그 디렉토리에서
> `sha256sum db.dump attachments.tar.gz > SHA256SUMS`로 적어 두고 되살리기 전에 `sha256sum -c SHA256SUMS`로 본다.

### 3.4 서버가 돌려보낸 편집을 본다 (Phase 9)

관리 화면 → **감사로그**에서 행위를 `page.collab.reject`로 고른다. 같이 쓰는 문서에서 서버가 받지 않고 끊은 편집이다.

**평소에는 비어 있어야 한다.** 한 줄이라도 있으면 장애대응 가이드 7.23절을 따라 까닭을 본다 — 우리 편집기와 서버 규칙이
어긋났거나(개발 결함), 누가 조작한 프로그램을 쓰고 있다.

### 3.5 LLM 질문이 잘 되는지 본다 (Phase 10)

관리 화면 → **감사로그**에서 행위를 `llm.ask`로 고른다(감사 기록 단계가 1이면 남지 않는다 — 장애대응 7.38절). 누가·언제·어느 LLM에 물었고 결과(`detail.status`)가 무엇인지 보인다 —
**질문 내용은 없다.** `failed`가 몰려 있으면 장애대응 가이드 7.25절을 따라 까닭을 본다. 관리 화면 → **LLM 연결**에서 **연결 확인**을
한 번 눌러 본다.

## 4. 매월 — 20분

### 4.1 복원을 **실제로** 해 본다

백업 파일이 있는 것과 되살아나는 것은 다른 이야기다. 한 달에 한 번, 마지막 백업이
정말 열리는지 본다. **시험용 서버에서** 한다.

**운영 서버에서 뜬 백업**(10.1절 — `db.dump`·`attachments.tar.gz`)은 10.3절의 순서로 **시험용 서버에서** 되살려 본다. 운영 서버에는
pnpm이 없고, `pnpm backup:restore`는 저장소가 있는 곳에서 `pnpm backup:create`로 뜬 백업(`dump.pgc`·`attachments.tar`·`BACKUP.json`)만
읽는다 — 두 형식은 서로 바꿔 쓰지 못한다. 저장소가 있는 시험 서버라면:

```bash
pnpm backup:restore .local/backups/<시각>
```

빈 볼륨에 되살리고, 끝에 앱 계정과 권한을 맞춘다(Phase 13 — 예전에는 빈 볼륨에서 권한 줄 때문에 전체가 롤백됐다, T-056).

> **주의.** 이 명령은 **비어 있지 않은 대상을 거부한다.** 운영 볼륨을 실수로 덮어쓰지
> 않게 만들어 둔 것이다. 그래서 운영에서 그냥 돌리면 "비어 있지 않다"며 멈춘다 —
> 그것이 정상이다. 복원 연습은 **시험용 서버에서** 한다. 운영에서 하려면 진짜 장애가
> 났을 때뿐이고, 그때는 장애대응 가이드가 순서를 알려 준다.

### 4.2 지울 것을 지운다

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/trash-purge.js
docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/audit-purge.js
```

저장소가 있는 곳에서는 `pnpm trash:purge`·`pnpm audit:purge`가 **같은 코드**를 부른다.

> **백업과 같은 시각에 돌리지 않는다.** 백업은 "무엇이 몇 건이었나"를 먼저 세고 그다음에
> 덤프를 뜬다. 그 사이에 정리가 행을 지우면 **덤프가 센 것보다 적어지고**, 나중에 그
> 백업으로 복원할 때 "행이 모자란다"로 실패한다 — 실제로 잃은 것은 없는데 그렇게 보인다.
> 정리는 **백업을 뜬 뒤에** 한다.

휴지통에서 보존 기간이 지난 것과, 보존 기간이 지난 감사기록을 실제로 지운다.
**둘 다 첫 줄에 어느 데이터베이스를 만지는지(`대상 DB: postgres:5432/workfluence (사용자 workfluence)`), 끝에 무엇을 몇 건 지웠는지
출력한다.** 휴지통 정리는 볼륨의 첨부 파일도 함께 지운다 — 아무도 안 쓰게 된 것만. 보존 기간은 관리 화면에서 바꿀 수 있고,
감사기록은 90일보다 짧게 내려가지 않는다 — 추적을 없애는 길을 막아 뒀다.

**둘 다 `tools`로 돌린다** — 소유 계정으로 붙는 작업 칸이다. 감사로그 정리를 `api`로 돌리면(`run --rm api …`) 앱 계정이라
감사기록을 지우지 못하고 `permission denied`로 멈춘다 — 일부러 그렇다(장애대응 7.30절).

검색 재색인은 달마다 할 일이 아니다 — 검색 결과가 이상할 때 한다(10.2절).

### 4.2-1 LLM 대화가 차지하는 자리를 본다 (Phase 10)

```bash
docker compose -f compose.yml --env-file .env exec postgres psql -U workfluence -d workfluence -c "SELECT pg_size_pretty(pg_total_relation_size('llm_messages')) AS 메시지, (SELECT count(*) FROM llm_conversations) AS 대화"
```

대화는 사람마다 100개·7일로 스스로 줄지만, 한 대화가 모델의 문맥만큼 길어질 수 있다. 달마다 늘어나는 정도를 적어 두고,
디스크를 먼저 채우는 것이 보이면 운영 설정에서 기간·개수를 줄인다(장애대응 가이드 7.27절 — 줄이면 넘는 것이 지워진다).

### 4.3 인증서 남은 기간을 본다

```bash
openssl x509 -in certs/cert.pem -noout -enddate
```

**만료 한 달 전에 재발급을 요청한다.** 만료되면 아무도 접속하지 못하고, 그때 발급을
시작하면 며칠이 걸린다. 새 인증서에도 SAN이 있어야 한다 (반입 가이드 3절).

## 5. 사람이 요청해서 하는 일

| 요청 | 하는 일 | 어디서 |
|---|---|---|
| 새 사용자를 넣어 달라 | 가입 요청을 승인한다 | 관리 화면 → 사용자 |
| 비밀번호를 잊었다 | 사내 메일이 켜져 있으면 본인이 로그인 화면의 비밀번호 찾기에서 **내 email로 재설정 링크 받기**로 스스로 바꾼다(Phase 19 — `root`는 이 길이 없다). 관리자에게 온 **초기화 요청 알림**이나 직접 받은 부탁이면 본인인지 확인한 뒤 초기화한다. 임시 비밀번호는 **화면에 한 번만** 보인다 (사용자 가이드 1.6·16.5절) | 관리 화면 → 사용자 |
| email이 기억나지 않는다고 한다 (Phase 19) | `root`의 알림에 **email 확인이 요청됐다**가 온다 — **사용자 관리에서 보기**로 그 사람 줄의 이름 아래 email을 보고, 전화·대면으로 본인인지 확인한 뒤 알려 준다. 관리자(admin)에게는 오지 않는다 (사용자 가이드 16.5절, 장애대응 7.40절) | 관리 화면 → 사용자 |
| 메일로 비밀번호를 바꾸는 길을 막아 달라 · 다시 열어 달라 (Phase 19 — 보안 검토 등) | 운영 설정의 **email로 비밀번호 재설정 (passwordResetMail)** 을 **끔**(또는 **켬**). 끄면 단추가 사라지고 **이미 보낸 링크도 막힌다**. 관리자에게 초기화 요청은 그대로 된다 | 관리 화면 → 운영 설정 |
| 계정이 잠겼다 | 잠금을 푼다 | 관리 화면 → 사용자 |
| **퇴사자를 막아 달라** (Phase 13) | 그 사람 줄의 **정지**. 그 순간 로그인과 열어 둔 편집 창이 끊기고 다시 들어오지 못한다. 쓴 문서·댓글·Crew 소속은 남는다. 잘못 정지했으면 **정지 해제** (사용자 가이드 16.10절, 장애대응 7.32절) | 관리 화면 → 사용자 (**찾기**·**상태**로 사람을 찾는다) |
| 공간의 이름·설명·분류를 바꿔 달라, 공간을 멈춰(중지) 달라, 지워 달라 (Phase 14) | 그 공간을 찾아 **중지**·**다시 쓰기**·**지우기**(중지된 것만). 이름·설명·분류는 그 공간 화면 아래의 관리 칸(**스페이스 정보**)에서 바꾸고, 중지·지우기는 같은 칸의 **위험 구역**에 있다. 지운 공간은 휴지통에서 되살린다 (사용자 가이드 2.6·17.1절, 장애대응 7.36절) | 관리 화면 → 스페이스 관리 / 그 공간의 관리 칸 |
| 분류를 새로 만들거나 이름을 바꿔 달라, 지워 달라 (Phase 14 · Phase 15) | 새 분류는 누구나 자기 공간의 관리 칸(**스페이스 정보**의 **새 분류**)에서 만든다. 이름 바꾸기·지우기는 같은 칸의 **분류 관리** — 만든 사람도 하지만, 남의 공간이 쓰면 관리자와 **분류 관리**를 맡겨 받은 사람만 한다. **지우면 쓰던 공간(휴지통 포함)은 분류 없음이 된다** — 확인 대화가 몇 개인지 말하고, 어느 공간이었는지는 감사로그 `category.delete`의 `cleared`에 남는다. 되돌리려면 그 목록을 보고 분류를 다시 만들어 붙인다 (사용자 가이드 17.1절, 장애대응 7.36·7.37절) | 관리 화면 → 스페이스 관리 / 그 공간의 **관리** 칸 |
| 이 사람은 읽기만 하게 넣어 달라 (Phase 14) | 팀 공간의 **Crew** 칸에서 역할을 **viewer (읽기만)** 로 골라 넣거나, 넣은 사람의 역할을 바꾼다. 편집 창을 열어 두고 있었으면 몇 분 안에 끊긴다 (사용자 가이드 2.3절) | 그 공간의 **Crew** 칸 |
| 지운 문서를 살려 달라 | 휴지통에서 되살린다 | 휴지통 |
| 검색 결과가 이상하다 | 색인을 다시 만든다 (10.2절 — 저장소가 있는 곳은 `pnpm search:reindex`) | 명령 |
| 업로드 용량을 늘려 달라 | 서버의 천장(`.env`의 `WF_UPLOAD_MAX_MB`, 기본 20MB)보다 작게는 **관리 화면의 정책값만** 바꾼다. 천장을 올리려면 **세 곳을 같이 고친다** — `.env`의 `WF_UPLOAD_MAX_MB`, 묶음 디렉토리의 `nginx.conf`(저장소의 `deploy/nginx.conf`)에 있는 `client_max_body_size`, 그리고 관리 화면의 정책값. 두 파일을 고친 뒤 `docker compose -f compose.yml --env-file .env up -d --force-recreate api nginx` | 파일 + 화면 |
| 새 버전을 올려 달라 (새 반입 묶음이 왔다) | [반입 가이드](운영가이드_반입.md) **11절**의 순서 — 묶음 지문 확인, 새 키 채우기, 앱을 멈추고 백업, 이미지 올리기, 표 만들기, 다시 띄우기 | 명령 |
| 사내 LLM을 등록·삭제해 달라 | 시스템 관리자(`root`)나, root가 위임한 관리자가 한다. 등록하면 곧바로 연결 확인 — "연결됨"이 뜨면 끝이다 (장애대응 7.24절). **처음 붙일 때**는 반입 가이드 10절 "사내 LLM 연결하기" | 관리 화면 → LLM 연결 |
| 멘션을 메일로도 받게 해 달라 · 메일 주소·인증이 바뀌었다 (Phase 18) | 서버의 `.env`에서 `WF_MAIL_*`를 고치고 시험 메일을 한 통 보낸 뒤 앱을 다시 만든다(`up -d --force-recreate api`) — 순서는 반입 가이드 10-1절. 화면에는 메일 설정이 없다 | 서버 `.env` |
| 이 사람에게 분류 관리·관리자가 건 중지 풀기·스페이스 관리 전체를 맡겨 달라 (Phase 15) | 관리자나 `root`가 **사용자 관리** → 그 **member** 줄의 칸(**분류 관리** · **관리자가 건 중지 풀기** · **스페이스 관리 전체**)을 켠다. 거둘 때는 끈다. 그 사람의 다음 요청부터 먹는다. 관리자가 되면 사라진다(관리자는 원래 한다). **스페이스 관리 전체는 남의 공간의 문서를 읽게 하지 않는다** — 멈추고 지우고 되살리는 일만 (사용자 가이드 16.7절, 장애대응 7.37절) | 관리 화면 → 사용자 |
| 관리자가 멈춘 우리 공간을 우리가 풀게 해 달라 (Phase 15) | 관리자가 건 중지는 주인도 풀지 못한다. 관리자가 **스페이스 관리**에서 **다시 쓰기**를 누르거나, 그 주인에게 **관리자가 건 중지 풀기**를 켜 준다 — 켜 받은 주인은 자기 공간만 푼다 (사용자 가이드 2.5절, 장애대응 7.37절) | 관리 화면 → 스페이스 관리 / 사용자 |
| 조사하게 이 공간을 얼려 달라 — 주인이 풀지 못하게 (Phase 15) | **스페이스 관리**에서 **중지**. 이미 **주인이 걸었다**로 중지돼 있으면 주인은 언제든 푼다 — **관리자가 건 중지로 바꾸기**를 누른다. 얼려 둔 동안에는 주인이 Crew도 바꾸지 못한다 — 관리자만 바꾼다(Phase 16) (사용자 가이드 2.3·2.5·17.1절) | 관리 화면 → 스페이스 관리 |
| 관리자에게 LLM 연결을 맡겨 달라 | `root`가 **사용자 관리** → 그 관리자 줄의 "LLM 연결 관리"를 켠다. 거둘 때는 끈다. 관리자가 member가 되면 저절로 사라진다. 누가 언제 주고 거뒀는지는 감사로그 `user.grants.change`. **맡긴 관리자의 계정 일**(승인·비밀번호 초기화·잠금 해제·역할·세션 종료·정지)은 `root`나 **같은 것을 맡은 관리자**가 한다 — 맡기지 않은 관리자에게는 그 줄의 단추가 눌리지 않는다 | 관리 화면 → 사용자 |
| LLM의 API 키가 바뀌었다 | **지우고 새 키로 다시 등록한다.** 키는 다시 볼 수 없어 고쳐 넣는 화면이 없다. 대화는 남는다 | 관리 화면 → LLM 연결 |
| LLM 대화를 더 오래 남겨 달라 | 운영 설정의 `llmRetentionDays`·`llmConversationMax`·`llmPinnedMax`. 고정 수는 대화 수보다 작아야 한다 | 관리 화면 → 운영 설정 |

> **업로드 용량 줄을 조심한다.** 앱 쪽만 올리면 **앱은 받겠다고 하는데 nginx가 막는다.**
> 사람에게는 "HTTP 413"만 보이고 앱 기록에는 아무것도 안 남는다. 그래서 둘이
> 어긋나면 `pnpm verify:docs`가 실패하도록 해 뒀지만, 그 검사는 개발 쪽에서 돈다 —
> 운영에서 고칠 때는 **사람이 세 곳을 기억해야 한다.** 새 버전을 들여오면 묶음의 `nginx.conf`가 고친 것을 덮어쓴다 —
> 반입 가이드 11절 ③이 먼저 복사해 두게 한다.

## 6. 하지 말 것

| 하지 말 것 | 왜 |
|---|---|
| `docker compose down -v` | `-v`가 **볼륨을 지운다.** 데이터가 사라진다. 컨테이너만 내리려면 `-v` 없이 |
| `docker system prune` / `volume prune` | 이름을 보지 않고 지운다. 다른 것까지 사라진다 |
| 데이터베이스에 직접 붙어 고치는 것 | 감사기록이 남지 않고, 값 집합 제약에 걸려 어차피 거부되는 것이 많다. 화면으로 한다 |
| 표 만들기(`tools`의 `migrate.js`)를 아무 때나 치는 것 | 배포 절차의 명시적 단계다. 첫 설치(반입 가이드 5절), 새 버전을 올릴 때(백업을 뜬 뒤에 — 반입 가이드 11절), 백업을 되살린 뒤(10.3절), `WF_PG_APP_PASSWORD`를 바꾼 뒤(장애대응 7.31절), 앱 계정의 권한이 빈 것을 고칠 때(장애대응 7.30절)만 친다 |
| **api를 소유 계정으로 띄우는 것** — `compose.yml`의 api 접속 주소를 `workfluence`로 바꾸거나 api에 `WF_PG_PASSWORD`를 넘기는 것 | 기동 중인 앱이 표를 만들고 지우고 감사기록을 고칠 수 있는 열쇠를 쥐게 된다 — 계정을 나눈 뜻이 없어진다(보류 12). 앱이 데이터베이스에 붙지 못하면 계정을 바꾸지 말고 장애대응 7.30·7.31절을 본다 |
| **`tools`를 `up`에 넣는 것** — `--profile tools`로 올리거나 `compose.yml`에서 `profiles` 줄을 지우는 것 | `tools`는 소유 계정 비밀번호와 첫 root 비밀번호를 쥔다. 늘 떠 있게 두면 그 열쇠가 기동 중인 프로세스에 머문다. 부를 때만 돌고(`run --rm`) 끝나면 지워지는 것이 맞다 |
| `WF_PG_APP_PASSWORD`만 바꾸고 `up -d` 하는 것 | 앱은 새 비밀번호로 붙으려는데 계정은 옛 비밀번호다 — 먼저 표 만들기, 그다음 `up -d`(장애대응 7.31절) |
| 앱 로그를 지우는 것 | 로그는 compose가 서비스마다 순환한다(기본 20MB × 5). 용량이 문제면 `.env`의 `WF_LOG_MAX_SIZE`·`WF_LOG_MAX_FILES`를 바꾸고 `docker compose -f compose.yml --env-file .env up -d`로 컨테이너를 다시 만든다. 감사기록은 로그가 아니라 데이터베이스에 있다 |
| `WF_LLM_MASTER_KEY`를 바꾸거나 잃는 것 | 등록한 **모든** LLM의 API 키를 풀 수 없게 된다 — 전부 지우고 다시 등록해야 한다 (장애대응 7.26절). 이 값은 **백업에 들어가지 않는다** — 백업과 **다른 곳**에 안전하게 보관한다 |
| 마스터 키를 백업 파일 옆에 두는 것 | 백업이 새면 잠근 키까지 함께 풀린다 |
| **SELinux를 끄는 것**(`setenforce 0`·설정 파일의 `SELINUX=disabled`) (Phase 20) | 이 스택은 RHEL 9의 Enforcing에서 돈다. 끄면 서버 전체의 보호가 사라진다 — 무엇이 막히면 장애대응 7.41절의 순서로 그 까닭을 본다 |
| **`docker` 그룹에 여러 계정을 넣는 것** (Phase 20) | 그 그룹은 root와 같은 힘이다 — 반입과 운영을 맡은 계정 하나에만 준다(반입 가이드 0.3절 ⑤) |
| Docker를 인터넷 저장소에서 올리는 것 | 폐쇄망에는 없다. 판을 올릴 때는 밖에서 새 Docker 묶음을 만들어 들여온다(리눅스빌드 가이드 12-1절) — 반입 묶음의 이미지를 그 판으로 띄워 본 뒤에 |

## 7. 로그를 어디서 보나

앱 로그는 컨테이너 표준 출력에 **한 줄에 하나씩 JSON으로** 나간다.

```bash
docker compose -f compose.yml --env-file .env logs --tail 100 api
```

**비밀번호·토큰·세션 번호·문서 본문·LLM 질문과 답·지시문·LLM API 키는 로그에 없다.** 일부러 안 넣는다. 사용자는
사람이 읽을 수 없는 번호로만 나온다.

줄마다 **`event`**(무슨 일인가)가 있고, 요청 안에서 남긴 줄에는 **요청 번호**(`requestId`)가 있다 — 같은 번호로 nginx 로그와 감사기록의
그 행까지 찾는다(감사기록은 관리 화면 → 감사로그의 **"요청 번호"** 칸). 읽는 법과 event 목록은 장애대응 가이드 7.28절이다.

로그는 **서비스마다 20MB 파일 5개까지** 남고 넘으면 오래된 것부터 지워진다. 사고를 조사하려고 오래 두어야 하면 그 전에 파일로 옮겨
둔다: `docker compose -f compose.yml --env-file .env logs --no-color api > api-날짜.log`.

**"누가 무엇을 했나"는 로그가 아니라 감사기록에서 본다.** 관리 화면 → 감사로그다.
로그는 시스템이 어떻게 돌았는지를, 감사기록은 사람이 무엇을 했는지를 보여 준다.
감사기록은 **고치거나 지울 수 없게** 데이터베이스가 막아 두었다 — 규칙이 막고, Phase 13부터는 앱 계정에 그 권한 자체가 없다(1절).

> 중앙 로그 수집 장치는 두지 않았다 (보류 8). 수집기가 생기면 앱을 고치지 않고 붙일
> 수 있게 표준 출력 JSON으로 남겨 둔 것이다.

## 8. 연락 경로

| 무엇 | 누구에게 | 무엇을 들고 |
|---|---|---|
| 접속이 안 된다 / 컨테이너가 안 뜬다 | 먼저 장애대응 가이드를 본다 | `docker compose ps` 출력과 `logs --tail 100` |
| 데이터가 사라졌다 / 복원이 필요하다 | **바로 개발 담당** | 마지막 백업 날짜, `df -h /`, 언제부터 이상한지 |
| 인증서·방화벽·DNS | 사내 인프라 담당 | 오류 화면 그대로 |
| 사내 인증(IdP)으로 로그인이 안 된다 | IdP 담당 + 개발 담당 | 로그인 시각과 사용자 아이디. **비밀번호는 절대 옮기지 않는다** |
| 부르기 메일·재설정 메일이 안 온다 · 시험 메일이 받지 않는다 (Phase 18 · 19) | 먼저 장애대응 7.21절(메일 전체)·7.39절(재설정 메일). 그다음 사내 메일 API 담당 (+ 개발 담당 — 형식이 다를 때) | 시험 명령(반입 가이드 10-1절 ③)의 창 전체와 그 시각. **인증 값은 옮기지 않는다** — 창에도 가려져 있다 |
| 새 기능을 원한다 | 개발 담당 | 원하는 말 그대로. 요약하지 않는다 |

> **구체적인 이름과 연락처는 이 문서에 적지 않는다.** 이 저장소는 공개돼 있다
> (CLAUDE.md 12.3절). 이관받는 조직이 **자기 쪽 문서에** 표의 "누구에게" 칸을 채운다.

## 9. 무엇을 확인하지 못했나

정직하게 남긴다.

| 확인 못 한 것 | 왜 |
|---|---|
| **실제 재부팅 후 자동 기동** | 개발 서버가 다른 프로젝트와 공유하는 인스턴스라 재부팅할 수 없다. 대신 도커가 부팅 시 뜨도록 설정돼 있는 것과, 컨테이너가 죽으면 되살아나는 것을 따로 확인했다 (`P5_검증기록_Release`). **반입 당일에 한 번은 실제로 재부팅해 본다** (반입 가이드 7.1절) |
| **사내 인증(IdP) 실연동** | 개발 서버가 사내 IdP에 나갈 수 없다. 모의 서버로만 확인했다 (보류 11) |
| **운영 규모의 데이터** | 부하 측정은 합성 문서 5,000건으로 했다. 실제 문서가 쌓인 뒤 한 번 더 본다 |
| **첨부 바이러스 검사** | 넣을 자리만 만들어 두었다. 사내 보안 정책이 요구하면 그 자리에 끼운다 (보류 3) |
| **사내 메일 실연동** | 개발 서버는 사내 메일 API에 닿지 않는다. **가짜 메일 서버로만 확인했다** — 요청 모양은 사용자가 준 사내 API 설명 그대로다(보류 18 — 현장에서 닫는다). 처음 붙일 때는 반입 가이드 10-1절 "사내 메일 연결하기"(시험 메일 한 통 → 켜기 → 불러 보기 → 재설정 메일 한 통). "멘션 메일이 안 온다"는 신고는 장애대응 7.21절 — 먼저 시험 메일을 보낸다. 현장의 API가 다르면 `apps/api/src/mail/domain/request.ts` 한 파일을 고친다 |
| **실시간 편집 상태의 크기** | 긴 문서를 오래 편집하면 `page_realtime.state`가 자란다(옆의 `authors`도 함께 본다). 상한을 둘지는 실제로 재 보고 정한다 (보류 19) |
| **사내 LLM 실연동** | 사내 LLM 서버의 주소를 받지 못했다. **가짜 LLM 서버로만 확인했고 흐름의 모양은 vLLM의 OpenAI 호환 형식에서 온 가정이다** (보류 29). 주소가 `https`이고 사내 CA가 서명한 인증서면 그 기관의 인증서 파일 하나를 `ca/ca.pem`에 두고 앱을 다시 만든다(반입 가이드 10절 ②·③) — 현장에서 실제로 붙여 본 적은 아직 없다. 형식이 다르면 `apps/api/src/llm/domain/openai.ts`·`apps/api/src/llm/openai.client.ts` 두 파일을 고친다 |
| **10절의 되살리기를 운영 서버에서 해 본 것** | 되살리기 연습은 `pnpm backup:restore`(`P5_검증기록_Release` 3.1절)와 10.3절의 `docker`만 쓰는 순서(`docs/P13_검증기록_Readiness.md` 6절)로 했다 — 둘 다 개발 서버에서다. 운영 서버에서는 실제 장애 전에 **시험용 서버에서** 한 번 해 본다 |
| **Docker가 없는 빈 RHEL 9에 Docker 묶음을 까는 것** (Phase 20) | 개발 서버에는 Docker가 이미 있어 까는 것 자체는 해 보지 못했다 — 서명·지문과 빈 RHEL 9에 가까운 컨테이너에서의 의존 계산까지만 봤다. 반입 당일 반입 가이드 0.3절대로 하고 결과를 적는다. 막히면 장애대응 7.41절 |

## 10. 저장소가 없는 서버에서 하는 방법

운영 서버에 Node가 없을 때 쓴다 (0절). **`pnpm` 쪽과 같은 일을 하지만 확인이 적다** —
행 수 대조나 "비어 있지 않으면 거절" 같은 안전장치가 없으니 사람이 결과를 봐야 한다.
첨부를 만지는 명령은 **묶음에 든 앱 이미지의 `tar`**를 `tools`로 쓴다 — 폐쇄망에서는 다른 이미지를 받아 올 수 없다.

### 10.1 백업

```bash
D=~/workfluence/backups/$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p "$D"
docker exec workfluence-postgres pg_dump -U workfluence -Fc workfluence > "$D/db.dump"
docker compose -f compose.yml --env-file .env run --rm --no-deps -T --entrypoint tar tools -czf - -C /data/attachments . > "$D/attachments.tar.gz"
ls -lh "$D"
tar -tzf "$D/attachments.tar.gz" | wc -l
```

**`db.dump`가 0바이트가 아닌지 본다.** `pg_dump`가 실패해도 리다이렉션이 파일은 만든다 —
크기를 안 보면 빈 백업을 떠 놓고 안심한다. 마지막 줄은 첨부 백업을 끝까지 열어 든 것의 수를 센다 — 숫자만 나오면 된다. 지난 백업보다
눈에 띄게 적으면 이상하다(엉뚱한 디렉토리에서 쳐서 빈 볼륨을 뜬 것일 수 있다 — 0절). `gzip: stdin: not in gzip format`·`unexpected end of file`이
함께 나오면 그 백업을 쓰지 않는다.

### 10.2 보존 기간이 지난 것 지우기 · 검색 색인 다시 만들기

보존 기간이 지난 것을 지우는 명령은 **4.2절의 두 줄**이다 — 운영 서버에서 그대로 돈다. 휴지통 정리는 페이지·댓글·첨부·라벨을 정해진
순서로 지우고 **첨부 파일까지 함께 지우는** 일이라, 손으로 SQL을 쓰지 않는다 — 데이터베이스와 디스크가 어긋난다(행은 지워졌는데
파일이 남거나 그 반대).

검색 결과가 이상하면(장애대응 7.10절) 색인을 다시 만든다. 문서 본문에서 검색용 글자를 다시 뽑을 뿐이라 **몇 번 돌려도 안전하다.**

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/reindex.js
```

`재색인 완료: <N>개 페이지`가 나오면 된다. 저장소가 있는 곳에서는 `pnpm search:reindex`가 같은 코드다.

### 10.3 되살리기

```bash
docker compose -f compose.yml --env-file .env stop api nginx
docker exec -i workfluence-postgres pg_restore -U workfluence -d workfluence --clean --if-exists < <백업>/db.dump
docker compose -f compose.yml --env-file .env run --rm --no-deps -T --entrypoint find tools /data/attachments -mindepth 1 -delete
docker compose -f compose.yml --env-file .env run --rm --no-deps -T --entrypoint tar tools -xzf - -C /data/attachments < <백업>/attachments.tar.gz
docker compose -f compose.yml --env-file .env run --rm tools node dist/db/migrate.js
docker compose -f compose.yml --env-file .env up -d
```

- **`--clean --if-exists`가 기존 데이터를 지운다.** 셋째 줄은 지금의 첨부 파일을 지우고 넷째 줄이 백업의 것을 푼다. 되돌릴 수 없다.
  장애대응 7.18절의 순서(먼저 멈추고, **지금 상태를 먼저 뜨고**)를 지킨 뒤에만 한다.
- **다섯째 줄(표 만들기)을 빼지 않는다.** 되살린 데이터베이스에는 백업을 뜬 때의 권한이 들어온다. 앱 계정이 없던 때(Phase 13 전)의
  백업이면 앱 계정의 권한이 비어 앱이 `permission denied`를 낸다. 표 만들기가 권한을 다시 맞춘다(옛 판의
  백업은 아래 마지막 글머리). 여러 번 쳐도 같다.
- 새 서버에 되살리면: 반입 가이드 1~5절(묶음 풀기·이미지·설정·데이터베이스·표 만들기)을 먼저 하고 이 순서를 따른다. 5-1절(첫 계정)은
  하지 않는다 — 계정은 백업에 있다. `.env`의 `WF_LLM_MASTER_KEY`는 옛 서버와 같아야 한다(장애대응 7.26절).
- 되살린 뒤 반입 가이드 7절 표로 확인한다 — 로그인, 문서, 첨부, 7.2절의 두 가지.
- **백업이 지금 판보다 옛 것이면 위 순서가 맞지 않는다** (병합 전 자체 점검 12). `--clean`은 덤프에 있는 것만 지우므로 새 판이 만든 표가
  남고, 되살린 마이그레이션 기록은 옛 목록이라 다섯째 줄이 새 판의 마이그레이션을 다시 돌리다 "이미 있다"로 멈춘다(권한도 주지 못한다).
  그때는 **빈 데이터베이스**에 되살린다 — 반입 가이드 1~4절(5절의 표 만들기는 하지 않는다) → 둘째 줄에 `--no-privileges`를 더해 붓고
  (새 데이터베이스에는 앱 계정이 아직 없다) → 셋째~여섯째 줄. 이 경우는 **돌려 보지 않았다** — 개발 담당과 함께 한다.

이 순서는 **Phase 13 리허설에서 한 번 해 봤다** — 빈 볼륨에 반입 가이드대로 설치하고 8절 첫 백업을 뜬 뒤 문서·첨부를 더 만들었다가, 위
여섯 줄로 되살려 백업 시점으로 돌아간 것(더 만든 문서·첨부가 사라지고 옛 문서·첨부가 그대로)을 봤다 (`docs/P13_검증기록_Readiness.md`
6절). 개발 서버에서 한 것이라 운영 서버의 디스크·권한에서는 아직이다 — 실제로 쓸 일이 생기면 개발 담당과 함께 한다.
