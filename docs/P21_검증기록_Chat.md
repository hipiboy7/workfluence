## 3. 시험이 잡은 것 (설계서 I절 5·6)

- 한 연결이 연달아 보낸 메시지의 번호가 뒤바뀔 수 있었다 — 프레임마다 저장을 바로 불렀다. 연결마다 처리 줄을 둬 고쳤다(시험 "순서").
- 화면이 방 목록을 `hello`를 받은 뒤에야 받아, 연결이 막히면 비어 보였다 — 컴포넌트 시험이 잡았다. 연결과 상관없이 먼저 받게 고쳤다.
- 편집 게이트웨이가 채팅 경로를 404로 닫을 뻔했다(설계 단계에서 먼저 발견 — 통합 시험으로 고정).

## 4. 확인하지 못한 것

- **컨테이너 빌드·compose 기동·nginx 경유 WebSocket** — 이 Phase는 `deploy/compose.yml`에 환경변수 7개를 더했다(의존성은 없다). 이미지를 새로 빌드해 `docker compose`로 띄우고 nginx(`Upgrade` 헤더 전달) 너머에서 채팅이 붙는지는 아직 보지 않았다. 개발 서버에서 api를 직접 띄운 것만 확인했다(CLAUDE.md 1.1절 4단계 — Docker·nginx를 건드린 Phase는 Linux에서 pull → 빌드 → 기동까지).
- **병합 전 검토** — `self-reviewer`·`doc-consistency`·`/code-review`·`/security-review`를 아직 돌리지 않았다.
- **세션 유휴 만료와 오래 열어 둔 채팅 화면** — 화면이 읽음 표시(HTTP)를 보내는 동안은 세션이 연장되지만, 아무도 말하지 않는 방을 30분 넘게 열어 두면 세션이 만료되고 주기 재판정이 연결을 닫는다(close 4401 — 화면이 "로그인이 끝나…"를 보인다). 실제로 오래 열어 두고 재현하지 않았다.
- **부하** — 방·메시지가 많을 때(방 목록의 마지막 메시지 조회, 연결 수백 개)는 재지 않았다. 사용자 300명, 연결 수십~수백 개를 가정한 설계다.
- **실제 AI 에이전트와의 연동** — `aiagent` 쪽 구현으로 붙여 보지 않았다. E2E는 `ws` 패키지로 만든 클라이언트다(모의 통과는 완료가 아니다 — 9.1절과 같은 판단).
- **메시지의 보존·삭제·감사** — 하지 않았다(보류 39).
