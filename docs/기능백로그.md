# 기능 백로그

- 용도: 들어온 기능 요청을 **사용자의 말 그대로** 받아 적고, 크기와 어느 Phase의 일인지를 판정해 둔다
- 절차: [`CLAUDE.md`](../CLAUDE.md) 1.4절. **Claude는 크기와 영향만 알려주고, 지금 할지는 사용자가 정한다**
- 작성일: 2026-09-16 / 작성 LLM: Claude Opus 5

> **왜 이 문서가 있는가.** 기능 요청은 Phase 순서와 무관하게 온다. 바로 만들면 진행 중인 Phase의 검증이 반쪽이 되고, 안 적으면 요청 자체가 사라진다. 적어 두고 순서만 정하면 둘 다 피할 수 있다. **백로그에서 오래 기다리는 것은 손실이 아니다. 적어 두지 않은 요청만 사라진다.**

## 1. 크기 표기

| 표기 | 뜻 | 예 |
|---|---|---|
| **S** | 한 층만 만진다 | 화면 문구·버튼 위치·정렬 순서 |
| **M** | 두 층 이상을 만진다 | 새 목록 화면 + 그 목록을 주는 API |
| **L** | 데이터 구조가 바뀐다 | 새 테이블이나 새 컬럼이 필요하다 |

L은 되돌리기 어렵다. 운영 데이터가 이미 있으면 구조 변경에 별도 절차가 붙는다. 어느 층을 만지는지 판정하는 기준은 [`docs/설계서_Architecture.md`](설계서_Architecture.md) 11절이다.

## 2. 상태 표기

| 상태 | 뜻 |
|---|---|
| `접수` | 적어 두었다. 아직 어느 Phase에 넣을지 정하지 않았다 |
| `배정` | 어느 Phase에서 할지 정했다 |
| `진행` | 그 Phase의 설계서에 들어갔다 |
| `완료` | 검증기록에 결과가 있다 |
| `보류` | 지금은 하지 않기로 했다. 이유를 함께 적는다 |

### F-003 · 운영 로그를 디버깅·유지보수할 수 있게 · 접수 2026-09-25

Phase 10 검토 반영 도중에 들어온 **검토 요청**에서 나왔다. 사용자가 기능을 청한 것이 아니라 로깅 체계를 검토해 달라고 했고, 그 검토가
고칠 것을 찾았다. 원문은 `docs/prompts/phase10/scope.md`의 같은 날짜 절에 있다.

> 우리가 지금 개발하고 있는 프로그램은 로깅 체계가 어떻게 잡혀있어?
> 어느 시점에 로그를 남기고, 이를 디버깅 및 유지보수 할 수 있도록 되어있어?
> 프로그램 유지보수 용이성 및 확장성 측면에서 로그 구성은 적절하게 되어있는지 검토해줘.

| 항목 | 내용 |
|---|---|
| 상태 | `진행` — Phase 11 (`docs/P11_설계서_Ops.md` C.2). 사용자 지시 2026-09-26: "F-003 로그 개선 이어서 진행해서 완료해줘." **공통 로거의 오류 처리**(스택이 버려지고 DB 오류면 질의 매개변수가 실린다)는 Phase 10 검토 반영에 먼저 넣었다(7절 위반이라) |
| 크기 | **M** — 서버(요청 식별자·접근 로그·구조화 필드) · 설정(compose 로그 순환·nginx 로그 형식) · 문서(규칙서 7절·장애대응·운영이관) |
| 만지는 층 | ① nginx `$request_id` → `X-Request-Id` → 앱 로그·응답 머리말·감사 detail ② 앱 접근 로그 한 줄(메서드·경로 틀·상태·지연·사용자 불투명 id, **질의 문자열은 빼고**) ③ 로그 문장에 안정된 `event` 코드와 필드(`pageId`·`userId`)를 더하고 장애대응 가이드가 그 코드로 찾게 ④ compose 세 서비스에 `logging` 순환(`max-size`·`max-file`) ⑤ "실패는 구조화해 warn/error로 남긴다"를 규칙서에 ⑥ nginx 접근 로그 형식에서 질의 문자열(검색어)을 뺀다 |
| 배정 Phase | 11 (사용자 결정 2026-09-26) |
| 영향 | 동작은 바뀌지 않는다. 로그의 모양이 바뀌므로 장애대응 가이드의 검색어를 함께 고친다. ④는 반입 절차(compose)가 바뀐다 |
| 판단 근거 | 증적(감사로그)은 갖춰져 있고 운영 로그는 뼈대(JSON 표준 출력)만 있다. 500 한 줄을 누구의 어느 요청인지 이을 수 없고, 로그가 쌓이면 디스크가 하나라 DB 쓰기부터 깨진다(0.3절) |


### F-002 · 사내 LLM(vLLM·Qwen3)에 질문하는 메뉴 · 접수 2026-09-24

Phase 9 착수 도중에 들어온 요청이다.

> 추가로 다른 서버에 사내 구축된 llm이 있어. vllm을 사용하고있고, 모델은 qwen 3버전이야.
> 이를 workfluence 시스템에서도 사용하고 싶은데, 하나의 메뉴를 추가해서 질문하고 활용할 수 있는 페이지를 만들고 싶어. 서버에서 llm API만 등록해두면 사용할 수 있게. 이는 '시스템 관리자'가 '시스템 관리자 화면'에서 llm api를 쉽게 등록하고 삭제할 수 있게 해줬으면 좋겠어.
> 다만 사용자마다 각자 시스템 프롬프트나 프리프롬프트를 설정하고, 저장해서 활용할 수 있었으면 좋겠어. 대화 내용도 저장이 되면 좋겠지만, 이건 뭔가 리소스가 크게 들어갈 것 같네.
>
> 개발이 완료되고, 보류된 내용이 모두 해결되면 위에 내용도 이어서 할 수 있게 해줘.

| 항목 | 내용 |
|---|---|
| 상태 | `완료` — Phase 10 (`impl-phase10`, PR #9, 2026-09-25). 설계 `docs/P10_설계서_Llm.md`. 착수 쟁점의 답은 `docs/prompts/phase10/scope.md`. **사내 LLM 실연동은 보류 29** — 가짜 LLM 서버로만 확인했다 |
| 크기 | **L** — LLM 연결 정보를 담을 표와 사용자별 프롬프트 표가 필요하다. 대화를 남기기로 하면 대화 표도 |
| 만지는 층 | 화면(새 메뉴의 질문 화면 · 관리 화면의 LLM 등록·삭제) · API(등록 관리, 서버가 LLM에 대신 묻는 중계) · DB · 문서(설계서·운영가이드·반입 가이드) |
| 배정 Phase | 10 |
| 영향 | 기존 동작은 바뀌지 않는다. 다만 앱이 **사내의 다른 서버로 나가는 길**이 처음으로 하나 더 생긴다 — 사내 IdP(보류 11)·메일 API(보류 18)와 같은 부류라, 이 개발 서버에서 그 LLM 서버에 닿는지부터 확인해야 한다. 브라우저는 LLM에 직접 가지 않고 우리 서버만 거친다(7절 CSP) |
| 판단 근거 | 새 메뉴 하나지만 표가 새로 생겨 L이다. 착수 때 사용자가 정할 것이 있다 — 대화를 남길지(말씀대로 저장 공간과 보존 기간의 문제이고, 질문에 업무 내용이 들어가므로 문서 본문과 같은 민감도로 다뤄야 한다), LLM API 키를 어디에 둘지, 누가 쓸 수 있는지. "보류된 내용이 모두 해결되면"은 **지금 진행 중인 보류 22·23·24**로 읽었다 — 반입 뒤에야 풀 수 있는 보류(11·12·13·14·18·19)까지 기다리면 이 요청이 반입 뒤로 밀린다 |

### F-001 · 비밀번호 자가 재설정을 다시 볼 것 · 접수 2026-09-23

사용자 요청이 아니라 **문서 정합성 검사가 올린 것**이다. 원문 인용이 없는 유일한 항목이라 여기 밝혀 둔다.

Phase 1은 "대역 외 확인 수단이 없다 — 이 시스템에는 메일이 없다"를 근거로 자가 재설정을 두지 않기로 했다
(`docs/P1_설계서_Auth.md` 2.4절, `docs/scope-definition.md` 7.1절). **Phase 6에서 사내 메일 발송이 생겨 그 근거가 사라졌다.**
결정을 바꾸자는 것이 아니라, **없어진 근거 위에 남아 있는 결정**이라 다시 볼 자리라는 뜻이다.

| 항목 | 내용 |
|---|---|
| 상태 | `보류` — 사내 메일 API 실연동(보류 18) 전에는 판단할 수 없다 |
| 만지는 층 | 화면 · API · DB(토큰 표) · 문서 |
| 배정 Phase | — |
| 크기 | **L** — 일회용 토큰을 담을 표가 필요하다 |
| 영향 | 지금의 "요청만 남기고 관리자가 초기화" 흐름이 남을지 대체될지 |
| 판단 근거 | 메일 도달만으로 본인을 확인하는 흐름이라 보안 판단이 먼저다. 메일이 실제로 닿는지도 아직 모른다 |

## 4. 처리된 요청

프로토타입 단계에서 들어온 요청들은 이 문서를 만들기 전에 처리돼 `docs/prompts/` 아래에 원문으로 남아 있다. 요약하면 아래와 같고, 상세는 그 파일들을 본다.

| 요청 묶음 | 원문 | 처리 |

| 프로토타입 1차 (기본 화면·스페이스·페이지) | `docs/prompts/prototype-v1.md` | 완료 — `exp/prototype` 브랜치 |
| 프로토타입 2차 (가입 승인·계정 복구·역할·관리 화면·비밀번호 정책) | `docs/prompts/prototype-v2.md` | 완료 — `exp/prototype` 브랜치 |

**프로토타입에서 확인한 기능은 Phase마다 근거 문서와 테스트를 갖춰 다시 만든다.** 프로토타입은 "이런 화면이면 되겠다"를 눈으로 확인한 참조물이지 가져다 쓰는 코드가 아니다 (`CLAUDE.md` 1.5절).

2026-09-22 기준으로 1·2차 요청(가입 승인·계정 찾기·역할·비밀번호 정책, 스페이스·Crew·페이지·이력)은 Phase 1·2에서 본 제품에 들어왔다. 3차 요청의 화면 세부는 Phase 4에서 본다.

## 5. 요청을 넣는 방법

그냥 말씀하시면 된다. "이런 게 있으면 좋겠다" 정도로 충분하다. 제가 여기에 원문을 적고, 어느 단계의 일이고 얼마나 큰지, 기존 동작 중 무엇이 바뀌는지를 알려 드린다.

급한 요청도 적는 것이 먼저다. 다만 **장애와 보안 사안은 예외**로 진행 중인 작업을 멈추고 먼저 처리한다.
