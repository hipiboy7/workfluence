## 2. 가장 값있던 것

### ① 요구사항 하나가 조용히 사라졌다 — 토큰 수 (셋 다 짚었다)

FR-1118은 질문마다 토큰 수를 감사로그에 남긴다. 코드는 넣었고 시험도 초록이었다. 감사의 비밀 거르기가 이름에 `token`이 든 키를
통째로 버렸다 — **거르는 층이 있는 곳에서 시험이 적은 것만 보고 저장된 것을 보지 않았다.** T-043.

### ② 흐름이 화면과 세션의 수명에 묶이지 않았다 (코드 리뷰 1·5·6·8 · 자체 점검 5·6)

답 하나는 길게(기본 10분, 1시간까지) 열려 있는 연결이다. 그 연결이 **무엇으로 끝나는가**를 넷이 따로 짚었다.

- 화면을 떠나도(다른 메뉴·뒤로 가기) 요청이 살아 끝까지 흘렀다. 그 사람의 자리(FR-1114)를 쥐어 돌아와 물으면 409였고, 끝난 옛
  흐름이 사용자를 원래 대화로 끌고 갔다 → **FR-1122**: 떠나면 요청을 끊는다(서버는 받은 데까지 저장한다)
- 확인(`prepare`)하는 사이에 끊긴 연결은 알아채지 못했다 → 출구가 만들 때 `res.destroyed`를 본다
- 중지가 서버가 자리를 잡기 **전에** 눌렸고, 그러면 닿지 않아 답이 끝까지 흘러 "끝남"으로 남는데 다시 누를 수도 없었다 →
  흐름이 열린 뒤에만 누르고, `{stopped:false}`면 되살린다. 보내기와 같은 단추를 다시 쓰던 것도 나눴다
- 비밀번호 변경·강제 종료·로그아웃 뒤에도 답이 흘러 그 사람 이름으로 저장됐다 → **FR-1121**: 세션 파기 버스를 듣는다(P7과 같은 자리)

### ③ 시험이 결함을 기대값으로 고정하고 있었다 — 답을 받는 사이의 LLM 삭제 (코드 리뷰 2 · 자체 점검 4 · 보안 검토)

"저장이 실패하면" 시험은 저장 실패를 만들려고 **흐름 도중 LLM을 지웠다.** 그것은 FR-1101("지우면 대화는 남는다")이 막으려던
바로 그 상황이다 — 마스터 키를 바꾼 뒤 지우고 다시 등록하는 절차(D.4)를 밟는 사이 답을 받던 사람의 답이 통째로 사라졌다.
P9의 "관문은 받는데 저장은 못 하는 모양"과 같은 부류다: **시험을 짜려고 고른 상황이 결함이었다.** 저장 문장이 그 순간의 행을
보게 했고(없으면 NULL), 저장 실패는 DTO를 거치지 않은 U+0000으로 만든다.

### ④ 주소의 id로 다른 API를 부르게 할 수 있었다 — Phase 10 이전 화면까지 (보안 검토 문턱 아래)

라우터는 주소의 `%2F`를 풀어 넘긴다. 화면은 그 id를 API 경로에 넣는다. `/llm/..%2F..%2Fpages%2F<id>%2Fexport`를 열면
`GET /api/pages/<id>/export`가 나갔다. 같은 모양이 페이지 편집 같은 **기존 화면의 PUT**에도 있다 — 누군가 페이지에 심은 내부 링크를
관리자가 누르면 그 관리자의 세션과 CSRF 머리말로 다른 API가 불린다(7절의 CSRF 방어를 옆으로 돌아간다).

1.4절 5의 예외(보안)로 이 Phase에서 고쳤다. 화면마다 싸는 대신 **모든 호출이 지나는 한 곳**(`api()`)에서 경로의 `.`·`..` 조각을
막는다 — URL 해석이 점으로 읽는 `%2e`, `/`로 읽는 `\`, 지우는 탭·줄바꿈까지. 해석 규칙은 실제 WHATWG 해석기로 확인했다. E2E 28건
전부로 다른 화면이 깨지지 않았음을 봤다.

### ⑤ 암호의 묶음이 주소를 빠뜨렸다 (코드 리뷰 9 · 보안 검토 2)

D.4는 "DB를 만질 수 있는 사람"을 상대로 AAD에 행 id를 묶었다. 같은 행의 **주소만** 바꾸면 서버가 키를 풀어 `Authorization`에 실어
그 주소로 보냈다 — 막으려던 상대가 쓰는 가장 쉬운 길이었다. 등록을 고치는 API가 없어 주소를 AAD에 넣는 비용이 없다.

## 5. 종료 루틴 — 반영분에 다시 (`doc-consistency` · `self-reviewer`)

첫 판의 검토 셋을 고친 반영분(`cf00fa5..4af97a9`, 커밋 다섯·60파일)에 종료 루틴 둘을 동시에 돌렸다. 둘 다 오탐 0.

### 가장 값있던 것 — "코드·문장만 싣는다"는 전제가 틀렸다 (자체 점검 1)

반영분은 로그 규칙을 "DB 오류는 PostgreSQL의 코드·문장만 — 값은 `detail`에만"으로 세우고 규칙서 7절에도 그렇게 적었다. 자체 점검이
**실제 drizzle 0.45 + PostgreSQL 오류**를 `errorText`에 넣어 보니 데이터 예외(SQLSTATE 22)는 받은 값을 **문장 본문에** 따옴표로
싣는다 — `22P02 invalid input syntax for type uuid: "비밀-질문-본문-XYZ"`. 시험(`error-text.spec.ts`)은 합성 오류(`new Error(…, { cause })`)만
넣어 PostgreSQL이 문장의 어디에 값을 싣는지 한 번도 보지 않았다. **T-043과 같은 교훈이다 — 거르는 층은 실제로 거쳐 온 것으로 시험한다.**
지금은 닿는 길이 없었다(경로의 uuid는 `UuidPipe`가, 본문은 zod가 먼저 막는다). 고친 것: 데이터 예외의 문장은 따옴표 안을 가리고, 실제
PostgreSQL로 22P02·22003·22007과 따옴표 든 값을 시험한다(`error-text.integration.spec.ts`). 가리기를 빼면 그 시험이 실패함을 확인했다.
