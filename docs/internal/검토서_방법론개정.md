## 3. 낭비 — 무엇이 문제였나

### 3.1 같은 사실을 세 곳에 썼다

요구사항정의서와 설계서는 목차가 사실상 같았다. 전자가 열두 개 주제로 "이걸 만든다"를 쓰고 후자가 같은 열두 개로 "이렇게 만든다"를 썼다.

**증거.** CI를 단계별로 쪼갠 변경이 워크플로 파일에는 반영됐는데 설계서 9.2절과 요구사항정의서 FR-091에는 옛 문구로 남았다. 같은 사실이 세 곳에 있었고 **두 곳이 상했다.** `doc-consistency` 에이전트가 이것을 잡았다. 기계 검사는 "이 문장대로 하면 되는가"만 보고 "두 문장이 서로 반대말인가"는 못 본다.

### 3.2 검증 문서가 가장 크고 가장 빨리 낡았다

`P0_테스트결과서_Foundation.md`가 415줄로 최대 문서였다. 그 안의 재작업 서술 9꼭지 중 3꼭지(6.4·6.5·6.8)는 트러블슈팅 기록 T-007·T-008·T-010과 **내용이 겹쳤다.** 측정 수치는 CI가 매번 다시 뽑으므로 문서에 박히는 순간부터 틀리기 시작한다. 인수인계 받는 개발자가 읽을 문서도 아니다.

### 3.3 호출자 없는 코드를 먼저 만들었다

| 항목 | 줄 수 | 당시 호출자 |
|---|---|---|
| `packages/shared` 계약 5개 파일 | 684 | 사실상 없음 |
| 그 테스트 | 407 | — |

로그인·스페이스·페이지 등 스물다섯 개 요청 형식을 Phase 0에서 전부 정의했는데 앱 코드가 쓰는 것은 환경 스키마 하나뿐이었다. **A등급 커버리지 99%는 아무도 부르지 않는 코드에 대한 수치다.**

프로토타입에서 옮겨 온 것이라 버릴 필요는 없다. 다만 "완료"의 근거로 쓸 수 없다. 그래서 보류 결정 10을 새로 등재하고, 3절에 "호출자가 없는 코드의 커버리지는 품질 근거가 아니다"를 명시했다.

### 3.4 기록이 네 군데로 갈라졌다

세션 히스토리 파일, 커밋 메시지, PR 설명, 어시스턴트의 기억이 같은 일을 각각 적었다. 결함을 잡은 실적은 0이다. 게다가 히스토리 파일은 **이 세션에서 실제로 사실관계를 한 번 틀렸고** 정정 이력을 붙여야 했다. 같은 일을 네 번 적으면 넷 다 못 믿는다.

### 3.5 규칙서가 매 세션 전부 읽히는데 근거 산문이 섞여 있었다

`CLAUDE.md`가 383줄이었고 상당 부분이 "왜 이 규칙인가"였다. 규칙은 매번 읽어야 하지만 근거는 한 번 정하면 다시 읽을 일이 드물다. 분리했다.

### 3.6 작업 계획을 문서로 남겼더니 설계서와 같은 말을 두 번 했다 (2026-09-17)

사용자가 물었다. **"그런데 솔직히 프롬프트도 생성할 필요가 있을까?"**

Phase 0 작업 프롬프트는 122줄이고 절이 여섯 개였다. 실측해 보니 다섯 개가 설계서와 같은 내용이었다.

| 프롬프트의 절 | 같은 내용이 있는 곳 |
|---|---|
| 왜 Phase 0인가 | 설계서 A.1 목적 |
| 프로토타입 승격 규칙 | **어디에도 없었다** (아래 참조) |
| 산출물별 요구사항 | 설계서 A.4·A.5 |
| 완료 기준 | 설계서 A.6 |
| **착수 전 쟁점 4건** | **여기밖에 없었다** |
| 하지 않는 것 | 설계서 A.3 Out of Scope |

겹쳐 쓴 대가는 이미 치렀다. 이 파일 하나에 **정정 각주를 두 번** 붙여야 했다. 하나는 에이전트 개수가 달라진 것, 하나는 산출물 단계가 바뀐 것이다. 목차에 같은 파일명이 두 번 나오는 흉터도 남았다.

**살아 있던 것은 두 개뿐이었다.** 착수 쟁점 4건과 프로토타입 승격 규칙이다. 앞의 것은 사용자만 정할 수 있는 결정이고, 뒤의 것은 Phase 1~4에서도 쓰이는 규칙이다. 지우기 전에 확인해서 찾았다. **확인하지 않았으면 규칙 하나를 조용히 잃었을 것이다.**

같은 검토에서 요청 기록 폴더에 **세 종류가 섞여 있는 것**도 드러났다.

| 종류 | 성격 | 판정 |
|---|---|---|
| 사용자의 말 원문 | 다시 만들 수 없다 | 남긴다 |
| Claude가 쓴 작업 계획 | 설계서가 나오면 쓸모가 없다 | 없앤다 |
| 방법론 근거 | 검토서의 성격이다 | `docs/internal/`로 옮긴다 |

이 섞임이 11절 규칙을 무겁게 느껴지게 한 원인이었다.

## 4. 빠져 있던 것 — 사용자의 4번과 5번

낭비를 줄이는 것보다 이것이 더 중요했다.

**4번(소유자용 설명).** 규칙상 학습가이드는 **선택**이었고 위치도 운영 담당자가 읽지 않는 내부 폴더였다. Phase 0 종료 시점에 한 건도 없었다. 사용자가 필요하다고 말한 것이 규칙에서는 가장 낮은 우선순위에 있었다.

**5번(장애 대응 근거).** 트러블슈팅 기록은 전부 **개발 중** 문제였다. 운영에서 증상을 보고 원인으로 가는 문서가 없었다. 로그 항목의 뜻, 어떤 증상이면 어디를 보는지, 감사로그 조회 방법이 모두 Phase 5로 밀려 있었다. 그때까지 장애가 없다는 보장은 없다.

**3번(인수인계).** 새 개발자가 읽을 순서가 정해져 있지 않았다. 4.2절의 재독 순서는 문서 정합 검사를 위한 것이고 온보딩용이 아니다.

### 5.1 절 번호를 바꾸지 않은 이유

`CLAUDE.md`의 절 번호를 가리키는 참조가 문서와 코드 주석에 약 100곳 있었다. 번호를 재배열하면 그 100곳이 한꺼번에 상하고, 그것이 바로 이번에 고치려던 문제다. 그래서 **번호는 고정하고 안쪽만 줄였으며, 새 규칙은 새 하위 번호(1.4절)로 뒤에 붙였다.**

같은 이유로 `P0_설계서_Foundation.md`의 숫자 절(0~13)도 유지했다. 코드 주석 네 곳이 그 번호를 가리킨다. 합쳐 들어온 요구사항과 제품 대조는 **문자 절(A·B)**로 앞에 붙였다.

### 5.2 문서 분량 변화 (2026-09-16 개정 직후 실측)

| 구분 | 이전 | 이후 | 차이 |
|---|---|---|---|
| Phase 0 정규 산출물 + 대조서 | 1,046줄 (요구사항 246 · 설계 337 · 테스트결과 415 · 대조 48) | 835줄 (설계서 540 · 검증기록 295) | **-211** |

| 새로 생긴 문서 | — | 학습가이드 120 · 운영가이드 145 · 기능백로그 64 · 요청 기록 65 = **394줄**. 여기에 이 검토서가 더해진다 | +394 이상 |

이 표는 그날의 snapshot이다. **자기 문서의 줄 수를 표에 적었다가 그 절을 고치면서 어긋난 적이 한 번 있다**(`doc-consistency` 두 번째 실행이 잡았다). 그래서 이 표에서 자기 참조를 뺐다. 줄 수가 필요하면 `wc -l`로 센다.

**문서 총량은 늘었다. 줄이는 것이 목적이 아니었다.** 겹쳐 쓰던 211줄을 걷어내고, 그 자리에 사용자가 필요하다고 말한 4번(소유자용 설명)과 5번(장애 대응)을 넣었다.

규칙서가 22줄 늘어난 것은 근거 산문을 이 문서로 옮긴 대신 새 규칙(1.4절 기능 요청 접수, 10절 문서 목록 표)이 들어왔기 때문이다. **매 세션 읽히는 문서에 "왜"가 아니라 "무엇을"만 남긴 것이 이득이다.** 줄 수보다 읽을 때의 판단 부담이 줄었다.

문서를 지우는 판단에서 위험한 것은 **거기에만 있던 것을 못 알아보는 것**이다. 그래서 지우기 전에 절별로 대조했고, 살아 있는 내용 두 개를 옮겼다.

| 프로토타입 승격 규칙 4단계 | `CLAUDE.md` 1.5절 | Phase 1~4에서도 프로토타입 코드를 승격한다. 살아 있는 규칙이다 |
| 방법론 v1 근거 | `docs/internal/검토서_방법론v1.md` | 요청 기록이 아니라 판단 기록이다 |

**승인 관문은 줄지 않았다.** 착수 전에 쟁점을 대화로 제시하는 단계가 그대로 있고, 첫 산출물인 설계서를 사용자가 본다. 없어진 것은 "제가 무엇을 만들 계획인지 미리 요약한 파일" 하나다.

**잃은 것도 있다.** 계획을 글로 쓰면 시작 전에 한 번 더 생각하게 되고, Phase 0에서 그 효과는 실제로 있었다. 다만 그 생각의 산출 중 남길 가치가 있었던 것은 쟁점뿐이었다. 생각은 계속 하고, 결과만 남긴다.

**분량 (2026-09-17 실측).** 요청 기록 폴더에서 259줄이 빠졌다. 작업 계획 문서 122줄은 지웠고 방법론 v1 근거 137줄은 `docs/internal/`로 옮겼다. 요청 기록 문서는 65줄에서 34줄로 줄었다 — 분석을 이 검토서로 옮겼기 때문이다. 대신 규칙서가 405줄에서 422줄로, Phase 0 설계서가 540줄에서 553줄로 늘었다. 옮긴 내용이 들어간 만큼이다.

## 6. 이 개정이 틀렸다고 판정하는 방법

개정도 실적으로 평가한다. Phase 1 종료 시점에 아래를 확인한다.

| 확인할 것 | 실패 신호 | 그때 되돌릴 것 |
|---|---|---|
| 설계서 하나에 요구사항과 설계가 같이 있어 읽기 어려운가 | 설계서가 800줄을 넘고 "어디에 뭐가 있는지" 못 찾는다 | 다시 분리한다. 단 FR 표는 한쪽에만 둔다 |
| 검증기록이 짧아져 증거가 부족한가 | "이게 정말 돌아갔나"를 문서로 답할 수 없다 | 실호출 원문을 더 남긴다. 서술은 늘리지 않는다 |
| PR 설명이 세션 기록을 대신하는가 | 다음 세션이 상태를 못 이어받는다 | PR 설명 서식을 규칙으로 고정한다 |
| 학습가이드가 실제로 읽히는가 | 사용자가 같은 질문을 반복한다 | 그 질문을 문서에 넣는다. 문서가 아니라 질문이 기준이다 |
| 기능백로그가 실제로 쓰이는가 | 요청이 백로그를 건너뛰고 바로 코드로 간다 | 1.4절을 Phase 착수 체크리스트에 넣는다 |
| 작업 계획 문서 없이 착수해도 되는가 | 쟁점을 놓쳐 Phase 중간에 사용자에게 되묻는 일이 생기거나, 설계서가 "무엇을 만들지"를 못 담는다 | 쟁점 제시 단계를 체크리스트로 만든다. 계획 문서를 되살리지는 않는다 |

## 7. 개발 환경을 Linux로 옮긴 결정 (2026-09-21)

`CLAUDE.md` 확인 필요 **E**의 답이다. 규칙서에는 결과만 적혀 있고(0.3절·8.1절) 근거는 여기 있다.

### 7.1 무엇이 바뀌었나

사용자가 Phase 0의 리눅스 빌드 검증을 그 서버에서 마친 뒤 거기서 이어서 작업하겠다고 했다.
**환경 3종이 2종이 됐다.** 개발(Windows Server, Docker 없음)과 빌드(Linux 서버)가 한 호스트가 됐고,
운영(폐쇄망)만 그대로다.

| | 이전 | 이후 |
|---|---|---|
| 코드·테스트·문서 | Windows Server 2022 | 사내 Linux 서버 (RHEL 9) |
| 이미지 빌드 | 별도 Linux 서버 | **같은** 서버 |
| 데이터 위치 규칙 | D 드라이브 `.local/` (C와 분리) | 저장소 안 `.local/`. **분리할 드라이브가 없다** |
| 런타임 설치 | 개발 PC에 Node 24 | 사용자 홈 `~/.local/node` (공유 서버라 전역에 안 깐다) |

### 7.2 왜 이 결정을 그냥 받지 않고 검토했나

"장비가 하나 줄었다"로 보이지만 실제로는 **분리되어 있어서 공짜로 지켜지던 전제들이 한꺼번에 풀린다.**
옮기는 것 자체는 사용자가 정할 일이고 우리가 할 일은 **무엇이 풀렸는지 세는 것**이다. 셋이 나왔다.

| 분리가 대신 지켜 주던 것 | 합치자 생긴 일 | 어떻게 다뤘나 |
|---|---|---|
| 환경 파일 이름이 겹쳐도 기계가 달라 안 부딪혔다 | `.env` 하나를 개발과 compose가 다퉜다. 앱 strict 스키마가 `WF_PG_PASSWORD`를 모르는 키로 보고 기동 거부 | `.env`(개발) / `deploy/.env`(compose)로 분리. 8.1절·T-015 |
| "개발 PC에는 Docker가 없다"가 **컨테이너 확인을 강제**했다 | 호스트에서 되면 됐다고 넘길 수 있게 됐다. 운영은 여전히 컨테이너다 | 0.3절에 "개발에서 되는 것과 컨테이너에서 되는 것을 따로 확인한다"를 규칙으로 남겼다 |
| 데이터 드라이브가 분리돼 개발이 빌드를 못 굶겼다 | 디스크가 `/` 하나. 개발 데이터가 늘면 **빌드가 먼저 깨진다** | 8.1절에 사실로 적고 `pnpm check:env`의 여유 검사를 그 근거로 삼았다 |

### 7.3 실측으로 확인한 것

옮겼다고 적기 전에 **그 서버에서 실제로 돌려** 확인했다 (1.3절 "문서가 아니라 동작으로 확인한다").

| 확인 | 결과 |
|---|---|
| `pnpm check:env` | `READY` — Node v24.21.0, pnpm 12.4.1, 임베디드 PostgreSQL 17.10, 마이그레이션 1/1 |
| `pnpm check` | 통과 (lint·typecheck·테스트 18건·`verify:docs` 16개 문서) |
| 개발 DB와 compose DB 공존 | 임베디드 PG 5433(로컬 전용) / compose PG 5432(도커 네트워크 내부). 충돌 없음 |
| 디스크 | 전체 39GB, 사용 22GB, 여유 16GB. 개발 의존성이 더한 몫 약 1GB |

임베디드 PostgreSQL의 메이저 버전이 운영 이미지와 같은 17이라는 점이 그대로 유지됐다.
`@embedded-postgres/linux-x64`가 이미 `allowBuilds`에 있었다 — **이 이동이 설계상 배제돼 있지는 않았다.**

### 7.4 되짚기

Windows에서의 Phase 0 기록은 **고치지 않았다.** `docs/P0_검증기록_Foundation.md` 1절 표는
2026-09-16에 그 기계에서 잰 값이고, 그것을 리눅스 값으로 덮으면 측정 기록이 아니라 현재 상태
서술이 된다. 대신 같은 절에 "옮겨서 다시 돌려 통과했다"를 주석으로 붙였다. 결과적으로
**NFR-06(Windows·Linux 양쪽에서 같은 `pnpm` 명령이 동작)이 이번에 실측됐다** — 두 OS에서
같은 명령을 실제로 돌린 기록이 둘 다 남았다.

### 7.5 이 결정이 틀렸다고 판정하는 방법

| 확인할 것 | 실패 신호 | 그때 되돌릴 것 |
|---|---|---|
| 개발이 빌드를 굶기지 않는가 | `pnpm check:env`가 디스크로 실패하거나 빌드가 `no space left`로 죽는다 | 개발 데이터를 별도 볼륨으로 옮긴다. 8.1절 표의 경로만 바꾸면 된다 |
| 컨테이너 확인을 건너뛰지 않는가 | 호스트에서만 통과한 변경이 이미지 빌드나 기동에서 드러난다 | Phase 종료 루틴(1.1절 8-1)의 "Linux 빌드 확인"을 매 커밋 단위로 당긴다 |
| 공유 서버라서 생기는 사고가 없는가 | 다른 프로젝트의 컨테이너·볼륨이 영향을 받는다 | 전용 인스턴스를 요청한다. 그때까지는 `운영가이드_리눅스빌드.md` 3.1절 금지 목록을 지킨다 |
