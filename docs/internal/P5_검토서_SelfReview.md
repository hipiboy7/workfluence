## 1. 이 검토가 찾은 것 중 가장 중요한 넷

**전부 "돌려 보면 통과하는데 실제로는 안 되는" 유형이다.** 넷 다 고쳤다.

### 1.1 복원이 절반만 되고, 다시 시도할 수도 없었다

`backup-restore.ts`가 첨부를 `docker compose exec api tar`로 풀었다. 그런데 복원 절차의
**첫 단계가 "api를 멈춘다"**(`운영가이드_장애대응.md` 7.18절)다. `exec`는 떠 있는
컨테이너에만 붙으므로 그 뒤에 부르면 실패한다 — **DB는 이미 복원됐고 첨부만 빠진 상태**로
예외가 나고, 다시 돌리면 "비어 있지 않다"로 거부되어 첨부를 되살릴 길이 없다.

리허설에서는 안 걸렸다. **리허설은 api를 멈추지 않고 했기 때문이다** — 문서가 정한
순서를 따르지 않은 리허설이었다.

고친 방법: `run --rm --no-deps`로 **새 컨테이너를 띄운다.** api가 떠 있든 멈춰 있든 같게
동작하고 볼륨 이름을 손으로 적지 않아도 된다. 백업 쪽도 같은 이유로 함께 고쳤다.

### 1.2 복원이 성공한 뒤에 실패로 뒤집혔다

백업은 행 수를 **덤프보다 먼저** 센다. 주석은 그것을 "하한"이라고 했는데, 복원 쪽은
**완전 일치**를 요구했다. 주간 백업은 서비스가 도는 채로 뜨므로 **로그인 하나만 끼어도**
`audit_events`가 늘어난다 → 복원이 다 끝난 뒤 "수치가 다르다"로 예외 → DB는 비어 있지
않아 재시도 불가. **주석과 코드가 반대말을 하고 있었다.**

고친 방법: 모자란 것만 실패로 본다. 넘치는 것은 "백업 도중 들어온 쓰기"로 알려 준다.

### 1.3 평범한 로그인 트래픽이 가입 제한을 리셋했다

`RateLimitStore.hit`의 청소가 **지금 들어온 요청의 창**으로 모든 키를 판정했다.
로그인은 60초 창, 가입은 600초 창이다. 로그인 요청 하나가 들어오면 최근 60초에 히트가
없는 가입 키를 통째로 지운다 — **무차별 대입을 막으려고 둔 장치가 트래픽만 있으면 풀린다.**

T-027에서 상태를 새 클래스로 옮길 때 이 로직을 그대로 가져왔다. **옮기는 작업은 로직을
다시 읽지 않는다.**

고친 방법: 키마다 자기 창 길이를 함께 저장하고, 청소는 각 키의 자기 창으로 판정한다.
회귀 테스트 2건을 뒀다.

### 1.4 T-026이 한 곳 남아 있었다

`changeRole`이 "마지막 root인가"를 `this.db`로 셌다. 트랜잭션 안이므로 풀에 두 번째 연결을
요구한다. 지금은 `connectionTimeoutMillis` 때문에 10초 뒤 500으로 끝나지만 **원인은 그대로**였다.

내가 `users`·`auth`를 훑을 때 조회 도우미(`findBy*`)만 봤고 **"세는" 질의는 안 봤다.**
전수 조사를 다시 돌려 남은 것이 없음을 확인했다 — 지금은 `tx`를 받는 메서드 안에서
`this.db`를 쓰는 곳이 하나도 없다.

## 3. 반영하지 않은 것과 이유

| 지적 | 왜 안 했나 |
|---|---|
| `BACKUP.json`을 체크섬에 넣는다 | **다음에 손댈 때 함께.** 지금 넣으면 기존 백업이 전부 "체크섬 목록에 없는 파일"이 된다. 대조 근거가 상하는 경우는 "누가 그 파일만 고친 경우"인데, 그러면 행 수가 안 맞아 복원이 실패한다 — 조용히 통과하지는 않는다 |
| `meta.migrations`를 복원에서 비교 | **하지 않는 편이 맞다.** 복원 대상이 **더 새 버전**일 수 있다(반입 후 업그레이드). 마이그레이션 수가 다르면 실패시키면 정상적인 복원이 막힌다. 기록만 남기고 사람이 본다 |
| 이미지 태그를 `:<git-sha>`로 | **묶음에서는 `:latest`가 맞다.** compose가 `:latest`를 참조하므로 sha 태그로 저장하면 `docker load` 뒤 compose가 이미지를 못 찾는다. **어느 sha인지는 `MANIFEST.txt`가 답한다** — 그것을 검사하도록 이번에 고쳤다(#7b). 태그와 매니페스트 둘 다로 답하려면 compose가 태그를 변수로 받아야 하고, 그 쪽이 반입 당일 실수를 늘린다 |
| `reindexAll`에 운영 호출자가 없다 | **사실이다. 지우지는 않는다.** 관리 화면에서 부를 자리(FR-333)가 설계에 있고, 정의는 이제 스크립트와 공유한다. **검증기록 1.2절에 "호출자 없는 코드의 커버리지는 근거가 아니다"를 적었다** (보류 10과 같은 판단) |
| A등급 테스트 선행 이력 | **4절** |
| 문서 52건 중 8건 | 과거 서술(착수 시점 기록·검증기록의 그때 사실)이거나, 다른 브랜치 기록이다 |

## 4. 이 검토 중에 드러난 내 실수

**넷이다. 앞의 셋은 "확인했다고 적을 뻔한" 것이다.**

1. **A등급 테스트 선행 이력을 남기지 못했다.** `release.ts`와 `blob-path.ts`는 구현과
   테스트가 **같은 커밋**에 들어갔다. 실제 작업 순서는 테스트를 먼저 썼지만
   **이력으로 증명할 수 없다.** CLAUDE.md 1.5절 3단계는 "테스트가 먼저 있었음을 커밋
   이력으로 남긴다"다. 다음 A등급 모듈은 **테스트만 먼저 커밋한다** (Red 상태로).

2. **복원 리허설을 문서가 정한 순서로 하지 않았다.** api를 멈추지 않고 돌렸고, 그래서
   1.1절의 결함이 리허설을 통과했다. **절차서를 만들었으면 그 절차서대로 리허설한다.**

3. **T-026 전수 조사를 조회 도우미만 보고 끝냈다.** "세는" 질의를 빼먹었다. 같은 모양을
   찾을 때는 **패턴이 아니라 위치로** 찾아야 한다 — "트랜잭션 안에서 `this.db`를 쓰는 곳"
   전부를 기계로 훑는 것이 맞고, 이번에 그렇게 다시 했다.

4. **`docs/운영가이드_운영이관.md`에 백업 경로를 `.local/dumps/`로 적었다.** 실제는
   `.local/backups/`다. CLAUDE.md 8.1절 표를 보고 적었는데 그 표가 스크립트와 달랐다 —
   **문서를 보고 문서를 썼다.** 명령을 한 번 돌려 봤으면 바로 드러났다 (4.1절이 그것을
   요구한다). 표와 문서 양쪽을 실측에 맞췄다.

## 5. `/security-review` — **실제 취약점 하나를 찾았다** (High)

### 5.1 백업 파일을 고치면 복원할 때 임의 SQL이 DB 관리자 권한으로 실행된다

복원이 대조할 표 이름을 **`BACKUP.json`의 키에서 읽어** SQL에 그대로 넣었다.
`psql -tAc`는 세미콜론으로 이어진 문장을 여러 개 실행하고, 그 계정은 컨테이너의
DB 관리자다. 게다가 **`BACKUP.json`은 체크섬 목록에 없었다** — 백업이 체크섬을
먼저 만들고 이 파일을 그 뒤에 썼기 때문이다.

DB 계정이 없어도 **백업 공유 폴더나 반입 매체에 쓸 수 있는 사람**이 키 이름 한 줄을
고치면, 운영자가 `pnpm backup:restore`를 돌리는 순간 실행된다. 그리고 주입된 질의는
숫자가 아닌 값을 돌려주므로 `NaN`이 되어 **대조를 건너뛰고 "완료"를 출력한다.**

세 겹으로 막았다 (T-029).

| 무엇 | 왜 |
|---|---|
| 표 목록을 `packages/shared`로 옮기고 파일에서는 **숫자만** 받는다 | **식별자는 데이터에서 오지 않는다.** 값은 매개변수로 넘길 수 있지만 표 이름은 넘길 수 없다 |
| `BACKUP.json`을 **먼저 쓰고 체크섬에 넣는다** | 대조 근거를 담은 파일이 검사 밖에 있으면 대조 자체가 의미를 잃는다 |
| 복원이 **필수 파일이 체크섬 목록에 올라 있는지** 확인한다 | 목록에 없는 파일은 조용히 무검사로 통과한다 |

A등급 테스트 5건을 붙이고, **실제 백업으로 두 공격을 재현해** 둘 다 거부되는 것을
확인했다 — 예전 형식(목록에 `BACKUP.json` 없음)과 표 이름에 SQL을 넣은 것.

### 5.2 검토가 확인하고 통과시킨 것

`RateLimitStore`의 키 도출·환불 경로(환불은 **성공한 로그인에서만** 불린다),
`users`·`auth`의 `tx` 추가가 권한 검사를 건드리지 않았는지, `0006`이 `audit_events`의
예외를 건드리지 않는지, 정리 명령의 `interval` 보간(정책값이 정수 검사를 통과한 것만
들어온다), `blob-path`의 경로 이탈, `describeDatabaseUrl`의 비밀번호 누출,
`db.module`의 연결 옵션 주입, 백업 tar 전개, nginx 헬스체크의 `--no-check-certificate`
(자기 자신을 향한 loopback이라 중간자가 없다).

**보고 기준 아래로 남긴 것**: 묶음의 `SHA256SUMS`·`MANIFEST.txt`가 **서명돼 있지 않다.**
묶음을 고칠 수 있는 사람은 체크섬도 다시 만들 수 있다. 체크섬은 "옮기다 상했나"를
보는 장치이고 "누가 바꿨나"는 못 본다 — **서명은 별개의 일이다.** 폐쇄망 반입 심사가
요구하면 그때 붙인다. 지금 반입 묶음은 사람이 들고 들어가고, 그 사람이 곧 신뢰 경계다.

| 4 | 부하 측정이 **항상 종료 코드 0** | **고쳤다.** 판정을 종료 코드로 낸다 (12.2절). p95 3초에 오류 120건이어도 "통과"였다 |
| 5 | T-026 회귀 테스트가 **조용히 무장해제될 수 있다** | **고쳤다.** `TEST_POOL_MAX`를 내보내고 동시 요청 수를 `× 2`로 계산한다. 풀을 16으로 올리면 8은 전부 통과해 결함이 되살아난 채 초록이 된다 |
| 7 | `build:` 블록 건너뛰기가 **주석 하나에 깨지고**, 중괄호 없는 `$VAR`는 아예 놓친다 | **고쳤다.** `docker compose config --variables`로 물어본다. 걸러내는 기준은 이름 목록이 아니라 **규칙**(앱 설정은 전부 `WF_`, 5절)이다 |
| 8 | 복원 실패 시 **감사 기록이 남지 않는다.** `pg_restore`가 원자적이지 않다 | **고쳤다.** 감사 기록을 데이터 작업 직후·예외 전에 남기고 판정을 `detail`에 담는다. `--single-transaction --exit-on-error`를 붙여 도중 실패 시 **아무것도 들어가지 않게** 했다 |
| 10 | `backupCounts`가 표 목록이 늘면 **옛 백업을 못 쓰게 만든다** | **고쳤다.** 없는 키는 대조하지 않고(무엇을 대조 안 했는지 출력), 모르는 이름은 거부한다 — 주입은 계속 막힌다 |
| 11 | `verifyChecksums`가 `__proto__` 같은 이름에서 **터진다** | **고쳤다.** `Object.hasOwn`으로 본다. 이 입력은 반입 매체에서 온다 |
| 12 | `psql`에 `ON_ERROR_STOP`이 없다 | **고쳤다.** 감사 기록의 성패를 기본값에 맡기지 않는다 (12.2절) |
| 13 | **`scripts/**`가 타입 검사를 한 번도 받지 않았다** | **고쳤다.** `tsconfig.scripts.json`. 붙인 직후 실제 오류를 잡았다 (T-030) |
| 14 | api의 A등급 디렉토리가 여전히 합계 기준 | **고쳤다.** `perFile: true` |
| 15 | `describeDatabaseUrl`이 **커버리지 제외 파일**에 있다 | **고쳤다.** `apps/api/src/common/db-url.ts`로 옮기고 테스트 5건 |
| 16 | 겹친 JSDoc · `client_max_body_size 0`(무제한)을 위반으로 읽음 · 상한이 **세 곳**인데 둘만 대조 · `EISDIR` | **넷 다 고쳤다.** compose 기본값까지 대조한다 |
| 6b | 대조 목록에 `settings`·`space_members`·`labels`·`page_labels`·`space_categories`가 없다 | **고쳤다.** `space_members`가 사라지면 **팀 스페이스가 전부 접근 불가가 되는데 복원은 성공이라고 말한다** |

### 6.2 고치지 않은 것과 이유

| 지적 | 왜 |
|---|---|
| #6 행 수를 **덤프와 같은 스냅샷**에서 세기 | 제대로 하려면 `pg_dump --snapshot`으로 내보낸 스냅샷을 공유해야 하고, 그 절차는 지금 구조를 꽤 바꾼다. **대신 실패해도 기록이 남게** 했고(#8) 오류 문구에 재시도 경로를 적었다. 그리고 **백업과 정리 명령을 같이 돌리지 않는다**를 운영이관 4.2절에 적었다 — 이 경우가 생기는 유일한 조건이다 |
| #9 블롭 삭제와 같은 내용 업로드의 경합 | 창이 짧고, **정리가 도는 동안 같은 내용을 새로 올려야** 성립한다. 월 1회 수동 실행이라 사실상 닫힌 창이다. 고치려면 저장소 계층에 잠금을 넣어야 하는데 그쪽이 더 넓은 변경이다. **보류 14에 적었다** |
| 묶음 **서명** | 체크섬은 "옮기다 상했나"를 보고 "누가 바꿨나"는 못 본다. 서명은 별개의 일이고, 지금 묶음은 사람이 들고 들어가며 그 사람이 신뢰 경계다. 반입 심사가 요구하면 붙인다 (보안 검토 5.2에도 같은 판단) |
| 확인 필요 #2 **argon2가 트랜잭션 안에서 돈다** | 사실이다. 연결을 쥔 채 해싱하므로 로그인 처리량이 풀 크기에 묶인다. 고치려면 검증을 트랜잭션 **밖**으로 빼면서 "없는 계정도 더미 해시로 한 번 돌린다"는 타이밍 방어와 잠금 갱신의 원자성을 함께 지켜야 한다 — 인증 경로를 다시 짜는 일이다. **보류 16으로 등재했다** |
| 확인 필요 #1 `drizzle/meta`에 0005·0006 스냅샷 없음 | 손으로 쓴 마이그레이션이라 스냅샷이 없다. Phase 6에서 `pnpm db:generate`를 처음 돌릴 때 드러난다. **보류 17로 등재했다** — 그때 확인하는 것이 맞고 지금 만들면 손으로 쓴 스냅샷이 또 하나 생긴다 |
| 확인 필요 #3·#4 tar가 stdout을 타는 것, 512MB `maxBuffer` | 복원 왕복이 실제로 통했고 compose v2는 진행 상황을 stderr로 낸다. **다만 조용히 깨지는 모양이라** 백업 직후 `tar -tf`로 한 번 열어 보는 확인을 넣었다 |

### 6.3 검토가 확인하고 통과시킨 것

`0006`의 CHECK 값 집합이 `constants.ts`와 **다섯 개 모두 일치**하는 것,
`page_versions` UPDATE 트리거가 앱의 정상 경로를 하나도 막지 않는 것(버전 복원은 추가,
이동·제목 변경은 `pages`만 건드린다), 재색인 두 경로의 동등성, **T-026 전파가 완전한 것**
(트랜잭션 안의 `this.db`가 0건), `RateLimitStore`의 같은 밀리초·이중 환불·메모리 증가,
`trash-purge`의 FK 순서(0002~0004의 FK를 전부 열거해 확인), `audit-purge`의 GUC 예외 범위,
`parseManifest`의 CRLF·BOM·주석 처리.
