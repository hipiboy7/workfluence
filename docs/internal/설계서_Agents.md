# 설계서 — 서브에이전트·스킬 구성

- 작성일: 2026-09-16 (Phase 0)
- 대상: 전 Phase 공용 (`P<phase>` 접두사 없음)
- 정의 파일: `.claude/agents/doc-consistency.md`, `.claude/agents/self-reviewer.md`, `.claude/skills/troubleshoot/SKILL.md`
- 운영 절차: [`CLAUDE.md`](../../CLAUDE.md) 1.1절 8-1 (Phase 종료 루틴), 4.2절 (전체 재독)

> **이 문서가 있는 이유.** 에이전트 정의 파일은 "무엇을 하라"만 담는다. **왜 그 일을 맡기는지, 왜 어떤 일은 맡기지 않는지, 모델을 왜 그렇게 배정했는지**는 어디에도 남지 않는다. 저장소 규칙이 저장소 밖(대화·기억)을 가리키면 다음 담당자가 볼 수 없다.

## 1. 왜 서브에이전트를 쓰나

지금 대화하는 메인 세션을 팀장으로 보면, 팀장이 모든 일을 혼자 할 때 두 가지 문제가 생긴다.

| 문제 | 내용 |
|---|---|
| **책상이 넘친다** | 문서 전체를 읽으면 그 내용이 대화 끝까지 메인 컨텍스트에 남는다. 리뷰 반영마다 반복된다 |
| **작성자가 검토자다** | 자기 실수는 자기 눈에 안 보인다 |

서브에이전트는 **한 가지 일만 맡기는 계약직**이다. 별도 컨텍스트에서 일하고 결과 요약만 돌려준다. 읽은 수천 줄은 그쪽에 남고 메인은 깨끗하다.

**스킬**은 다르다 — 계약직이 아니라 **메인이 따르는 체크리스트**다.

### 1.1 에이전트로 만들 것과 아닌 것

넷 중 **셋 이상**이면 에이전트다.

| 기준 | 뜻 |
|---|---|
| **무거운 읽기** | 파일을 많이 읽어야 하고, 읽은 내용이 결론 도출 후에는 필요 없다 |
| **닫힌 범위** | 입력과 출력이 명확하고 "다 됐다"를 판정할 수 있다 |
| **승인 관문 없음** | 중간에 사용자에게 물어볼 일이 없다 (에이전트는 물어볼 수 없다) |
| **독립된 시각이 결과를 바꾼다** | 작성자가 아닌 눈이 필요한 일 |

## 2. 현재 구성

| 이름 | 형태 | 모델 | 하는 일 | 언제 |
|---|---|---|---|---|
| `doc-consistency` | 에이전트 | sonnet | 문서 전체를 읽고 변경과 어긋난 문장 목록을 낸다. 읽기 전용 | 리뷰·판단 변경 반영 시, Phase 종료 |
| `self-reviewer` | 에이전트 | fable | 코드·설정·문서의 어긋남과 조용히 잘못되는 결함을 찾는다. 읽기 전용 | Phase 종료 전 |
| `troubleshoot` | 스킬 | (메인) | 문제 해결 직후 트러블슈팅 기록 서식 | 해결 직후 |

## 3. 각각의 근거

### 3.1 `doc-consistency`

| 항목 | 내용 |
|---|---|
| **문제** | 판단 하나를 바꾸면 문서 여러 곳에서 흔적을 찾아 고쳐야 한다. `grep`은 **정확한 글자**만 찾는다 — "12자·3종"을 찾으면 표 안의 `| 비밀번호 | 12자 |`는 놓친다 |
| **왜 에이전트** | 무거운 읽기 ✅ / 닫힌 범위 ✅ (어긋남 목록) / 승인 관문 없음 ✅ / 독립 시각 ✅ — **4/4** |
| **읽기 전용인 이유** | 고치는 판단은 메인이 한다. 에이전트가 고치면 "정당한 이력"을 오탐으로 지울 위험이 있다 |
| **모델 sonnet인 이유** | 가장 자주 돈다. 결과가 목록이라 메인이 검토·수정하므로 놓침을 메인이 보완할 수 있다. 비용을 아낄 자리 |
| **한계** | 미묘한 모순을 약한 모델이 놓칠 수 있다. **처음 2~3회는 메인이 결과를 독립 재검토**해 놓침이 있으면 모델을 올린다 |

### 3.2 `self-reviewer`

| 항목 | 내용 |
|---|---|
| **문제** | 프로토타입에서 설정 키 미배선·순환 import·시드 계정 의존 테스트가 **전부 작성자 눈에 안 보였다**. 실행하거나 남이 봐야 드러났다 |
| **왜 에이전트** | 무거운 읽기 ✅ / 닫힌 범위 ✅ (결함 목록) / 승인 관문 없음 ✅ / 독립 시각 ✅ — **4/4** |
| **모델 fable인 이유** | 조용히 잘못되는 결함을 찾는 일이라 놓침의 대가가 크다. Phase당 1회라 총비용에 거의 영향이 없다 |
| **읽기 전용인 이유** | 수정까지 맡기면 "고쳤다"는 보고를 메인이 다시 검증해야 한다. 결함 목록이 더 값싸고 확실하다 |

### 3.3 `troubleshoot` (스킬)

| 항목 | 내용 |
|---|---|
| **문제** | 고친 기록이 대화에만 남으면 유지보수 담당자가 "이 오류 본 적 있나"를 찾을 곳이 없다 |
| **왜 에이전트가 아닌가** | **트러블이 터진 순간의 맥락(실제 오류 메시지·시도한 것)을 아는 건 메인이다.** 에이전트에 넘기면 git 기록으로 **재구성**해야 하고 그러면 부정확하다. 기준표로는 독립 시각 ❌ / 무거운 읽기 ❌ — **1/4** |
| **형태** | 서식 + 규칙. 메인이 해결 직후 직접 쓴다 |

## 4. 에이전트로 만들지 않은 것 — 그리고 이유

이 절이 없으면 나중에 "Phase 진행도 에이전트로 맡기자"는 제안이 나올 때 왜 안 되는지 찾을 곳이 없다.

| 영역 | 왜 안 맞나 | 기준표 |
|---|---|---|
| **Phase 진행 자체** | 승인 관문이 여러 개다 — 프롬프트 승인, 쟁점 결정, 리뷰, 병합 요청. 에이전트는 중간에 물어볼 수 없다 | 승인 관문 ❌ |
| **IdP·외부 연동 탐색** | 각 호출 결과가 다음 시도를 결정한다. 탐색 사이에 판단이 필요하고 그 발견이 설계를 바꾼다 | 닫힌 범위 ❌ |
| **테스트결과서 본문** | "무슨 일이 있었나"를 아는 건 그 자리에 있던 메인이다. 산출물만 보고 쓰면 시행착오의 **이유**가 빠진다 | 독립 시각이 오히려 해가 됨 |
| **코드 모듈 병렬 작성** | 빨라질 뿐 좋아지지 않고 토큰은 N배다. 테스트 선행 확인·스타일·통합 위험을 메인이 다시 본다 | 비용 대비 효과 ❌ |
| **실측값 → 문서 동기화** | 입력이 같으면 출력이 항상 같다. **판단이 없는 일에 에이전트를 쓰는 건 계산기 대신 사람을 고용하는 것.** 스크립트가 맞다 | 결정적 → 스크립트 |

## 5. 모델 배정 원칙과 승격 규칙

### 5.1 배정 원칙 — 빈도 × 결과물의 무게

| 빈도 | 결과물 | 모델 |
|---|---|---|
| 높음 | 메인이 검토하는 중간 산출(목록·표) | sonnet |
| 낮음 | 판단이 필요한 산출 | opus |
| 낮음 | **미묘한 결함 탐지·최종 산출물** | fable |

자주 도는 것만 싼 모델이다. 비용의 대부분은 반복 호출에서 나오므로 거기만 아낀다.

### 5.2 승격 규칙

**결과에서 놓침이나 오탐이 확인되면 그 에이전트를 최고 모델로 올리고 되돌리지 않는다.**

- "문제" = 결과에서 **놓침이나 오탐이 확인**된 것. `doc-consistency`가 미묘한 모순을 놓치면 `CLAUDE.md` 4.2절이 경고한 *"무시되는 관문"*이 된다
- 절차: 정의 파일의 `model:`을 바꾸고 **6절에 왜 올렸는지 한 줄** 남긴다
- **처음 2~3회 실행은 메인이 결과를 독립 재검토**한다. 재검토 방법: 결과를 보기 **전에** 메인이 자기 방식(grep 등)으로 대조 기준을 만들고, 결과가 오면 비교한다. 결과를 먼저 보면 편향된다

### 5.3 정의 파일에서 모델을 비우지 않는다

`model:`을 비우면 메인 세션 모델을 상속한다. 그러면 비용 통제가 안 되고, 메인 모델을 바꾸면 에이전트 동작도 조용히 바뀐다. 전부 명시한다.
