## T-001 · pnpm store가 `.local/` 대신 드라이브 루트에 생긴다 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | `.npmrc`에 `store-dir=.local/pnpm-store`를 넣고 설치했는데 `pnpm store path`가 `D:\.pnpm-store\v11`을 가리켰다. 192MB가 저장소 밖에 쌓였다 |
| **환경** | Windows, pnpm 12.4.1, 프로토타입 초기 설정 |
| **원인** | **pnpm 12는 `.npmrc`의 pnpm 전용 설정을 읽지 않는다.** 설정 위치가 `pnpm-workspace.yaml`로 옮겨졌다. `.npmrc`는 조용히 무시되어 기본 위치가 쓰였다 |
| **조치** | `.npmrc` 삭제, `pnpm-workspace.yaml`에 `storeDir`·`cacheDir` 추가. 루트의 잘못된 store 삭제 |
| **재발 방지** | 문서 — `CLAUDE.md` 8.1절 표에 설정 위치를 명시. 검사 — `pnpm check:env`가 데이터 경로가 `.local/` 아래인지 확인한다 |
| **확인 방법** | `pnpm store path` 결과가 저장소 경로로 시작하는가 |
| **관련** | `CLAUDE.md` 8.1절, `docs/P0_설계서_Foundation.md` FR-002 |

### 왜 이런 일이 생겼나
설정이 **조용히 무시**됐다. 오류도 경고도 없었고 설치는 성공했다. 도구의 메이저 버전이 오르면 설정 위치가 바뀔 수 있는데, 문서를 읽고 "썼으니 됐다"고 믿으면 확인 단계가 빠진다. **설정을 넣었으면 그 설정이 실제로 먹었는지 다른 경로(`pnpm store path`)로 확인한다.**

## T-002 · `pnpm install`이 `ERR_PNPM_IGNORED_BUILDS`로 중단된다 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | `× installing dependencies ╰─▶ Ignored build scripts: @embedded-postgres/windows-x64, esbuild` 후 실패 |
| **환경** | Windows, pnpm 12.4.1 |
| **원인** | pnpm 10+는 의존성의 설치 스크립트를 **기본 차단**한다(공급망 공격 완화). 허용 목록 키가 `onlyBuiltDependencies`(배열)에서 `allowBuilds`(맵)로 바뀌어 옛 키가 무시됐다 |
| **조치** | `pnpm-workspace.yaml`에 `allowBuilds: { esbuild: true, embedded-postgres: true, @embedded-postgres/*: true }` |
| **재발 방지** | 설계 — 허용 목록을 명시적으로 유지한다. 임의 패키지의 postinstall이 도는 것을 막는 것이 원래 의도이므로 전체 허용으로 우회하지 않는다 |
| **확인 방법** | `pnpm install` 출력에 `Ignored build scripts`가 있는가 |
| **관련** | `docs/P0_설계서_Foundation.md` FR-004 |

### 왜 이런 일이 생겼나
보안 기본값이 강화되는 방향으로 도구가 바뀌면, 기존 설정은 **이름만 남고 효력을 잃는다.** 오류 메시지가 해결책(`pnpm approve-builds`)을 안내했지만 그 명령은 대화형이라 자동화에 맞지 않았다. 설정 파일에 명시하는 쪽이 재현 가능하다.

| **원인** | `pages.service.ts`가 `spaces.module.ts`를 import하고, `spaces.module.ts`가 `pages.service.ts`의 변환 함수를 import했다. **CommonJS 순환 import에서 먼저 평가되는 쪽이 상대 모듈의 export를 `undefined`로 받는다.** 타입만 보면 문제가 없다 |

| **재발 방지** | 설계 — `설계서_Architecture.md` 2.1절에 "두 모듈이 함께 쓰는 변환 함수는 제3의 파일로" 규칙. 검사 — lint에 `import type`으로 주입 대상을 가져오는 패턴 금지 규칙 |
| **확인 방법** | 기동 오류 메시지의 `?` 위치 인자가 무엇인지 보고, 그 클래스가 있는 모듈과 현재 파일이 서로 import하는지 확인 |

## T-008 · `verify:docs`가 "위반 없음"인데 한글 이름 문서를 검사하지 않았다 · 2026-09-16

| 항목 | 내용 |
|---|---|
| **증상** | `verify:docs — 문서 12개, 위반 없음`. 그런데 실제로 검사한 문서는 5개였다. 한글 이름 문서(`설계서_Architecture.md` 등)를 열지 못하고 건너뛰었다. 같은 커밋의 CI는 별개 이유로 실패했다 |
| **환경** | Phase 0, Windows 개발 PC / GitHub-hosted runner |
| **원인** | 세 가지가 겹쳤다. ① `git ls-files`는 기본값(`core.quotepath=true`)에서 비ASCII 파일명을 8진 이스케이프로 감싸 내놓는다. 그 문자열로는 파일을 찾을 수 없는데 코드가 `continue`로 **조용히 넘겼다**. ② 출력의 "문서 N개"가 검사한 수가 아니라 **목록의 길이**였다. ③ 별건으로, 런타임 데이터 경로(`.local/`)를 저장소 경로로 검사해 갓 클론한 CI에서 실패했다 |
| **조치** | `git -c core.quotepath=false ls-files`로 읽고, 목록에 있는데 열 수 없으면 **위반으로 보고**하도록 고쳤다. 출력은 실제 검사한 수를 센다. `.local/`을 저장소 경로 접두에서 제외했다. 부수로 인라인 코드 안의 파이프를 표 열 구분자로 오인하던 것과 pnpm 내장 명령 오탐도 고쳤다 |
| **재발 방지** | 코드 — 건너뛰기를 없앴다. 읽지 못하면 실패한다. 절차 — 검사기를 고치면 **저장소 밖**에 갓 클론해 실행한다. 저장소 안에 클론하면 pnpm이 바깥 워크스페이스와 얽혀 `node_modules`가 깨진다 (실제로 겪었고 재설치로 복구했다) |
| **확인 방법** | `pnpm verify:docs` 출력의 "문서 N개 검사"가 `git ls-files`로 센 대상 문서 수와 같은가 |
| **관련** | T-007, `scripts/verify-docs.ts`, `docs/P0_설계서_Foundation.md` FR-082 |

### 왜 이런 일이 생겼나
**관문이 조용히 통과하면 없는 것보다 나쁘다.** "위반 없음"을 믿고 문서를 고치지 않게 되기 때문이다. 원인은 흔한 습관 두 개였다. 못 읽은 입력을 `continue`로 넘긴 것, 그리고 셈의 대상을 확인하지 않고 출력한 것이다. 검사 도구는 **검사하지 못한 것을 반드시 말해야** 한다.

## T-010 · 로컬에서 통과한 `verify:docs`가 CI에서만 경로 위반을 낸다 · 2026-09-16

| 항목 | 내용 |
|---|---|
| **증상** | CI의 `문서 검사 (verify:docs)` 단계만 실패. 같은 명령이 개발 PC에서는 "위반 없음" |

| **확인 방법** | 저장소 밖에서 `git clone` 후 `pnpm verify:docs`. 개발 PC의 빌드 산출물이 없는 상태여야 CI와 같다 |

**검사 기준이 "환경의 상태"였다.** 환경은 사람마다 다르므로 그런 관문은 반드시 어긋난다. 저장소에 관한 주장은 **저장소에게** 물어야 한다 — 디스크가 아니라 `git ls-files`에. 또 하나, 앞선 같은 실패를 예외 목록으로 막은 것이 실수였다. 예외는 원인을 남겨 둔 채 증상만 지우므로 다음 실패를 예약한다.

## T-014 · `git clone`은 되는데 도커 빌드가 네트워크에서 죽는다 · 2026-09-21

| 항목 | 내용 |
|---|---|
| **증상** | `docker compose -f deploy/compose.yml --env-file deploy/.env build api`가 `RUN npm install -g pnpm@12.4.1`에서 **471초** 매달린 뒤 죽었다. `npm error code ETIMEDOUT` / `npm error network request to https://registry.npmjs.org/pnpm failed`. 베이스 이미지 `node:24-bookworm-slim` 받기는 **성공**했다 |
| **환경** | 사내 Linux 빌드 서버(프록시 뒤), Docker 29.6.1, Compose v5.3.1, Phase 0 첫 빌드 |
| **원인** | 도커 **데몬**에는 프록시가 설정돼 있고(`/etc/systemd/system/docker.service.d/proxy.conf`) `~/.docker/config.json`에는 `proxies` 키가 없었다. 데몬이 하는 **이미지 받기는 프록시를 타지만**, 빌드 컨테이너 안에서 도는 `RUN` 단계는 프록시 환경변수를 물려받지 못해 레지스트리로 직접 나가려다 끊겼다 |
| **조치** | `deploy/compose.yml`의 `api.build.args`에 프록시 6종(`HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` 대소문자)을 **셸 환경에서 받아** 넘기게 했다. 값은 `${HTTP_PROXY:-}`라 저장소에 사내 주소가 남지 않고, 프록시가 없는 폐쇄망에서는 빈 값이라 무해하다. 같은 단계가 471초 → **2.5초** |
| **재발 방지** | 문서 — `docs/운영가이드_리눅스빌드.md` 1.1절(미리 확인하는 한 줄)과 10절 증상 표. 설정 — compose가 자동으로 넘기므로 사람이 기억할 필요가 없다 |
| **확인 방법** | `docker history workfluence-app:latest`에 프록시 값이 없고(도커가 predefined build arg로 처리해 제거한다), `--no-cache` 빌드가 통과하는가 |
| **관련** | `CLAUDE.md` 8.1절·8.2절, `docs/P0_검증기록_Foundation.md` 6절 |

### 왜 이런 일이 생겼나
**조용히 잘못되는 쪽이 아니라, 조용히 잘돼 보이는 쪽이 문제였다.** `git clone`이 성공한다. 호스트 셸에 프록시 환경변수가 있어서 `git`이 그것을 쓰기 때문이다. 베이스 이미지도 받아진다. 데몬이 프록시를 쓰기 때문이다. **그래서 "이 서버는 네트워크가 된다"는 결론이 두 번 확인된 것처럼 보인다.** 실제로 막히는 것은 세 번째 경로 — 빌드 컨테이너 안 — 이고 그것만 확인이 안 돼 있었다.

가이드 1절의 준비물 점검이 "`git clone`이 되는지"를 묻고 있었던 것이 정확히 이 함정이다. **점검 항목은 "네트워크가 되는가"가 아니라 "그 일을 실제로 하는 주체가 나갈 수 있는가"로 써야 한다.** 주체가 셋이면 셋을 따로 묻는다.

**환경이 합쳐지면 전에 없던 충돌이 생긴다.** 두 파일은 원래 이름이 같아도 기계가 달라 문제가 아니었다. 기계를 합치는 결정은 "장비가 하나 줄었다"로 보이지만, 실제로는 **분리되어 있어서 공짜로 지켜지던 전제들이 한꺼번에 풀린다.** 통합할 때는 "무엇이 편해지나"가 아니라 **"분리가 무엇을 대신 지켜 주고 있었나"**를 먼저 세어야 한다.

## T-023 · 로그인 제한이 정상 사용자를 막는다 (E2E가 먼저 부딪혔다) · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | Phase 4에서 E2E가 16건으로 늘자 **한 번 실행 안에서** 로그인이 `429`로 막혔다. 실패하는 테스트가 실행할 때마다 달라져 "간헐적"으로 보였다 |
| **환경** | Phase 4, `impl-phase4`, `RATE_LIMITS.login = 20회 / 60초 / IP` |
| **원인** | 제한이 **로그인 시도 전부**를 셌다. 목적은 무차별 대입을 막는 것인데 성공까지 세면, 한 주소에서 여럿이 정상 로그인하는 것만으로 한도가 찬다 |
| **조치** | **성공한 로그인은 예산을 돌려준다.** 가드가 요청에 자기 몫(키+찍은 시각)을 남기고, 컨트롤러가 세션을 연 뒤 `refund(req)`를 부른다. 실패는 그대로 센다 |
| **재발 방지** | 테스트 4건. 그중 하나는 **돌려주기를 두 번 불러도 남의 몫을 지우지 않는지**를 본다 — 처음 구현은 "가장 최근 것을 뺀다"였고 그 테스트가 잡았다 |
| **확인 방법** | 같은 IP에서 성공 로그인을 상한보다 많이 반복한다 |
| **관련** | T-019, `CLAUDE.md` 7절 |

### 왜 이런 일이 생겼나
**이것은 테스트 편의를 위한 완화가 아니다.** 사용자 300명이 사내 NAT 한 주소로 나가는
환경에서 분당 20회는 아침 출근 시간에 쉽게 넘는다. 즉 **운영에서 먼저 터졌을 결함**이고,
E2E가 그 환경을 우연히 재현해 준 것이다.

고치면서 규칙 하나가 분명해졌다 — **제한은 "막고 싶은 것"을 세야 한다.** 무차별 대입을
막고 싶으면 실패를 세고, 비용이 드는 작업을 막고 싶으면 그 작업을 센다. "요청 수"는
그 둘 중 무엇도 아니다. 가입·ID 찾기·비밀번호 찾기는 성공 자체가 드물고 비용이 있는
행위라 지금처럼 전부 세는 것이 맞다 — 그래서 로그인만 바꿨다.

## T-024 · 같은 실수를 두 번째로 했다 — 새 모듈이 또 커버리지 밖 · 2026-09-22

| 항목 | 내용 |

## T-025 · 자동 기동을 확인하려고 컨테이너를 죽였는데, 죽지도 살아나지도 않았다 · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | `restart: unless-stopped`가 붙은 `workfluence-api`를 `docker kill`로 죽였다. 80초를 기다려도 되살아나지 않고 `RestartCount`는 `0` 그대로였다. 그다음 컨테이너 **안에서** `kill -9 1`을 했더니 이번에는 **오류도 안 나고 아무 일도 일어나지 않았다** — 프로세스가 그대로 살아 있었다 |
| **환경** | Phase 5, 공유 Linux 서버, Docker 29.6.1, `deploy/compose.yml` |
| **원인** | 서로 다른 두 가지다. ① 도커는 `docker kill`을 `docker stop`과 **같은 부류로 기록한다** — "사람이 멈춘 것"이므로 재시작 정책을 일부러 건너뛴다. ② 리눅스 커널은 PID 네임스페이스 안에서 **PID 1에게 같은 네임스페이스 안에서 보낸 신호 중 처리기가 없는 것을 무시한다.** `SIGKILL`도 예외가 아니다. `kill`은 성공을 반환하므로 **조용히 아무 일도 안 한 것**이다 |
| **조치** | **프로세스가 스스로 죽는 상황을 만든다.** `workfluence-app:latest`에 `--restart unless-stopped`를 주고 곧 종료하는 명령을 물려 띄우니 `RestartCount`가 35초 만에 `0 → 6`으로 올라갔다. 정책은 정상이었다. 확인이 끝나면 그 컨테이너는 지운다 |
| **재발 방지** | `docs/P5_설계서_Release.md` C절에 세 방법과 각각의 결과를 표로 박아 뒀다. "죽여 보면 된다"는 직관이 여기서는 틀린다 |
| **확인 방법** | `docker inspect -f '{{.RestartCount}}'`가 올라가는지 본다. `docker ps`의 상태만 보면 두 실패 모두 "살아 있음"으로 보인다 |
| **관련** | — |

### 왜 이런 일이 생겼나

**두 실패 모두 "성공한 것처럼 보였다."** `docker kill`은 종료 코드 0으로 끝났고,
`kill -9 1`도 오류를 내지 않았다. 확인하려던 것(재시작 횟수)을 안 봤다면 두 번 다
"자동 기동 확인 완료"로 적었을 것이다 — **한 번은 정책이 안 걸린 줄 모르고,
한 번은 죽인 적도 없으면서.**

여기서 배울 것은 도커의 동작이 아니라 **확인 절차의 모양**이다. 무언가를 확인할 때
"확인하는 행동"의 성공이 아니라 **"확인하려던 상태"의 변화**를 본다. 죽었는지를
`kill`의 종료 코드로 판정하면 안 되고, 되살아났는지를 `docker ps`로 판정하면 안 된다.
CLAUDE.md 1.3절 "문서가 아니라 동작으로 확인한다"의 다음 칸이 이것이다 —
**동작시켰다는 사실도 확인해야 한다.**

## T-026 · 동시 로그인 50개 뒤 앱이 영구히 멈췄다 — 오류도 로그도 없이 · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | 부하 측정으로 로그인 50개를 동시에 던졌다. 그 뒤 `/api/health`가 **영원히 응답하지 않는다.** 300초를 기다려도 안 온다. 그런데 컨테이너는 `healthy`였다가 서서히 죽고, CPU는 0.19%, 로그에는 마지막 줄이 "기동" 그대로다. 오류가 한 줄도 없다. 반면 DB를 안 타는 경로(CSRF 거부 403)는 **18ms 만에** 돌아왔다 |
| **환경** | Phase 5, 컨테이너 스택(api·postgres·nginx), 풀 `max: 10` |
| **원인** | `pg_stat_activity`를 보니 연결 10개가 전부 `state='idle in transaction'`, `query='begin'`, 16분째였다. `AuthService.login`은 트랜잭션을 열고 `UsersService.verifyCredentials(..., tx)`를 부르는데, 그 안의 첫 줄이 **`this.findByUsername(username)` — `tx`를 안 넘긴다.** `this.db`는 풀이므로 **이미 연결 하나를 쥔 채 두 번째 연결을 달라고 한다.** 동시 요청이 10개가 되는 순간 열 개가 각자 하나씩 쥐고 서로 하나씩을 기다린다. 아무도 놓지 않으므로 **영원히 풀리지 않는다.** 같은 모양이 OIDC 로그인 경로(`findByOidcSub`·`freeEmail`·`freeUsername`)와 가입(`assertUnique`)에도 있었다 |
| **조치** | ① 조회 도우미 전부에 `tx: Db = this.db`를 달고 호출부에서 넘긴다 — 이 코드베이스가 다른 곳에서 이미 쓰던 방식이다. ② **구조로 막는다**: 풀에 `connectionTimeoutMillis`(10초)를 줘 연결을 못 얻으면 **실패**하게 하고, `idle_in_transaction_session_timeout`(30초)으로 잊힌 트랜잭션은 DB가 끊게 했다 (`packages/shared`의 `DB_POOL`). ③ 회귀 테스트: 테스트 풀(4)의 두 배를 동시에 던져 20초 안에 전부 돌아오는지 본다 |
| **재발 방지** | 새는 곳이 또 생겨도 **멈추지 않고 실패한다.** 회귀 테스트는 고친 코드를 되돌려 실제로 실패하는 것을 확인했다 |
| **확인 방법** | `select state, query from pg_stat_activity` — `idle in transaction`이 쌓이면 이것이다 |
| **관련** | T-025 |

### 왜 이런 일이 생겼나

**이 결함은 테스트로도 리뷰로도 안 잡혔다.** 기능 테스트는 요청을 하나씩 보내고, 하나만
보내면 연결 두 개를 순서대로 얻는 데 아무 문제가 없다. 코드만 봐도 이상하지 않다 —
`findByUsername(username)`은 그 줄만 놓고 보면 완벽히 옳은 코드다. **틀린 것은 그 줄이
아니라 그 줄이 놓인 자리다.**

동시성 결함의 공통점이 이것이다. *한 번에 하나씩* 하면 전부 옳고, **동시에 하면 틀린다.**
그래서 부하 측정은 "빠른가"를 재는 일이 아니다. 여기서 실제로 얻은 것은 숫자가 아니라
**이 결함의 발견**이다. 300명 중 열 명이 아침에 동시에 로그인하면 재현됐을 것이고,
그때는 폐쇄망 안이라 `pg_stat_activity`를 볼 사람도 없었다.

두 번째로 남길 것은 **무한 대기를 코드에 두지 않는다**는 규칙이다. 원래 원인(`tx` 누락)은
사람이 또 만들 수 있다. 그러나 기다림에 상한이 있었다면 증상은 "10초 뒤 500"이었고,
로그에 남아 30분이 아니라 3분이면 찾았다. **조용히 멈추는 실패를 시끄럽게 실패하도록
바꾸는 것**이 원인을 하나 고치는 것보다 오래 간다 (T-024와 같은 판단).

## T-027 · 성공한 로그인이 계속 예산을 먹는다 — T-023의 수정이 실제로는 한 번도 동작하지 않았다 · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | 부하 측정이 로그인 단계에서 `429`로 막혔다. 성공 로그인 **정확히 20번** 뒤부터다. T-023에서 "성공한 요청은 제한 예산을 쓰지 않는다"로 고쳐 뒀는데도 그렇다. 순차로 8번 해 보니 전부 성공해서 한동안 다른 데를 뒤졌다 — **8은 상한 20보다 작아서 환불이 없어도 통과한다.** 그 확인은 아무것도 확인하지 않았다 |
| **환경** | Phase 5, 컨테이너 스택, `RATE_LIMITS.login = { max: 20, windowSec: 60 }` |
| **원인** | 가드에 임시 로그를 넣어 인스턴스 식별자를 찍어 봤다. **세는 가드와 환불을 받는 가드가 서로 다른 객체였다** — 센 쪽 `inst=uugjt`, 환불 쪽 `inst=suvww`이고 환불 쪽의 Map은 비어 있었다. Nest는 `@UseGuards(RateLimitGuard)`에 클래스를 주면 그 가드를 **provider와 별개의 인스턴스로** 만든다. 컨트롤러가 주입받은 것은 provider 쪽이라 환불이 딴 곳에 가 있었다. `auth.module.ts`에는 "같은 싱글턴이다"라고 주석까지 적혀 있었다 — **틀린 전제를 주석으로 못 박아 둔 것** |
| **조치** | **상태를 가드에서 떼어냈다.** 센 것을 `RateLimitStore`(provider)가 들고, 가드는 그것을 주입받아 쓴다. 가드가 몇 개로 만들어지든 예산은 하나다. `RateLimitGuard`에는 `refund`가 **없어졌으므로** 컨트롤러가 가드로 환불하는 예전 실수는 이제 컴파일이 막는다 |
| **재발 방지** | 구조가 막는다. 더해서 가드 **두 개**가 한 저장소를 공유하는 테스트를 뒀다 — 예전 코드에서는 실패한다 |
| **확인 방법** | 컨테이너에서 성공 로그인 50회(10개씩 다섯 묶음)를 던져 전부 201인지 본다. 고치기 전에는 21번째부터 429였다 |
| **관련** | T-023, T-025 |

### 왜 이런 일이 생겼나

**T-023의 단위 테스트는 가드를 하나만 만들었다.** `new RateLimitGuard(...)` 한 개로
세고 환불하니 당연히 통과한다. 테스트가 검증한 것은 *로직*이었고, 틀린 것은 *조립*이었다.
**틀린 층을 테스트하고 있었다.**

여기에 T-025와 같은 모양이 겹쳤다. 확인을 한다고 순차 로그인 8회를 돌리고 "정상"이라고
판정했는데, 상한이 20이라 **환불이 완전히 죽어 있어도 8회는 통과한다.** 확인하려는 것의
경계를 넘지 않는 확인은 확인이 아니다. 20을 넘겨 보는 데 1초도 안 걸렸는데 그걸 안 했다.

남길 규칙 둘.
**하나.** 프레임워크가 객체를 몇 개 만드는지를 주석으로 단정하지 않는다. 주석은 확인이
아니다. 단정하고 싶으면 **상태를 그 프레임워크가 손대지 않는 곳에 둔다.**
**둘.** 한도를 확인할 때는 **한도를 넘겨서** 확인한다.

## T-028 · 테스트 24건이 "상태가 샌다"로 깨졌는데, 새는 것은 다른 프로세스였다 · 2026-09-22

|---|---|
| **증상** | `pnpm test:cov`에서 통합 테스트 24건이 `테스트 정리 실패: users에 2행이 남았다. 앞 테스트의 상태가 샌다`로 깨졌다. 그런데 **단독으로 돌리면 290건 전부 통과한다** |

| **관련** | T-022 |

### 왜 이런 일이 생겼나

**정리 실패를 잡아 주는 장치(`resetTables`의 행 수 확인)가 오히려 잘못된 곳을 가리켰다.**

남길 것은 **오류 문구가 원인을 단정하면 의심하라**는 것이다. `resetTables`는 "앞 테스트"밖에
상상할 수 없는 자리에 있고, 실제 원인은 그 자리에서 보이지 않는 곳에 있었다.
테스트가 단독으로는 통과하고 함께 돌리면 깨질 때, 가능성은 "순서"만이 아니라 **"같은
자원을 쓰는 다른 무엇"**도 있다.

## T-029 · 백업 파일 한 줄을 고치면 복원할 때 임의 SQL이 실행된다 · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | 증상이 없다. **아무 일도 안 일어나는 것처럼 보이는 것이 이 결함의 성질이다.** 보안 검토가 코드를 읽어 찾았다 |
| **환경** | Phase 5, `scripts/backup-restore.ts` |
| **원인** | 복원이 대조할 표 이름을 **`BACKUP.json`의 키에서 읽어** `SELECT count(*) FROM ${표}`에 그대로 넣었다. `psql -tAc`는 세미콜론으로 이어진 문장을 **여러 개 실행하고**, 그 계정은 컨테이너의 DB 관리자다. 게다가 `BACKUP.json`은 **체크섬 목록에 없었다** — 백업은 체크섬을 먼저 만들고 이 파일을 그 뒤에 썼기 때문이다. 즉 **대조 근거를 담은 파일이 무결성 검사 밖**에 있었다. 마지막으로, 주입된 질의는 숫자가 아닌 값을 돌려주므로 `Number(...)`가 `NaN`이 되고 `NaN`은 어떤 비교에도 `false`라서 **"모자라다"도 "넘친다"도 아닌 것이 되어 대조를 건너뛰고 "완료"를 출력한다** |
| **조치** | 세 겹으로 막았다. ① **표 목록을 `packages/shared`로 옮겼다** — 식별자는 파일에서 오지 않고 우리 목록에서만 온다. `BACKUP.json`에서는 **숫자만** 받고, 숫자가 아니면 거부한다. ② `BACKUP.json`을 **먼저 쓰고 체크섬에 넣는다.** ③ 복원이 **필수 파일이 체크섬 목록에 올라 있는지** 확인한다 — 목록에 없는 파일은 검사를 받지 않고 통과하기 때문이다 |
| **재발 방지** | A등급 테스트 5건(`release.spec.ts`)이 표 이름에 SQL을 적은 입력과 숫자가 아닌 행 수를 거부하는지 본다. 실제 백업으로 두 공격을 재현해 둘 다 거부되는 것을 확인했다 |
| **확인 방법** | `BACKUP.json`의 키를 고치고 체크섬을 다시 만들어 복원을 시도한다. `행 수가 숫자가 아니다`로 멈춰야 한다 |
| **관련** | — |

### 왜 이런 일이 생겼나

**"우리가 만든 파일"이라고 생각했다.** 백업은 우리 스크립트가 만들고 우리 스크립트가
읽는다. 그러니 그 안의 값은 신뢰할 수 있다고 무의식적으로 전제했다.

그런데 백업 파일이 놓이는 곳은 **백업 공유 폴더와 반입 매체**다. 거기에 쓸 수 있는 사람은
DB 계정이 없어도 이 파일을 고칠 수 있고, **복원은 사람이 가장 다급할 때 돌리는 명령이다.**
그때 출력은 "완료"였을 것이다.

남길 규칙은 **식별자는 데이터에서 오지 않는다**다. 값(숫자·문자열)은 파일에서 와도 되지만
표 이름·컬럼 이름처럼 **질의의 구조를 이루는 것**은 우리 코드의 목록에서만 와야 한다.
값이면 매개변수로 넘길 수 있고, 식별자는 넘길 수 없다 — 그 차이가 경계다.

두 번째로, **무결성 검사는 "검사 대상 목록"부터 검사해야 한다.** 체크섬 파일에 어떤 파일이
빠져 있으면 그 파일은 조용히 무검사로 통과한다. 목록에 없는 것이 통과하는 검사는
**검사하지 않는 것과 구분되지 않는다.**

| **조치** | `tsconfig.scripts.json`을 두고 `typecheck`에 붙였다. `module: esnext` + `moduleResolution: bundler`는 **tsx가 실제로 그렇게 동작하기 때문이다** — 스크립트는 `import.meta`를 쓰고 ESM 전용 의존성도 부른다 |
| **재발 방지** | `pnpm check`가 잡는다. 붙인 직후 실제로 이 오류를 잡아냈다 |
| **확인 방법** | `scripts/` 아무 파일에 없는 식별자를 쓰고 `pnpm typecheck`를 돌린다 |
| **관련** | — |

### 왜 이런 일이 생겼나

**검사가 "무엇을 검사하지 않는지"는 어디에도 적혀 있지 않았다.** `pnpm check`가 초록이면
검사된 것이라고 읽었고, 그 명령이 도는 범위를 확인한 적이 없다.

이 결함을 찾은 것도 우연이 아니다. **코드 리뷰가 "`scripts/**`는 타입 검사를 받지
않는다"고 지적했고, 그것을 고치자마자 그 검사가 바로 이 실수를 잡았다.** 지적을
반영하는 그 순간에 증명된 셈이다.

T-020·T-024와 같은 계열이다. 그때는 **커버리지의 측정 범위**가 새 디렉토리를 빠뜨렸고,
이번에는 **타입 검사의 대상 범위**가 한 디렉토리를 통째로 빠뜨렸다. 공통점은
**"관문이 초록인 것"과 "검사된 것"을 같은 뜻으로 읽은 것**이다. 관문을 만들 때는
그것이 **무엇을 안 보는지**도 함께 적어야 한다.

## T-032 · Origin 검사가 컨테이너에서 모든 연결을 막는다

| 항목 | 내용 |
|---|---|
| 일자 | 2026-09-23 (Phase 7) |
| 증상 | 개발 서버(Vite 프록시)에서는 실시간 편집이 붙는데, **컨테이너로 띄우면 WebSocket이 전부 401**이 된다 |
| 조용히 잘못되는가 | **아니다 — 시끄럽게 잘못된다.** 다만 개발에서 안 드러나는 쪽이라, 알아채는 자리가 반입 당일이 될 수 있었다 |

### 무엇을 했나

Phase 6 보안 검토가 "WebSocket 업그레이드에 `Origin` 검사가 없다"고 했다. WS는 커스텀 헤더를
붙일 수 없어 이 앱의 CSRF 두 겹(SameSite + 헤더) 중 한 겹이 비어 있다. 그래서 업그레이드에
`new URL(origin).host === req.headers.host`를 넣었다.

### 왜 깨졌나

`deploy/nginx.conf`가 `proxy_set_header Host $host`였다. **nginx의 `$host`는 포트를 떼어 낸다.**

```
브라우저 → nginx     Origin: https://호스트:8443   Host: 호스트:8443
nginx    → api       Origin: https://호스트:8443   Host: 호스트        ← 포트가 없다
```

`new URL('https://호스트:8443').host`는 `호스트:8443`이고 `req.headers.host`는 `호스트`다.
**영영 안 맞는다.** 기본 노출 포트가 8443(`WF_HTTPS_PORT`)이라 기본 구성에서 100% 재현된다.

개발에서는 드러나지 않았다. Vite 프록시는 `changeOrigin`이 꺼져 있어 `Host`를 그대로 넘긴다 —
둘 다 `localhost:5173`이라 맞는다. **"개발에서 되는 것과 컨테이너에서 되는 것을 따로 확인한다"는
0.3절의 습관이 아니었으면 반입해서야 드러났다.**

### 어떻게 고쳤나

`proxy_set_header Host $http_host`로 바꿨다. `$http_host`는 클라이언트가 보낸 `Host`를
**포트까지 그대로** 넘긴다. 컨테이너를 띄워 실제로 붙여 확인했다 (`P7_검증기록_Hardening` 4.1절).

### 재발 방지

- 반입 가이드 7절 사후 검증에 **"두 브라우저에서 같이 고칠 수 있다"**를 넣었다. 이 유형은
  헬스체크가 잡지 못한다 — `/api/health`는 200이고 화면도 뜬다.
- **요청 헤더를 보고 판정하는 코드는 프록시를 거친 값으로 시험한다.** 9.1절이 `redirect_uri`에
  대해 같은 말을 한다("요청 헤더로 조립하지 않는다"). 같은 함정의 다른 얼굴이다.

## T-033 · `git push`가 "Host key verification failed"로 죽는다 · 2026-09-24

| 항목 | 내용 |
|---|---|
| **증상** | Phase 8 첫 push에서 `Host key verification failed.` / `fatal: Could not read from remote repository.` 원격 주소는 `https://github.com/hipiboy7/workfluence.git`(https)이었다 |
| **환경** | Phase 8, `impl-phase8`, RHEL 9 공유 서버. `gh auth status`는 로그인됨·스코프 `repo`·`workflow` |

| **조치** | 전역 설정은 건드리지 않았다(공유 서버). **저장소 로컬** 원격 주소를 `https://hipiboy7@github.com/hipiboy7/workfluence.git`로 바꿨다 — 접두사가 `https://github.com/`이 아니어서 치환에 걸리지 않고, gh 자격 증명 도우미는 호스트로 맞춰 그대로 동작한다 (`git config remote.origin.url …`). 커밋 없음(로컬 설정) |

| **확인 방법** | `git config --show-origin --get-regexp 'url\..*'` — `file:/etc/gitconfig url.git@github.com:.insteadof https://github.com/`이 나오면 이것이다. `git remote -v`에 `git@github.com:`이 보이면(설정은 https인데) 치환이 걸린 것이다 |

### 왜 이런 일이 생겼나
`insteadOf`는 **원격 주소를 보여 줄 때부터** 바꾼다. 그래서 `git config remote.origin.url`은 https인데
`git remote -v`는 ssh를 보여 주고, 오류는 ssh의 것이 나온다. "권한이 없다"처럼 읽혀 토큰을 먼저 의심하게
되지만 토큰은 쓰이지도 않았다. 공유 서버에서는 **내 설정이 아닌 설정**(시스템 전역)이 동작을 바꿀 수 있다 —
`--show-origin`이 그 출처를 가려 준다.

| **원인** | pnpm은 설치할 때마다 실행 스크립트(`.bin/*`)를 다시 쓰고 그 대상(`bin/eslint.js` 등)에 **실행 권한을 다시 매긴다(chmod)**. chmod는 권한 비트와 상관없이 **파일 주인만** 할 수 있다. 트리의 파일은 모두 이전 계정 것이다. pnpm은 잠금 파일을 쓰기 전에 죽지만, 그 전에 링크와 실행 스크립트를 이미 바꿔 두고 되돌리지 않는다 |
| **조치** | ① 이전 계정 트리를 잠금 파일대로 되돌렸다 — web의 `vitest` 링크를 원래 조합으로, 이 계정이 만든 링크·패키지 폴더를 지우고, 사라진 실행 스크립트 18개를 같은 형식으로 다시 썼다(`.modules.yaml`·`.pnpm/lock.yaml`은 바뀌지 않았다). `pnpm lint`·`pnpm typecheck`·web 32건·shared 294건 통과로 확인 ② **이 계정 소유의 사본**(`git clone`)을 만들어 `pnpm install --frozen-lockfile` 뒤 의존성을 더했다(+21개, 약 24MB). `.env`·`deploy/.env`는 복사했고, 개발 DB는 이전 계정이 띄운 것(:5433)을 그대로 쓴다. Playwright 브라우저는 `.local/ms-playwright`를 이전 트리의 것으로 잇는다 |
| **재발 방지** | 없음 — 계정을 옮기는 것은 사람의 결정이다. 대신 **다른 계정의 트리에서는 `pnpm add`·`pnpm install`을 하지 않는다** — PR 설명의 "환경 주의"에 T-040과 함께 적는다. 의존성을 바꿀 일이 있으면 처음부터 자기 계정의 사본에서 한다 |
| **확인 방법** | `stat -c '%U' node_modules/.bin/tsc`가 내 계정이 아니면 이 트리에서 pnpm이 실행 스크립트를 다시 쓸 수 없다. 이미 실패했다면 `readlink apps/web/node_modules/vitest`가 `pnpm-lock.yaml`의 조합과 같은지 본다 |
| **관련** | T-040(같은 이어받기의 git 쪽), `docs/P10_설계서_Llm.md` J절(보류 28 — 이때 더한 의존성) |

### 왜 이런 일이 생겼나
권한을 777로 넓히면 읽고 쓰기는 누구나 되지만 **chmod처럼 주인만 하는 일**은 넓혀지지 않는다. pnpm은 설치할 때마다 실행 스크립트를
다시 만들고 권한을 매긴다. 그리고 실패해도 되돌리지 않는다 — 잠금 파일이 그대로라 "아무 일도 없었다"로 보이는데 트리는 반쯤 새 상태다.
**조용히 잘못되는 유형이다**: 다음 `pnpm test`가 엉뚱한 자리에서 실패한다.

## T-043 · 감사로그 `llm.ask`에 토큰 수가 조용히 빠진다 · 2026-09-25

| 항목 | 내용 |
|---|---|
| **증상** | 설계서 FR-1118은 질문마다 토큰 수를 감사로그에 남긴다고 했고, 코드도 `detail`에 `promptTokens`·`completionTokens`를 넣었다. 저장된 `audit_events.detail`에는 `providerId`·`provider`·`model`·`status`·`newConversation`·`questionChars`·`answerChars`·`durationMs`·`saved`·`evicted`만 있고 **두 키가 없다.** 오류·경고 없음. 통합 시험은 `toMatchObject`로 다른 키만 단언해 초록이었다 |
| **환경** | Phase 10, `impl-phase10`. 병합 전 검토 셋(자체 점검·코드 리뷰·보안 검토)이 모두 짚었다 — 자체 점검이 실제 `sanitizeDetail`에 그 모양을 넣어 확인했다 |
| **원인** | `apps/api/src/audit/audit.service.ts`의 `SECRET_KEYS = /pass\|secret\|token\|…/i`가 **맨 윗단 키 이름**을 보고 맞으면 버린다. 비밀을 놓치지 않으려고 일부러 넓게 잡은 패턴이다(P1 — `sid`만 넣었다가 `sessionId`가 통과했다). 토큰 **수**는 비밀이 아닌데 이름이 맞았다 |
| **조치** | `usage: { prompt, completion }`로 한 겹 아래에 둔다(거르기는 맨 윗단만 본다). 패턴은 좁히지 않았다 — 좁히면 새는 쪽으로 틀린다. 커밋 `5520733` |
| **재발 방지** | 통합 시험이 저장된 감사 행의 `usage`를 단언하고(`llm.integration.spec.ts`), E2E가 가짜 vLLM이 알린 값(12·4)을 감사 행에서 읽는다(`e2e/llm.spec.ts`). `SECRET_KEYS` 주석에 "이 낱말이 든 이름의 평범한 값은 한 겹 아래에"를 적었다. 모든 `audit.record`의 맨 윗단 키를 그 패턴에 대 보았다 — 지금 걸리는 것은 없다 |
| **확인 방법** | `SELECT detail FROM audit_events WHERE action = 'llm.ask' ORDER BY created_at DESC LIMIT 1` — `usage`가 있으면 고친 판이다. 새 감사 키를 더할 때는 그 이름을 `SECRET_KEYS`에 대 본다 |
| **관련** | `docs/P10_설계서_Llm.md` FR-1118, `docs/internal/P10_검토서_Review.md` |

### 왜 이런 일이 생겼나
비밀 거르기는 **빠뜨리지 않는 쪽**으로 넓게 짜여 있고, 그 대가는 "기록이 조금 부실해질 뿐"이라고 적혀 있었다. 그 부실함이
요구사항 하나를 통째로 지웠는데 아무것도 알리지 않았다. 시험은 "있어야 할 것이 있는가"가 아니라 "적은 것이 맞는가"(`toMatchObject`로
일부만)를 보고 있었다 — **거르는 층이 있는 곳에서는 저장된 결과를 읽어 단언해야 한다.**

## T-044 · 새 대화의 답을 중지하면 알림이 사라진다 — 두 경로의 트리 모양이 달랐다 · 2026-09-25

| 항목 | 내용 |
|---|---|
| **증상** | `e2e/llm.spec.ts` "중지하면 LLM 요청을 끊고 거기까지 남긴다"가 `Error: expect(locator).toBeVisible() failed` · `Locator: getByText('중지했다 — 거기까지 저장했다')` · `Error: element(s) not found`로 실패. 대화는 저장돼 목록에 있고 "중지됨" 표지도 있다 — **알림만 없다.** 직전 빌드(28건 통과)와의 차이는 경로 지킴(`RequireUuidParam`)을 더한 것뿐이었다 |
| **환경** | Phase 10 종료 루틴 반영(`5afb6fe`), React 19 · react-router 7.18 |
| **원인** | 새 대화(`/llm`)의 답이 끝나면 화면이 `/llm/<새 id>`로 옮긴다. 두 경로가 같은 화면(`LlmPage`)을 그리고, 옮겨도 React가 **같은 자리의 같은 종류**라 화면을 그대로 두어 알림(`chat.notice`)이 남았다. `/llm/:id`에만 `RequireUuidParam`을 감싸자 트리 모양이 `RequireAuth > LlmPage`와 `RequireAuth > RequireUuidParam > LlmPage`로 갈라져, 옮길 때 화면을 **새로 만들었다**(상태를 잃는다) |
| **조치** | 두 경로를 똑같이 감싼다 — `RequireUuidParam`은 `:id`가 없으면 그대로 그린다. 커밋은 이 기록과 같은 커밋 |
| **재발 방지** | 컴포넌트 시험 "같은 화면의 두 경로 사이를 옮겨도 화면을 새로 만들지 않는다"(`RequireUuidParam.spec.tsx`) — 한쪽만 감싸면 실패함을 확인했다. `RequireUuidParam` 주석에 "같은 화면이 두 경로에 있으면 둘 다 감싼다"를 적었다. 배선(`App.tsx`) 자체는 E2E가 본다 |
| **확인 방법** | 같은 화면을 그리는 경로들의 `element`가 같은 모양(같은 감싸는 요소, 같은 차례)인지 본다: `grep -n "LlmPage" apps/web/src/App.tsx` |
| **관련** | `docs/internal/P10_검토서_Review.md` §5, `docs/P10_설계서_Llm.md` G절 |

### 왜 이런 일이 생겼나
화면이 옮겨 가도 상태가 남는 것은 **라우터가 준 기능이 아니라 React가 트리를 맞춰 보는 방식의 부산물**이었다 — 어디에도 적혀 있지
않았다. 그래서 한 경로에만 감싸는 요소를 더하는 "무해한" 변경이 그것을 깼고, 오류 없이 알림 하나가 사라졌다. 컴포넌트 시험은 그 화면을
한 경로로만 그려 보아 잡지 못했고, 두 경로를 오가는 E2E가 잡았다.
