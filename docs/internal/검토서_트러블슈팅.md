## T-001 · pnpm store가 `.local/` 대신 드라이브 루트에 생긴다 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | `.npmrc`에 `store-dir=.local/pnpm-store`를 넣고 설치했는데 `pnpm store path`가 `D:\.pnpm-store\v11`을 가리켰다. 192MB가 저장소 밖에 쌓였다 |
| **환경** | Windows, pnpm 12.4.1, 프로토타입 초기 설정 |
| **원인** | **pnpm 12는 `.npmrc`의 pnpm 전용 설정을 읽지 않는다.** 설정 위치가 `pnpm-workspace.yaml`로 옮겨졌다. `.npmrc`는 조용히 무시되어 기본 위치가 쓰였다 |
| **조치** | `.npmrc` 삭제, `pnpm-workspace.yaml`에 `storeDir`·`cacheDir` 추가. 루트의 잘못된 store 삭제 |
| **재발 방지** | 문서 — `CLAUDE.md` 8.1절 표에 설정 위치를 명시. 검사 — `pnpm check:env`가 데이터 경로가 `.local/` 아래인지 확인한다 |
| **확인 방법** | `pnpm store path` 결과가 저장소 경로로 시작하는가 |
| **관련** | `CLAUDE.md` 8.1절, `docs/P0_설계서_Foundation.md` FR-002 |

### 왜 이런 일이 생겼나
설정이 **조용히 무시**됐다. 오류도 경고도 없었고 설치는 성공했다. 도구의 메이저 버전이 오르면 설정 위치가 바뀔 수 있는데, 문서를 읽고 "썼으니 됐다"고 믿으면 확인 단계가 빠진다. **설정을 넣었으면 그 설정이 실제로 먹었는지 다른 경로(`pnpm store path`)로 확인한다.**

## T-002 · `pnpm install`이 `ERR_PNPM_IGNORED_BUILDS`로 중단된다 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | `× installing dependencies ╰─▶ Ignored build scripts: @embedded-postgres/windows-x64, esbuild` 후 실패 |
| **환경** | Windows, pnpm 12.4.1 |
| **원인** | pnpm 10+는 의존성의 설치 스크립트를 **기본 차단**한다(공급망 공격 완화). 허용 목록 키가 `onlyBuiltDependencies`(배열)에서 `allowBuilds`(맵)로 바뀌어 옛 키가 무시됐다 |
| **조치** | `pnpm-workspace.yaml`에 `allowBuilds: { esbuild: true, embedded-postgres: true, @embedded-postgres/*: true }` |
| **재발 방지** | 설계 — 허용 목록을 명시적으로 유지한다. 임의 패키지의 postinstall이 도는 것을 막는 것이 원래 의도이므로 전체 허용으로 우회하지 않는다 |
| **확인 방법** | `pnpm install` 출력에 `Ignored build scripts`가 있는가 |
| **관련** | `docs/P0_설계서_Foundation.md` FR-004 |

### 왜 이런 일이 생겼나
보안 기본값이 강화되는 방향으로 도구가 바뀌면, 기존 설정은 **이름만 남고 효력을 잃는다.** 오류 메시지가 해결책(`pnpm approve-builds`)을 안내했지만 그 명령은 대화형이라 자동화에 맞지 않았다. 설정 파일에 명시하는 쪽이 재현 가능하다.

## T-003 · 타입 검사는 통과하는데 기동 시 의존성 해석 실패 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | `UndefinedDependencyException: Nest can't resolve dependencies of the PagesService (Symbol(DB), AuditService, ?). Please make sure that the argument at index [2] is available` — 해당 모듈은 정상적으로 import되어 있고 `tsc`는 오류 0 |
| **환경** | 프로토타입 v2, Node 24, NestJS 12, CommonJS 출력 |
| **원인** | `pages.service.ts`가 `spaces.module.ts`를 import하고, `spaces.module.ts`가 `pages.service.ts`의 변환 함수를 import했다. **CommonJS 순환 import에서 먼저 평가되는 쪽이 상대 모듈의 export를 `undefined`로 받는다.** 타입만 보면 문제가 없다 |
| **조치** | 공용 변환 함수를 제3의 파일(`pages/page-view.ts`)로 분리해 순환을 끊었다 |
| **재발 방지** | 설계 — `설계서_Architecture.md` 2.1절에 "두 모듈이 함께 쓰는 변환 함수는 제3의 파일로" 규칙. 검사 — lint에 `import type`으로 주입 대상을 가져오는 패턴 금지 규칙 |
| **확인 방법** | 기동 오류 메시지의 `?` 위치 인자가 무엇인지 보고, 그 클래스가 있는 모듈과 현재 파일이 서로 import하는지 확인 |
| **관련** | `docs/설계서_Architecture.md` 2.1절 |

### 왜 이런 일이 생겼나
**타입 검사와 런타임 모듈 그래프가 다른 것을 본다.** TypeScript는 순환을 허용하고(타입은 지연 해석), CommonJS는 평가 순서에 따라 부분 초기화된 객체를 넘긴다. 의존성 주입은 런타임에 생성자 메타데이터를 읽으므로 이 틈에 정확히 걸린다. "컴파일되니까 괜찮다"가 통하지 않는 영역이다.

## T-004 · 환경변수 기본값이 변환되지 않고 문자열로 남는다 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | 테스트 실패 `expected "3000" to be 3000`. `.env`에 `WF_PORT`를 넣으면 숫자인데, 넣지 않으면 문자열이었다 |
| **환경** | zod 4.6, 프로토타입 v1 |
| **원인** | zod 4의 `.default()`는 **입력이 아니라 출력 타입** 값을 받고, 값이 없으면 파싱·변환을 **건너뛴다**. `z.string().transform(Number).default('3000')`은 변환 없이 `'3000'`을 그대로 돌려준다 |
| **조치** | `intString(min, max, def: number)`처럼 변환 파이프 **뒤에** 숫자 기본값을 붙였다 |
| **재발 방지** | 테스트 — `parseEnv({})`가 기본값을 **숫자로** 돌려주는지 단언한다. 문서 — `P0_설계서_Foundation.md` 1.2절에 주의 |
| **확인 방법** | `typeof parseEnv({...}).WF_PORT === 'number'` |
| **관련** | `packages/shared/src/env.ts`, `docs/P0_설계서_Foundation.md` 1.2절 |

### 왜 이런 일이 생겼나
라이브러리 메이저 버전이 오르며 **같은 이름의 API가 다른 의미**가 됐다. 타입은 통과했다 — `.default()`가 출력 타입을 받도록 선언되어 있어 문자열을 넣으면 타입 오류가 났어야 하는데, 이전 코드에서는 제네릭 추론이 느슨한 지점이었다. **기본값 경로는 `.env`가 채워진 개발 환경에서 잘 안 밟힌다.** 빈 입력에 대한 테스트가 없으면 운영에서 처음 드러난다.

## T-005 · 정적 자산에 immutable 캐시가 붙지 않는다 · 2026-09-15

| 항목 | 내용 |
|---|---|
| **증상** | `curl -i /assets/index-tdLAKn4c.js` → `Cache-Control: no-store`. 해시 파일명인데 매번 다시 받는다 |
| **환경** | 프로토타입 v1, Vite 8 빌드 산출물 |
| **원인** | 해시 판별 정규식을 `\.[0-9a-f]{8,}\.`(16진수)로 썼다. **Vite 해시는 base64url**(`tdLAKn4c`)이라 대문자·`-`·`_`가 들어가 매칭되지 않았다 |
| **조치** | `[\\/]assets[\\/][^\\/]+-[A-Za-z0-9_-]{8,}\.[a-z0-9]+$`로 교체 |
| **재발 방지** | E2E — 해시 자산 응답 헤더가 `immutable`인지 단언한다 |
| **확인 방법** | `curl -i http://127.0.0.1:3000/assets/<빌드된 파일명>` 의 `Cache-Control` |
| **관련** | `apps/api/src/app.module.ts`, `docs/P0_설계서_Foundation.md` 6절 |

### 왜 이런 일이 생겼나
"해시처럼 보이는 것"을 문자 집합으로 판별했는데 도구가 쓰는 인코딩을 확인하지 않았다. **조용히 잘못되는 유형**이다 — 페이지는 정상 동작하고 성능만 나빠진다. 실제 파일명을 한 번 보고 규칙을 세웠어야 했다.

## T-006 · 통과하던 E2E가 코드 변경 없이 실패한다 · 2026-09-16

| 항목 | 내용 |
|---|---|
| **증상** | `승인 대기 계정은 로그인할 수 없다` 실패. `expect(locator('.error')).toContainText('승인 대기')` → `element(s) not found`. 스냅샷을 보니 **로그인에 성공해 홈 화면**이었다 |
| **환경** | 프로토타입 v3 작업 중. 앱 코드는 그 테스트와 무관하게만 바뀌었다 |
| **원인** | 테스트가 시드 계정 `pending1`이 `승인 대기` 상태라고 전제했다. 전날 사용자가 화면에서 그 계정을 **승인**해 `활성`이 됐다. 감사로그 `user.approve`로 확인 |

## T-008 · `verify:docs`가 "위반 없음"인데 한글 이름 문서를 검사하지 않았다 · 2026-09-16

| 항목 | 내용 |
|---|---|
| **증상** | `verify:docs — 문서 12개, 위반 없음`. 그런데 실제로 검사한 문서는 5개였다. 한글 이름 문서(`설계서_Architecture.md` 등)를 열지 못하고 건너뛰었다. 같은 커밋의 CI는 별개 이유로 실패했다 |
| **환경** | Phase 0, Windows 개발 PC / GitHub-hosted runner |
| **원인** | 세 가지가 겹쳤다. ① `git ls-files`는 기본값(`core.quotepath=true`)에서 비ASCII 파일명을 8진 이스케이프로 감싸 내놓는다. 그 문자열로는 파일을 찾을 수 없는데 코드가 `continue`로 **조용히 넘겼다**. ② 출력의 "문서 N개"가 검사한 수가 아니라 **목록의 길이**였다. ③ 별건으로, 런타임 데이터 경로(`.local/`)를 저장소 경로로 검사해 갓 클론한 CI에서 실패했다 |
| **조치** | `git -c core.quotepath=false ls-files`로 읽고, 목록에 있는데 열 수 없으면 **위반으로 보고**하도록 고쳤다. 출력은 실제 검사한 수를 센다. `.local/`을 저장소 경로 접두에서 제외했다. 부수로 인라인 코드 안의 파이프를 표 열 구분자로 오인하던 것과 pnpm 내장 명령 오탐도 고쳤다 |
| **재발 방지** | 코드 — 건너뛰기를 없앴다. 읽지 못하면 실패한다. 절차 — 검사기를 고치면 **저장소 밖**에 갓 클론해 실행한다. 저장소 안에 클론하면 pnpm이 바깥 워크스페이스와 얽혀 `node_modules`가 깨진다 (실제로 겪었고 재설치로 복구했다) |
| **확인 방법** | `pnpm verify:docs` 출력의 "문서 N개 검사"가 `git ls-files`로 센 대상 문서 수와 같은가 |
| **관련** | T-007, `scripts/verify-docs.ts`, `docs/P0_설계서_Foundation.md` FR-082 |

### 왜 이런 일이 생겼나
**관문이 조용히 통과하면 없는 것보다 나쁘다.** "위반 없음"을 믿고 문서를 고치지 않게 되기 때문이다. 원인은 흔한 습관 두 개였다. 못 읽은 입력을 `continue`로 넘긴 것, 그리고 셈의 대상을 확인하지 않고 출력한 것이다. 검사 도구는 **검사하지 못한 것을 반드시 말해야** 한다.

## T-009 · `pnpm dev:db`가 `lock file "postmaster.pid" already exists`로 실패한다 · 2026-09-16

| 항목 | 내용 |
|---|---|
| **증상** | `FATAL: lock file "postmaster.pid" already exists` / `HINT: Is another postmaster (PID 8508) running in data directory ...` 후 `[dev-db] 실패: undefined` |
| **환경** | Phase 0, Windows. 이전 `pnpm dev:db`를 Ctrl+C가 아니라 작업 종료로 죽인 뒤 |
| **원인** | 래퍼(pnpm·tsx)만 죽고 **PostgreSQL 서버 프로세스는 남는다.** 스크립트의 `SIGINT`/`SIGTERM` 처리는 래퍼가 정상 신호를 받을 때만 동작한다. 남은 서버가 데이터 디렉토리를 잠그고 있어 새 인스턴스가 못 뜬다. 부수적으로, 그때 `createDatabase` 실패를 `Error`로 가정해 다시 던진 탓에 메시지가 `undefined`로 찍혀 원인이 가려졌다 |
| **조치** | ① 기동 전 `postmaster.pid`를 검사해 **그 PID가 살아 있지 않을 때만** 잠금 파일을 치운다. 살아 있으면 "이미 떠 있다"고 분명히 알린다. ② DB 존재 확인을 오류 메시지 대신 `pg_database` 조회로 바꿨다. ③ 실패 로그에서 `Error`가 아닌 값도 그대로 출력한다 |
| **재발 방지** | 코드 — 위 세 가지. 절차 — `dev:db`는 Ctrl+C로 종료한다. 창을 그냥 닫았다면 다음 기동 때 스크립트가 알아서 정리하거나, 살아 있는 프로세스를 알려 준다 |
| **확인 방법** | 포트 5433을 듣는 프로세스가 있는지 본다. 없는데 `.local/pgdata/postmaster.pid`가 있으면 남은 잠금이다 |
| **관련** | `scripts/dev-db.ts`, `docs/P0_설계서_Foundation.md` 8절 |

### 왜 이런 일이 생겼나
**"오류 메시지로 상태를 판단"하는 습관이 원인을 두 번 가렸다.** 첫 번째는 DB 존재 여부를 `already exists` 문자열로 판단하려 한 것이고, 두 번째는 그 실패를 `Error`로 가정해 `undefined`를 출력한 것이다. 상태는 **상태를 묻는 질의**로 확인하고, 오류는 **모양을 가정하지 않고** 출력한다.

## T-010 · 로컬에서 통과한 `verify:docs`가 CI에서만 경로 위반을 낸다 · 2026-09-16

| 항목 | 내용 |
|---|---|
| **증상** | CI의 `문서 검사 (verify:docs)` 단계만 실패. 같은 명령이 개발 PC에서는 "위반 없음" |
| **환경** | Phase 0, `impl-phase0`. CI는 갓 클론한 저장소에서 `pnpm build` 이전에 문서 검사를 돈다 |
| **원인** | 경로 검사가 **파일이 디스크에 있는가**(`existsSync`)를 물었다. 테스트결과서가 빌드 산출물 디렉토리를 백틱 경로로 적었는데, 그 디렉토리는 git이 무시한다. 개발 PC에는 빌드해 둔 것이 남아 있어 통과하고 갓 클론한 CI에는 없어 실패한다. 같은 원인을 앞서 런타임 데이터 디렉토리에서 한 번 겪고 접두 목록에서 빼는 식으로 넘겼다 — **증상만 지웠고 원인은 남아 있었다** |

| **재발 방지** | 코드 — 생성물·런타임 데이터는 접두 목록으로 하나씩 빼지 않아도 자동으로 검사 밖이다. 이제 접두 목록은 "무엇을 경로로 볼까"만 정한다 |
| **확인 방법** | 저장소 밖에서 `git clone` 후 `pnpm verify:docs`. 개발 PC의 빌드 산출물이 없는 상태여야 CI와 같다 |
| **관련** | `scripts/verify-docs.ts`, `docs/P0_검증기록_Foundation.md` 3.7절, T-007, T-008 |

### 왜 이런 일이 생겼나
**검사 기준이 "환경의 상태"였다.** 환경은 사람마다 다르므로 그런 관문은 반드시 어긋난다. 저장소에 관한 주장은 **저장소에게** 물어야 한다 — 디스크가 아니라 `git ls-files`에. 또 하나, 앞선 같은 실패를 예외 목록으로 막은 것이 실수였다. 예외는 원인을 남겨 둔 채 증상만 지우므로 다음 실패를 예약한다.

| **증상** | `docker compose -f deploy/compose.yml --env-file deploy/.env build api`가 `RUN npm install -g pnpm@12.4.1`에서 **471초** 매달린 뒤 죽었다. `npm error code ETIMEDOUT` / `npm error network request to https://registry.npmjs.org/pnpm failed`. 베이스 이미지 `node:24-bookworm-slim` 받기는 **성공**했다 |

### 왜 이런 일이 생겼나
**조용히 잘못되는 쪽이 아니라, 조용히 잘돼 보이는 쪽이 문제였다.** `git clone`이 성공한다. 호스트 셸에 프록시 환경변수가 있어서 `git`이 그것을 쓰기 때문이다. 베이스 이미지도 받아진다. 데몬이 프록시를 쓰기 때문이다. **그래서 "이 서버는 네트워크가 된다"는 결론이 두 번 확인된 것처럼 보인다.** 실제로 막히는 것은 세 번째 경로 — 빌드 컨테이너 안 — 이고 그것만 확인이 안 돼 있었다.

가이드 1절의 준비물 점검이 "`git clone`이 되는지"를 묻고 있었던 것이 정확히 이 함정이다. **점검 항목은 "네트워크가 되는가"가 아니라 "그 일을 실제로 하는 주체가 나갈 수 있는가"로 써야 한다.** 주체가 셋이면 셋을 따로 묻는다.

## T-015 · 개발용과 compose용이 `.env` 한 파일을 다툰다 · 2026-09-21

| **확인 방법** | `pnpm check:env`가 `READY`이고, 같은 시점에 `docker compose -f deploy/compose.yml --env-file deploy/.env ps`가 동작하는가 |

### 왜 이런 일이 생겼나
**환경이 합쳐지면 전에 없던 충돌이 생긴다.** 두 파일은 원래 이름이 같아도 기계가 달라 문제가 아니었다. 기계를 합치는 결정은 "장비가 하나 줄었다"로 보이지만, 실제로는 **분리되어 있어서 공짜로 지켜지던 전제들이 한꺼번에 풀린다.** 통합할 때는 "무엇이 편해지나"가 아니라 **"분리가 무엇을 대신 지켜 주고 있었나"**를 먼저 세어야 한다.

| **재발 방지** | 규칙 — **CI가 빨간 상태를 한 Phase 이상 끌고 가지 않는다.** 빨간 CI는 "한 가지가 깨졌다"가 아니라 **"그 뒤는 아무것도 확인되지 않고 있다"**는 뜻이다. T-017을 Phase 1에서 바로 올리지 못한 것(토큰 권한)이 두 Phase치의 관문을 덮어 버렸다 |
| **확인 방법** | 관문 단계를 로컬 셸에 그대로 붙여 실행 |
| **관련** | T-017, `P0_설계서_Foundation` 9.2절 |

### 왜 이런 일이 생겼나
**"CI가 빨갛다"를 하나의 상태로 취급한 것이 문제였다.** 실제로는 *어디까지 확인됐는지*가 계속 줄고 있었는데, 빨간불 하나로 보여서 그 줄어듦이 보이지 않았다. 단계를 나눈 것(P0 9.2절)은 좋은 결정이었지만, **나눈 단계는 앞이 멈추면 뒤가 안 돈다**는 대가가 딸려 있었다. 막힌 원인이 코드 밖(토큰 권한)에 있어 "나중에"가 된 것도 겹쳤다 — 코드 밖의 막힘일수록 빨리 걷어내야 한다.

## T-022 · 라벨 테스트가 다른 파일과 함께 돌 때만 깨진다 · 2026-09-22

| 항목 | 내용 |

| **확인 방법** | 그 표에 행을 남기는 테스트를 두 개 이상 만들고 파일 전체를 돌린다 |
| **관련** | T-011, `CLAUDE.md` 3절 |

### 왜 이런 일이 생겼나
정리 방법이 **"users를 지우면 나머지는 따라 지워진다"**는 구조에 기대고 있었다. 그 전제는 그때까지 맞았지만 규칙으로 적혀 있지 않았고, 전제를 깨는 표(`labels`)가 Phase 3에서 들어올 때 아무도 확인하지 않았다. 실제로 그 표는 Phase 3 내내 비어 있었기 때문에 **Phase 4에서 처음 쓰기 시작한 순간에야** 드러났다.

**조용히 기다리는 결함이다.** 테이블을 만든 커밋과 깨지는 커밋이 한 Phase 떨어져 있어, 깨졌을 때 원인을 그 자리에서 찾지 않는다.

## T-023 · 로그인 제한이 정상 사용자를 막는다 (E2E가 먼저 부딪혔다) · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | Phase 4에서 E2E가 16건으로 늘자 **한 번 실행 안에서** 로그인이 `429`로 막혔다. 실패하는 테스트가 실행할 때마다 달라져 "간헐적"으로 보였다 |
| **환경** | Phase 4, `impl-phase4`, `RATE_LIMITS.login = 20회 / 60초 / IP` |
| **원인** | 제한이 **로그인 시도 전부**를 셌다. 목적은 무차별 대입을 막는 것인데 성공까지 세면, 한 주소에서 여럿이 정상 로그인하는 것만으로 한도가 찬다 |
| **조치** | **성공한 로그인은 예산을 돌려준다.** 가드가 요청에 자기 몫(키+찍은 시각)을 남기고, 컨트롤러가 세션을 연 뒤 `refund(req)`를 부른다. 실패는 그대로 센다 |
| **재발 방지** | 테스트 4건. 그중 하나는 **돌려주기를 두 번 불러도 남의 몫을 지우지 않는지**를 본다 — 처음 구현은 "가장 최근 것을 뺀다"였고 그 테스트가 잡았다 |
| **확인 방법** | 같은 IP에서 성공 로그인을 상한보다 많이 반복한다 |
| **관련** | T-019, `CLAUDE.md` 7절 |

### 왜 이런 일이 생겼나
**이것은 테스트 편의를 위한 완화가 아니다.** 사용자 300명이 사내 NAT 한 주소로 나가는
환경에서 분당 20회는 아침 출근 시간에 쉽게 넘는다. 즉 **운영에서 먼저 터졌을 결함**이고,
E2E가 그 환경을 우연히 재현해 준 것이다.

고치면서 규칙 하나가 분명해졌다 — **제한은 "막고 싶은 것"을 세야 한다.** 무차별 대입을
막고 싶으면 실패를 세고, 비용이 드는 작업을 막고 싶으면 그 작업을 센다. "요청 수"는
그 둘 중 무엇도 아니다. 가입·ID 찾기·비밀번호 찾기는 성공 자체가 드물고 비용이 있는
행위라 지금처럼 전부 세는 것이 맞다 — 그래서 로그인만 바꿨다.

## T-025 · 자동 기동을 확인하려고 컨테이너를 죽였는데, 죽지도 살아나지도 않았다 · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | `restart: unless-stopped`가 붙은 `workfluence-api`를 `docker kill`로 죽였다. 80초를 기다려도 되살아나지 않고 `RestartCount`는 `0` 그대로였다. 그다음 컨테이너 **안에서** `kill -9 1`을 했더니 이번에는 **오류도 안 나고 아무 일도 일어나지 않았다** — 프로세스가 그대로 살아 있었다 |
| **환경** | Phase 5, 공유 Linux 서버, Docker 29.6.1, `deploy/compose.yml` |
| **원인** | 서로 다른 두 가지다. ① 도커는 `docker kill`을 `docker stop`과 **같은 부류로 기록한다** — "사람이 멈춘 것"이므로 재시작 정책을 일부러 건너뛴다. ② 리눅스 커널은 PID 네임스페이스 안에서 **PID 1에게 같은 네임스페이스 안에서 보낸 신호 중 처리기가 없는 것을 무시한다.** `SIGKILL`도 예외가 아니다. `kill`은 성공을 반환하므로 **조용히 아무 일도 안 한 것**이다 |
| **조치** | **프로세스가 스스로 죽는 상황을 만든다.** `workfluence-app:latest`에 `--restart unless-stopped`를 주고 곧 종료하는 명령을 물려 띄우니 `RestartCount`가 35초 만에 `0 → 6`으로 올라갔다. 정책은 정상이었다. 확인이 끝나면 그 컨테이너는 지운다 |
| **재발 방지** | `docs/P5_설계서_Release.md` C절에 세 방법과 각각의 결과를 표로 박아 뒀다. "죽여 보면 된다"는 직관이 여기서는 틀린다 |
| **확인 방법** | `docker inspect -f '{{.RestartCount}}'`가 올라가는지 본다. `docker ps`의 상태만 보면 두 실패 모두 "살아 있음"으로 보인다 |
| **관련** | — |

### 왜 이런 일이 생겼나

**두 실패 모두 "성공한 것처럼 보였다."** `docker kill`은 종료 코드 0으로 끝났고,
`kill -9 1`도 오류를 내지 않았다. 확인하려던 것(재시작 횟수)을 안 봤다면 두 번 다
"자동 기동 확인 완료"로 적었을 것이다 — **한 번은 정책이 안 걸린 줄 모르고,
한 번은 죽인 적도 없으면서.**

여기서 배울 것은 도커의 동작이 아니라 **확인 절차의 모양**이다. 무언가를 확인할 때
"확인하는 행동"의 성공이 아니라 **"확인하려던 상태"의 변화**를 본다. 죽었는지를
`kill`의 종료 코드로 판정하면 안 되고, 되살아났는지를 `docker ps`로 판정하면 안 된다.
CLAUDE.md 1.3절 "문서가 아니라 동작으로 확인한다"의 다음 칸이 이것이다 —
**동작시켰다는 사실도 확인해야 한다.**

## T-026 · 동시 로그인 50개 뒤 앱이 영구히 멈췄다 — 오류도 로그도 없이 · 2026-09-22

| 항목 | 내용 |
|---|---|
| **증상** | 부하 측정으로 로그인 50개를 동시에 던졌다. 그 뒤 `/api/health`가 **영원히 응답하지 않는다.** 300초를 기다려도 안 온다. 그런데 컨테이너는 `healthy`였다가 서서히 죽고, CPU는 0.19%, 로그에는 마지막 줄이 "기동" 그대로다. 오류가 한 줄도 없다. 반면 DB를 안 타는 경로(CSRF 거부 403)는 **18ms 만에** 돌아왔다 |
| **환경** | Phase 5, 컨테이너 스택(api·postgres·nginx), 풀 `max: 10` |
| **원인** | `pg_stat_activity`를 보니 연결 10개가 전부 `state='idle in transaction'`, `query='begin'`, 16분째였다. `AuthService.login`은 트랜잭션을 열고 `UsersService.verifyCredentials(..., tx)`를 부르는데, 그 안의 첫 줄이 **`this.findByUsername(username)` — `tx`를 안 넘긴다.** `this.db`는 풀이므로 **이미 연결 하나를 쥔 채 두 번째 연결을 달라고 한다.** 동시 요청이 10개가 되는 순간 열 개가 각자 하나씩 쥐고 서로 하나씩을 기다린다. 아무도 놓지 않으므로 **영원히 풀리지 않는다.** 같은 모양이 OIDC 로그인 경로(`findByOidcSub`·`freeEmail`·`freeUsername`)와 가입(`assertUnique`)에도 있었다 |
| **조치** | ① 조회 도우미 전부에 `tx: Db = this.db`를 달고 호출부에서 넘긴다 — 이 코드베이스가 다른 곳에서 이미 쓰던 방식이다. ② **구조로 막는다**: 풀에 `connectionTimeoutMillis`(10초)를 줘 연결을 못 얻으면 **실패**하게 하고, `idle_in_transaction_session_timeout`(30초)으로 잊힌 트랜잭션은 DB가 끊게 했다 (`packages/shared`의 `DB_POOL`). ③ 회귀 테스트: 테스트 풀(4)의 두 배를 동시에 던져 20초 안에 전부 돌아오는지 본다 |
| **재발 방지** | 새는 곳이 또 생겨도 **멈추지 않고 실패한다.** 회귀 테스트는 고친 코드를 되돌려 실제로 실패하는 것을 확인했다 |
| **확인 방법** | `select state, query from pg_stat_activity` — `idle in transaction`이 쌓이면 이것이다 |
| **관련** | T-025 |

### 왜 이런 일이 생겼나

**이 결함은 테스트로도 리뷰로도 안 잡혔다.** 기능 테스트는 요청을 하나씩 보내고, 하나만
보내면 연결 두 개를 순서대로 얻는 데 아무 문제가 없다. 코드만 봐도 이상하지 않다 —
`findByUsername(username)`은 그 줄만 놓고 보면 완벽히 옳은 코드다. **틀린 것은 그 줄이
아니라 그 줄이 놓인 자리다.**

동시성 결함의 공통점이 이것이다. *한 번에 하나씩* 하면 전부 옳고, **동시에 하면 틀린다.**
그래서 부하 측정은 "빠른가"를 재는 일이 아니다. 여기서 실제로 얻은 것은 숫자가 아니라
**이 결함의 발견**이다. 300명 중 열 명이 아침에 동시에 로그인하면 재현됐을 것이고,
그때는 폐쇄망 안이라 `pg_stat_activity`를 볼 사람도 없었다.

두 번째로 남길 것은 **무한 대기를 코드에 두지 않는다**는 규칙이다. 원래 원인(`tx` 누락)은
사람이 또 만들 수 있다. 그러나 기다림에 상한이 있었다면 증상은 "10초 뒤 500"이었고,
로그에 남아 30분이 아니라 3분이면 찾았다. **조용히 멈추는 실패를 시끄럽게 실패하도록
바꾸는 것**이 원인을 하나 고치는 것보다 오래 간다 (T-024와 같은 판단).

| 항목 | 내용 |
|---|---|
| **증상** | 부하 측정이 로그인 단계에서 `429`로 막혔다. 성공 로그인 **정확히 20번** 뒤부터다. T-023에서 "성공한 요청은 제한 예산을 쓰지 않는다"로 고쳐 뒀는데도 그렇다. 순차로 8번 해 보니 전부 성공해서 한동안 다른 데를 뒤졌다 — **8은 상한 20보다 작아서 환불이 없어도 통과한다.** 그 확인은 아무것도 확인하지 않았다 |
| **환경** | Phase 5, 컨테이너 스택, `RATE_LIMITS.login = { max: 20, windowSec: 60 }` |
| **원인** | 가드에 임시 로그를 넣어 인스턴스 식별자를 찍어 봤다. **세는 가드와 환불을 받는 가드가 서로 다른 객체였다** — 센 쪽 `inst=uugjt`, 환불 쪽 `inst=suvww`이고 환불 쪽의 Map은 비어 있었다. Nest는 `@UseGuards(RateLimitGuard)`에 클래스를 주면 그 가드를 **provider와 별개의 인스턴스로** 만든다. 컨트롤러가 주입받은 것은 provider 쪽이라 환불이 딴 곳에 가 있었다. `auth.module.ts`에는 "같은 싱글턴이다"라고 주석까지 적혀 있었다 — **틀린 전제를 주석으로 못 박아 둔 것** |
| **조치** | **상태를 가드에서 떼어냈다.** 센 것을 `RateLimitStore`(provider)가 들고, 가드는 그것을 주입받아 쓴다. 가드가 몇 개로 만들어지든 예산은 하나다. `RateLimitGuard`에는 `refund`가 **없어졌으므로** 컨트롤러가 가드로 환불하는 예전 실수는 이제 컴파일이 막는다 |
| **재발 방지** | 구조가 막는다. 더해서 가드 **두 개**가 한 저장소를 공유하는 테스트를 뒀다 — 예전 코드에서는 실패한다 |
| **확인 방법** | 컨테이너에서 성공 로그인 50회(10개씩 다섯 묶음)를 던져 전부 201인지 본다. 고치기 전에는 21번째부터 429였다 |
| **관련** | T-023, T-025 |

### 왜 이런 일이 생겼나

**T-023의 단위 테스트는 가드를 하나만 만들었다.** `new RateLimitGuard(...)` 한 개로
세고 환불하니 당연히 통과한다. 테스트가 검증한 것은 *로직*이었고, 틀린 것은 *조립*이었다.
**틀린 층을 테스트하고 있었다.**

여기에 T-025와 같은 모양이 겹쳤다. 확인을 한다고 순차 로그인 8회를 돌리고 "정상"이라고
판정했는데, 상한이 20이라 **환불이 완전히 죽어 있어도 8회는 통과한다.** 확인하려는 것의
경계를 넘지 않는 확인은 확인이 아니다. 20을 넘겨 보는 데 1초도 안 걸렸는데 그걸 안 했다.

남길 규칙 둘.
**하나.** 프레임워크가 객체를 몇 개 만드는지를 주석으로 단정하지 않는다. 주석은 확인이
아니다. 단정하고 싶으면 **상태를 그 프레임워크가 손대지 않는 곳에 둔다.**
**둘.** 한도를 확인할 때는 **한도를 넘겨서** 확인한다.
