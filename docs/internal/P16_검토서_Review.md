## 2. 가장 값있던 것

### ① Crew 쓰기가 판정한 공간 상태를 잠그지 않았다 (T-072)

Phase 16은 `canManageMembers`를 공간의 상태와 건 사람에 달리게 했다. 그런데 Crew를 바꾸는 세 문장은 다른 표(`space_members`)에 쓰고, 외래 키 검사의
`FOR KEY SHARE`는 상태 고치기와 부딪히지 않는다 — 관리자의 중지가 커밋되는 사이 주인의 넣기가 얼린 공간에 들어갔다. P15의 처방(판정에 쓴 칸을 쓰기의
`WHERE`에, T-070)은 같은 행을 고칠 때만 통한다. 판정 전에 공간 행을 `FOR SHARE`로 잠그게 했다(설계서 A.1-5). 코드 리뷰는 반대 방향의 write skew(상태
바꾸기가 자기 자리를 옛 값으로 읽는다 — 결과는 더 엄격한 쪽)도 짚었다 — 설계서 L에 남는 것으로 적었다.

### ② "얼었다"를 서버와 화면이 따로 짐작했다 (코드 리뷰 9)

서버는 "주인인데 `canManageMembers`가 거짓"을, 화면은 "`isOwner && !canManageMembers`"를 얼었다로 읽었다. 막는 까닭이 하나 더 생기면 둘 다 조용히 틀린 까닭을
말한다. `spaceAccess`가 `crewFrozen`을 돌려주게 했다(A.1-6) — A등급 Red를 먼저 썼다.

### ③ 기다림이 아무것도 기다리지 않았다 (코드 리뷰 6 — T-071)

첫 판의 T-071은 E2E 흔들림의 원인을 "그려지는 때의 차이인 것 같다"로만 적었다. 코드 리뷰가 셋째 단계의 글자 기다림이 **저장 전 댓글 쓰기 칸의 글자**로
통과한다는 것을 짚었다 — `.first()`만으로는 페이지가 댓글 저장 전에 지워져 알림 단계가 가끔 깨질 수 있었다.
