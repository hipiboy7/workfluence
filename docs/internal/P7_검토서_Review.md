# P7 검토서 — Phase 6가 남긴 검토 셋과 그 처리

- 작성일: 2026-09-23 / 작성 LLM: Claude Opus 5
- 대상: Phase 6 병합 범위 `6f143e8..97ecaa3` (64개 파일, +4,450/−61)

Phase 6은 예산이 막혀 `self-reviewer`만 돌리고 끝났다. 남은 셋을 Phase 7의 첫 작업으로 돌렸다
(`P6_검토서_SelfReview.md` §5가 그렇게 적어 두었다).

## 1. 어떻게 돌렸나

`/code-review`와 `/security-review`는 **"이 브랜치의 변경분"**을 본다. Phase 6은 이미 `main`에
병합돼 그 차이가 비어 있다. 그대로 부르면 **아무것도 보지 않고 "문제 없음"이 나온다** — 가장
나쁜 결과다. 그래서 같은 지침을 병합 범위에 적용해 돌렸다. 이것을 여기 적는 이유는, 다음에
같은 상황이 오면 **병합 전에 돌려야 한다**는 것이 요점이기 때문이다.

| 검토 | 결과 | 오탐 |
|---|---|---|
| `doc-consistency` | 어긋남 **31건** (+ 낮게 본 것 2건). 정당한 과거 서술 13건을 구분해 냈다 | 0 |
| 보안 검토 | HIGH **1건**, 확신도 8 미만 **4건** | 0 |
| 코드 리뷰 | 높음 **6건** · 중간 **7건** · 낮음 **8건** | 0 (1건은 스스로 "미확인" 표시) |

**셋 다 오탐이 없었다.** 그리고 셋이 서로 다른 것을 봤다 — 보안 검토의 HIGH 1건은 코드 리뷰의
"중간 9번"과 같은 자리인데 **심각도 판정이 갈렸고**, 문서 검사는 코드가 아니라 "만들어 놓고
문서에 안 적은 것"을 냈다.

## 2. 가장 값있던 것 셋

### ① 창을 닫으면 서버가 내려간다 (코드 리뷰 1 + 2)

`socket.on('close')`의 저장이 `void`였다. 저장이 실패하면 처리되지 않은 거부가 되고 Node 24는
그것으로 **프로세스를 끝낸다.** 실패는 평범하게 일어난다 — 편집 중 다른 사람이 그 페이지를
휴지통에 넣으면 `saveCollabVersion`의 `FOR UPDATE ... deleted_at IS NULL`이 못 찾아 던진다.

그리고 **쓰기 권한이 있는 사람이 원하는 때에 그것을 일으킬 수 있었다.** `ALLOWED_NODES`가
평범한 객체 리터럴이라 `'constructor' in ALLOWED_NODES`가 `true`이고, 그러면
`ALLOWED_NODES['constructor']`는 배열이 아니라 **함수**다. 검증기가 오류 목록을 돌려주는 대신
`TypeError`를 던진다. 재현:

```
$ npx tsx (scratch)
던졌다: TypeError allowed.includes is not a function
```

REST로는 400 대신 500이고, 실시간 편집에서는 그 예외가 저장 경로를 타고 올라가 위의 경로로
프로세스를 죽인다. `Object.hasOwn`으로 바꾸고 양쪽에 테스트를 더했다.

> **이것이 두 검토를 함께 돌린 값이다.** 1번만 있으면 "드물게 죽는다"이고, 2번만 있으면
> "500이 난다"이다. 둘을 합쳐야 **누구나 서버를 끌 수 있다**가 된다.

### ② 이력 비교가 링크 주소 변경을 "같다"고 말한다 (코드 리뷰 4)

`diff.ts`의 `fingerprint`가 `node.marks`를 읽지 않았다. 굵게·기울임이야 사소하지만
`href`가 `/a`에서 `/evil`로 바뀐 것을 **이력 비교가 "두 버전의 내용이 같다"고 답하는 것**은
이 시스템에서 가장 곤란한 종류의 오답이다.

바로 옆 `realtime.ts`의 같은 이름 함수는 처음부터 마크를 담고 있었다. 복사해 오면서 한쪽만
빠졌고, **E2E가 그것을 통과시켰다** — 단언이 `toContainText(/변경|추가|삭제/)`였는데 요약줄은
아무것도 못 찾아도 늘 "변경 0 · 추가 0 · 삭제 0"을 담는다. **절대 실패하지 않는 단언**이었다.
단언을 찾아낸 낱말 자체(`.w-added`)로 바꿨다.

### ③ "세션을 끊어 봉쇄한다"가 이 채널에서는 통하지 않는다 (보안 검토 HIGH)

보류 20 ①에 이미 적혀 있던 것이지만, 보안 검토는 **그것이 왜 HIGH인지**를 정확히 짚었다 —
관리자 강제 종료·비밀번호 변경·계정 정지·Crew 제거 넷 모두 **사고 대응 수단**인데, 열려 있는
WebSocket에는 하나도 닿지 않았다. 게다가 하트비트가 없어 nginx도 끊지 못하므로 공격자가
5분마다 프레임 하나만 보내면 **무기한** 문서를 고칠 수 있었다.

## 5. 이 검토 중에 내가 만든 실수

**`Origin` 검사를 넣고 컨테이너를 깨뜨릴 뻔했다.** nginx가 `proxy_set_header Host $host`인데
`$host`는 **포트를 떼어 낸다.** 기본 노출 포트가 8443이라 브라우저는 `Origin: https://호스트:8443`을
보내는데 앱이 받는 `Host`는 `호스트`가 되어 **모든 실시간 편집 연결이 401**이 된다.
배포 전에 알아챈 것은 운이 아니라 **컨테이너에서 확인하는 습관** 덕이다 (`CLAUDE.md` 0.3절).
`$http_host`로 바꾸고 실제로 붙여 확인했다 (`P7_검증기록_Hardening` 4절). T-032로 남겼다.

## 1. 내가 고치면서 만든 결함 — 높음 셋

### ① `joining` 표가 영영 안 내려간다

방이 지워지는 것을 막으려고 `joining` 카운터를 넣었는데(코드 리뷰 3의 수정), `ws`의
`handleUpgrade`는 **클라이언트가 이미 끊었거나 핸드셰이크 헤더가 불량하면 콜백을 부르지
않는다.** 그러면 표가 걸린 채 남아 **그 방을 아무도 지우지 못한다** — 고아 방을 치우려고
만든 조건이 고아 방을 영구화한다. 원시 소켓의 `close`로도 표를 되돌리게 고쳤다.

> 인증 대기 중(DB 질의 서너 번) 새로고침하면 재현된다. 드문 일이 아니다.

### ② 검증에 실패하면 **사람이 남아 있는 방을 지웠다**

`manual` 저장에서 문서가 검증을 통과하지 못하면 방을 맵에서 지웠다. 소켓은 열려 있으므로
그 사람들은 **맵에 없는 방에서 계속 편집하고 아무도 저장하지 않는다.** 다음에 들어온
사람은 두 번째 방을 만들어 둘이 갈린다. 사람이 남아 있으면 지우지 않도록 고쳤다.

### ③ `flush`가 "방이 있었다"를 "남겼다"로 답했다

같은 자리다. 검증에 실패해도 `true`를 돌려줘 화면이 보기로 넘어갔다. 실제 판정을
돌려주고 화면이 **이유를 말하게** 고쳤다.

## 3. 되돌린 것 — `Origin`의 스킴 검사

보안 검토 참고 1을 받아 `Origin`의 **스킴까지** 보게 했다가 **뺐다.**

기대하는 스킴을 알려면 `X-Forwarded-Proto`를 믿어야 하는데, **앞단에 장비가 하나 더 있어
거기서 TLS를 끝내고 nginx에 http로 넘기면** 브라우저 Origin은 https이고 그 헤더는 http라
**모든 실시간 편집이 막힌다.** T-032와 똑같은 함정의 다른 얼굴이다.

**배치에 따라 전면 장애가 되는 검사를 심층 방어로 넣지 않는다.** 호스트 동일성만으로
막으려던 것은 막힌다 — 공격자 페이지의 Origin은 호스트가 다르다.

## 4. 이 검토 중에 드러난 내 실수 (둘)

1. **`blockText`에 구분자와 마크 표기를 섞었다.** 그 값은 **화면에 그대로 그려지는 글자**
   이기도 하다. 비교 화면에 제어문자가 찍힐 뻔했다. 보여 주는 글자(`blockText`)와 짝짓기용
   구조 지문(`blockKey`)을 나눴다.
2. **구분자 한 글자로는 부족했다.** 사람이 그 글자를 본문에 넣으면 충돌한다 —
   `['사과','배']`와 `['사과\u0000배']`가 같아진다. 직접 넣어 보고 확인했다.
   괄호로 감싸도 마찬가지라 `JSON.stringify`로 갔다. `realtime.ts`의 `<…>` 형식에도
   같은 충돌이 있어 함께 고쳤다.
3. **빈 파일을 하나 만들어 두고 몰랐다.** `auth.spec.ts`(빈 파일)가 0줄로 남아
   `pnpm check`가 "테스트가 없다"로 깨졌다. 지웠다.

## 5. 테스트가 거짓말하던 자리 하나 더

`heartbeat` 테스트가 `await`를 빠뜨려 **단언이 한 번도 실행되지 않았다.** `attach`가 DB에서
양보하는 사이 `heartbeat()`가 빈 방을 돌고 for 본문에 들어가지 않는다. 늘 초록이었다.
Phase 6의 "절대 실패할 수 없는 E2E 단언"과 같은 유형이다 — **초록은 통과의 증거가 아니다.**

## 6. 그리고 테스트가 결정적이지 않았다

새 통합 테스트가 퇴장 저장을 띄워 놓은 채 끝나, **다음 파일의 `TRUNCATE`와 교착**했다
(T-028과 같은 자리). 고치면서 **게이트웨이가 떠 있는 뒷일을 알고 종료 때 기다리도록**
했다 — 테스트만의 문제가 아니라, 그대로 두면 **프로세스가 내려갈 때 진행 중인 저장이
잘린다.** 세 번 연속 통과로 확인했다.
