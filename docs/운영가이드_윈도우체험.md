## 1. 어느 길로 띄우나

| 길 | 필요한 것 | 되는가 | 이 문서 |
|---|---|---|---|
| **라. 받아서 푸는 묶음 (가장 쉽다)** | GitHub에 로그인해 zip 하나를 받는다. **설치할 것이 없다** — Node·데이터베이스·VC++ 런타임이 들어 있다. **가상화 기능이 필요 없다** | **된다** — Windows Server 2025 러너에서 저장소가 없는 빈 폴더에 풀어 띄웠고, 사용자도 자기 Windows에서 받아 써 봤다(10.4절) | 10절 |
| **가. Node로 직접 띄운다 (추천)** | Node.js 24 · pnpm · Visual C++ 재배포 패키지. **가상화 기능이 필요 없다** | **된다** — Windows Server 2025에서 이 문서대로 돌려 봤다(9.2절) | 2~6절 |
| 나. Docker로 운영과 같은 컨테이너를 띄운다 | Linux 컨테이너를 돌리는 Docker. Windows 10·11은 Docker Desktop, Windows Server는 WSL2 안의 Docker. **둘 다 가상화가 필요하고, 클라우드 VM이면 중첩 가상화가 필요하다** | 확인하지 못했다 | 7절 |
| 다. WSL2 안의 Linux에서 Node로 띄운다 | WSL2 (나와 같은 가상화 조건) | Linux와 같다. 확인하지 못했다 | 7.4절 |

**써 보기만 하려면 라(10절), 저장소를 받아 고쳐 가며 보려면 가를 권한다.** 가·라를 나·다보다 권하는 이유는 셋이다.

1. 가상화가 필요 없어 **어느 클라우드 VM에서든** 된다. 나·다는 VM 크기와 설정에 따라 아예 안 된다 (7.1절).
2. Docker Desktop은 **직원 250명 이상 또는 연 매출 1천만 달러 이상인 회사가 쓰면 유료 구독이 필요하다** ([Docker 문서](https://docs.docker.com/subscription/desktop-license/)). 그리고 Windows Server에서는 지원하지 않는다 (7.1절).
3. 화면과 기능은 컨테이너와 **같은 코드**다. 다른 것은 암호화 연결(TLS)·nginx가 없다는 점 등이다 — 8절.

## 3. 설치

### 3.1 Node.js 24

[nodejs.org](https://nodejs.org/)에서 **Windows Installer (.msi), x64**를 받아 설치한다. 운영과 같은 판을 쓰려면 [v24.21.0](https://nodejs.org/dist/v24.21.0/)의 `node-v24.21.0-x64.msi`다. 24의 다른 판도 `pnpm check:env`를 통과한다 (앞자리만 본다).

설치 중 "Tools for Native Modules"(빌드 도구 자동 설치)는 **체크하지 않아도 된다.** 비밀번호 암호화 모듈 등은 Windows용으로 미리 만들어진 파일이 설치 묶음에 들어 있다 (9절).

설치가 끝나면 **새** PowerShell 창을 열어 확인한다.

```powershell
node --version
```

### 3.2 pnpm

**관리자 권한** PowerShell 창에서 한 번 친다. Node가 `C:\Program Files`에 깔려 있어 그 폴더에 pnpm 연결 파일을 만들기 때문이다.

```powershell
corepack enable
```

판 확인은 저장소를 받은 뒤(3.4절) **그 폴더 안에서** 한다. corepack이 저장소가 정한 판(12.4.1)을 인터넷에서 받아 쓴다. 저장소 밖에서 치면 다른 판이 나올 수 있다.

**Windows 10·11의 PowerShell**에서 `pnpm`이 "이 시스템에서 스크립트를 실행할 수 없으므로 ... pnpm.ps1"로 막히면 먼저 한 번 친다(6절 첫 줄 — Windows Server에서는 나지 않는다).

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

### 3.3 Visual C++ 재배포 가능 패키지

이미 깔려 있는지 본다. 둘 다 `True`면 건너뛴다.

```powershell
Test-Path "$env:SystemRoot\System32\vcruntime140.dll"
Test-Path "$env:SystemRoot\System32\msvcp140.dll"
```

`False`가 나오면 Microsoft가 주는 설치 파일을 받아 설치한다 — [https://aka.ms/vc14/vc_redist.x64.exe](https://aka.ms/vc14/vc_redist.x64.exe) ([Microsoft 문서](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist)).

> **새로 만든 VM에 처음부터 있는지는 이미지마다 다르다 — 확인 필요.** GitHub의 Windows Server 2025 러너에는 둘 다 있었다(9.2절). 없으면 데이터베이스 실행 파일이 **아무 설명 없이** 끝난다. `pnpm dev:db`가 그 종료 코드를 보고 이 절을 가리킨다 (6절).

### 3.4 저장소 받기

**공백·한글이 없는 짧은 경로**에 받는다. 설치되는 파일의 경로가 길어 Windows의 경로 길이 제한(260자)에 닿지 않게 하려는 것이고, 공백·한글이 든 경로는 확인하지 않았다.

```powershell
git clone https://github.com/hipiboy7/workfluence.git C:\workfluence
cd C:\workfluence
pnpm --version
```

`12.4.1`이 나와야 한다. 받는 것은 기본 브랜치 `main`이다 — 이 문서와 Windows용 고침(9절)이 들어 있다.

Git 없이 GitHub의 **Code → Download ZIP**으로 받아 `C:\workfluence`에 풀어도 된다.

## 4. 띄우기

**창을 두 개 쓴다.** 창 1은 데이터베이스, 창 2는 앱이다. 둘 다 `C:\workfluence`에서 연다.

### 4.1 설치 (창 2)

```text
pnpm install
```

처음에는 인터넷에서 부품을 받느라 몇 분 걸린다.

### 4.2 설정 파일 (창 2)

```text
pnpm setup:env
notepad .env
```

메모장에서 **세 줄만** 고치고 저장한다. 나머지는 그대로 둔다.

| 줄 | 바꿀 값 | 왜 |
|---|---|---|
| `WF_SERVE_WEB=false` | `WF_SERVE_WEB=true` | 화면과 API를 프로그램 하나가 함께 준다. 운영 이미지와 같은 방식이다 |
| `WF_ROOT_PASSWORD=change-me-on-first-login` | 처음 로그인할 비밀번호 | 최초 관리자(`root`)의 첫 비밀번호다. 첫 로그인에서 바꾸게 된다 |
| `WF_SESSION_SECRET=change-me-to-a-long-random-string-32chars` | 32자 이상의 아무 글자 | 로그인 쿠키에 서명하는 값이다. 짧으면 앱이 뜨지 않는다 |

32자 넘는 무작위 글자는 PowerShell에서 이렇게 만든다 (64자).

```powershell
[guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
```

> **`WF_ENV=development`는 그대로 둔다.** `production`으로 바꾸면 로그인 쿠키에 "암호화 연결에서만 보낸다(Secure)"는 표시가 붙어, `http://`로는 로그인이 되지 않는다 (6절·8절).
>
> **`.env`는 메모장으로 고친다.** Windows PowerShell 5.1에서 `echo ... > .env`처럼 만들면 파일이 UTF-16으로 저장되어 앱이 한 줄도 못 읽는다 ([Microsoft 문서](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1)).

### 4.3 데이터베이스 (창 1)

```text
pnpm dev:db
```

처음에는 데이터 폴더를 만드느라 조금 걸린다. 마지막 줄이 `[dev-db] READY. Ctrl+C로 종료.`이면 된 것이다. **이 창은 닫지 않고 둔다.** 데이터는 `C:\workfluence\.local\pgdata`에 남는다.

관리자 권한 창이어도 뜨게 고쳤다 (6절 셋째 줄, 9절). 데이터베이스는 이 컴퓨터 안에서만 접속을 받는다 — 밖에서는 닿지 않는다.

### 4.4 표 만들기 · 최초 관리자 · 확인 (창 2)

```text
pnpm db:migrate
pnpm db:seed
pnpm check:env
```

`pnpm check:env`의 마지막 줄이 `READY`여야 한다. `WARN 데이터가 시스템 드라이브가 아닌 곳에 있음`은 **괜찮다** (6절).

### 4.5 앱 띄우기 (창 2)

```text
pnpm build
pnpm start
```

`"event":"app.started"`가 든 줄이 나오면 떴다. `pnpm build`는 처음과 코드를 새로 받았을 때만 하면 된다.

처음 띄울 때 Windows 방화벽이 "Node.js"를 허용할지 물을 수 있다. **이 컴퓨터에서만 쓰면 허용하지 않아도 된다** — 같은 컴퓨터 안의 접속은 방화벽이 막지 않는다. 다른 PC에서 들어오게 하려면 5.3절.

## 5. 브라우저로 로그인하고 써 보기

### 5.1 첫 로그인

같은 컴퓨터의 브라우저에서 `http://127.0.0.1:3000`을 연다.

1. 아이디 `root`, 비밀번호는 4.2절에서 `WF_ROOT_PASSWORD`에 적은 값
2. **비밀번호 변경** 화면이 먼저 나온다. 새 비밀번호는 8자 이상, 영문 대문자·소문자·숫자·특수문자 중 2종 이상
3. 바꾸면 첫 화면이 열린다. 내 공간에서 페이지를 만들고, 고치고, 이력을 보고, 파일을 붙이고, 검색해 본다

### 5.2 두 사람이 같이 써 보기

1. 다른 브라우저(또는 InPrivate 창)에서 로그인 화면의 **가입 요청**으로 두 번째 계정을 만든다
2. `root`로 **사용자 관리**에 가서 그 계정을 **승인**한다
3. `root`가 **팀 스페이스 만들기**로 공간을 하나 만들고, 그 공간의 **Crew**에 두 번째 아이디를 추가한다. 개인 공간은 본인만 들어간다
4. 그 공간에 페이지를 만들고 두 창에서 같은 페이지를 동시에 고친다 — 서로의 글이 바로 보인다

### 5.3 다른 PC에서 들어오게 하려면

**권하지 않는다.** 이 길에는 암호화 연결(https)이 없어 **비밀번호와 문서가 암호화되지 않은 채** 네트워크를 지난다. VM이면 원격 데스크톱으로 들어가 VM 안의 브라우저로 쓰는 것이 가장 안전하다.

그래도 필요하면 셋을 모두 한다.

1. Windows 방화벽에 3000번을 연다 (관리자 권한 PowerShell)

   ```powershell
   New-NetFirewallRule -DisplayName "workfluence 체험" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow
   ```

2. 클라우드 콘솔의 보안 규칙(Azure는 네트워크 보안 그룹, AWS는 보안 그룹)에서 3000번을 **내 PC의 주소에만** 연다
3. 내 PC의 브라우저에서 `http://<VM 주소>:3000`을 연다

끝나면 방화벽 규칙을 지운다.

```powershell
Remove-NetFirewallRule -DisplayName "workfluence 체험"
```

| 멈춘다 | 창 2에서 `Ctrl+C`, 그다음 창 1에서 `Ctrl+C`. "일괄 작업을 끝내시겠습니까 (Y/N)?"가 나오면 `Y` |
| 다시 띄운다 | 창 1에서 `pnpm dev:db`, 창 2에서 `pnpm start` (설치·표 만들기는 다시 하지 않는다) |
| 새 코드를 받는다 | 멈춘 뒤 `git pull` → `pnpm install` → `pnpm db:migrate` → `pnpm build` → 다시 띄운다 |
| 전부 지운다 | 멈춘 뒤 `C:\workfluence` 폴더를 지운다. 데이터(`.local` 폴더)도 그 안에 있다 |

## 6. 잘 안 될 때

| 증상 | 원인 | 조치 |
|---|---|---|
| PowerShell에서 `pnpm`을 치면 "이 시스템에서 스크립트를 실행할 수 없으므로 ... pnpm.ps1" | Windows 10·11의 기본 실행 정책(Restricted)이 pnpm의 PowerShell용 연결 파일을 막는다. Windows Server의 기본값(RemoteSigned)에서는 나지 않는다 ([Microsoft 문서](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1)) | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`를 한 번 치거나, `pnpm` 대신 `pnpm.cmd`로 친다. 명령 프롬프트(cmd)에서는 나지 않는다 |
| `pnpm`을 처음 칠 때 `Error when performing the request to https://registry.npmjs.org/pnpm/...` · `ConnectTimeoutError`(`UND_ERR_CONNECT_TIMEOUT`) | 회사망처럼 **프록시 뒤**다. 브라우저는 Windows의 프록시 설정을 쓰지만, corepack이 쓰는 Node의 내장 fetch는 그 설정도 프록시 환경변수도 기본으로 보지 않는다(`CLAUDE.md` 8.1절 — 개발 서버와 같은 까닭) | 프록시 주소를 확인하고(`netsh winhttp show proxy`, 없으면 설정 → 네트워크 및 인터넷 → 프록시) 같은 창에서 `$env:HTTPS_PROXY = 'http://<프록시주소>:<포트>'` · `$env:HTTP_PROXY = $env:HTTPS_PROXY` · `$env:NODE_USE_ENV_PROXY = '1'`을 친 뒤 다시 한다(그 창에서만 먹는다). 프록시를 다루지 않으려면 **라. 받아서 푸는 묶음**(10절 — 브라우저로 받는다) |
| `pnpm`을 모른다고 하거나 `pnpm --version`이 12.4.1이 아니다 | `corepack enable`을 안 했거나 관리자 권한이 아닌 창에서 했다. 또는 저장소 밖에서 쳤다 | 관리자 권한 창에서 `corepack enable` (3.2절). 판은 `C:\workfluence` 안에서 본다 |
| `pnpm dev:db`가 `Execution of PostgreSQL by a user with administrative permissions is not permitted`를 내고 `[dev-db] 실패: undefined`로 끝난다 | Windows용 고침이 들어가기 전의 옛 코드다(2026-09-28 Phase 14 병합 전의 `main`, 또는 그 무렵 받은 폴더). 예전 방식은 데이터베이스 서버를 직접 띄우는데, PostgreSQL은 **관리자 권한 창에서 직접 뜨기를 거부한다.** 클라우드 VM의 내장 Administrator 계정은 모든 창이 관리자 권한이다 ([Microsoft 문서](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/settings-and-configuration)) | `main`을 새로 받는다(`git pull`, 3.4절). 지금 코드는 Windows에서 `pg_ctl`로 띄운다 — `pg_ctl`은 관리자 권한을 뺀 채로 서버를 띄운다 |
| `pnpm dev:db`가 아무 설명 없이 `code: 3221225781` 또는 `종료 코드 3221225781`로 실패하거나, "Visual C++ 재배포 가능 패키지" 안내가 나온다 | 데이터베이스 실행 파일이 쓰는 `VCRUNTIME140.dll`·`MSVCP140.dll`이 없다 (3221225781 = Windows의 "DLL을 찾을 수 없음") | 3.3절대로 설치하고 다시 띄운다 |
| `이미 PostgreSQL이 떠 있다 (PID 1234)` | 앞서 띄운 데이터베이스가 아직 돌고 있다 | 그것을 띄운 창 1이 열려 있으면 그대로 쓴다. 없으면 작업 관리자에서 `postgres.exe`를 끝내거나 `Stop-Process -Id 1234`로 끝낸 뒤 다시 띄운다 |
| `pnpm check:env`가 `FAIL PostgreSQL 연결` | 창 1의 데이터베이스가 떠 있지 않다 | 4.3절부터 |
| `pnpm check:env`가 `WARN 데이터가 시스템 드라이브가 아닌 곳에 있음` | 저장소를 C:에 받았다. 예전 Windows 개발 서버에서 C:를 피하던 규칙이 알려 줄 뿐이다 | **그대로 쓴다.** 체험에는 지장이 없다. Azure VM의 D:는 VM을 멈추면 지워질 수 있는 임시 디스크라([Microsoft 문서](https://learn.microsoft.com/en-us/azure/virtual-machines/managed-disks-overview)) 오히려 옮기면 안 된다 |
| `pnpm start`가 `WF_SERVE_WEB=true인데 SPA 산출물이 없다` | 화면 파일을 아직 만들지 않았다 | `pnpm build`를 먼저 한다 |
| `pnpm start`가 `환경변수 검증 실패`와 `WF_SESSION_SECRET: 32자 이상` | 세션 값이 짧다 | 4.2절의 무작위 글자로 바꾼다 |
| `환경변수 검증 실패`가 `.env`에 분명히 있는 `WF_DATABASE_URL`·`WF_SESSION_SECRET`·`WF_ROOT_PASSWORD`를 없다고 한다 | `.env`가 UTF-16으로 저장됐다 (4.2절 끝) | 메모장에서 **다른 이름으로 저장 → 인코딩 UTF-8**로 다시 저장한다 |
| 로그인을 눌러도 로그인 화면으로 돌아오고 오류도 없다 | `WF_ENV=production`으로 바꿨다. 운영 모드는 로그인 쿠키를 암호화 연결에서만 보내므로 `http://`에서는 쿠키가 오지 않는다 | `WF_ENV=development`로 되돌리고 `pnpm start`를 다시 한다. 운영과 같은 https가 필요하면 7절 |
| 다른 PC에서 `http://<VM 주소>:3000`이 안 열린다 | Windows 방화벽이나 클라우드 보안 규칙이 막는다 | 5.3절의 세 가지를 모두 했는지 본다 |
| 개발 실행(`pnpm dev`)의 화면이 `http://127.0.0.1:5173`에서 안 열린다 | 개발 화면 서버(Vite)는 `localhost`로 듣는다. Windows에서는 `localhost`가 IPv6(`::1`)로 먼저 풀려 127.0.0.1로는 닿지 않을 수 있다 | `http://localhost:5173`으로 연다. 체험에는 개발 실행이 필요 없다 — 4.5절의 한 프로세스 실행을 쓴다 |

더 깊은 장애(느림, 편집 연결 끊김 등)는 운영과 같은 앱이므로 [`docs/운영가이드_장애대응.md`](운영가이드_장애대응.md)를 본다. 단 그 문서의 명령은 컨테이너(`docker compose`) 기준이다.

## 7. Docker로 띄우는 길 — 확인하지 못했다

**이 절의 절차는 실제로 돌려 보지 않았다.** GitHub의 Windows 러너는 Linux 컨테이너를 돌리지 못한다 — Docker를 쓰는 작업은 Linux 러너에서만 된다 ([GitHub 문서](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers)). 아래는 공식 문서와 이 저장소의 compose 설정에서 읽은 것이다.

### 7.1 되는 조건

| 환경 | 조건 | 출처 |
|---|---|---|
| Windows 10·11 + Docker Desktop | Windows 10 22H2(19045) 이상 또는 11 23H2(22631) 이상의 Enterprise·Pro·Education, WSL 2.1.5 이상, 가상화 켠 x64 CPU, RAM 8GB | [Docker 문서](https://docs.docker.com/desktop/setup/install/windows-install/) |
| Windows Server + Docker Desktop | **지원하지 않는다** — "Docker Desktop is not supported on server versions of Windows" | [Docker 문서](https://docs.docker.com/desktop/setup/install/windows-install/) |
| 클라우드 VM 안의 Docker Desktop | 중첩 가상화가 켜져 있어야 하고, Docker가 지원하는 것은 VMware ESXi·Azure 위에서 Docker Business 고객일 때다 | [Docker 문서](https://docs.docker.com/desktop/setup/vm-vdi/) |
| Windows Server 2022·2025 + WSL2 | 관리자 PowerShell에서 `wsl.exe --install` 후 다시 시작. VM 안이면 **중첩 가상화가 켜져 있어야 한다** | [Microsoft 문서 — 서버 설치](https://learn.microsoft.com/en-us/windows/wsl/install-on-server) · [Microsoft 문서 — FAQ](https://learn.microsoft.com/en-us/windows/wsl/faq) |
| Azure VM | 크기(시리즈)마다 중첩 가상화 지원이 다르다. 예: Dsv5 시리즈는 "Nested Virtualization: Supported" | [Microsoft 문서](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/general-purpose/dsv5-series) |
| AWS EC2 | 중첩 가상화는 정해진 인스턴스 종류(M7i·C7i·R7i·M8i 등)에서 켜야 되고, `.metal`은 기본으로 된다. 그 밖에서는 WSL 1만 된다 | [AWS 문서 — 중첩 가상화](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nested-virtualization.html) · [AWS 문서 — WSL](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/install-wsl-on-ec2-windows-instance.html) |
| Google Cloud VM | 중첩 가상화의 호스트로 Linux KVM만 지원하고 Hyper-V는 지원하지 않는다. WSL2는 Hyper-V의 일부(Virtual Machine Platform)를 쓰므로 **되지 않을 것으로 본다 — 확인 필요** | [Google Cloud 문서](https://docs.cloud.google.com/compute/docs/instances/nested-virtualization/overview) · [Microsoft 문서 — FAQ](https://learn.microsoft.com/en-us/windows/wsl/faq) |

중첩 가상화가 없으면 WSL 1만 되는데, Docker Desktop은 WSL 2를 요구한다. 그때는 가(2~6절)로 간다.

### 7.2 Docker Desktop 설치 (Windows 10·11)

[Docker Desktop for Windows](https://docs.docker.com/desktop/setup/install/windows-install/)를 받아 설치하고, 설정에서 WSL 2 기반 엔진을 쓴다. 회사 규모에 따라 유료 구독이 필요하다 (1절).

Windows Server라면 Docker Desktop 대신 WSL2의 Ubuntu 안에 Docker Engine을 설치하고, 그 안에서 7.3절을 한다 — Linux 서버에서 하는 것과 같다. Docker Engine 설치는 Docker 문서의 Ubuntu 절차를 따른다. **WSL 안에서 Docker Engine이 서비스로 도는지는 확인 필요**다.

### 7.3 compose로 띄울 때 가와 다른 점

절차는 [`docs/운영가이드_리눅스빌드.md`](운영가이드_리눅스빌드.md) 4~8절과 같다 — `deploy/.env`의 필수 키(4절)와, 표 만들기·첫 root 계정을 **앱보다 먼저** `tools`로 하는 순서(6절)까지 그대로 따른다. Phase 13부터 앱은 표를 만들 권한이 없는 앱 계정으로 붙어, 이 순서를 건너뛰면 앱이 데이터베이스에 붙지 못하고 root로 로그인할 수도 없다. 다른 것만 적는다.

| 다른 점 | 왜 | 할 일 |
|---|---|---|
| **https로만 로그인된다** | compose가 앱을 운영 모드(`WF_ENV: production`)로 띄워 로그인 쿠키를 암호화 연결에서만 보낸다. 앱 포트(3000)를 http로 열어 두면 화면은 뜨는데 로그인만 안 된다 | nginx까지 띄우고 `https://localhost:8443`으로 들어간다. nginx는 인증서가 있어야 뜬다 — 아래 |
| 인증서를 직접 만든다 | 인증서는 저장소에 넣지 않는다 (`CLAUDE.md` 12.3절). nginx는 `deploy` 아래 `certs` 폴더의 `cert.pem`·`key.pem`을 읽는다 (`deploy/nginx.conf`) | 아래 명령. 스스로 서명한 인증서라 브라우저가 경고를 낸다 — 체험이니 넘어간다 |

인증서는 openssl이 있는 셸(WSL의 Ubuntu 등)에서, 저장소 폴더를 기준으로 만든다. **인증서에 SAN(주체 대체 이름)이 있어야 한다** — 없으면 요즘 브라우저는 경고가 아니라 오류로 막는다 ([`docs/운영가이드_반입.md`](운영가이드_반입.md) 3절).

```bash
mkdir -p deploy/certs
openssl req -x509 -newkey rsa:2048 -nodes -days 30 \
  -keyout deploy/certs/key.pem -out deploy/certs/cert.pem \
  -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

> **줄바꿈은 걱정하지 않아도 된다.** 컨테이너의 시작 스크립트(`deploy/entrypoint.sh`)는 Windows 줄바꿈(CRLF)이면 Linux에서 돌지 않는데, 저장소의 `.gitattributes`가 Windows에서 받아도 LF로 두게 한다. 편집기로 그 파일을 열어 CRLF로 저장하지만 않으면 된다.

### 7.4 다. WSL2 안의 Linux에서 Node로

WSL2의 Ubuntu는 Linux다. 저장소의 [`README.md`](../README.md) "개발 환경 준비"·"실행"을 그 안에서 그대로 하고, `pnpm db:seed`로 최초 관리자를 만든다. 확인하지 못했지만 달라질 것은 셋이다.

- **저장소는 Linux 쪽 홈(`/home/<이름>/`)에 받는다.** `/mnt/c` 아래(Windows 드라이브)에 두면 느리다 ([Microsoft 문서](https://learn.microsoft.com/en-us/windows/wsl/filesystems))
- **root가 아닌 WSL 기본 사용자로 한다.** Linux의 PostgreSQL은 root로 뜨기를 거부한다 (`CLAUDE.md` 8.1절)
- Windows의 브라우저에서 `http://localhost:3000`으로 들어간다. WSL은 Windows의 localhost로 포트를 이어 준다 ([Microsoft 문서 — FAQ](https://learn.microsoft.com/en-us/windows/wsl/faq))

## 8. 폐쇄망 운영과 다른 점

| 항목 | 체험 (가) | 운영 (폐쇄망) | 알아 둘 것 |
|---|---|---|---|
| 띄우는 방식 | Node 프로그램 하나 + 체험용 데이터베이스(`pnpm dev:db`) | 컨테이너 셋 (앱·nginx·PostgreSQL) | 화면과 기능은 같은 코드다 |
| 연결 | `http://` — 암호화 없음 | `https://` — nginx가 TLS를 맡는다 | 다른 PC에서 http로 쓰면 비밀번호·문서가 암호화되지 않고 지난다 (5.3절) |
| 실행 모드 | `WF_ENV=development` | `production` | 로그인 쿠키에 Secure가 없고(그래서 http로 로그인된다), 브라우저에 https만 쓰라고 알리는 표시(HSTS)가 없다 |
| 업로드 크기 | 앱이 본다 (기본 20MB) | nginx도 같은 값으로 본다 | 같은 값이라 체감은 같다 |
| 요청 번호 | 앱이 만든다 | nginx가 만들어 넘긴다 | 로그를 잇는 방식만 다르다 |
| 데이터베이스 | 임베디드 PostgreSQL 17, 정렬 규칙 `C` | PostgreSQL 17 컨테이너 (정렬 규칙은 이미지 기본값) | 영문 대소문자·기호가 섞인 목록은 **정렬 순서가 조금 다를 수 있다** |
| 데이터베이스 계정 | 하나 — 앱이 표를 만드는 계정 그대로 붙는다(`.env`의 `WF_DB_APP_ROLE`이 비어 있다) | 둘 — 표 만들기·월간 작업은 소유 계정(`tools`), 앱은 표를 만들 권한이 없는 앱 계정 (Phase 13) | 감사로그를 고치지 못하게 막는 트리거는 둘 다 있다. 운영은 거기에 권한까지 한 겹 더 막는다 |
| 자동 기동 | 없다. 창을 닫으면 멈춘다 | 재부팅 뒤 자동으로 올라온다 | — |
| 백업·반입 도구 | `pnpm backup:create` 등은 쓰지 못한다 — 컨테이너를 전제로 한다 | 쓴다 | 체험 데이터는 버리는 것으로 본다 |
| 사내 로그인·메일·사내 LLM | 꺼져 있다 | 사내 설정으로 켠다 | 외부 LLM 서비스를 등록하면 질문과 붙인 문서가 그 회사로 나간다 |
| **데이터** | **합성 데이터만** | 실제 업무 데이터 | 체험 PC·VM은 인터넷에 붙어 있다. 실제 업무 문서·직원 정보·운영 로그를 넣지 않는다 (`CLAUDE.md` 6절·12.3절) |

## 9. 무엇을 확인했고 무엇을 못 했나 (2026-09-27)

### 9.1 코드·실행 파일을 읽어 판정한 것

| 항목 | 본 곳 | 판정 |
|---|---|---|
| 명령이 bash·`cp`·`rm -rf`에 기대는가 | 네 `package.json`의 스크립트 전부 | 기대지 않는다. 전부 `pnpm`·`tsx`·`tsc`·`vite`·`vitest`·`node`다 |

### 10.2 띄우기 · 멈추기

- `시작.cmd`를 두 번 누른다. 처음에는 1~2분 — 데이터베이스와 첫 관리자를 만든다. `위키가 떴다`가 나오면 브라우저가 `http://127.0.0.1:3000`을 연다.
- 첫 로그인은 아이디 `root`, 비밀번호는 그 창에 보인다(잊었으면 `data\settings.env`의 `WF_ROOT_PASSWORD` 줄 — 첫 로그인 전까지만 쓸모 있다). 첫 로그인에서 새 비밀번호로 바꾼다(5.1절).
  비밀번호는 첫 관리자를 **새로 만든 실행에서만** 보인다.
- 첫 관리자는 시작할 때마다 확인한다(없으면 만들고, 비밀번호는 덮어쓰지 않는다 — 데이터베이스를 새로 만든 뒤에도 root가 생긴다). **그 확인이 실패하면 멈춘다 —
  "그 아이디가 root가 아니다" 하나만 빼고.** 예를 들어 root를 하나 더 만들고 처음 `root`를 관리자로 내렸으면 창이 "첫 관리자(root)를 확인하지 못했다 — 위키는
  그대로 띄운다"를 말하고 뜬다 — 그 계정이 root가 아니면 root가 따로 있다(마지막 root는 내릴 수 없다). 다른 root로 로그인해 쓰면 되고, 그 경고를 없애려면
  `data\settings.env`의 `WF_ROOT_USERNAME`을 **지금 root인 계정의 아이디**로 바꾼다(없는 아이디로 바꾸면 그 파일에 남은 첫 비밀번호로 root가 새로 생긴다).
  그 아이디의 계정이 **없는데** `WF_ROOT_PASSWORD`가 비었으면(첫 로그인 뒤 그 줄을 비우고 `data\pgdata`를 지웠다 등) 몇 번을 눌러도 "첫 관리자를 … 못했다 —
  WF_ROOT_PASSWORD가 없다"로 멈춘다 — 띄우면 아무도 로그인하지 못한다. 그 줄에 비밀번호를 적어 저장하고 다시 누른다.
- **떠 있을 때 `시작.cmd`를 다시 누르면** "이미 떠 있다"를 말하고 브라우저만 연다 — 떠 있는 위키는 그대로다.
- 멈추기는 그 창에서 Ctrl+C. 창을 그냥 닫았으면 `멈추기.cmd`를 누른다 — 이 폴더의 Node로 도는 여는 스크립트·앱과 이 폴더의 데이터베이스만 멈춘다.
  다시 쓰려면 `시작.cmd` — 데이터는 `data\`에 남는다. 같은 폴더를 다른 모양의 경로로 불러도(`subst` 드라이브, 8.3 짧은 이름) 같은 묶음으로 알아본다(10.4절).
- **확인하지 못한 것은 건드리지 않는다.** `시작.cmd`를 관리자 권한 창에서 누르고 `멈추기.cmd`를 보통 창에서 누르면, 보통 창에서는 관리자 권한 프로세스의 경로·명령줄이
  보이지 않는다 — 멈추기는 그 실행과 데이터베이스를 그대로 두고 "같은 권한으로 누른다"를 말하며 1로 끝난다(`시작.cmd`도 그 실행을 떠 있는 것으로 보고
  `data\launcher.pid`를 지우지 않는다). 멈추기가 데이터베이스를 멈추는 것은 **이 폴더의 Node를 모두 확인하고 모두 끝냈을 때뿐이다** — 권한이 다른 창의 Node가
  하나라도 보이거나(`data\launcher.pid`가 낡았어도), 끝내지 못한 것이 아직 떠 있거나, 프로세스를 확인하지 못했는데(PowerShell이 막혔다) 앱 자리(3000번)가 답하면
  데이터베이스를 두고 1로 끝난다(데이터베이스만 멈추면 앱이 자리를 쥔 채 남는다).
  그 Node가 이 묶음의 것이 아니면(다른 프로그램) 멈추기를 관리자 권한으로 누른다 — 그 창에서는 보여서 남의 것으로 알아보고 데이터베이스를 멈춘다. 멈추기는 끝에
  앱 자리(3000번)에 위키가 아직 답하는지 본다. 여는 스크립트는 PowerShell로 프로세스를 본다 — 회사 보안 도구가 PowerShell을 막으면 멈추기가 "확인하지 못했다"를
  말하고 여는 스크립트·앱을 끝내지 않는다. 그때는 그 창에서 Ctrl+C로 멈춘다.
- **멈춘 뒤에는 폴더를 옮겨도 된다** — 다음 시작이 앱 부품의 연결과, 설정의 자리(첨부·데이터베이스 폴더와 데이터베이스 주소)를 새 자리로 다시 쓴다(10.4절에서 첨부를 올리고
  옮겨 내려받아 봤다). 떠 있는 동안에는 옮기지 않는다.
- **처음부터 다시** 하려면 멈춘 뒤 `data` 폴더를 통째로 지운다. 모두 지우려면 멈춘 뒤 폴더째 지운다. 처음 실행이 중간에 끊겼으면 그냥 `시작.cmd`를 다시 누른다 —
  끝까지 만들지 못한 데이터베이스는 **지우지 않고** `data\pgdata.broken-<시각>`으로 옮겨 두고 새로 만든다(쓸 것이 없으면 그 폴더는 지워도 된다). 끝까지 만들었는지는
  `data\pgdata` 안의 사실로 본다 — 서버가 한 번이라도 떴거나(`postmaster.opts`) 앱의 데이터베이스가 있으면 다 만든 것이다. 끝났다는 표시(`data\pgdata.ready`)는 그 폴더 밖에
  있어 따로 사라질 수 있지만, 그것만 없다고 쓰던 데이터베이스를 옮기지 않는다(10.4절).
- **새 묶음으로 옮기려면**(새로 받은 묶음에 쓰던 데이터를 가져간다) 두 묶음을 모두 멈추고, 옛 묶음의 `data` 폴더를 새 묶음의 폴더에 복사한 뒤 새 묶음의 `시작.cmd`를
  누른다 — 표는 시작할 때 새 판으로 고쳐진다. 새 판이 모르는 설정 줄(없어졌거나 이름이 바뀐 `WF_` 키)이 `settings.env`에 있으면 창이 그 이름을 알리고 앱에 넘기지
  않는다 — 줄은 지우지 않는다(메모장으로 지우면 경고가 없어진다). PostgreSQL의 큰 판(지금 17)이 바뀐 묶음으로는 이렇게 옮길 수 없다 — 데이터베이스가 뜨지 않는다.
- **3000번(앱)·5439번(데이터베이스) 자리를 다른 프로그램이 쓰면**(다른 폴더의 묶음, 가 길의 `pnpm start` 등) `시작.cmd`가 그 자리를 말하고 멈춘다.
  메모장으로 `data\settings.env`의 `WF_PORT`(앱)나 `WF_PG_EMBEDDED_PORT`(데이터베이스)를 다른 수로 바꿔 저장하고 다시 누른다 — 데이터베이스 주소는 시작할 때 그 값으로 다시 만든다.
- **Windows 방화벽이 "Node.js"의 액세스를 허용할지 물으면 허용하지 않는다(취소).** 앱은 이 PC의 **모든 네트워크 주소**(`0.0.0.0`)에서 접속을 받는 상태로 뜬다 — 앱에는
  듣는 주소를 정하는 설정이 없다. 허용하거나, 방화벽이 꺼져 있거나, 3000번을 열어 둔 PC(5.3절)에서는 같은 망의 다른 PC가 암호화 없는 http로 로그인 화면에 닿는다.
  이 PC 안의 브라우저는 허용하지 않아도 된다(4.5절과 같다). 데이터베이스는 이 PC 안에서만 접속을 받는다.
- `data\`에는 비밀 값(`settings.env`)과 데이터베이스가 든다. **시작할 때마다** `data\`와 `settings.env`를 **지금 사용자·SYSTEM·Administrators**만 열 수 있게 한다 —
  `data\`의 상속을 끊고 셋에게만 주고, 다른 계정에 따로 준 항목을 지우고(`settings.env`에 따로 준 것도), 주인이 다른 계정이면 지금 사용자로 바꾼다(이미 그렇면 그대로다).
  고친 뒤 다시 보고, 아직 넓으면 "권한을 좁히지 못했다(아직 넓은 것: …)"를 말한다 — 그때는 속성 → 보안에서 그 항목을 지운다. 탐색기로 폴더를 복사하면 `data\`가 새
  자리의 권한을 물려받는데, 다음 시작이 다시 좁힌다. 폴더의 나머지(실행 파일)는 좁히지 않는다(10.1절 3번). 그래도 **혼자 쓰는 PC에서, 합성 데이터로만** 쓴다(8절).
