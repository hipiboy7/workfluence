## 3. 보류 17 — `db:generate`를 실제로 돌려 봤다

```
$ pnpm db:generate
[✓] Your SQL migration file ➜ drizzle/0008_lying_power_pack.sql 🚀
```

**오류 없이 성공했다.** 그런데 생성된 파일이 `page_realtime`·`page_templates`를
**CREATE TABLE로 다시 만든다** — 손으로 쓴 `0007_collab`이 이미 만든 표다.
스냅샷 사슬이 `0004`에서 멈춰 있어 drizzle이 0005~0007을 모르기 때문이다.

그대로 적용하면 "이미 있는 관계"로 죽는다. **조용히 틀리는 쪽이 아니라 시끄럽게
죽는 쪽이라 그나마 낫지만**, 생성된 파일을 그대로 믿으면 안 된다는 것은 같다.

생성된 것은 지웠고 journal도 되돌렸다. **마이그레이션은 계속 손으로 쓴다** —
스냅샷 사슬을 다시 세우려면 손으로 쓴 SQL(트리거·CHECK·GUC 예외)을 drizzle 스키마로
옮겨야 하는데, 그것들은 애초에 drizzle이 표현하지 못해서 손으로 쓴 것이다.

## 4. 실시간 동시 편집 (FR-700~712)

### 4.1 인증이 실제로 막는다 (FR-703)

`ws://…/api/ws/pages/<id>`에 붙어 봤다.

| 시도 | 결과 |
|---|---|
| 쿠키 없음 | **HTTP 401** |
| 가짜 서명 (`s:fake.badsignature`) | **HTTP 401** |
| 서명 없는 sid | **HTTP 401** |
| uuid가 아닌 경로 | 연결 거부 (우리 처리기가 손대지 않는다) |

**실패 사유를 구분해 주지 않는다.** 권한 없음과 페이지 없음을 나누면 그것만으로
"그 페이지가 있다"가 새어 나간다 (7절 계정 열거 방지와 같은 판단).

### 4.2 두 클라이언트로 끝까지 (FR-700·701·706·707)

```
준비 완료 — 페이지 750f2e9a…, 현재 버전 1
A: 연결됨 / B: 연결됨
B가 A의 글을 본다: YES      A가 B의 글을 본다: YES      둘 다 남는다: YES
저장된 버전: 2 (처음 1)     정본에 A의 글: YES  정본에 B의 글: YES
가만히 둔 뒤 버전: 2 (안 늘었다 — 정상)
```

마지막 줄이 FR-707이다. 커서만 움직여도 Yjs 변경이 오므로 이것이 없으면
**가만히 보고만 있어도 버전이 쌓인다.**

**전파 지연을 쟀다** (NFR-60). A가 한 글자 넣고 B가 그것을 보기까지, 표본 20:

```
p50 2.3ms · p95 3.2ms · max 3.2ms      목표 1초 → 통과 (0.3%)
```

같은 호스트의 두 프로세스라 **망 지연이 0에 가깝다.** 실제 사무실에서는 여기에
왕복 시간이 더해진다 — 사내망 기준으로도 목표에 한참 못 미칠 것이라 보지만,
**그것은 재 본 것이 아니다.**

### 4.3 컨테이너 스택에서 — **nginx를 거쳐** 확인했다

개발 서버(:3000)만으로는 부족하다. 운영은 nginx가 TLS를 끝내고 `Upgrade`를 넘기는
경로이고, **호스트에서만 통하는 것에 기대면 반입해서야 드러난다** (0.3절).

```
페이지 준비: 201
nginx 경유 WebSocket 연결: OK        ← wss://localhost:8443
버전: 2 | 정본에 글: YES
```

`NODE_EXTRA_CA_CERTS`로 개발 인증서를 신뢰시켰고 **TLS 검증을 끄지 않았다** (7절).
nginx 설정은 Phase 0부터 `Upgrade`를 넘기게 돼 있어 **한 줄도 고치지 않았다** —
그때 적어 둔 "Phase 6 실시간 편집 대비" 주석이 그대로 맞았다.

컨테이너 이미지 크기는 **400MB**다. NFR-64 예산과 **같다** — Yjs·ws가 들어오면서
390MB에서 올랐다. 다음에 의존성이 늘면 넘는다 (9절).

### 4.4 브라우저 둘로 (E2E)

사람")에 나오고, 편집을 멈추면 버전이 남는 것까지 확인한다.

## 6. 템플릿 (FR-740~746)

```
관리자 생성 201 · 같은 이름 다시 201 (같은 id — 멱등)
일반 사용자 생성 403 · 목록 200 · 검증 실패 문서 400
일반 사용자 삭제 403 · 관리자 삭제 200
감사로그: template.create, template.delete
```

멱등 호출은 감사로그에 남기지 않는다 — 남기면 "만들었다"로 가득 차는데 바뀐 것은 없다.

## 7. 메일 (FR-750~757)

```
감사로그: mail.send, page.update, page.create, …
모의 발송 — 받는이 ***@example.internal · 제목 "[위키] … 님이 회원님을 불렀습니다"
```

받는 사람 주소는 **도메인만 남기고 가린다** (7절 로그 규칙). 감사로그에는 **받은
사람 수만** 적는다 — 감사로그는 오래 남고 주소는 개인정보다.

**트랜잭션 밖에서 보낸다** (FR-754). 안에서 보내면 연결을 쥔 채 남의 서버를 기다리고
(T-026과 같은 모양), 롤백되면 없던 일에 대한 메일이 나간다.

## 8. Phase 2의 인수 기준 하나가 바뀌었다

**이 Phase가 이전 Phase의 인수 기준을 바꾼 유일한 곳이라 따로 적는다.**

Phase 2의 "두 사람이 같은 버전을 저장하면 뒤가 **화면에서** 충돌 안내를 받는다"는
실시간 편집에서 **일어나지 않는다** — 병합되므로 충돌할 것이 없다.

`CLAUDE.md` 0.1절이 애초에 그렇게 적어 뒀다: "실시간 동시 편집은 Phase 6.
**그 전에는** 편집 잠금 + 저장 시 버전 충돌 감지."

FR-709는 REST 저장 경로와 409를 **그대로 두라**고 하고, 그것은 여전히 사실이다.
`e2e/space-page.spec.ts`를 **API의 409를 직접 확인하는 것**으로 바꿨다 —
같은 `baseVersionNo`로 두 번 저장하면 두 번째가 409이고 `currentVersionNo`가 3이다.

## 10. 검증기록을 쓰다 갚은 빚 둘

검증기록을 쓰면서 **내가 만든 빚 둘을 발견해 그 자리에서 갚았다.** 미루려다 말았다 —
둘 다 "다음에"가 아니라 지금 고치는 것이 싼 것이었다.

| 빚 | 무엇이 문제였나 | 어떻게 했나 |
|---|---|---|
| `WF_COLLAB_MAX_STATE_KB` | 설계서 설정 표에 적고 **코드가 쓰지 않았다** (5절 위반) | 표에서 뺐다. **넘었을 때 무엇을 할지 정하지 못한 것**이 진짜 이유다 — 보류 19로 등재 |
| `purgeOrphanState` | 함수는 있고 **호출부가 없었다** (3절 호출자 없는 코드) | 함수를 지우고 `pnpm trash:purge`에 SQL 한 줄로 넣었다. 정리 명령이 이미 고아를 치우는 곳이다 |

두 번째가 더 나은 결말이다. **호출부를 붙이는 대신 함수를 지웠다** — 정리 명령은
이미 라벨 고아를 치우고 있었고, 거기 한 줄을 더하는 것이 클래스에 메서드를 두고
밖에서 부르는 것보다 단순하다.
