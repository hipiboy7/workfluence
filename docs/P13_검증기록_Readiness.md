### 2.3 저장소의 측정 도구 — `pnpm load:test`

도구에 몰린 로그인(`LOAD_LOGIN_STORM`·`LOAD_LOGIN_STORM_CONCURRENCY`·`LOAD_LOGIN_STORM_USER_PREFIX`)과 쉬어 가며 읽기(`LOAD_THINK_MS`)를
더했다(설계서 I절). 판정은 읽기로 한다 — 몰린 로그인 자체의 지연은 CPU에 묶인다. 한 계정의 로그인은 이제 차례로 처리되므로(FR-1431) 여러
사람을 재려면 접두를 준다. 2.2절은 임시 스크립트로 쟀다 — **저장소만으로 다시 잴 수 있게** 같은 모양을 이 도구로 다시 쟀다(06:27~06:39 UTC,
2.2절과 같은 스택, 합성 계정 301개 — 관리자 1과 몰린 로그인용 300. 끝나고 지웠다).

```
NODE_EXTRA_CA_CERTS=$PWD/deploy/certs/cert.pem LOAD_BASE=https://127.0.0.1:8443 \
  LOAD_USER=<합성 관리자> LOAD_PASSWORD=<비밀번호> LOAD_SESSIONS=50 LOAD_ROUNDS=10 LOAD_THINK_MS=1000 \
  LOAD_LOGIN_STORM=300 LOAD_LOGIN_STORM_CONCURRENCY=20 LOAD_LOGIN_STORM_USER_PREFIX=<접두> \
  pnpm load:test
```

| 모양 | 몰리지 않을 때 가장 느린 단계 p95 | 몰린 동안 단계별 p95 (스페이스 / 검색 / 알림 / 감사) | 몰린 동안 로그인 | 판정 (종료 코드) |
|---|---|---|---|---|
| **쉬어 가며 읽기** (`LOAD_THINK_MS=1000`) — NFR-131의 판정 | 20ms | **316** / 212 / 186 / 187ms | 300/300 · p95 5,664ms · 초당 4.6 | 목표 안 (0) |
| 쉬지 않고 읽기 (`LOAD_THINK_MS` 없음 — 보류 6의 모양) | 790ms | 1,447 / 1,095 / 789 / 809ms | 300/300 · p95 6,938ms · 초당 3.6 | 목표 밖 (1) |
| 쉬지 않고 읽기 — **고치기 전**(에이전트, 04:03 UTC. 그때는 한 계정을 되풀이했다 — 한 계정도 줄을 서지 않던 때라 여러 사람과 같다) | 454ms | 4,204 / 2,803 / 2,201 / 2,622ms | 300/300 · p95 4,057ms · 초당 6.0 | 목표 밖 (1) |

→ 쉬지 않는 판은 세션마다 늘 한 건이 떠 있어 지연이 "떠 있는 수 ÷ 처리량"으로 정해진다. 고친 뒤 몰린 동안 읽기 처리량은 초당 약 22건 →
80건(3.6배)이 됐지만, argon2가 CPU를 나눠 가져(한 건이 스레드 넷 — `p=4`) 2코어 공유 서버(다른 프로젝트가 0.55~0.75코어)에서는 1초 안에
들지 못했다. **연결이 아니라 CPU를 기다린다.** NFR-131은 사람이 쓰는 모양인 쉬어 가며 읽는 판으로 판정한다(설계서 C.10). 이 도구의 쉬어
가며 읽기는 처음에 회마다 세션을 맞춰, 가장 무거운 첫 단계를 한꺼번에 쳤다 → T-055.

## 10. 확인하지 못한 것

- **여러 주소에서 20건 넘게 한꺼번에** 오는 로그인 — 보류 31. 한 주소에서는 로그인 제한(IP별 20건/60초)이 20건만 들인다. 출발지를 여럿으로
  흉내 내는 측정은 이 서버의 권한 검사가 "보안 우회"로 막아 하지 않았다. 계산만 했다 — 몰린 로그인 처리량이 초당 약 7건(S0a)이라, 고치기
  전의 경로(로그인이 연결을 쥔 채 확인)에서는 한꺼번에 약 70건이 오면 마지막 것이 연결 대기 한도(10초)에 닿는다. 고친 뒤는 로그인이 연결을
  쥐지 않아 이 한도와 상관이 없고, 줄에서 기다리는 시간만 길어진다
- **사내 계정(OIDC) 경로의 실측** — 모의 제공자로만(보류 11)
- 운영 서버의 코어 수 — 이 측정은 2코어 공유 서버에 묶인다
