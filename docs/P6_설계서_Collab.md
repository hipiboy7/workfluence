선행: [`docs/P5_검증기록_Release.md`](P5_검증기록_Release.md) · 구조: [`docs/설계서_Architecture.md`](설계서_Architecture.md)

# A. 착수 쟁점 (사용자 확정 2026-09-22)

| # | 쟁점 | 확정 | 근거 |
|---|---|---|---|
| 1 | Phase 6에 무엇을 넣는가 | **실시간 편집 + 버전 비교(diff) + HTML 내보내기 + 페이지 템플릿 + 외부 알림(메일)** | 사용자 선택 "위 전부 + 템플릿" |
| 2 | PDF 내보내기 (보류 7) | **하지 않는다.** HTML + 인쇄 CSS로 간다 | 사용자 선택. 헤드리스 브라우저는 반입 묶음을 수백 MB 늘리고, app 이미지가 이미 390MB로 예산 400MB에 10MB만 남았다 |
| 3 | 외부 알림 | **만든다.** 사용자 답: "메일 전송 API 기능이 있다" | 발송 경로가 있다는 것이 `scope-definition` 4.2절이 기다린 조건이었다 |
| 4 | Confluence 데이터 가져오기 | **하지 않는다 — 닫는다** | 사용자 선택 "이관하지 않는다". 새로 시작한다 |

## A.1 확인 필요 — 사내 메일 API의 요청 형식

사용자가 "메일 전송 API가 있다"고 했고 **그 API의 요청 형식은 아직 모른다.**
그래서 IdP와 **같은 방식**으로 둔다 (2절 DIP): 주입 토큰 뒤에 인터페이스를 두고,
개발은 모의 구현으로 하고, 실제 어댑터는 **한 파일**이다.

가정한 형식은 아래다. **틀리면 `HttpMailSender` 한 파일만 고친다.**

```
POST {WF_MAIL_API_URL}
Authorization: Bearer {WF_MAIL_API_TOKEN}
Content-Type: application/json

{ "from": "...", "to": ["..."], "subject": "...", "text": "..." }
```

**실연동 확인은 보류 18이다.** 모의 통과는 완료가 아니다 (9.1절과 같은 판단).

# B. 요구사항

## B.1 실시간 동시 편집 (FR-700 ~ FR-712) — 보류 4를 닫는다

| # | 요구 | 근거 |
|---|---|---|
| FR-700 | 두 사람이 같은 페이지를 동시에 열어 고치면 서로의 입력이 **실시간으로 보인다** | 0.1절 |

| FR-703 | WebSocket 연결은 **세션을 검증하고 쓰기 권한을 판정한다.** 기본 거부 | 7절 |
| FR-704 | 권한 판정은 `packages/shared/src/permissions.ts`의 같은 함수를 쓴다 | 7절 "판정은 한 곳" |

# C. 실시간 편집을 어떻게 만드는가

## C.1 무엇이 정본인가 — 보류 4의 답

```
   편집 중                                   저장된 것
   ┌──────────────┐   유휴 N초    ┌───────────────────────┐
   │ page_realtime│ ────────────▶ │ page_versions         │
   │ (Yjs 상태)   │               │ .content_json  ← 정본 │
   │ 버려도 된다   │ ◀──────────── │ 언제든 여기서 다시 시작│
   └──────────────┘   처음 열 때   └───────────────────────┘
```

**실시간 상태를 정본으로 삼지 않는다.** 이유가 셋이다.

1. **읽는 쪽이 전부 JSON을 본다.** 검색 인덱스·내보내기·비교·알림 멘션 추출이 모두
   `content_json`을 읽는다. 정본을 Yjs 상태로 옮기면 그 전부가 Yjs를 해석해야 한다.
2. **버릴 수 있어야 한다.** Yjs 상태는 라이브러리 버전에 묶인 이진 형식이다. 정본이면
   라이브러리를 올리는 일이 데이터 마이그레이션이 된다.
3. **되돌릴 수 있어야 한다.** 실시간 편집을 끄는 결정(FR-711)이 데이터 이전을
   요구하면 그것은 끌 수 있는 것이 아니다.

## C.2 서버는 중계하고 저장한다

`y-websocket`의 서버 구현을 쓰지 않고 **`y-protocols`의 sync·awareness 프로토콜로
직접 중계한다.** 이유는 **연결 시점에 권한을 판정해야** 하기 때문이다 (FR-703).
남의 서버 구현에 인증을 끼워 넣는 것보다, 프로토콜 두 개를 우리가 다루는 편이
경계가 분명하다 (1.3절).

```
클라이언트                        서버 (PagesGateway)
   │  WS /api/ws/pages/:id          │
   ├───────────────────────────────▶ │ ① 세션 쿠키 → userId
   │                                │ ② spaceAccess().canWrite  ← 아니면 닫는다
   │                                │ ③ page_realtime에서 상태 복원
   │                                │    없으면 content_json으로 Y.Doc을 만든다
   │  ◀── sync step 1/2 ────────────┤
   │  ─── update ──────────────────▶ │ ④ 같은 방의 다른 연결에 그대로 보낸다
   │                                │ ⑤ 유휴 N초 → JSON으로 바꿔 버전 추가
   │  ─── awareness ───────────────▶ │ ⑥ 커서·이름을 중계한다 (저장하지 않는다)
```

**⑤가 이 Phase에서 가장 조심할 곳이다.** `page_versions`는 append-only라(6절)
잘못 만든 버전을 지울 수 없다. 그래서 세 가지를 지킨다.

- **유휴 기준으로 묶는다.** 타이핑 중에는 버전을 만들지 않는다.
- **내용이 같으면 만들지 않는다** (FR-707). 커서만 움직여도 update가 오기 때문이다.
- **스키마 검증을 통과해야 만든다** (FR-708). 실패하면 버전 없이 로그만 남긴다 —
  실시간 상태는 그대로 살아 있으므로 사람이 고칠 수 있다.

## C.3 정리는 언제 하는가

마지막 연결이 끊기면 그 페이지의 실시간 상태를 지운다 (FR-710). **지우기 전에
마지막 버전을 남긴다** — 순서를 뒤집으면 마지막 몇 초의 편집이 사라진다.

프로세스가 죽으면 실시간 상태가 남는다. 그것은 **문제가 아니다** — 다음에 열면
그 상태에서 이어지고, 정본보다 앞선 내용이면 첫 유휴에 버전이 된다. 영구히 쌓이는
것만 막으면 되므로 `pnpm trash:purge`가 **오래된 고아 실시간 상태**도 함께 지운다.

page_templates(
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name          text NOT NULL UNIQUE,

`page_templates.name`은 유일해야 하므로 DB가 막는다 (FR-745).
