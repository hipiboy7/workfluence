# A. 착수 쟁점

1.1절 1단계는 사용자에게 묻게 되어 있으나 **"phase5까지 물어보지 말고 진행"** 지시가
있었다 (`docs/prompts/usage-cap-and-autonomy.md`). Phase 4와 같이 **정한 것과 근거·되돌릴
조건**을 적는다.

| # | 쟁점 | 정한 것 | 근거 · 되돌릴 조건 |
|---|---|---|---|
| 1 | 반입 리허설을 어디서 하나 | **이 서버 안에서 "옮김"을 흉내 낸다.** 이미지를 `docker save` → 레지스트리·캐시를 거치지 않고 `docker load` → 별도 compose 프로젝트로 기동 | 폐쇄망 장비가 없다. 중요한 것은 **"인터넷 없이 tar만으로 서는가"**이고 그것은 여기서도 확인된다. 실제 반입은 그 절차서를 그대로 따른다 |
| 2 | 부하 300명을 어떻게 재나 | **동시 50세션**(`CLAUDE.md` 보류 6의 판정 조건)으로 읽기 위주 시나리오. 도구는 추가하지 않고 `tsx` 스크립트로 | 사용자 300명 중 동시 세션은 수십 수준이다 (0.1절). k6·Gatling을 반입 목록에 넣지 않으려면 도구를 늘리지 않는 편이 낫다 |
| 3 | 백업 대상과 방법 | `pg_dump -Fc` + 첨부 디렉토리 tar. **복원은 빈 볼륨에서** 한다 | 8.3절. "덮어쓰기 복원"은 남은 것이 섞여 성공처럼 보인다 — 빈 데서 서야 진짜 복원이다 |
| 4 | SBOM 형식 | **CycloneDX JSON.** `pnpm licenses list`의 출력을 우리 스크립트가 변환한다 | 도구를 늘리지 않는다. 반입 심사는 "무엇이 들었나"를 보는 것이지 특정 형식을 요구하지 않는다 (요구가 오면 그때 맞춘다) |
| 5 | 보류 5(자동 빌드) | **닫는다 — 하지 않는다** | 트리거가 "수동 빌드 3회 연속 성공"이다. Phase 3·4·5에서 채웠다. 그러나 self-hosted runner는 **이 공유 서버에 상주 프로세스를 하나 더 얹는 일**이고, 빌드가 수동으로 3분이면 얻는 것이 적다 |
| 6 | 보류 8(중앙 로그 수집) | **닫는다 — 하지 않는다** | 판정 방법이 "운영 측 수집 인프라 유무 확인"이다. 확인되지 않았고(확인 필요 B 계열), 없으면 stdout JSON + `docker logs`로 간다고 이미 정해 두었다 |
| 7 | 보류 6(이중화) | **부하 측정 결과로 판정한다** | 조건이 "동시 50세션에서 p95 1초 초과 또는 가용성 요구". 재 보고 적는다 |

# C. 재부팅을 못 하는 환경에서 "자동 기동"을 확인하는 법

8.3절은 "재부팅 후 자동 기동을 실제로 확인한다"고 한다. 그런데 **이 서버는 공유 인스턴스라
재부팅할 수 없다** (사용자 지시). 확인을 포기하는 대신 **같은 것을 묻는 다른 방법**을 쓴다.

재부팅이 확인하려는 것은 두 가지다.

1. 도커 데몬이 부팅 시 뜨는가 → `systemctl is-enabled docker`
2. 컨테이너가 데몬과 함께 되살아나는가 → `restart: unless-stopped`가 실제로 그렇게 동작하는가

2번을 어떻게 확인하느냐가 문제다. **처음에 쓴 방법 둘은 아무것도 확인하지 못했다** (T-025).

| 시도한 방법 | 결과 | 왜 |
|---|---|---|
| `docker kill workfluence-api` | 되살아나지 않는다 | 도커는 `kill`도 **사람이 멈춘 것**으로 기록한다. `stop`과 같은 취급이라 정책이 걸리지 않는다 |
| 컨테이너 안에서 `kill -9 1` | 아무 일도 없다 | 커널이 **네임스페이스 안에서 PID 1로 보낸 신호를 무시**한다. 오류도 안 난다 |
| **같은 이미지·같은 정책으로 일부러 죽는 컨테이너를 띄운다** | 재시작 횟수가 실제로 올라간다 | 프로세스가 **스스로 죽는 것**이 부팅 실패·크래시와 같은 경로다 |

그래서 2번은 세 번째 방법으로 확인한다. `workfluence-app` 이미지에 `--restart unless-stopped`를
주고 곧바로 종료하는 명령을 물려 띄운 뒤, `RestartCount`가 올라가는지 본다. 확인이 끝나면 지운다.
실제 서비스 컨테이너에 대해서는 **정책이 붙어 있는지**(`docker inspect`)를 따로 본다.

**이것이 재부팅과 같지 않다는 것을 검증기록에 명시한다.** 실제 재부팅 확인은 폐쇄망
반입 당일의 절차에 남긴다.

# E. 설정 항목

**앱 환경변수(`WF_*`)를 만들지 않는다.** 반입·백업·복원은 전부 인자와 기존 설정으로 돈다 —
운영 `.env`에 개발용 키가 늘어나는 것을 피한다.

부하 측정만 인자가 필요해서 환경변수를 쓴다. **`WF_` 접두사를 붙이지 않는다.**
`WF_*`는 앱 설정이고 스키마가 모르는 `WF_` 키를 보면 **기동을 거부한다** — 누군가
`.env`에 적는 순간 앱이 안 뜬다. 앱 설정이 아님을 이름으로 드러낸다.

| 키 | 기본값 | 무엇 |
|---|---|---|
| `LOAD_BASE` | `http://127.0.0.1:3000` | 측정 대상. 컨테이너 스택은 `https://localhost:8443` |
| `LOAD_SESSIONS` | `50` | 동시 세션 수 |
| `LOAD_ROUNDS` | `10` | 세션당 반복 횟수 |
| `LOAD_LOGIN_CHUNK` | `5` | 세션을 한 번에 몇 개씩 여는가 (로그인 제한 때문) |
| `LOAD_USER` / `LOAD_PASSWORD` | 없음 (필수) | **합성 계정.** 감사로그 단계가 있어 관리자여야 한다 |

### 왜 DB 계정 분리를 또 미루는가

Phase 1이 "운영화 단계에서 배포 절차와 함께" 미뤘고, Phase 5가 왔는데 **또 미룬다.**
두 번 미루는 결정이므로 이유를 분명히 적는다.

계정을 나누면 **마이그레이션을 누가 어떤 계정으로 돌리는지가 배포 절차의 일부가 된다.**
`.env`에 계정이 둘 늘고, compose의 postgres 초기화와 `pnpm db:migrate`가 서로 다른
자격을 쓰게 된다. 그 절차는 **실제 운영 환경에서 한 번 돌려 보지 않으면 맞는지 알 수 없다** —
그런데 우리는 아직 그 환경에 들어가 본 적이 없다. 지금 만들면 **반입 당일에 처음
시험하는 절차**가 하나 더 늘어난다.

지금 막고 있는 것은 트리거 한 겹이다. 그것은 **실수와 앱 버그를 막고**, 막지 못하는 것은
"DB 계정을 가진 사람이 일부러 고치는 것"이다. 그 사람은 계정을 나눠도 마이그레이션
계정으로 같은 일을 할 수 있다. **계정 분리가 더하는 방어는 "앱이 탈취됐을 때"뿐이고**,
그 시나리오에서도 감사기록을 지우려면 앱 계정으로 트리거를 넘어야 한다.

그래서 순서를 이렇게 본다. **반입해서 운영 절차가 한 번 돌아간 뒤에**, 그 절차에 계정
분리를 더한다. 트리거가 그때까지 버틴다.
