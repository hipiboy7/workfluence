## 1. 사용자 요청 (원문)

> 좋은데 보완하면 더 좋은 것들이 몇가지 보이는 군. 실제로 프로젝트를 진행하면서 넣으면 좋은 것들이야.
> 우선 패스워드는 8자 이상, 2종 조합으로 축소해. 엄청난 보안을 요하는 곳이 아니야.
> 추가로 사용자는 관리자가 등록하는게 아니라, 새로운 사람이 가입 요청을 하면 관리자가 승인하는 구조로 갔으면 좋겠어.
> 그리고 비밀번호를 할때, 비밀번호 칸에 눈 모양으로 표시를 두고, 기본은 눈을 감은 모양, 해당 눈을 누르면 눈을 뜬 모양이 되었으면 좋겠어. 눈을 감았을 때는 비밀번호가 마스킹되어있고, 눈을 눌러서 눈을 뜨면 비밀번호가 보이도록.
>
> 처음 페이지에서부터 얘기를 해보자.
> 첫 페이지에 보이는 것은 로그인, 신규 가입, ID 찾기, PWD 찾기, 담당자 확인 버튼이 있었으면 좋겠어.
> pwd찾기는 ID와 email을 넣으면, 초기화 비밀번호를 얻을 수 있도록
> ID찾기는 가입한 사용자의 email을 넣어서 찾도록
> 그런데 여기서 개인정보 문제가 발생하면 안돼.
>
> 그다음에 로그인 했을 때, 사용자와 관리자는 당연히 보여지는게 달라야해.
> 지금 구조에서 관리자는 사용자가 이용하는 페이지와 기능이 다 보이고 사용 가능해야해.
> 우선 사용자 기준으로 말을 해볼게
> 사용자는 스페이스를 기본 '개인'의 스페이스가 보여야해.
> 그리고 '스페이스' 문자 옆에 '팀 스페이스' 보기 버튼이 있어서, 누르면 왔다갔다 할 수 있게 했으면 좋겠어.
> 현재 새 스페이스 만들기는 유지하되, '키' 보다는 '분류' 를 넣고, 드롭다운 메뉴로 내려오게 한 다음에, 그 중에서 고르도록 하고, 제일 위에는 '+새 카테고리 만들기' 를 넣고 그 기능이 구현되어야 해.
> '이름' 대신에 '스페이스 명'이라고 바꿔.
> 하나의 특정 스페이스를 들어가면 현재 잘 되어있는 것 같아.
> 그런데 '팀 스페이스'의 경우 해당 스페이스를 함께 쓰는 사용자를 볼 수 있는 메뉴가 필요해. 스페이스 명과 '+새 페이지' 버튼 사이에 'crew'나 'coworker'라는 작은 버튼을 넣고, 그걸 누르면 해당 스페이스를 같이 작업하는 사람들 또는 볼수 있는 사람들의 목록이 보여지도록 해야해.
> 스페이스는 '생성자'가 '중지'는 할 수 있지만, 사용자가 2명 이상이 되면, '삭제'는 할 수 없도록 해. '중지'하게되면, admin만 삭제할 수 있어야해.
>
> 다음으로 관리자는 system-admin과 admin을 나눠.
> root는 workfluence의 시스템적 영역을 관리하는 사람이야.
> admin은 스페이스와 사용자들을 관리하는 사람이야.
> root로 부터 admin이 부여되고, admin은 또다른 admin과 user를 생성할 수 있어야해.
> 아직 root 의 페이지는 생각을 못했어.
>
> admin은 지금처럼 첫페이지에서 '관리' 버튼과 기능을 유지해.
> '관리' 버튼을 누르면, 관리자 화면으로 들어가는데 '사용자', '스페이스', '감사로그'를 각각 5건씩만 보여주고, 각각의 글씨를 클릭하면 각 페이지로 이동하도록 해
> '사용자'를 관리하는 페이지와 '감사 로그'를 볼 수 있는 페이지, '스페이스'를 볼 수 있는 페이지는 분리해.
> '사용자' 페이지에서 신규 가입한 사람은 '승인 대기'상태로 두고, '승인'을 하면 '활성' 상태로 변경이되며, 비밀번호가 잠기면'잠김' 상태가 되면 돼.
> 사용자 컬럼은 ID, 이름, 역할, email, 생성일자, 상태 컬럼으로 만들어.
> 또한 각 사용자 행 끝부분에는 '비밀번호 초기화' 버튼이 있어서 비밀번호 초기화해 주고 그 값을 볼 수 있는 기능을 넣어줘. 비밀번호는 난수로 2종 이상으로 생성 하고.
> '스페이스' 페이지는 새로 아래 테이블을 보여주면 돼.
> 컬럼은 '스페이스명', '카테고리', '생성자'(생성한 사람ID), '생성일자', '상태'로 구성되면 돼.
> 하나의 row를 선택하면, 위에는 스페이스명, 카테고리, 생성일자, 상태를 보여주고, 밑으로는 사용자 목록을 보여주면 돼.
> 그리고 '상태 변경하기' 버튼을 만들어줘.
> '스페이스 상태'는 '활성' '중지' 2가지로 시작하자.
> 또한 '스페이스명'을 클릭하면 해당 스페이스로 이동할 수 있게 해.

## 2. 해석과 가정 (원문에 없는 부분은 Claude가 정했다 — 확인 후 바꿀 수 있다)

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 비밀번호 정책 | 8자 이상, 영문 대·소문자·숫자·특수 중 2종. 5회 실패 15분 잠금은 유지 | 요청. '잠김' 상태가 요청에 있으므로 잠금은 유지 |
| 2 | 가입 흐름 | 가입 요청 → `승인 대기` → 관리자 승인 → `활성`. 승인 시 개인 스페이스 1개를 자동 생성 | "기본 '개인'의 스페이스가 보여야" 하려면 처음부터 하나 있어야 자연스럽다 |
| 3 | ID 찾기 | **email + 이름** 둘 다 입력. 결과는 마스킹된 ID(`ho***gd`)만. 분당 5회 제한. 감사로그 기록 | email만으로 ID를 돌려주면 email 보유자가 계정을 열거할 수 있다. 두 정보 요구 + 마스킹으로 개인정보 노출을 줄인다 |
| 4 | PWD 찾기 | ID + email 일치 시 임시 비밀번호를 **화면에 1회 표시**, 다음 로그인 시 비밀번호 변경 강제. 10분당 3회 제한. 잠금도 함께 해제 | 폐쇄망이라 메일 발송이 없다. 표시 후 즉시 변경으로 노출 창을 줄인다 |
| 5 | 담당자 확인 | admin/root가 편집하는 안내문 + admin 이름 목록. email은 표시하지 않음 | 개인정보 최소 노출 |
| 6 | 눈 아이콘 | 모든 비밀번호 입력란 공통 컴포넌트. 기본 감은 눈(마스킹), 누르면 뜬 눈(표시). 외부 아이콘 없이 인라인 SVG | 7절 외부 자원 0 |
| 7 | 스페이스 종류 | `개인` / `팀`. 개인: 생성자(+admin)만 보고 편집. Crew 없음. 팀: Crew(owner·editor·viewer)만 목록에 보이고 읽기, owner·editor가 편집 | "함께 쓰는 사람 또는 볼 수 있는 사람"이 Crew 역할 2종(editor·viewer)에 대응 |
| 8 | 관리자 시야 | admin·root는 모든 스페이스(개인 포함)를 보고 편집할 수 있다. 사용자용 목록에서 `팀 스페이스 보기`는 admin에게 전체 팀 스페이스를 보여준다 | "관리자는 사용자가 이용하는 페이지와 기능이 다 보이고 사용 가능해야" |
| 9 | 카테고리 | 모든 활성 사용자가 만들 수 있다. 이름 중복 불가 | 드롭다운 맨 위 "+ 새 카테고리 만들기"가 사용자에게 보이므로 |
| 10 | 스페이스 키 | 화면에서 제거. 내부 식별자는 자동 생성 | "'키' 보다는 '분류'" |
| 11 | 스페이스 상태 | `활성` / `중지`. 중지되면 읽기 전용. 생성자와 admin이 전환. 삭제: 생성자는 Crew가 본인뿐일 때, admin은 중지 상태일 때 | 요청 규칙을 그대로 |
| 12 | 역할 | `root` ⊃ `admin` ⊃ `member`. root만 root를 부여. admin은 admin·member 생성과 승인·초기화·잠금 해제. admin은 root 계정을 건드릴 수 없다 | "root로부터 admin 부여, admin은 admin과 user 생성" |
| 13 | root 화면 | 최소: 시스템 정보(버전·DB·건수), 담당자 안내문 편집, 관리 화면 진입. 이후 설계 | "아직 root의 페이지는 생각을 못했어" |
| 14 | 사용자 상태 표시 | `승인 대기` / `활성` / `잠김`(잠금 시각으로 파생). 관리자가 잠금 해제 가능 | 요청의 3상태 |
| 15 | 개발 시드 | root(env) + `admin1`(admin) + `member1`(member, DEMO editor, 개인 스페이스 있음) + `pending1`(승인 대기). 개발 계정 비밀번호는 root 초기 비밀번호와 같음 | 승인·역할별 화면을 바로 확인하려면 계정이 필요. 합성 계정만 |
| 16 | 환경변수 | `WF_ADMIN_*` → `WF_ROOT_USERNAME` / `WF_ROOT_INITIAL_PASSWORD` / `WF_ROOT_EMAIL` | 최초 계정이 root가 되므로 이름을 맞춘다 |
