# P14 설계서 — Spaces (페이지 트리를 화면에서 · 스페이스를 화면에서 관리)

Phase 14는 기능백로그의 **F-007**(페이지 트리에서 하위 페이지를 만들고 옮긴다)과 **F-008**(관리자가 화면에서 스페이스를 관리한다)이다. 둘 다
**서버 기능은 Phase 2·4에 있는데 누를 화면이 없다** — Phase 13에서 사용자 가이드를 쓰다가 코드에서 나왔다. 요청 원문은
`docs/prompts/phase14/scope.md`, 요구사항 번호는 **FR-1500**, 비기능은 **NFR-140**부터다.

선행: [`docs/P2_설계서_Page.md`](P2_설계서_Page.md) FR-346 · [`docs/P4_설계서_Admin.md`](P4_설계서_Admin.md) FR-530·532·537·538 ·

| FR-1505 | 하위 페이지 만들기·옮기기는 **쓸 수 있는 사람에게만** 보인다(`access.canWrite`) | P2 FR-345 |

## D. 설계

### D.1 자리 다시 매기기 (FR-1502·1503, NFR-140)

- **식별자는 경계에서 소문자로** — 본문·쿼리의 식별자 칸은 `idSchema`(uuid 모양이면 대문자도 받고 소문자로), 경로는 `parseId`(`UuidPipe`, 실시간
  편집의 방 이름). DB의 uuid는 소문자라, 대문자를 그대로 두면 순환 판정(`a.id === selfId`)·잠금 이름·방 이름에서 같은 것이 다른 값이 됐다 —
  대문자로 보낸 옮기기가 자기 아래로 가 고리를 만들었다(반영분 점검 2). 안쪽은 소문자만 본다.
- **자리 값에 틈을 둔다** — `PAGE_POSITION_GAP`(1024)씩. 새 페이지는 형제의 맨 뒤 + 간격(`max + 1024`, 첫 페이지는 0)에 붙는다. 휴지통에서 맨 위로
  되살릴 때도 같다.
- **`placeAt`**(A등급, `apps/api/src/pages/domain/tree.ts`) — 새 부모 아래 형제의 지금 순서(`{ id, position }`)와 옮기는 페이지, 번째(0부터)를
  받아 **옮긴 페이지의 새 자리 값**을 돌려준다. 옮기는 페이지가 목록에 있으면 먼저 뺀다(같은 부모 안에서 옮기기). 번째는 0과 형제 수 사이로 자른다.
  - 틈이 있으면 **옮긴 한 줄만** — 이웃 사이의 가운데, 맨 앞이면 첫 형제 − 간격, 맨 뒤면 마지막 + 간격.
  - 틈이 없으면(이웃이 붙었거나 같다 — 옛 API가 남긴 겹친 자리도) 또는 값이 한도(`PAGE_POSITION_LIMIT`, 2³⁰ — `integer` 열의 안쪽)를 넘으면
    형제 전체를 간격으로 다시 매긴 순서(`renumber`)를 함께 돌려준다.
  - 조회하지 않는다 — `checkMove`와 같은 판단.
- **트리 잠금**(`apps/api/src/pages/tree-lock.ts`의 `lockTree`) — 스페이스마다 `pg_advisory_xact_lock(hashtext('page-tree:<스페이스 id>'))`.
  잠금 모양은 이 저장소의 다른 줄 세우기와 같다(`users:last-root`, `llm:<사용자>`). **옮기기·만들기·지우기·휴지통 되살리기가 같이 쓴다**(FR-1503).
  기다림은 `lock_timeout`으로 `PAGE_TREE_LOCK_WAIT_MS`(2초)까지 — 넘으면(`55P03`) 409. 잠근 뒤에는 `lock_timeout`을 **원래 값으로** 되돌린다(같은
  트랜잭션의 다른 잠금은 평소대로 기다린다). 트랜잭션이 끝나면 풀린다 — **트랜잭션 밖에서 부르면 막는다**(잠금이 그 문장으로 끝나 줄 세우기가 오류
  없이 사라진다 — 반영분 점검 10).
- **네 길의 모양은 같다** — 대상을 읽고 → **권한을 본다**(권한 없는 사람은 줄에 서지 않는다 — 반영분 점검 12) → 잠근다 → **대상을 다시 읽는다**(기다리는
  사이 누가 지우거나 옮기거나 되살렸을 수 있다 — 반영분 점검 1. 두 번 누른 되살리기·지우기는 뒤의 것이 404) → **권한을 다시 본다**(기다리는 사이
  중지되거나 Crew에서 빠졌을 수 있다 — 병합 전 보안 검토 3) → 판정과 쓰기. 만들기는 본문의 글자 뽑기를 잠그기 전에 한다(잠금은 커밋까지 쥔다).
- **서비스**(`PagesService.move`) — 한 트랜잭션에서(NFR-140):
  1. 옮길 페이지를 읽고 쓰기 권한(`assertWrite`)을 본다.
  2. **트리 잠금.** 그리고 페이지를 **다시 읽고** 권한을 다시 본다 — "어디서"(감사)는 다시 읽은 자리다. 잠금이 부모 판정보다 먼저여야 X를 Y 아래로,
     Y를 X 아래로 동시에 옮길 때 뒤의 것이 앞의 결과를 보고 순환으로 거절된다(시험이 앞의 옮기기를 커밋 전에 붙잡아 둔다).
  3. 부모 판정(`checkMove` — 자기 아래, 깊이, 다른 스페이스는 없는 부모와 같은 404).
  4. 새 부모 아래의 형제(같은 스페이스, 지워지지 않은 것)를 화면과 같은 순서(`position`, 만든 시각)로 읽는다.
  5. `placeAt`. 옮긴 페이지는 부모·자리·고친 사람·시각을 고친다. 다시 매길 때는 **자리가 바뀐 형제만 한 문장으로** 고친다
     (`UPDATE … FROM (VALUES …)`) — 형제는 자리만 바뀌고 고친 사람·시각은 그대로다(형제를 "최근에 고친 문서"에 올리지 않는다).
  6. 감사 `page.move` — 어디서 어디로(FR-1516).
- 만들기는 잠근 뒤 맨 뒤 + 간격을 읽는다(동시에 만들어도 겹치지 않는다). 지우기는 잠근 뒤 자식을 센다(지우는 사이 그 아래로 옮겨 오는 것을
  막는다). 되살리기는 잠근 뒤 부모를 보고, **제자리가 깊이 10을 넘게 됐으면 맨 위로** 되살린다 — 지운 뒤 부모가 더 깊이 옮겨졌을 수 있다
  (옮기기의 깊이 판정은 지운 자식을 세지 않는다, 병합 전 코드 리뷰 7).
- 옛 부모 아래에 남은 형제는 그대로 둔다 — 자리에 틈이 생겨도 순서는 같다.

### D.2 화면 — 페이지 트리 (FR-1500·1501·1504·1505)

- **트리 펼치기**(`apps/web/src/components/pageTree.ts`, 순수 함수) — 서버가 준 목록(부모·자리 순서)을 들여쓰기 깊이와 함께 한 줄로 펼친다.
  "자기와 그 아래"를 구한다. 스페이스 화면의 트리, 위치 고르기, 옮기기 칸이 이것 하나를 쓴다.
- **스페이스 화면** — 트리는 **목록 안의 목록**이다(화면 낭독기가 단계를 읽는다 — 여백으로만 들이면 한 단계로 읽힌다). 새 페이지 칸에 **위치**
  (맨 위 / 들여 쓴 페이지 목록). 고르기 목록의 들여쓰기는 **줄바꿈 없는 공백**(U+00A0)이다 — 보통 공백은 `<option>`에서 접혀 깊이가 사라진다.
  안쪽 목록은 브라우저의 기본 들여쓰기(40px)를 없앤다 — 줄의 16px만 단계마다 더한다(더해지면 단계마다 56px라 깊은 페이지가 칸 밖으로 밀렸다 —
  반영분 점검 3). 주소의 `?parent=<페이지>`가 있으면 **그 값으로 온 때 한 번만**, **그 스페이스의 트리에 있을 때만** 골라 두고 제목 칸으로 간다 — 다시 읽을 때마다
  고르면 사람이 바꾼 위치가 되돌아가고, 없는 id를 받으면 칸은 "맨 위"를 보이면서 그 id를 보낸다. 고른 부모가 다시 읽은 트리에 없으면 맨 위로
  보이고 맨 위로 보낸다. 다시 읽기는 늦게 온 옛 응답을 버린다.
- **페이지 보기** — 쓸 수 있으면 **하위 페이지 만들기**(→ `/spaces/<스페이스>?parent=<이 페이지>`)와 **옮기기**.
  옮기기 칸(`apps/web/src/components/MovePage.tsx`)은 새 부모(맨 위 + 자기와 그 아래를 뺀 페이지들)와 자리(맨 앞 / "<형제> 다음")를 고르고
  `PATCH /api/pages/:id/move`를 부른다. 거절되면 서버의 까닭을 그 칸에 보인다. 옮기면 트리가 있는 스페이스 화면으로 간다. 부모가 목록에 없으면
  (그 사이 지워진 고아) 맨 위로 친다.

### D.3 화면 — 스페이스 관리 (FR-1510 ~ FR-1515)

- **스페이스 화면의 관리 칸**(`apps/web/src/components/SpaceManage.tsx`) — `access.canChangeStatus`면 이름·설명·분류(쓸 수 있을 때)와
  중지·다시 쓰기, `access.canDelete`면 지우기(확인 → `DELETE` → 스페이스 목록). 분류 목록은 칸이 보일 때만 `GET /api/categories`. 중지를 묻는 말은
  관리 콘솔과 같은 함수(`confirmSuspendText`) — 열어 둔 편집 창은 곧바로가 아니라 주기 재판정(`WF_COLLAB_RECHECK_MS`)이 끊는다고 말한다.
- **Crew** — 넣을 때 역할 고르기(editor·viewer), 줄마다 역할 고르기(`PATCH /api/spaces/:id/members/:userId`). owner 줄은 바꾸지 않는다.
- **관리 콘솔의 스페이스 화면**(`apps/web/src/pages/admin/AdminSpacesPage.tsx`) — 찾기 칸(입력을 멈추면 찾는다)·상태 고르기 →
  `GET /api/spaces?scope=all&q=&status=&limit=500`. 줄마다 이름(열기)·키·종류·상태·분류·Crew 수·만든 사람과 동작(중지·다시 쓰기, 중지된
  것은 지우기). 500개를 채우면 "찾기로 좁힌다"를 보인다. 아래에 분류 칸(만들기·이름 바꾸기·지우기 — 같은 이름이면 서버가 있던 것을 돌려주므로
  "이미 있다"고 말한다. 만들기는 앞의 것이 끝날 때까지 받지 않는다). 찾기는 늦게 온 옛 응답과 옛 실패를 버리고, 되면 **찾기의** 앞선 실패만
  지운다(분류 읽기·조치의 실패는 남긴다 — 반영분 점검 5). 분류 만들기는 서버에서 유일 제약에 맡긴다(`ON CONFLICT DO NOTHING` 뒤 있던 것을
  읽는다) — 먼저 찾고 넣으면 동시에 온 둘째가 유일 제약에 걸려 500이었다(FR-308의 멱등, 반영분 점검 11). 찾기 칸은 `LIST_SEARCH_MAX`자까지, 입력을 멈추고
  기다리는 시간은 사용자 관리와 같은 값(`apps/web/src/timing.ts`)이다.
- **스페이스 목록 화면**의 관리 메뉴에 **스페이스 관리**(`space.manage`일 때).

### D.4 서버 — 모든 스페이스의 찾기 (FR-1514)

`spaceListQueryDto`에 `q`(앞뒤 공백을 자른 1~`LIST_SEARCH_MAX`자 — 사용자 찾기와 같은 상수)와 `status`를 더한다. `q`는 이름·키의 `ILIKE` 부분
일치 — `%`·`_`는 `apps/api/src/common/like.ts`로 막는다(P13 사용자 찾기와 같다). 두 조건은 어느 범위(`scope`)에서나 먹는다. `scope=all`은
`space.manage`만 부르고 그 사람에게는 모두 읽을 수 있으므로 **SQL에서 자른 뒤** 줄마다 보기를 만든다 — 자르기 전에 만들면 스페이스마다 질의 서넛이
한꺼번에 연결 풀로 몰린다(병합 전 코드 리뷰 3). **보기는 줄 수와 무관하게 질의 넷으로 만든다**(`toViews` — 내 자리·Crew 수·만든 사람·분류). SQL에서
자르는 것만으로는 500개 안의 흔한 경우(300명의 개인 스페이스)를 줄이지 못했다(반영분 점검 8).
