# 학습가이드 — 이 시스템 이해하기

- 읽는 사람: **개발을 하지 않는 시스템 담당자와 소유자.** 개발 용어를 쓰지 않거나, 쓰면 그 자리에서 풀어 쓴다
- 갱신: **매 Phase 필수** (`CLAUDE.md` 1.1절 6단계). Phase가 끝나면 그 Phase에서 할 수 있게 된 일을 이 문서에 더한다
- 현재 반영 범위: **Phase 0까지**
- 작성일: 2026-09-16 / 작성 LLM: Claude Opus 5

> 이 문서는 "이게 어떻게 돌아가는가"를 설명한다. 무엇을 왜 만드는지는 [`docs/scope-definition.md`](scope-definition.md), 문제가 났을 때는 [`docs/운영가이드_장애대응.md`](운영가이드_장애대응.md)를 본다.

## 1. 이 시스템은 무엇인가

사내에서 쓰는 **문서 협업 도구**다. 부서나 팀마다 공간을 만들고, 그 안에 문서를 폴더처럼 겹쳐 쌓고, 여러 사람이 같이 고친다. 상업 제품 Confluence가 하는 일과 같고, 그것을 우리가 직접 만드는 이유는 인터넷이 닿지 않는 망 안에서 돌려야 하기 때문이다.

인터넷이 없다는 제약이 이 시스템의 거의 모든 설계를 결정했다. 바깥에서 글꼴 하나, 아이콘 하나를 받아 오는 코드가 있으면 그 화면은 망 안에서 깨진다. 그래서 필요한 모든 것을 미리 한 덩어리로 묶어 들고 들어간다.

## 2. 세 덩어리로 되어 있다

| 덩어리 | 하는 일 | 비유 |
|---|---|---|
| **화면** | 사람이 보고 누르는 부분 | 가게의 매장 |
| **서버** | 요청을 받아 판단하고 답하는 부분 | 가게의 주방과 계산대 |
| **데이터베이스** | 문서·계정·기록을 실제로 담아 두는 부분 | 가게의 창고 |

여기에 **앞잡이** 하나가 더 있다. 바깥에서 들어오는 접속을 먼저 받아 암호화를 풀고 서버로 넘기는 역할이다. 이름은 nginx이고, 문 앞의 안내 데스크에 해당한다.

중요한 점이 하나 있다. 화면과 서버가 **한 프로그램으로 합쳐져** 있다. 따로 두면 옮겨야 할 덩어리가 하나 늘고, "어느 쪽이 문제인가"를 가릴 일이 늘기 때문이다. 그래서 운영에서 돌아가는 것은 세 개다. 프로그램 하나, 데이터베이스 하나, 안내 데스크 하나.

## 3. 어디서 무엇을 하는가

이 프로젝트는 장소가 두 곳이라는 점이 조금 특이하다. 헷갈리기 쉬운 부분이라 먼저 정리한다.

| 장소 | 하는 일 | 왜 나눠져 있나 |
|---|---|---|
| **작업 서버** (사내 Linux) | 코드를 쓰고 시험하고, **한 덩어리로 묶는다** | 인터넷이 되는 곳이라야 부품을 받아 묶을 수 있다 |
| **폐쇄망** | 묶인 덩어리를 받아 실제로 돌린다 | 인터넷이 없다. 받아서 켜는 것만 가능하다 |

2026-09-21까지는 장소가 세 곳이었다. 코드를 쓰는 곳(Windows PC)과 묶는 곳(Linux 서버)이 따로였는데, 둘을 합쳤다. 오가는 단계가 하나 줄었다.

한 덩어리로 묶은 것을 **이미지**라고 부른다. 짐을 싸서 봉인한 상자로 생각하면 된다. 상자 안에는 프로그램과 그것이 필요로 하는 부품이 전부 들어 있다. 폐쇄망에서는 상자를 풀지 않고 그대로 켠다. 그래서 "우리 PC에서는 되는데 저쪽에서는 안 된다"는 일이 줄어든다.

코드가 이동하는 경로는 이렇다. 작업 서버에서 GitHub으로 올리고, 같은 서버가 그것을 받아 상자를 만들고, 그 상자를 파일 하나로 뽑아 폐쇄망으로 들여간다.

> 같은 서버에서 쓰고 묶는데도 **GitHub을 거치는 이유**가 있다. 묶을 때는 "내 작업 폴더에 지금 있는 것"이 아니라 **올려서 남긴 것**을 받아서 묶는다. 그래야 나중에 "그 상자가 어느 코드로 만들어졌나"를 되짚을 수 있다.

## 4. Phase 0에서 만든 것 — 왜 기능이 없는가

지금까지 만든 것을 켜면 화면에 나오는 것은 **"잘 살아 있습니다"라는 확인 화면 하나**다. 로그인도 없고 문서도 없다. 일부러 그렇게 했다.

집을 지을 때 방부터 만들지 않는다. 터를 다지고 상하수도와 전기를 먼저 넣는다. 나중에 넣으려면 벽을 뚫어야 하기 때문이다. Phase 0에서 넣은 "상하수도"는 이런 것들이다.

| 만든 것 | 왜 먼저 만들었나 |
|---|---|
| 설정을 읽는 방식 | 나중에 각 기능이 제멋대로 설정을 읽으면 어디를 고쳐야 하는지 아무도 모른다 |
| 누가 무엇을 할 수 있는지 판단하는 규칙 | 화면과 서버가 따로 판단하면 **버튼은 보이는데 누르면 거부당하는** 일이 생긴다 |
| 기록을 남기는 방식 | 나중에 붙이면 그 전에 일어난 일은 영원히 기록이 없다 |
| 데이터베이스 구조를 바꾸는 절차 | 운영 중에 구조를 바꾸는 일은 되돌리기 어렵다. 절차를 먼저 정해 둔다 |
| **폐쇄망까지 들어가는 경로 전체** | 이것이 가장 중요하다. 다 만들고 나서 "안 들어간다"를 알면 설계를 뒤집어야 한다 |

그래서 Phase 0이 끝났다고 말할 수 있는 조건은 문서가 아니라 **Linux 서버에서 만든 상자를 켜서 "살아 있습니다"라는 답을 받는 것**이다. 이 조건이 아직 안 끝났다.

## 5. 직접 확인해 보기

명령을 그대로 복사해 붙여 넣으면 된다. 터미널 두 개를 쓴다.

**첫 번째 터미널** — 데이터 창고를 켠다. 처음 켤 때는 창고를 만드는 데 시간이 조금 걸린다.

```bash
pnpm dev:db
```

`READY`라고 나오면 켜진 것이다. **이 창은 닫지 말고 그대로 둔다.** 끝낼 때는 그 창에서 Ctrl+C를 누른다. 창을 그냥 닫으면 창고가 잠긴 채로 남는데, 다음에 켤 때 프로그램이 알아서 정리한다.

**두 번째 터미널** — 준비 상태를 확인한다.

```bash
pnpm check:env
```

마지막 줄에 `READY`가 나오면 준비가 끝났다는 뜻이다. 그 위의 줄들은 하나하나 무엇을 확인했는지 보여준다. 어딘가 `FAIL`이 있으면 그 줄이 문제를 말해 준다.

이어서 프로그램을 켜고 브라우저로 본다.

```bash
pnpm build
pnpm start
```

브라우저에서 `http://127.0.0.1:3000` 으로 들어간다. 화면에 API와 데이터베이스가 각각 `ok`로 보이면 세 덩어리가 서로 붙어 있다는 뜻이다.

숫자로 보고 싶으면 이렇게도 물어볼 수 있다.

```bash
curl http://127.0.0.1:3000/api/health
```

`{"status":"ok","db":"ok",...}` 라고 답하면 정상이다. `db`가 `ok`가 아니면 창고가 안 켜진 것이다.

## 6. 알아 두면 좋은 판단 몇 가지

이 시스템에는 "일부러 불편하게 만든" 곳이 몇 군데 있다. 나중에 "왜 이렇게 되어 있나" 싶을 때 여기를 보면 된다.

**설정에 모르는 항목이 있으면 프로그램이 아예 켜지지 않는다.** 보통은 모르는 설정을 무시하고 켜진다. 그런데 그러면 설정 이름을 한 글자 틀렸을 때 프로그램은 잘 켜지고 그 설정만 조용히 무시된다. 값을 바꿨는데 아무 일도 안 일어나는 상태가 가장 찾기 어렵다. 그래서 차라리 켜지지 않게 했다.

**"살아 있습니까"라고 물으면 창고까지 확인하고 답한다.** 프로그램만 살아 있고 창고가 죽은 상태는 꽤 흔한 고장이다. 이때 "살아 있다"고 답하면 자동 복구 장치가 아무 일도 하지 않는다.

**데이터베이스 구조 변경은 켤 때 자동으로 되지 않는다.** 운영에서는 사람이 따로 명령을 내려야 바뀐다. 자동이면 프로그램을 다시 켜는 순간 데이터 구조가 바뀌고, 그건 되돌리기 어렵다.

**기록은 지울 수 없게 되어 있다.** 누가 언제 무엇을 했는지를 남기는 기록은 프로그램으로도, 데이터베이스 명령으로도 수정과 삭제가 막혀 있다. 고칠 수 있는 기록은 증거가 되지 않는다.

**비밀번호는 8자 이상, 두 종류 조합이다.** 더 길고 복잡하게 할 수도 있지만 그러면 사람들이 메모지에 적어 둔다. 사내망 안에서만 닿는 시스템이라 그 편이 더 위험하다고 판단했다.

## 7. 앞으로 무엇이 생기는가

| 다음 단계 | 그때 할 수 있게 되는 일 |
|---|---|
| Phase 1 | 로그인. 가입을 요청하면 관리자가 승인하고, 사내 인증 시스템 계정으로도 들어올 수 있다 |
| Phase 2 | 공간을 만들고 문서를 쓴다. 고친 이력이 남고 이전 내용으로 되돌릴 수 있다 |
| Phase 3 | 한글로 검색한다. 파일을 붙이고 댓글을 단다 |
| Phase 4 | 관리 화면. 누가 무엇을 볼 수 있는지 조절하고, 지운 문서를 되살린다 |
| Phase 5 | 폐쇄망에 실제로 들여가는 연습. 백업에서 되살리는 연습 |
| Phase 6 | 두 사람이 같은 문서를 동시에 고치기 |

새 기능이 필요해지면 [`docs/기능백로그.md`](기능백로그.md)에 적는다. 말씀하시면 제가 적고, 그 기능이 어느 단계의 일이고 얼마나 큰지 알려 드린다. 순서를 정하는 것은 소유자다.
