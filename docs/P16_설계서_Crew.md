# P16 설계서 — Crew (관리자가 건 중지 동안 Crew를 얼린다)

Phase 16은 보류 35를 사용자의 답으로 닫는다. 관리자가 조사하려고 공간을 멈춰 둔 동안에도 주인은 Crew에 사람을 더해 읽을 사람을 넓힐 수 있었다(Phase 15 전부터 —
Crew 관리는 공간의 상태를 보지 않았다). 이제 **관리자가 건 중지 동안에는 주인이 Crew를 바꾸지 못한다.**

## A.1 묻지 않고 정한 것 — 근거와 되돌릴 조건

| # | 정한 것 | 근거 | 되돌릴 조건 |
|---|---|---|---|
| 1 | **판정은 `spaceAccess.canManageMembers` 한 곳**이다 — 팀 공간에서 `admin || (isOwner && !관리자가 건 중지)` | 서버의 Crew 관리 셋(`assertManage`)과 화면의 Crew 칸(넣기 칸·자리 고르기·제거)이 이미 그 값 하나를 본다. 한 곳을 바꾸면 둘이 함께 따라온다(`CLAUDE.md` 7절 "판정은 한 곳") | — |
| 2 | **스스로 풀 수 있는 주인도**("관리자가 건 중지 풀기"나 "스페이스 관리 전체"를 받았다) 관리자가 건 중지 동안에는 Crew를 바꾸지 못한다 — 먼저 다시 쓰기로 푼다. 풀고 바꾼 뒤 다시 멈추면 주인이 건 중지가 된다(P15 A.1-12 — 그 권한을 준 것이 그 믿음이다. 감사에 모두 남는다) | 얼리는 것은 중지의 상태다. 풀 권한이 있으면 풀고 나서 바꾸면 된다. 권한마다 예외를 두면 "얼었는지"를 한 번에 알 수 없다 | — |
| 3 | 막힌 주인에게는 **까닭을 말한다** — 서버는 403 "관리자가 중지한 스페이스다 — Crew는 관리자가 바꾼다", 화면의 Crew 칸은 넣기 칸 대신 안내 한 줄을 보인다(G) | 단추만 사라지면 권한을 잃은 줄 안다(P15 FR-1612와 같은 원칙) | — |
| 4 | Crew **목록 보기**는 막지 않는다 | 읽기는 중지와 무관하다(중지는 읽기만 되는 상태다) | — |
| 5 | **Crew 쓰기도 판정한 상태에서만 한다** — 넣기·자리 바꾸기·빼기는 **판정하고, 공간 행을 잠그고(`FOR NO KEY UPDATE`), 다시 판정한 뒤** 쓴다. 공간 행을 고치는 일(상태 바꾸기·넘겨받기·지우기·이름·설명·분류 바꾸기, 분류 지우기가 공간을 분류 없음으로 만드는 것, 휴지통 되살리기)과 같은 공간의 다른 Crew 변경은 그 트랜잭션이 끝날 때까지 기다리고, 먼저 와 있던 것은 Crew 쪽이 기다렸다가 새 상태로 판정한다. 권한 없는 사람은 잠그기 전에 거절된다 — 줄에 서지 않는다. 늘 트랜잭션 안에서 한다(받은 트랜잭션 안이면 저장점) — 잠금이 쓰기의 커밋까지 간다 | Crew를 바꿀 수 있는지가 이제 공간의 상태·건 사람에 달린다. 잠그지 않으면 관리자의 중지가 커밋되는 사이 주인의 넣기가 들어가고(외래 키 검사의 `FOR KEY SHARE`는 상태 고치기와 부딪히지 않는다), 관리자가 얼린 뒤 뺀 사람을 주인의 늦은 요청이 되돌리는 순서도 있었다(병합 전 검토 셋 — T-072). P15의 조건부 쓰기(A.1-14)는 **같은 행**을 고칠 때 통한다 — Crew 쓰기는 다른 표에 쓰므로 조건만으로는 커밋 전의 중지를 보지 못한다. 둘째 판은 판정 전에 나눔 잠금(`FOR SHARE`)을 잡았다 — 공간 id만 아는 사람도 줄에 섰고, 나눔 잠금은 나눔 잠금만 걸린 행에 새 나눔 잠금을 기다림 없이 주어 기다리는 상태 바꾸기가 끝없이 밀릴 수 있었다(좁은 재점검 — T-073). 배타 잠금은 온 순서대로 줄을 서고, 페이지 만들기의 외래 키 검사(`FOR KEY SHARE`)와는 부딪히지 않는다. 페이지 트리·분류의 "권한 없는 사람은 줄에 서지 않는다"와 같은 모양이다 | — |
| 6 | **얼었는지는 판정이 말한다** — `spaceAccess`가 `crewFrozen`(주인인데 관리자가 건 중지라 Crew를 바꾸지 못한다)을 돌려준다. 서버의 거절 까닭과 화면의 안내가 이 값 하나를 본다 | "주인인데 `canManageMembers`가 거짓이면 얼었다"를 서버와 화면이 따로 짐작하면, 막는 까닭이 하나 더 생길 때 둘 다 조용히 틀린 까닭을 말한다(병합 전 코드 리뷰). `CLAUDE.md` 7절 "판정은 한 곳" | — |
| 7 | 화면에서 Crew를 바꾸다 **거절되면 지금 상태를 다시 읽는다** — 까닭은 남긴다 | 화면을 연 사이 관리자가 중지하면 옛 화면이 넣기 칸을 계속 보여 같은 403을 되풀이했다(병합 전 검토). P15 관리 칸의 "거절되면 다시 읽는다"와 같은 원칙이다 | — |
| 8 | **스스로 풀 수 있는 주인에게는 관리자에게 부탁하라고 하지 않는다** — "아래 관리 칸의 다시 쓰기로 먼저 풀면 바꾼다"를 보인다(G). 카드의 머리글은 **관리**다 — 첫 판은 "스페이스 관리의 다시 쓰기"라고 해 그 주인이 화면에서 찾을 수 없는 이름을 댔다(스페이스 관리는 카드의 보이지 않는 이름이고, 보이는 "스페이스 관리"는 관리 콘솔이다 — 좁은 재점검) | 할 수 있는 일을 가리지 않는다(A.1-2) | — |

## D. 설계

- **`spaceAccess`**(A등급, `packages/shared/src/permissions.ts`) — 팀 공간의 `canManageMembers`를 `admin || (isOwner && !adminSuspended)`로 한다.
  `adminSuspended`는 `status === 'suspended' && suspendedByOwner !== true`다(모르면 관리자가 건 것 — `canResume`과 같은 값 `ownerSuspended`를 본다, P15 D.2).
  **`crewFrozen`** = `!admin && isOwner && adminSuspended`(A.1-6). 개인 공간은 둘 다 `false`다(Crew가 없다).
- **서버**(`apps/api/src/spaces/spaces.service.ts`) — Crew 관리 셋(`addMember`·`changeMemberRole`·`removeMember`)은 `manageMembers` 한 길로 간다: `assertManage`로
  판정하고, 공간 행을 `FOR NO KEY UPDATE`로 잠그고(A.1-5 — 늘 트랜잭션 안에서, 받은 트랜잭션 안이면 저장점), 다시 판정한 뒤 쓴다. `assertManage`는 `crewFrozen`이면 까닭을 나눠 말한다(A.1-3).
  데이터·마이그레이션은 없다.
- **화면**(`apps/web/src/pages/SpacePage.tsx`) — Crew 칸은 이미 `access.canManageMembers`로 넣기 칸·자리 고르기·제거를 보인다. `crewFrozen`이면 안내 한 줄을
  더하고(G), 거절되면 다시 읽는다(A.1-7).

## F. API 계약

| 경로 | 바뀜 |
|---|---|
| `POST /api/spaces/:id/members` · `PATCH`·`DELETE /api/spaces/:id/members/:userId` | 관리자가 건 중지 동안 주인은 403(관리자는 된다). 판정하고 공간 행을 잠근 뒤 다시 판정한다 |

## G. 화면 — Crew 칸의 네 모양

| 누가·언제 | Crew 칸 |
|---|---|
| Crew를 바꿀 수 있다(관리자, 활성이거나 주인이 건 중지의 주인) | 줄마다 자리 고르기·**제거**, 아래에 **아이디로 Crew 추가** — 지금과 같다 |
| 관리자가 건 중지의 주인 | 목록만. 안내 "관리자가 중지한 스페이스라 Crew를 바꾸지 못한다 — 관리자에게 부탁한다. 다시 쓰게 되면 주인도 바꾼다." |
| 관리자가 건 중지의 주인인데 스스로 풀 수 있다(`canChangeStatus`) | 목록만. 안내 "관리자가 중지한 스페이스라 Crew를 바꾸지 못한다 — 아래 관리 칸의 다시 쓰기로 먼저 풀면 바꾼다." |
| 주인이 아니다(editor·viewer) | 목록만, 안내 없음 — 원래 바꾸지 않는다 |

Crew를 바꾸다 거절되면(화면을 연 사이 관리자가 중지했다) 위쪽에 서버의 까닭이 남고, 화면이 스페이스를 다시 읽어 칸이 위의 모양으로 바뀐다.

## K. 구현 순서

1. A등급 Red → Green — `spaceAccess.canManageMembers`
2. 서버 — 막힌 주인의 까닭(통합 시험 — 넣기·자리 바꾸기·빼기 셋, 관리자, 주인이 건 중지, 다시 쓰게 한 뒤)
3. 화면 — Crew 칸의 안내(컴포넌트 시험). E2E의 "관리자가 건 중지" 흐름에 Crew 칸을 더한다
4. 문서 — 사용자 가이드·학습가이드·장애대응·운영이관·범위·규칙서, 검증기록
5. 병합 전 검토 반영 — A등급 Red(`crewFrozen`·판정의 빈칸) → Green, Crew 쓰기의 잠금(통합 시험 — 앞의 일을 붙잡아 두고), 화면(안내 둘·거절 뒤 다시 읽기),
   E2E(권한을 받은 뒤의 안내, T-071의 원인)
6. 반영분의 좁은 재점검 반영 — 판정 → 잠금 → 다시 판정(`FOR NO KEY UPDATE`, 통합 시험 둘 — 줄에 서지 않는다·Crew 변경끼리 한 줄), 화면 문구(관리 칸), 문서의 전제
