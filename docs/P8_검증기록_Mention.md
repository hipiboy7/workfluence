## 2. 실측 — Yjs가 보여 주는 것

설계의 전제를 코드보다 먼저 실측했다. 전부 `node -e`로 yjs를 직접 불렀다.

**① 자기 오타 수정과 남의 삭제는 구조만으로는 같다.** 구조를 보고 "누가 만들었나"를 추론하는 방식이 틀리는 까닭이다.

```
자기 오타:  777:@kim | ~777:Deleted | 777: 확인      ("@kimm" → 지움 → " 확인")
남이 지움:  504:@kim | ~504:Deleted | 504: 확인      ("@kim.lee 확인" → B가 ".lee" 삭제)
```

**② 보류 위조는 "보낸 것보다 더 바뀐다"로 드러난다.**

```
B가 보낸 위조(A의 ID)   A:10..17  → 들어간 것 없음 (보류)
A가 보낸 것            A:5..10   → 들어간 것 A:5..17    서버 글 "hello 안녕하세 @carol"
```

위조 **삭제**도 같다 — 지울 글자가 아직 없는 삭제 집합은 보류됐다가, 주인의 변경이 그 글자를 넣는 트랜잭션에서
지운다(통합 테스트로 재현, 4.5절). 주인이 보낸 변경에는 그 삭제가 없다.

**③ 화면은 보류분을 끼우지 않는다.** 위조를 전달받은 화면 문서에서 로컬로 다섯 글자를 쳐도 보류가 그대로 남고, 보낸 구간은
`5..10`이다. 화면은 받은 변경을 되돌려 보내지도 않는다(`CollabEditor.tsx` — `origin === 'remote'`는 보내지 않는다).
그래서 정상 사용에서는 **변경이 보낸 것만큼만 문서를 바꾼다** — `isFaithful`이 기대는 사실이다.

**④ 서식·재전송은 글자를 바꾸지 않는다.** 다른 클라이언트가 `@bob`에 굵게를 걸어도 `@bob` 글자는 그대로고, 화면이 접속
직후 보내는 전체 상태는 `update` 이벤트를 내지 않는다.

**⑤ 변경마다 멘션 자리를 훑는 비용.** 500문단·61,390자·멘션 1,000개 문서에서 **한 번에 2.76ms**(100회 평균).
보통 문서(수천 자)는 0.3ms 안쪽이다.

## 4. 실제로 동작시켜 확인한 것

### 4.1 브라우저 — 인수 흐름 (`e2e/collab.spec.ts` 3번째)

두 브라우저 문맥에서 A(관리자)가 `@동료아이디 확인부탁…`을 치고, **유휴 저장이 끼기 전에** B(동료)가 끝에 ` B가덧붙임`을 친다.
9초 뒤 B의 알림함 첫 항목의 굵은 이름이 `E2E 관리자`다. 셋째 판(`0f5a36a`)에서 다시 돌려 통과했다.

첫 실행 때 그 실행의 감사로그를 DB에서 따로 읽어, 이 시험이 정말 "B가 마지막 작성자"인 상태를 만드는지 확인했다:

```
page.create       actor 7686319e   (A)
page.collab.save  actor bdca1be6   trigger idle   (B)
```

저장은 한 번이고 그 작성자는 B다 — **옛 코드였으면 B 자신의 이름이 떴을 상황**이다. 실제 편집기(y-prosemirror)가 한 글자씩
만드는 변경 모양에서 셋째 판이 A를 적는다는 뜻이기도 하다. E2E 전체를 돌리는 동안 호스트 api 로그에
`변경이 보낸 것보다 문서를 더 바꿨다` 경고는 **0건**이었다.

### 4.2 컨테이너 — 인수 시나리오 (`workfluence-app:0f5a36a-p8`)

api 컨테이너 안에서 WebSocket 클라이언트 둘로 같은 흐름을 돌렸다(Origin·세션 쿠키로 정상 업그레이드).

```
A가 부름: @p8b-1790230231029
B가 마지막으로 고침
자동 저장 1 회 · 저장 작성자 = B
B의 알림함: [{"actorName":"P8 부른사람","pageTitle":"P8 확인"}]
✅ "P8 부른사람 님이 불렀다" — 마지막 작성자(B)가 아니다
```

### 4.3 컨테이너 — 재기동을 넘는가 (FR-903, 사용자 결정)

A가 멘션과 **저장할 수 없는 노드**를 함께 넣어 버전은 생기지 않고 상태만 남게 한 뒤, `docker restart workfluence-api`.
재기동한 서버에 B가 붙어 그 노드를 **지우기만** 했다(새 멘션 없음).

```
A가 부름 + 깨진 노드. 저장 버튼 → {"saved":false,"reason":"문서 검증 실패 (1건)","currentVersionNo":1}
page_realtime 남음: true · @p8rb-1790230241109 을 만든 사람 → A
정본 버전 1 (1이면 버전이 안 생겼다)
--- docker restart 뒤 (1초)
재기동 뒤 B가 받은 블록: paragraph,paragraph,script
자동 저장 1 회 · 저장 작성자 = B
B의 알림함: [{"actorName":"P8 재기동 부른사람"}]
✅ 재기동을 넘어 "P8 재기동 부른사람 님이 불렀다"
```

표가 남지 않았으면 방을 다시 만들 때 그 멘션은 "모름"이 됐다. 두 컨테이너 확인 동안 **경고 0건**이었다.
확인용 계정·페이지는 스크립트가 끝에 지웠다(감사로그는 append-only라 남는다).

### 4.4 변이 시험 — 테스트가 정말 그 규칙을 잡는가

셋째 판의 규칙을 하나씩 일부러 끄고 해당 테스트가 실패하는지 봤다. 끈 뒤에는 되돌렸다.

| 끈 규칙 | 실패한 테스트 |
|---|---|
| 변경을 늘 믿는다 (`isFaithful` 무시) | 보류 조각 위조 · 보류 삭제 위조 **2건** |
| 삭제는 보지 않는다 | 보류 삭제 위조 1건 |
| 옮긴 것을 가리지 않는다 | 남의 문단을 제목으로 1건 |
| 있던 자리도 새로 적는다 | **4건** — 인수 기준·서식 걸었다 풀기·조사 붙이기·재기동 |
| 재기동 때 표를 잇지 않는다 | 재기동 1건 |

첫 판·둘째 판에서도 같은 시험을 했다(각 3종·5종, 전부 잡혔다). 규칙이 테스트에 잡힌다는 것과 **규칙이 옳다는 것은 다르다**는 것을
두 번째 검토가 보여 줬다 — 둘째 판의 다섯 규칙은 전부 테스트에 잡혔지만 우회 셋이 남아 있었다.

### 4.5 통합 테스트가 확인한 것 (게이트웨이를 실제로 탄다)

사람마다 화면처럼 문서 하나를 두고, 방에서 받은 것은 되돌려 보내지 않으며, 자기 트랜잭션 하나씩만 보낸다.

| 경우 | 부른 사람 |
|---|---|
| **인수 기준** — A가 `@B`, B가 접속 직후 전체 상태를 보내고 다른 문단을 고침 | **A** (메일 이름·메일 감사 actor도 A) |
| 남의 글 뒤에 이어 부름 | 부른 사람 |
| 자기 오타를 지우고 이어 침 | 부른 사람 |
| **정본 글자를 지우고 그 자리에 부름** (두 번째 검토 4) | 부른 사람 |
| **남이 서식을 걸었다 풂** (두 번째 검토 6) | 부른 사람 |
| 남이 바로 뒤에 조사를 붙임 | 부른 사람 |
| 자기 문단을 자기가 제목으로 | 부른 사람 |
| 남이 글자를 지워 새 이름을 만듦 (`@collab-cx` → `@collab-c`) | **지운 사람** |
| 남이 앞글자를 지워 멘션으로 만듦 | 지운 사람 |
| 남이 경계에 공백을 끼움 | 끼운 사람 |
| 남이 이름을 가름 | 가른 사람 |
| 둘이 나눠 침 (A `@collab-`, B `c`) | **B** — 그 입력이 `@collab-c`를 만들었다 |
| **남의 문단을 제목으로 바꿈** (두 번째 검토 5) | **모름** |
| 남의 클라이언트 ID로 보냄 | **보낸 사람** — 이름은 연결이 정한다 |
| **보류된 위조 조각**이 주인의 변경에 묻어 들어옴 | **모름** + 경고 |
| **보류된 위조 삭제**가 주인의 변경을 지움 (두 번째 검토 1) | **모름** |
| 옛 문서를 통째로 다시 보냄 | 보낸 사람 |
| 표가 `page_realtime`에 남고 새 게이트웨이가 잇는다 | 부른 사람 |

그 밖에: 알림 목록이 부른 사람 없는 알림을 버리지 않는다(`leftJoin`), 스스로 부른 곳이 앞에 있어도 남이 부른 곳이 있으면
알림이 간다, 메일은 받는 사람별 이름 → 기본 이름 → 이름 없음 순서로 고르고 감사에 일으킨 사람을 남긴다, 새 페이지도 부른
사람들을 호출부에 넘긴다(메일).

## 9. 확인하지 못한 것

- **셋째 판에 검토를 한 번 더 돌리지 않았다.** 셋째 판은 두 번째 묶음의 지적을 받아 새로 쓴 것이다. 규칙이 줄었고 믿는 것이
  "인증된 연결" 하나라 앞의 두 판보다 공격면이 좁다고 판단했지만, **독립 검토로 확인한 것은 아니다.**
- **조작한 클라이언트로 공격을 실제 WebSocket 너머에서 재현하지 않았다.** 공격은 게이트웨이 안쪽(가짜 소켓 + 실제 yjs)으로
  확인했다. 컨테이너 확인은 정상 클라이언트 둘이다.
- **실제 사용에서 "모름"이 얼마나 나오는지 모른다.** 반입 뒤 알림 중 `actor_id IS NULL`의 비율로 잰다 —
  `SELECT count(*) FILTER (WHERE actor_id IS NULL), count(*) FROM notifications`.
- **편집기의 복잡한 조작을 E2E로 돌리지 않았다** — 목록·표 안의 멘션, 붙여 넣기, 되돌리기(undo). 붙여 넣은 사람은 그 안의
  멘션을 만든 사람이 되고, 되돌리기로 되살아난 멘션은 되돌린 사람이 만든 것이 된다 — 규칙에서 따라 나오는 결과이고 실측은 없다.
- **표의 실제 크기.** 지금 문서의 멘션 자리 수만큼이지만 동시 편집자가 많은 방에서 재지 않았다. 보류 19와 함께 잰다.
- 화면의 "문서에서 불렸다" 분기에 **컴포넌트 테스트가 없다**(web은 테스트 파일 0개, 3절이 관문을 두지 않는다). API 쪽
  `actorName: null`은 통합 테스트가 단언한다.
- **메일은 여전히 모의 발송이다** (보류 18). 받는 사람별 이름이 실제 메일 API에서 어떻게 보이는지는 확인하지 못했다.
