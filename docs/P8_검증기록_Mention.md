## 2. 실측 — Yjs가 보여 주는 것

설계의 전제를 코드보다 먼저 실측했다. 전부 yjs를 직접 불렀다.

**① 자기 오타 수정과 남의 삭제는 구조만으로는 같다.** 구조를 보고 "누가 만들었나"를 추론하는 방식(첫·둘째 판)이 틀리는 까닭이다.

```
자기 오타:  777:@kim | ~777:Deleted | 777: 확인      ("@kimm" → 지움 → " 확인")
남이 지움:  504:@kim | ~504:Deleted | 504: 확인      ("@kim.lee 확인" → B가 ".lee" 삭제)
```

**② 보류 위조는 "보낸 것보다 더 바뀐다"로 드러난다.**

```
B가 보낸 위조(A의 ID)   A:10..17  → 들어간 것 없음 (보류)
A가 보낸 것            A:5..10   → 들어간 것 A:5..17    서버 글 "hello 안녕하세 @carol"
```

위조 **삭제**도 같다 — 지울 글자가 아직 없는 삭제 집합은 보류됐다가, 주인의 변경이 그 글자를 넣는 트랜잭션에서 지운다
(통합 테스트로 재현, 4.5절). 주인이 보낸 변경에는 그 삭제가 없다.

**③ 화면은 보류분을 끼우지 않는다.** 위조를 전달받은 화면 문서에서 로컬로 다섯 글자를 쳐도 보류가 그대로 남고, 보낸 구간은
`5..10`이다. 화면은 받은 변경을 되돌려 보내지도 않는다(`CollabEditor.tsx` — `origin === 'remote'`는 보내지 않는다).

**④ 동시 편집에서 Yjs가 스스로 지우는 것** (넷째 판의 "설명되는 삭제"가 기대는 사실).

```
(1) X가 문단에 치는 동안 U가 그 문단을 지운다 (U는 X의 새 글자를 모른다)
    U가 보낸 삭제: 750:0x4
    [origin=U] deleted=[750:0 Type(root) | 750:1 Type(parent 750:0) | 750:2x2 String(parent 750:1) | 901:0x4 String(parent 750:1)]
    → X의 글자(901:0x4)는 U가 보내지 않았지만, 부모(750:1)의 삭제는 U가 보낸 것이다
(2) 반대 순서 — 이미 지워진 문단 안으로 X의 글자가 들어온다
    [origin=X] integrated=977:0..4 deleted=[]          → 삭제로 나타나지 않는다(부모가 GC돼 GC 조각으로 들어온다)
(3) 둘이 같은 속성을 동시에 바꾼다
    [origin=U] integrated=303:0..1 deleted=[303:0x1 [map] ...]   → 진 쪽 값은 속성 값(맵 항목)이다
```

**⑤ 변경마다 멘션 자리를 훑는 비용** (실제 코드 `mentionSites` + `scanMentions`, 100회 평균).

| 구조 | 글자 | 자리 | 한 번 |
|---|---|---|---|
| 500문단 | 61,890 | 1,000 | 3.84ms |
| 한 문단에 몰아서 | 60,000 | 1,000 | 3.50ms |
| 두 클라이언트가 번갈아 친 잘게 쪼개진 조각 | 45,000 | 1,500 | 3.34ms |

세 번째 `self-reviewer`는 같은 규모에서 4.2~6.0ms를 쟀다(측정자·시각에 따라 다르다). 보통 문서(수천 자)는 0.3ms 안쪽이다.

## 4. 실제로 동작시켜 확인한 것

### 4.1 브라우저 — 인수 흐름 (`e2e/collab.spec.ts` 3번째)

두 브라우저 문맥에서 A(관리자)가 `@동료아이디 확인부탁…`을 치고, **유휴 저장이 끼기 전에** B(동료)가 끝에 ` B가덧붙임`을 친다.
9초 뒤 B의 알림함 첫 항목의 굵은 이름이 `E2E 관리자`다. 병합 후보(`a1d1c5e`)에서 다시 돌려 통과했다 — **실제 편집기(y-prosemirror)가
한 글자씩 만드는 변경 모양이 넷째 판의 세 조건(믿을 수 있는 변경·자기 클라이언트의 글자·옮김 아님)을 모두 지난다**는 뜻이다.

첫 실행 때 그 실행의 감사로그를 DB에서 따로 읽어, 이 시험이 정말 "B가 마지막 작성자"인 상태를 만드는지 확인했다:

```
page.create       actor 7686319e   (A)
page.collab.save  actor bdca1be6   trigger idle   (B)
```

저장은 한 번이고 그 작성자는 B다 — **옛 코드였으면 B 자신의 이름이 떴을 상황**이다. E2E 전체를 돌리는 동안 호스트 api 로그에
`변경이 보낸 것보다 문서를 더 바꿨다` 경고와 `멘션 장부를 고치지 못했다`·`변경을 적용하는 중 예외가 났다` 오류는 **셋 다 0건**이었다.

### 4.2 컨테이너 — 인수 시나리오 (`workfluence-app:a1d1c5e-p8`)

api 컨테이너 안에서 WebSocket 클라이언트 둘로 같은 흐름을 돌렸다(Origin·세션 쿠키로 정상 업그레이드).

```
A가 부름: @p8b-1790236018884
B가 마지막으로 고침
자동 저장 1 회 · 저장 작성자 = B
B의 알림함: [{"actorName":"P8 부른사람","pageTitle":"P8 확인"}]
✅ "P8 부른사람 님이 불렀다" — 마지막 작성자(B)가 아니다
```

### 4.3 컨테이너 — 재기동을 넘는가 (FR-903, 사용자 결정)

A가 멘션과 **저장할 수 없는 노드**를 함께 넣어 버전은 생기지 않고 상태만 남게 한 뒤, `docker restart workfluence-api`.
재기동한 서버에 B가 붙어 그 노드를 **지우기만** 했다(새 멘션 없음).

```
A가 부름 + 깨진 노드. 저장 버튼 → {"saved":false,"reason":"문서 검증 실패 (1건)","currentVersionNo":1}
page_realtime 남음: true · @p8rb-1790236028955 을 만든 사람 → A
정본 버전 1 (1이면 버전이 안 생겼다)
--- docker restart 뒤 (2초)
재기동 뒤 B가 받은 블록: paragraph,paragraph,script
자동 저장 1 회 · 저장 작성자 = B
B의 알림함: [{"actorName":"P8 재기동 부른사람"}]
✅ 재기동을 넘어 "P8 재기동 부른사람 님이 불렀다"
```

장부가 남지 않았으면 방을 다시 만들 때 그 멘션은 "모름"이 됐다. 두 컨테이너 확인 동안 **경고·장부 오류·적용 예외 0건**이었다.
확인용 계정·페이지는 스크립트가 끝에 지웠다(감사로그는 append-only라 남는다).

### 4.4 변이 시험 — 테스트가 정말 그 규칙을 잡는가

넷째 판의 규칙을 하나씩 일부러 끄고 해당 테스트가 실패하는지 봤다. 끈 뒤에는 되돌렸다(`cmp`로 확인).

| 끈 규칙 | 실패한 테스트 |
|---|---|
| (a) 글자를 들여온 사람을 보지 않는다 | **12건** — 게이트웨이 8(남이 지움·앞글자 지움·경계 끼우기·이름 가르기·**공백 하나로 완성**·나눠 치기·남의 클라이언트 ID·옛 문서 통째로) + A등급 4 |
| (b) 옮김을 보지 않는다 | 4건 — 잘라 붙이기(게이트웨이·A등급)·남의 문단 재구성·한 변경 안의 옮김 |
| (c) 부모 삭제로 설명하지 않는다 | 2건 — 문단을 지우는 동안 친 글자(게이트웨이·A등급) |
| (d) 연결이 만든 클라이언트인지 보지 않는다 | 남의 클라이언트 ID 1건 |
| (e) 여러 클라이언트짜리 변경의 글자도 적는다 | 옛 문서 통째로 1건 |
| (f) 변경을 늘 믿는다 | 보류 조각·보류 삭제 2건 |
| (g) 자라는 이름도 사라짐으로 친다 | 중간 이름 1건 |
| (h) 저장하면 옮김 기억을 전부 잊는다 | 잘라냄 → 저장 → 붙여 넣기 2건 |
| (i) 훑기가 편집기가 만들지 않는 노드를 거르지 않는다 | 4건 — A등급 3(XmlHook·Text·Map) + 중계·저장이 이어진다 1 |
| (j) 자람은 누가 했든 사라짐이 아니다 | 남이 내 멘션을 자라게 한 뒤 옮김 1건 |
| (k) 저장하면 그 이름의 기억을 순번과 상관없이 잊는다 | 저장하는 사이 생긴 기억 2건 |
| (l) 적용 중 예외면 퍼뜨리지 않는다 | 다른 관찰자가 던져도 퍼뜨린다 1건 |
| (m1) 한 번에 생겼는지 보지 않는다 | 지운 이름을 다시 쳐서 부르기 2건(게이트웨이·A등급) |
| (m2) 같은 사람의 재접속을 이어받지 않는다 | 2건(게이트웨이·A등급) |
| (m3) 자기 클라이언트는 믿을 수 있는 변경에서만 알아본다 | 첫 변경에 보류 조각이 묻음·첫 조각이 지워진 문단 2건 |
| (m4) 문서가 바뀌지 않았으면 자기 클라이언트도 보지 않는다 | 첫 조각이 지워진 문단 1건 |
| (n) 바뀌지 않은 문서도 되풀이해 판정한다 (FR-910) | 2건 — 썼다 지워 정본과 같아짐·검증 실패 |

변이 시험은 **규칙이 테스트에 잡히는지**를 볼 뿐 규칙이 옳은지는 보지 않는다 — T-034.

### 4.5 통합 테스트가 확인한 것 (게이트웨이를 실제로 탄다)

사람마다 화면처럼 문서 하나를 두고, 방에서 받은 것은 되돌려 보내지 않으며, 자기 트랜잭션 하나씩만 보낸다.

| 경우 | 부른 사람 |
|---|---|
| **인수 기준** — A가 `@B`, B가 접속 직후 전체 상태를 보내고 다른 문단을 고침 | **A** (메일 이름·메일 감사 actor도 A) |
| 남의 글 뒤에 이어 부름 | 부른 사람 |
| 자기 오타를 지우고 이어 침 | 부른 사람 |
| **정본 글자를 지우고 그 자리에 부름** | 부른 사람 |
| **남이 서식을 걸었다 풂** | 부른 사람 |
| 남이 바로 뒤에 조사를 붙임 | 부른 사람 |
| 자기 문단을 자기가 제목으로 | 부른 사람 |
| 남이 글자를 지워 새 이름을 만듦 / 앞글자를 지움 / 경계에 공백을 끼움 / 이름을 가름 | **모름** |
| **남의 글을 내 공백 하나가 멘션으로 완성** (`hello@collab-c` + 공백) | **모름** |
| **남의 멘션을 잘라 붙임** / **잘라낸 뒤 저장이 끼고 붙여 넣음** | **모름** |
| 둘이 나눠 침 (A `@collab-`, B `c`) | 모름 |
| **남의 문단을 제목으로 바꿈** | 모름 |
| 남의 클라이언트 ID로 보냄 / 옛 문서를 통째로 다시 보냄 | 모름 |
| **보류된 위조 조각**이 주인의 변경에 묻어 들어옴 | 모름 + 경고 |
| **보류된 위조 삭제**가 주인의 변경을 지움 | 모름 |
| **U가 문단을 지우는 동안 X가 그 문단에 침** / **둘이 같은 속성을 동시에 바꿈** | 경고 없음 (동시 편집은 위조가 아니다) |
| **편집기가 만들지 않는 노드(`Y.XmlHook`)가 들어온 뒤** U가 부름 | 부른 사람 — 중계가 이어지고 저장된다 |
| **적용한 뒤 다른 관찰자가 던짐** | 그래도 퍼뜨린다 |
| **남이 지운 이름을 내가 한 글자씩 쳐서 부름**(그 사이 저장) | 부른 사람 — 옮김은 통째로 생길 때만 |
| **같은 Y.Doc으로 다시 붙은 뒤** 부름 | 부른 사람 — 같은 사람이 만든 클라이언트를 이어받는다 |
| **첫 변경에 남의 보류 조각이 묻은 뒤** 부름 / **첫 조각이 이미 지워진 문단에 들어간 뒤** 부름 | 부른 사람 |
| 남이 내 멘션을 자라게 했다가 잘라 붙여 다듬음 / 저장하는 사이 잘라냄 | 모름 (A등급) |
| 잘라낸 남의 멘션을 **두 번에 나눠** 붙임 | 붙인 사람 (A등급) — 한 글자씩 친 것과 가릴 수 없다. 설계서 C.2 |
| **X가 커서 정보로 알려진 U의 클라이언트 ID로 먼저 씀** → U의 화면이 받아 새 ID로 바꾼 뒤 U가 부름 | X가 쓴 멘션은 **X**, U의 멘션은 **U** — U의 ID로 썼어도 U의 이름이 붙지 않는다 |
| 같은 공격인데 U가 **이미 더 쳐 두었음** (Yjs가 ID를 바꾸지 않는다) | 그 ID로 이어 친 멘션은 **모름**(X도 아니다). 서버는 U의 앞 글자를 버리고 나머지를 X의 문단에 붙인다 — 보류 24 |
| 썼다 지워 정본과 같아짐 / 검증에 실패한 문서 (FR-910) | 유휴 판정은 한 번 — 매초 질의·상태 쓰기·경고를 되풀이하지 않는다. 다음 변경은 다시 저장된다 |
| 장부가 `page_realtime`에 남고 새 게이트웨이가 잇는다 | 부른 사람 |

그 밖에: 알림 목록이 부른 사람 없는 알림을 버리지 않는다(`leftJoin`), 스스로 부른 곳이 앞에 있어도 남이 부른 곳이 있으면
알림이 간다, 메일은 받는 사람별 이름 → 기본 이름 → 이름 없음 순서로 고르고 감사에 일으킨 사람을 남긴다, 새 페이지도 부른
사람들을 호출부에 넘긴다(메일).

## 9. 확인하지 못한 것

- **다섯 번째 묶음의 지적을 반영한 마지막 변경은 독립 검토를 따로 돌리지 않았다.** 네·다섯 번째 묶음은 높음이 없었고 제3자의
  이름이 붙는 길을 찾지 못했다. 마지막 변경은 문서·주석, 시험 넷, 그리고 유휴 저장의 가드 한 줄(FR-910)이다.
- **조작한 클라이언트로 공격을 실제 WebSocket 너머에서 재현하지 않았다.** 공격은 게이트웨이 안쪽(가짜 소켓 + 실제 yjs)으로
  확인했다. 컨테이너 확인은 정상 클라이언트 둘이다. FR-909(이상한 노드)도 컨테이너에서 따로 돌리지 않았다.
- **남는 것** (설계서 C.2): ① 서버가 한 사람의 글자를 **전부** 잃은 뒤 다른 사람의 화면이 같은 Y.Doc으로 다시 붙어 그 글자만
  다시 보내면, 그 연결이 남의 클라이언트를 자기 것으로 여긴다 — 재접속을 붙이는 날 다시 본다. ② 남이 피해자의 클라이언트 ID로
  **먼저**(그 ID는 커서 정보로 첫 편집 전에 알려진다) 또는 앞선 시계의 조각으로 보내면 피해자의 입력이 서버에 닿지 않고 화면과
  서버가 갈린다(Yjs 수준, P6부터) — 보류 24. ③ 편집기가 만들지 않는 Yjs 타입이
  동료들의 편집기 렌더를 깨뜨린다 — 보류 23. ④ 보이지 않는 금지 요소·속성이 협업 자동 저장을 막는다 — 보류 22.
- **실제 사용에서 "모름"이 얼마나 나오는지 모른다.** 반입 뒤 알림 중 `actor_id IS NULL`의 비율로 잰다 —
  `SELECT count(*) FILTER (WHERE actor_id IS NULL), count(*) FROM notifications`.
- **편집기의 복잡한 조작을 E2E로 돌리지 않았다** — 목록·표 안의 멘션, 붙여 넣기, 되돌리기(undo), Enter로 나누기. 게이트웨이 통합
  테스트와 두 번째·세 번째 `self-reviewer`의 y-prosemirror 1.3.7 재현이 전부다.
- **장부의 실제 크기.** 동시 편집자가 많고 오래 열린 방에서 재지 않았다. 보류 19와 함께 잰다.
- 화면의 "문서에서 불렸다" 분기에 **컴포넌트 테스트가 없다**(web은 테스트 파일 0개, 3절이 관문을 두지 않는다). API 쪽
  `actorName: null`은 통합 테스트가 단언한다.
- **메일은 여전히 모의 발송이다** (보류 18). 받는 사람별 이름이 실제 메일 API에서 어떻게 보이는지는 확인하지 못했다.
