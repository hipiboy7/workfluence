## 2. 실측 — Yjs가 보여 주는 것

설계의 전제를 코드보다 먼저 실측했다. 전부 `node -e`로 yjs를 직접 불렀다.

**① 글자의 주인은 서식·재전송에 흔들리지 않는다.**

```
454767248 ContentString "hi "    ← A
114681792 ContentFormat          ← C가 건 굵게
454767248 ContentString "@bob"   ← 여전히 A
114681792 ContentFormat
114681792 ContentString " x"     ← C
(C가 전체 상태를 다시 보냄 → update 이벤트 없음)
```

**② 자기 오타 수정과 남의 삭제는 흔적만으로는 같다.** 이것이 "지우는 순간 누가 지웠는지 적는다"(설계서 C.2)의 이유다.

```
자기 오타:  777:@kim | ~777:Deleted | 777: 확인      ("@kimm" → 지움 → " 확인")
남이 지움:  504:@kim | ~504:Deleted | 504: 확인      ("@kim.lee 확인" → B가 ".lee" 삭제)
```

**③ 지운 내용과 지운 사람은 트랜잭션이 끝나는 순간에만 보인다.**

```
afterTransaction 지운 것 585:4 len 4 ".lee" origin= memberX
update 시점 내용 undefined ContentDeleted
```

**④ 끼워 넣기는 `origin`·`rightOrigin`으로 가려진다.**

| 경우 | 관찰 | 판정 |
|---|---|---|
| (a) 남의 `참석: ` 뒤에 U가 `@kim` | `@kim`의 origin = 남의 마지막 글자(지금의 왼쪽) | 통과 |
| (b) U의 `x@kim`에 X가 공백 | `@`의 origin = `x` ≠ 지금의 왼쪽(X의 공백) | 모름 |
| (c) U의 `@kimlee`에 X가 공백 | X 공백의 rightOrigin = `l`(아이디 글자) | 모름 |
| (d) U의 `@kim 확인`에 X가 `님` | X `님`의 rightOrigin = U의 공백 | 통과 |

**⑤ 보류 위조는 "보낸 것보다 더 들어온다"로 드러난다.**

```
B가 보낸 위조(A의 ID)   A:10..17  → 들어간 것 없음 (보류)
A가 보낸 것            A:5..10   → 들어간 것 A:5..17    서버 글 "hello 안녕하세 @carol"
화면 쪽: 위조를 전달받은 A의 문서에서 로컬로 다섯 글자 → 보낸 구간 5..10, 보류 그대로 남음
```

## 4. 실제로 동작시켜 확인한 것

### 4.1 브라우저 — 인수 흐름 (`e2e/collab.spec.ts` 3번째)

두 브라우저 문맥에서 A(관리자)가 `@동료아이디 확인부탁…`을 치고, **유휴 저장이 끼기 전에** B(동료)가 끝에 ` B가덧붙임`을 친다.
9초 뒤 B의 알림함 첫 항목의 굵은 이름이 `E2E 관리자`다.

그 실행의 감사로그를 DB에서 따로 읽어, 이 시험이 정말 "B가 마지막 작성자"인 상태를 만들었는지 확인했다:

```
page.create       actor 7686319e   (A)
page.collab.save  actor bdca1be6   trigger idle   (B)
```

저장은 한 번이고 그 작성자는 B다 — **옛 코드였으면 B 자신의 이름이 떴을 상황**이다. 검토 반영 뒤(`8af017e`)에도 다시 돌려 통과했다.
실제 편집기(y-prosemirror)가 글자 단위로 친 멘션이 새 규칙(설계서 C.3의 넷)을 모두 통과한다는 뜻이기도 하다.

### 4.2 컨테이너 — 인수 시나리오 (`workfluence-app:8af017e-p8`)

api 컨테이너 안에서 WebSocket 클라이언트 둘로 같은 흐름을 돌렸다(Origin·세션 쿠키로 정상 업그레이드).

```
A가 부름: @p8b-1790220605998
B가 마지막으로 고침
자동 저장 1 회 · 저장 작성자 = B
B의 알림함: [{"actorName":"P8 부른사람","pageTitle":"P8 확인"}]
✅ "P8 부른사람 님이 불렀다" — 마지막 작성자(B)가 아니다
```

### 4.3 컨테이너 — 재기동을 넘는가 (FR-903, 사용자 결정)

A가 멘션과 **저장할 수 없는 노드**를 함께 넣어 버전은 생기지 않고 상태만 남게 한 뒤, `docker restart workfluence-api`.
재기동한 서버에 B가 붙어 그 노드를 **지우기만** 했다(새 글자 없음).

```
A가 부름 + 깨진 노드. 저장 버튼 → {"saved":false,"reason":"문서 검증 실패 (1건)","currentVersionNo":1}
page_realtime 남음: true · A의 클라이언트 1513966098 → A
정본 버전 1 (1이면 버전이 안 생겼다)
--- docker restart 뒤
재기동 뒤 B가 받은 블록: paragraph,paragraph,script
자동 저장 1 회 · 저장 작성자 = B
B의 알림함: [{"actorName":"P8 재기동 부른사람"}]
✅ 재기동을 넘어 "P8 재기동 부른사람 님이 불렀다"
```

대응표가 남지 않았으면 방을 다시 만들 때 A의 ID가 "모름"으로 굳어 이름이 비었다. 두 컨테이너 확인과 E2E 전체를 돌리는 동안
**`클라이언트 ID가 맞지 않는다` 경고는 0건**이었다(컨테이너 로그·호스트 api 로그) — 정상 사용이 거짓 경고를 내지 않는다.
확인용 계정·페이지는 스크립트가 끝에 지웠다(감사로그는 append-only라 남는다).

### 4.4 변이 시험 — 테스트가 정말 그 공격을 잡는가

규칙을 하나씩 일부러 끄고 해당 테스트가 실패하는지 봤다. 끈 뒤에는 되돌렸다.

| 대응표 잇기 (첫 판) | 재기동 1건 |

| 앞 경계 검사 | 경계 끼워 넣기 1건 |

## 9. 확인하지 못한 것

- **조작한 클라이언트로 공격을 실제 WebSocket 너머에서 재현하지 않았다.** 공격 여섯은 Yjs 직접 조작(A등급)과 게이트웨이
  안쪽(가짜 소켓, B등급)으로 확인했다. 컨테이너 확인은 정상 클라이언트 둘이다.
- **실제 사용에서 "모름"이 얼마나 나오는지 모른다.** 규칙은 안전한 쪽으로 틀린다(설계서 C.3 "치르는 값"). 그 빈도는 반입 뒤
  알림 중 `actor_id IS NULL`의 비율로 잰다 — `SELECT count(*) FILTER (WHERE actor_id IS NULL), count(*) FROM notifications`.
- **편집기의 복잡한 조작을 E2E로 돌리지 않았다** — 목록·표 안의 멘션, 붙여 넣기, 되돌리기(undo). 붙여 넣은 글자는 붙인 사람의
  것이 되고(설계서 C.2 "남는 것"과 같은 성격), 되돌리기는 되돌린 사람이 새로 넣은 글자가 된다 — 코드로 추론했고 실측은 없다.
- **대응표와 지운 흔적의 실제 크기.** 동시 편집자가 많고 하루 종일 열린 방에서 재지 않았다. 보류 19와 함께 잰다.
- 화면의 "문서에서 불렸다" 분기에 **컴포넌트 테스트가 없다**(web은 관문이 없다, 3절). API 쪽 `actorName: null`은 통합 테스트가 단언한다.
- **메일은 여전히 모의 발송이다** (보류 18). 받는 사람별 이름이 실제 메일 API에서 어떻게 보이는지는 확인하지 못했다.
