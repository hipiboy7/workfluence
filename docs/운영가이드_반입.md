## 0. 들고 갈 것과 미리 확인할 것

대상은 **RHEL 9 서버**다(다른 리눅스도 Docker와 compose가 있으면 1절부터 같다). 순서는 0.1(무엇을 들고 가나) → 0.2(서버에 무엇이 있나) →
Docker가 없으면 0.3 → 0.4 → 1절이다.

> **출력은 영어로 본다.** 이 문서가 적은 출력(`OK`·`digests signatures OK`·`nothing provides` …)은 영어다. 서버가 한국어로 답하게 설정돼 있으면 같은
> 결과가 다른 글자로 나와 견줄 수 없다. **창을 열 때마다**(다시 로그인했을 때도) 먼저 친다 — 그 창에서만 바뀌고, 한글 파일 이름은 그대로 보인다.
>
> ```bash
> export LC_ALL=C.UTF-8
> ```

### 0.1 들고 갈 것 — 필요한 파일만

반입 매체에는 **아래 표의 파일만** 담는다. 만드는 쪽(개발·빌드 서버)의 절차는 저장소의 리눅스빌드 가이드 12절(반입 묶음)·12-1절(Docker 묶음)이다 — 그 문서는
묶음에 들어 있지 않다.

| 파일 | 언제 | 크기(어림) | 무엇 |
|---|---|---|---|
| `workfluence-<날짜>.tar` | **늘** | 약 270MB | 반입 묶음 — 이미지 셋·띄우는 설정·설정의 틀·운영 문서·지문·부품 목록(1절의 표) |
| `workfluence-<날짜>.tar.sha256` | **늘** | 한 줄 | 그 tar의 지문 — 옮기다 상하지 않았는지 먼저 본다(1절) |
| `docker-rhel9-<날짜>.tar` | 서버에 **Docker가 없을 때만**(0.2절에서 가린다) | 약 80MB | Docker 묶음 — Docker CE의 RPM 넷과 그것이 늘 쓰는 RHEL 부품(`container-selinux`), firewalld가 없는 서버에 모자란 RHEL 부품 넷(`deps/`), 판·라이선스 목록(`PACKAGES.txt`), Docker의 공개키, 지문(0.3절) |
| `docker-rhel9-<날짜>.tar.sha256` | 위와 함께 | 한 줄 | 그 tar의 지문 |

- **두 `.tar.sha256`의 값(앞의 64자)은 매체와 따로 가는 기록에도 적는다** — 반입 신청서·결재 문서처럼 매체와 다른 길로 가는 것. 지문 파일은 매체에 같이 들어 있어
  매체째 바뀌면 함께 바뀐다. 현장에서 1절·0.3절 ①·11절 ①의 `cat …tar.sha256`을 그 기록과 견준다 — 같고 `sha256sum -c`가 `OK`면 만든 곳의 것 그대로다.
- **현장에서 받는 것** — TLS 인증서와 개인키(3절). 반입 매체에 담지 않고 사내 인프라 담당에게 받는다 — 개인키가 여럿이 만지는 매체에 남지 않게. 사내 인증 기관의
  인증서가 필요하면(사내 LLM·메일·IdP가 사내 인증서의 `https`일 때) 그것도 현장에서(10절 ②).
- **들고 가지 않는 것** — 저장소(소스 코드)·`node_modules`·Node·pnpm·git·개발용 설정 파일. 폐쇄망 서버에서 앱의 코드가 하는 일(표 만들기·첫 계정·월간 정리·시험 메일)은
  **앱 이미지 안에서** 돈다(5절의 `tools`). 인터넷에서 받아야 하는 것은 하나도 없다.
- 반입 매체의 파일은 받은 그대로 한 자리에 둔다 — 이 문서는 그 자리를 `/media/반입`으로 적는다. 다른 자리면 명령의 그 부분만 바꾼다. 매체는 **exFAT·FAT32·ext4**로
  만든다 — RHEL 9는 NTFS(Windows가 흔히 쓰는 형식)를 붙이지 못한다.

### 0.2 서버에 있어야 하는 것

| 확인 | 명령 | 기준 |
|---|---|---|
| RHEL 9인가 | `cat /etc/redhat-release` | `Red Hat Enterprise Linux release 9.x` — Docker 묶음을 쓰려면 **9.2 이상**(묶음의 `container-selinux`가 9.2부터의 SELinux 정책을 요구한다). 0.3·0.4절은 RHEL 9 기준이다 |
| 도커가 있고 부팅 시 뜬다 | `systemctl is-enabled docker` | `enabled`. **`not-found`나 `Failed to get unit file state`가 나오면 Docker가 없다 — 0.3절**(Docker 묶음을 들고 온다) |
| compose가 있다 | `docker compose version` | `Docker Compose version v2` 이상(v2.x·v5.x). **띄어 쓴 `docker compose`**다 — 옛 `docker-compose`(v1)로는 이 문서의 명령이 돌지 않는다 |
| 디스크 여유 | `df -h ~ /var/lib/docker /var/lib/containerd` — Docker가 아직 없으면 `df -h ~ /var/lib` | 묶음을 풀 자리(`~`)와 도커의 두 자리가 **각 5GB 이상** — 올린 이미지는 `/var/lib/containerd`에, 데이터베이스·첨부는 `/var/lib/docker`에 쌓인다(Docker 29). 따로 붙은 디스크인 서버가 있다 — 그러면 `/var/lib`가 아니라 그 디스크를 본다(Docker를 들인 뒤 0.4절에서 한 번 더) |
| `tar`·`sha256sum`이 있다 | `tar --version` · `sha256sum --version` | 버전이 나온다. **`tar`가 없으면**(RHEL 최소 설치에 없을 수 있다) 그 서버의 RHEL 설치 매체나 사내 저장소에서 먼저 넣는다 — 두 묶음을 풀려면 있어야 한다 |
| `openssl`이 있다 | `openssl version` | 버전이 나온다 — 3절에서 비밀번호를 만든다 |

> **이 서버에 Node나 pnpm이 있다고 가정하지 않는다.** 묶음에는 컨테이너 이미지와 설정만
> 들어 있고 저장소도 `node_modules`도 없다. 그래서 **반입 절차의 모든 명령은 `docker`와
> 기본 리눅스 도구만 쓴다.** 개발 쪽에 있는 `pnpm release:verify`는 같은 일을 하는 편한
> 도구일 뿐이고, 여기서는 쓸 수 없다 — 그래서 체크섬 형식을 **`sha256sum`과 호환**되게 만들었다.
> 표 만들기·첫 계정·월간 정리처럼 앱의 코드가 해야 하는 일은 **앱 이미지 안에서** 돈다(5절의 `tools`).

### 0.3 RHEL 9에 Docker가 없으면 — Docker 묶음으로 들인다

**Docker가 이미 있으면 건너뛴다.** `sudo`를 쓸 수 있는 계정으로 한다. 이 절의 명령은 그 서버에 있는 도구(`sha256sum`·`tar`·`gpg`·`rpm`·`dnf`·`systemctl`)만 쓴다.

**① 지문을 보고 푼다.**

```bash
cd /media/반입
cat docker-rhel9-<날짜>.tar.sha256
sha256sum -c docker-rhel9-<날짜>.tar.sha256
rm -rf ~/docker-rhel9
mkdir -p ~/docker-rhel9
tar -xf docker-rhel9-<날짜>.tar -C ~/docker-rhel9 --strip-components=1
cd ~/docker-rhel9
sha256sum -c SHA256SUMS
cat PACKAGES.txt
```

- `cat`의 앞 64자가 0.1절의 따로 간 기록과 같아야 하고, `sha256sum -c`는 두 번 다 모든 줄이 `OK`여야 한다. `FAILED`가 하나라도 있으면 그 묶음을 쓰지 않는다 — 옮기다 상했다.
- `rm -rf`는 전에 풀어 둔 것을 치운다 — 남아 있으면 ④의 `./*.rpm`이 옛 판까지 넣는다(`SHA256SUMS`는 목록 밖의 파일을 보지 않는다).
- `PACKAGES.txt`는 묶음에 든 RPM의 판·라이선스·만든 곳이다. **첫 줄이 이 묶음을 만든 서버의 RHEL 판**이다(④에서 본다).

**② 서명을 본다 — 누가 만든 파일인가.** 지문은 옮기다 상했는지만 말한다. 서명은 **임시 자리**에서 본다 — 이 서버의 설정에 아무것도 남기지 않는다.

```bash
gpg --show-keys --with-colons docker-ce.gpg | awk -F: '$1=="pub"{n++} $1=="fpr"&&!f{f=$10} END{print n":"f}'
K=$(mktemp -d)
rpm --dbpath "$K" --import docker-ce.gpg /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release
rpm --dbpath "$K" -K *.rpm deps/*.rpm | grep -v ': digests signatures OK$'
rm -rf "$K"
```

- 첫 명령은 **`1:060A61C51B558A7F742B77AAC52FEB6B621E9F35`** 한 줄이어야 한다(처음 치는 계정이면 그 앞에 gpg가 `… created` 줄을 먼저 낸다 — 괜찮다). 키 파일에 키가
  하나이고, 그 지문이 Docker의 것(Docker Release (CE rpm))이라는 뜻이다. 다르면 멈춘다.
- 넷째 명령은 **아무것도 내지 않아야 한다** — 서명이 맞는 줄은 거르고 나머지만 보인다. 무엇이든 나오면 설치하지 않는다: `digests SIGNATURES NOT OK`(키가 없거나
  서명이 틀렸다), `digests OK`만 있는 줄(**서명이 없는 RPM**이다 — `NOT OK`라는 글자가 없어 눈으로 찾으면 지나친다). 장애대응 7.41절.
- Red Hat의 부품(`container-selinux`·`deps/`)은 **이 서버 자신의** Red Hat 키(`/etc/pki/rpm-gpg/`)로 본다. Docker의 키는 이 매체로 왔다 — 매체째 바뀐 것은 0.1절의
  따로 간 기록으로 가린다.

둘 다 맞으면 두 키를 이 서버에 들인다 — ④의 dnf가 설치하면서 서명을 **스스로 한 번 더** 보게 한다(이미 들어 있는 키는 다시 들여도 아무 일이 없다).

```bash
sudo rpm --import docker-ce.gpg /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release
```

**③ 부딪히는 패키지를 본다.** Docker의 containerd는 RHEL의 `runc`·`containerd`와 함께 있을 수 없고(설치하면 dnf가 묻지 않고 치운다), `podman-docker`는 같은
`docker` 명령을 가진다.

```bash
rpm -qa --qf '%{NAME}\n' | grep -xE 'podman|podman-docker|buildah|runc|containerd|docker|docker-io'
```

아무것도 나오지 않으면 ④로 간다. 나오면 **그 서버에서 그것을 쓰는 일이 없는지 먼저 확인한다** — 다른 일이 podman으로 돌고 있으면 지우는 순간 그 일이 멈춘다(그렇다면 이
서버에 Docker를 두지 않는다 — 사내 인프라 담당과 정한다). 쓰는 일이 없으면 나온 것만 지운다 — **`-y` 없이** 쳐서 거래표를 본다(예: `sudo dnf remove podman buildah runc`).
표에 그것 말고 다른 것(예: `cockpit-podman`, 함께 깔렸던 부품)까지 있으면 `N`으로 멈추고 사내 인프라 담당과 정한다.

**④ 설치한다 — 거래표를 보고 답한다.**

```bash
sudo dnf install --setopt=localpkg_gpgcheck=1 ./*.rpm
```

- **`-y`를 붙이지 않는다.** dnf가 거래표를 보이고 묻는다. 묶음의 다섯은 `Installing:`에(저장소 칸이 `@commandline`), 사내 저장소에서 가져오는 것은
  `Installing dependencies:`에 있다. **`Upgrading:`·`Downgrading:`·`Removing:`이 있으면 멈추고 그 줄을 본다** — 저장소 칸이 `@commandline`(묶음의 파일)이면 `N`(③을
  건너뛰었거나 이 서버의 부 버전이 묶음과 다르다). 이 서버의 저장소에서 온 것이면 이 서버의 업데이트를 함께 당기는 것이다 — 사내 인프라 담당과 정한다. 괜찮으면 `y`.
- `--setopt=localpkg_gpgcheck=1`은 파일로 까는 RPM의 서명도 dnf가 보게 한다(기본은 보지 않는다) — 서명이 없거나 ②에서 들인 키로 맞지 않으면 dnf가 거절한다.
- 사내 RHEL 저장소에 닿지 못해 실패하면(`Failed to download metadata for repo …`) 저장소를 빼고 다시 친다:
  `sudo dnf install --setopt=localpkg_gpgcheck=1 --disablerepo='*' ./*.rpm`
- dnf가 **`nothing provides (iptables-nft or iptables)`·`nothing provides nftables`**를 말하면 firewalld가 없는 서버다 — **`cat /etc/redhat-release`가 `PACKAGES.txt`의
  첫 줄과 같을 때만** `deps/`를 더한다: `sudo dnf install --setopt=localpkg_gpgcheck=1 --disablerepo='*' ./*.rpm ./deps/*.rpm`(이미 같은 판이 있는 것은 dnf가 건너뛴다).
  판이 다르면 `deps/`를 쓰지 않는다 — 그 판은 묶음을 만든 서버의 것이라(`iptables-nft`는 같은 판의 `iptables-libs`를 요구한다) 다른 부 버전에는 맞지 않는다. 그 서버의
  **RHEL 설치 매체(DVD의 BaseOS·AppStream)나 사내 저장소**에서 `iptables-nft`·`nftables`·`libnftnl`(서버에 따라 `jansson`도)을 넣는다. 같은 판이어도
  `deps/`를 넣었더니 `nothing provides iptables-libs(x86-64) = …`가 나오면 이 서버의 `iptables-libs`가 묶음과 다른 판이다(같은 부 버전이라도 업데이트가 다르면) —
  `deps/`를 빼고 같은 매체·저장소에서 넣는다.
- 그 밖의 것이 모자란다고 하면(`selinux-policy`·`policycoreutils`·`xz` 등 — RHEL 설치에 늘 있는 것들이다) 같은 RHEL 매체·사내 저장소에서 **같은 부 버전의 것**을 넣는다
  (장애대응 7.41절). 매체의 RPM 파일을 넣을 때도 `--setopt=localpkg_gpgcheck=1`을 붙인다 — Red Hat 키는 ②에서 들였다.

**⑤ 켜기 전에 — Docker가 쓸 망의 대역.** Docker는 컨테이너끼리의 망에 `172.17.0.0/16`부터 `172.31.0.0/16`까지를, 그다음 `192.168.0.0/16`을 잘게 나눠 차례로 쓴다. **사내 PC나 게이트웨이의 주소가 그 안에
있으면** 그 PC에서 접속이 안 된다 — 서버의 답이 바깥이 아니라 Docker의 망으로 간다. 사내 인프라 담당에게 묻고, **걸리면 켜기 전에** 쓰지 않는 대역을 적는다. 걸리지
않으면 건너뛴다.

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "bip": "10.210.0.1/24",
  "default-address-pools": [{ "base": "10.211.0.0/16", "size": 24 }]
}
EOF
dockerd --validate --config-file /etc/docker/daemon.json
```

`10.210…`(Docker의 기본 망 하나)·`10.211…`(compose가 만드는 망들)은 **예다** — 사내 인프라 담당이 준 대역으로 바꾼다. 마지막 줄이 `configuration OK`여야 한다 — 이것은 **모양(JSON의 문법과 키 이름)만** 본다.
대역의 값이 틀리면(`/33` 같은 것) 그래도 `configuration OK`이고 ⑥에서 켤 때 실패한다(장애대응 7.41절). 켠 뒤에 바꾸면 compose의 망을 다시 만들어야 한다(같은 절).

**⑥ 켜고, 작업 계정에 권한을 준다.** 먼저 **`docker` 그룹을 쓸지** 정한다 — 그 그룹의 계정은 데몬을 시켜 서버의 무엇이든 읽고 바꿀 수 있고(root와 같은 힘), 그룹으로 친
`docker` 명령은 sudo 기록에 남지 않는다. 사내 보안이 그룹을 막거나 서버 작업의 기록을 요구하면 그룹을 쓰지 않고 이 문서의 `docker` 명령을 모두 `sudo docker …`로 친다 —
명령은 같다. 그룹을 쓰면 **반입과 운영을 맡은 계정 하나에만** 준다.

```bash
sudo systemctl enable --now docker
sudo gpasswd -a "$USER" docker
grep '^docker:' /etc/group
```

- 그룹을 쓰지 않으면 첫 줄만 친다.
- 마지막 줄은 `docker:x:<번호>:<이 계정>` **한 줄**이어야 한다. 끝에 다른 계정이 있으면 그 계정도 root의 힘을 가진 것이다 — 사내 인프라 담당과 정한다. **아무것도 나오지
  않으면**(둘째 줄이 `gpasswd: group 'docker' does not exist in /etc/group`을 낸다) `docker` 그룹이 이 서버가 아니라 사내 디렉토리(LDAP 등)의 그룹이다 — 그 그룹의 모든 사람이 이 서버의 root 힘을 얻는다.
  멈추고 사내 인프라 담당과 정한다.

그다음 **로그아웃했다가 다시 로그인한다**(그룹은 새 로그인부터 먹는다 — 새 창에서는 `export LC_ALL=C.UTF-8`부터). 그리고 0.2절의 표를 다시 본다 — `systemctl is-enabled docker`가
`enabled`, `docker compose version`이 나와야 한다. `docker version`의 `Server` 판이 `PACKAGES.txt`의 `docker-ce` 판이다.

### 0.4 RHEL 9에서 한 번 더 볼 것

| 확인 | 명령 | 기준 · 조치 |
|---|---|---|
| 방화벽 | `sudo firewall-cmd --state` | **바꿀 것이 없다.** Docker는 compose가 연 접속 포트(3절의 `WF_HTTPS_PORT`, 기본 8443)를 firewalld의 포트 목록과 상관없이 연다 — firewalld로 열 것도, 그 목록으로 막을 것도 없다. `running`이든 `not running`·`command not found`(firewalld가 없다)든 같다. **밖으로 열리는 포트는 그 하나다**(compose). 접속할 PC를 좁히려면 사내 망 방화벽에서 좁힌다 — 사내 인프라 담당. firewalld가 켜진 서버에서는 해 보지 못했다(Phase 20) |
| SELinux | `getenforce` | `Enforcing`이면 **그대로 둔다 — 끄지 않는다**(`setenforce 0`은 서버 전체의 보호를 끈다). 이 스택은 RHEL 9 · Enforcing에서 돈다(Phase 20 — 개발 서버에서 이 문서대로 설치해 봤다). Docker의 기본 설정에서 컨테이너는 SELinux가 가두지 않는 자리(`spc_t`)에서 돈다 — 그래서 붙이는 설정 파일의 라벨을 바꿀 일이 없다 |
| Docker의 망 대역 | 표 아래의 명령 | 보이는 대역(기본 `172.17.0.0/16`부터, 모자라면 `192.168.0.0/16`)이 사내 PC·게이트웨이의 주소와 **겹치지 않아야** 한다 — 사내 인프라 담당에게 묻는다. 겹치면 0.3절 ⑤. Docker가 전부터 있던 서버면 바꾸는 동안 그 서버의 다른 컨테이너도 멈춘다 — 사내 인프라 담당과 정한다 |
| 서버 시각 | `timedatectl` | `System clock synchronized: yes` — 세션 만료와 감사 기록의 시각이 이 서버의 시계다. `no`면 사내 시각 서버(chrony)를 사내 인프라 담당에게 묻는다 |
| 디스크 세 자리 | `df -h ~ /var/lib/docker /var/lib/containerd` | 각 5GB 이상 — Docker를 방금 들였으면 여기서 도커의 두 자리가 처음 생긴다 |

## 1. 묶음을 푼다 — **`deploy/`라는 이름으로 푼다**

```bash
cd /media/반입
cat workfluence-<날짜>.tar.sha256
sha256sum -c workfluence-<날짜>.tar.sha256
mkdir -p ~/workfluence/deploy
tar -xf /media/반입/workfluence-<날짜>.tar -C ~/workfluence/deploy --strip-components=1
cd ~/workfluence/deploy
sha256sum -c SHA256SUMS
```

`<날짜>`는 받은 파일 이름의 날짜다(예: `workfluence-2026-09-30.tar`). `cat`의 앞 64자는 0.1절의 **따로 간 기록과 같아야** 한다. 그다음 줄은 **옮긴 tar가 통째로 온전한지**, `SHA256SUMS`는 **푼 파일 하나하나가
온전한지** 본다 — 모든 줄이 `OK`여야 한다. **하나라도 `FAILED`면 그 묶음을 쓰지 않는다** —
옮기는 중에 상했다. 부분 반입이 되면 무엇이 빠졌는지 안에서 알 수 없다.

> **디렉토리 이름을 `deploy`로 하는 이유가 있다.** compose는 **디렉토리 이름을 프로젝트
> 이름으로** 쓰고, 볼륨 이름이 거기서 나온다 — `deploy_postgres_data`·`deploy_attachments`다.
> 다른 이름으로 풀면 볼륨 이름이 달라져서 [운영이관](운영가이드_운영이관.md)·[장애대응](운영가이드_장애대응.md)
> 가이드의 명령이 그대로 안 맞는다. **이름을 맞춰 두면 세 문서가 같은 경로를 말한다.**
> 이 문서와 두 가이드의 `docker` 명령은 모두 **이 디렉토리(`~/workfluence/deploy`)에서** 친다 — 다른 디렉토리에서 치면 compose가 다른
> 설치로 알아, `tools`가 **비어 있는 새 볼륨**을 붙인다(8절의 첨부 백업이 빈 채로 오류 없이 끝난다).

그다음 매니페스트를 읽고 **버전과 git sha를 작업 기록에 적는다.**


나중에 "무엇이 들어갔나"를 답할 수 있는 유일한 단서다.

## 3. 설정을 만든다

```bash
cp env.template .env
chmod 600 .env
```

`.env`의 값은 **비어 있다.** 반드시 채울 것은 넷이다. 아래를 그대로 치면 **새 값을 만들어 채운다** — 사람이 지어낼 필요가 없다.
첫 줄은 네 키의 줄이 틀에 없어도 되게 먼저 만들어 둔다(있으면 아무것도 하지 않는다).

```bash
for k in WF_PG_PASSWORD WF_PG_APP_PASSWORD WF_SESSION_SECRET WF_ROOT_PASSWORD; do grep -q "^$k=" .env || echo "$k=" >> .env; done
sed -i "s/^WF_PG_PASSWORD=.*/WF_PG_PASSWORD=$(openssl rand -hex 16)/" .env
sed -i "s/^WF_PG_APP_PASSWORD=.*/WF_PG_APP_PASSWORD=$(openssl rand -hex 16)/" .env
sed -i "s/^WF_SESSION_SECRET=.*/WF_SESSION_SECRET=$(openssl rand -hex 32)/" .env
sed -i "s/^WF_ROOT_PASSWORD=.*/WF_ROOT_PASSWORD=$(openssl rand -hex 12)/" .env
grep -cE '^WF_(PG_PASSWORD|PG_APP_PASSWORD|SESSION_SECRET|ROOT_PASSWORD)=.' .env
```

마지막 줄이 `4`여야 한다. 값은 화면에 띄우지 않는다.

| 키 | 무엇 |
|---|---|
| `WF_PG_PASSWORD` | 데이터베이스 **소유 계정**(`workfluence`)의 비밀번호. 표를 만들고 고치는 일(5절의 `tools`)만 쓴다. **데이터베이스를 처음 만들 때만 먹는다** — 설치한 뒤 이 값만 바꾸면 붙지 못한다 |
| `WF_PG_APP_PASSWORD` | **앱 계정**(`workfluence_app`)의 비밀번호 (Phase 13). 기동 중인 앱은 이 계정으로 붙는다 — 표를 만들거나 지울 권한이 없고, 감사기록은 넣고 읽기만 한다. 계정은 5절이 만든다. 바꾸면 5절을 다시 친 뒤 `up -d`(장애대응 7.31절) |
| `WF_SESSION_SECRET` | 세션 서명 키. **32자 이상**(위 명령은 64자). 바꾸면 모두 로그아웃된다 |
| `WF_ROOT_PASSWORD` | 첫 시스템 관리자(`root`)의 비밀번호. 5-1절이 이 값으로 계정을 만들고, 첫 로그인에서 바꾼다. 계정이 생긴 뒤에는 쓰이지 않는다 |

**값을 손으로 넣을 때는** `openssl rand -hex 16`처럼 숫자와 a~f만 나오는 값을 쓴다. `/ ? # %`가 든 비밀번호는 데이터베이스
접속 주소에 그대로 들어가 주소가 깨지고, `$`는 compose가 변수로 읽어 다른 값이 된다.

필요할 때만 채우는 것:

| 키 | 무엇 |
|---|---|
| `WF_HTTPS_PORT` | 접속 포트. 비우면 **8443** — 주소가 `https://<호스트>:8443`이 된다. 포트 없는 주소로 쓰려면 `443` |
| `WF_ROOT_USERNAME` | 첫 계정의 아이디. 비우면 `root` |
| `WF_OIDC_*` | 사내 인증을 쓸 때만. `WF_OIDC_REDIRECT_URI`에는 포트까지 적는다(`https://<호스트>:8443/api/auth/oidc/callback`) |
| `WF_MAIL_*` · `WF_PUBLIC_URL` | 메일을 켤 때만 — **반입한 날 하지 않아도 된다**, 10-1절(사내 메일 연결하기). `WF_PUBLIC_URL`도 포트까지(`https://<호스트>:8443`) |
| `WF_LLM_MASTER_KEY` | 사내 LLM의 API 키를 잠그는 키. **키가 있는 LLM을 등록할 때만** 필요하다. `openssl rand -base64 32`의 출력을 그대로 넣는다. **잃거나 바꾸면 등록한 키를 모두 다시 넣어야 한다** — 백업과 **다른 곳**에 따로 보관한다 (장애대응 7.26절) |

나머지 키는 비워 두면 기본값이다. **필수 셋(`WF_PG_PASSWORD`·`WF_PG_APP_PASSWORD`·`WF_SESSION_SECRET`)이 비어 있으면 compose가
아무것도 띄우지 않고 그 키를 말한다**(`… 를 .env에 설정`). 반대로 **키 이름을 틀리게 적으면 아무도 알려 주지 않는다** — compose는
자기가 모르는 키를 앱에 넘기지 않고, 그 설정은 기본값으로 돈다(장애대응 4절). `env.template`에서 온 이름을 고치지 않는다.

TLS 인증서는 지금 디렉토리의 `certs/cert.pem`·`certs/key.pem`에 둔다 (다른 문서에서는 저장소 기준이라 `deploy` 아래의 `certs`로 적힌 그 자리다). **묶음에 들어 있지 않다** —
인증서는 저장소에도 반입 묶음에도 넣지 않는다.

```bash
mkdir -p certs
cp <받은 인증서 파일> certs/cert.pem
cp <받은 개인키 파일> certs/key.pem
chmod 600 certs/key.pem
```

개인키는 **작업 계정만 읽는다**(`600`) — nginx는 컨테이너 안의 root로 읽어 그대로 된다(Phase 20). 다른 계정이 읽게 넓히지 않는다.

**인증서에 SAN(주체 대체 이름)이 있어야 한다.** `CN`에만 호스트명이 있고 SAN이 없는
인증서는 요즘 브라우저와 Node가 **호스트명 확인 자체를 거부한다.** 접속하면 경고가 아니라
오류가 난다. 받은 인증서를 먼저 확인한다.

```bash
openssl x509 -in certs/cert.pem -noout -subject -ext subjectAltName
```

`X509v3 Subject Alternative Name`에 실제 접속 호스트명이 보여야 한다. 안 보이면
인증서를 다시 발급받는다 — 반입 당일에 알면 늦다.

## 4. 데이터베이스를 먼저 띄운다

```bash
docker compose -f compose.yml --env-file .env up -d postgres
docker compose -f compose.yml --env-file .env ps
```

`healthy`가 될 때까지 기다린다.

## 5. 표를 만든다 — **사람이 따로 하는 단계다**

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/db/migrate.js
```

`tools`는 앱 이미지로 **한 번 돌고 끝나는 작업 칸**이다 — 표 만들기·첫 계정(5-1절)·월간 정리·첨부 백업(8절)·메일 시험(10-1절)이 여기서 돈다.
`up`으로는 뜨지 않고 부를 때만 돌며, 끝나면 지워진다(`--rm`). 소유 계정으로 붙는다.

이 단계가 **앱 계정(`workfluence_app`)과 그 권한도 만든다.** 출력 끝의 두 줄을 본다.

```text
[migrate] <N>개 마이그레이션 적용 상태
[migrate] 앱 계정 workfluence_app: 권한 적용
```

둘째 줄이 없으면 앱이 표를 읽지 못한다 — 멈추고 장애대응 7.30절을 본다. 운영에서는 기동과 함께 자동으로 바뀌지 않는다.
두 번 실행해도 결과가 같다.

## 5-1. 첫 root 계정을 만든다 — **빠뜨리면 아무도 로그인하지 못한다**

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/db/seed.js
```

`[seed] root 계정 생성: root (첫 로그인에서 비밀번호 변경 강제)`가 나와야 한다.

- 이 시스템에는 계정을 만드는 화면이 없다. 가입 요청은 승인할 관리자가 있어야 하므로, **첫 관리자는 이 명령만 만든다.**
- 두 번 쳐도 된다. 계정이 이미 있으면 `[seed] root 계정 이미 정상: root`이고 **비밀번호를 바꾸지 않는다.**
- `WF_ROOT_PASSWORD가 없다`로 멈추면 3절의 넷째 줄을 빠뜨렸다.
- `아이디 root인 계정이 이미 있는데 root가 아니다 …`로 멈추면 **누가 그 아이디로 먼저 가입해 두었다**(앱을 이 단계보다 먼저 띄웠다). 시드는 그 계정을 root로 올리지 않는다 — 장애대응 7.29절.
- 로그인할 비밀번호는 `.env`에 있다: `grep '^WF_ROOT_PASSWORD=' .env`

## 6. 전부 띄운다

```bash
docker compose -f compose.yml --env-file .env up -d
docker compose -f compose.yml --env-file .env ps
```

셋(postgres·api·nginx)이 보인다. `tools`는 목록에 없는 것이 정상이다.

## 7. 사후 검증 — 여기까지 해야 끝이다

아래 주소의 `8443`은 3절의 `WF_HTTPS_PORT`다(비웠으면 8443).

| 확인 | 명령·행동 | 기준 |
|---|---|---|
| 앱이 산다 | `curl -sk https://<호스트>:8443/api/health` | `{"status":"ok","db":"ok"}` |
| 화면이 뜬다 | 브라우저로 `https://<호스트>:8443` | 로그인 화면 |
| 로그인된다 | `root` / 5-1절의 비밀번호 | 비밀번호 변경 화면으로 간다. 새 비밀번호를 정한다 |
| 문서를 만든다 | 공간 → 페이지 → 저장 | 버전이 2가 된다 |
| 파일이 붙는다 | 첨부 올리고 내려받기 | 원래 이름 그대로 |
| 기록이 남는다 | 관리자 → 감사로그 | 방금 한 일이 보인다 |
| **앱이 앱 계정으로 붙는다** | 7.2절 ① | `WF_DATABASE_URL=postgres://workfluence_app` 한 줄과 `0` 한 줄 |
| **감사기록은 쌓기만 된다** | 7.2절 ② | `INSERT`·`SELECT` 두 줄 |
| **같이 고칠 수 있다** | 두 브라우저에서 같은 페이지를 연다 | 한쪽에서 친 글자가 다른 쪽에 바로 보인다. 안 보이면 nginx가 WebSocket을 넘기지 않거나 `Host` 헤더에서 포트가 떨어진 것이다 (`docs/운영가이드_장애대응.md` 7.19절·7.19-2절) |
| **오래 열어 둬도 안 끊긴다** | 혼자 편집 화면을 6분 이상 열어 둔다 | 편집 화면 아래에 "연결이 끊겼다"가 뜨지 않는다 |
| **사내 LLM에 묻는다** (쓸 때만) | **10절** 순서대로 — 반입한 날이 아니어도 된다 | 곧바로 "연결됨"이 뜬다. 일반 사용자로 **LLM 질문**에서 물으면 답이 **쓰이는 대로** 나온다. 한꺼번에 나오면 앞단 프록시가 모은다 (장애대응 7.25절) |
| **요청마다 번호가 붙는다** | `curl -sk -D - -o /dev/null https://<호스트>:8443/api/health` | 머리말에 `X-Request-Id`가 **하나** 있다. `docker compose -f compose.yml logs nginx --tail 1`이 JSON 한 줄이다 (장애대응 7.28절) |
| **로그가 순환한다** | `docker inspect workfluence-api --format '{{.HostConfig.LogConfig}}'` | `max-file:5 max-size:20m`이 보인다(`.env`로 바꿨으면 그 값). nginx·postgres도 같다 |
| **재부팅해도 저절로 뜬다** | 아래 7.1절 | 사람이 아무것도 안 해도 `healthy` |

root의 새 비밀번호를 정한 뒤에는 `.env`의 `WF_ROOT_PASSWORD`가 더 쓰이지 않는다. 옛 값이 파일에 남아 있을 이유가 없으니 비워 둔다:
`sed -i 's/^WF_ROOT_PASSWORD=.*/WF_ROOT_PASSWORD=/' .env`

### 7.1 자동 기동은 **실제로 재부팅해서** 확인한다

```bash
sudo reboot
# 다시 접속한 뒤
docker ps
curl -k https://localhost:8443/api/health
```

사람이 아무 명령도 안 했는데 셋이 `Up`이고 헬스체크가 200이어야 한다(`WF_HTTPS_PORT`를 바꿨으면 그 포트로 묻는다).

> **`docker kill`로 확인하지 않는다.** 도커는 `kill`도 `stop`과 **같은 부류로 기록한다** —
> "사람이 멈춘 것"이므로 재시작 정책을 일부러 건너뛴다. 그래서 이 방법으로는 컨테이너가
> **죽은 채로 남고**, 정상인 시스템을 고장으로 판정하게 된다. 컨테이너 안에서 `kill -9 1`도
> 커널이 무시하므로 아무 일도 일어나지 않는다 (둘 다 T-025에서 실측했다).
>
> **반입 당일은 실제로 재부팅할 수 있는 거의 유일한 시점이다.** 서비스를 시작하기 전이라
> 아무도 쓰지 않는다. 개발 서버는 공유 인스턴스라 이것을 할 수 없어서, 이 확인은
> **여기서만 할 수 있다.** 건너뛰면 다음 기회는 밤에 전원이 나갈 때다.

### 7.2 데이터베이스 계정이 나뉘었는지 본다 (Phase 13)

앱은 표를 읽고 쓰기만 하는 **앱 계정**으로 붙고, 표를 만드는 일은 **소유 계정**을 쥔 `tools`만 한다. 그것이 실제로 그런지 본다.

① 앱이 어느 계정으로 붙는가 — 비밀번호는 보이지 않게 계정 이름만 뽑는다:

```bash
docker exec workfluence-api sh -c 'tr "\0" "\n" < /proc/1/environ | grep -o "^WF_DATABASE_URL=postgres://[a-z_]*"'
docker exec workfluence-api sh -c 'tr "\0" "\n" < /proc/1/environ | grep -c "^WF_ROOT_"'
```

첫 줄이 `WF_DATABASE_URL=postgres://workfluence_app`, 둘째 줄이 `0`이어야 한다 — 기동 중인 앱에는 소유 계정 비밀번호도
첫 root 비밀번호도 없다.

② 감사기록에 앱 계정이 할 수 있는 것:

```bash
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT privilege_type FROM information_schema.role_table_grants WHERE grantee = 'workfluence_app' AND table_name = 'audit_events' ORDER BY 1"
```

```text
 privilege_type
----------------
 INSERT
 SELECT
(2 rows)
```

`UPDATE`·`DELETE`가 보이면 기록을 고치거나 지울 수 있는 상태다 — 5절을 다시 친다. 아무 줄도 없으면 앱이 기록을 남기지 못한다 —
역시 5절이다(장애대응 7.30절).

## 8. 첫 백업을 뜬다

반입 당일에 **비어 있는 상태의 백업**을 한 번 떠 둔다. 복원 절차가 이 환경에서 도는지를
사고가 나기 전에 확인하는 것이 목적이다.

이 서버에는 Node가 없으므로 `docker`로만 한다 (0절). 첨부는 **묶음에 든 앱 이미지의 `tar`**로 뜬다(`tools`) — 폐쇄망에서는 다른
이미지를 받아 올 수 없다. 결과는 표준 출력으로 받아 호스트의 파일에 쓴다.

```bash
mkdir -p ~/workfluence/backups/first
docker exec workfluence-postgres pg_dump -U workfluence -Fc workfluence > ~/workfluence/backups/first/db.dump
docker compose -f compose.yml --env-file .env run --rm --no-deps -T --entrypoint tar tools -czf - -C /data/attachments . > ~/workfluence/backups/first/attachments.tar.gz
ls -lh ~/workfluence/backups/first/
tar -tzf ~/workfluence/backups/first/attachments.tar.gz | wc -l
```

`db.dump`가 **0바이트가 아닌지** 반드시 본다. `pg_dump`가 실패해도 리다이렉션은 파일을
만들기 때문에, 크기를 안 보면 빈 백업을 떠 놓고 안심하게 된다.

마지막 줄은 첨부 백업을 **끝까지 열어 보고** 든 것의 수를 센다. 숫자만 나오면 된다(아직 첨부가 없으면 `1` — 맨 위 디렉토리 하나다).
`gzip: stdin: not in gzip format`·`unexpected end of file`이 함께 나오면 백업이 깨졌거나 다른 글이 섞였다 — 그 백업을 쓰지 않는다.

> 평소의 백업 주기와, 되살릴 때의 순서는 [`docs/운영가이드_운영이관.md`](운영가이드_운영이관.md) 3.2절·10절에 있다.

## 10. 사내 LLM 연결하기 — 반입 뒤, LLM 서버가 준비된 날

workfluence에 사내 LLM(vLLM)을 붙이는 절차다. **반입한 날 하지 않아도 된다.** 순서대로 따라 하면 되고, **`compose.yml`은 고치지 않는다.**

**준비할 것** — LLM 서버 담당에게 받는다.

| 무엇 | 예 |
|---|---|
| 주소 | `http://llm.example.internal:8000/v1` — **끝의 `/v1`까지** |
| 모델 이름 | `Qwen/Qwen3-32B` — LLM 서버의 모델 목록에 보이는 이름 그대로 |
| API 키 | 있으면 받는다. 없어도 된다 |
| 사내 인증 기관 인증서 | **주소가 `https`일 때만.** PEM 파일 하나 |

**① API 키가 있으면 — 마스터 키를 만든다.** `.env`에 `WF_LLM_MASTER_KEY`가 이미 채워져 있으면 건너뛴다.

```bash
openssl rand -base64 32
```

출력을 `.env`의 `WF_LLM_MASTER_KEY=` 뒤에 그대로 붙인다. **이 값은 백업과 다른 곳에 따로 적어 둔다** — 잃으면 등록한 키를 모두 다시
넣어야 한다(장애대응 7.26절).

**② 주소가 `https`이면 — 사내 인증 기관 인증서를 둔다.** `http`면 건너뛴다.

```bash
mkdir -p ca
cp <받은 인증서 파일> ca/ca.pem
chmod 755 ca
chmod 644 ca/ca.pem
```

앱은 컨테이너 안의 다른 계정(`node`)으로 이 디렉토리를 지나 파일을 읽는다 — 그래서 `755`·`644`다(비밀이 아니다 — 기관의 공개 인증서다). 작업 계정의
기본 권한(umask)이 좁으면 묶음을 풀 때 `ca`가 `750`·`700`이 된다. **디렉토리를 지나지 못하면 앱은 파일이 없는 것으로 알고 로그도 없이** 이 기관을 모르는 채로
돈다. 파일만 읽지 못하면 로그에 `Ignoring extra certs from … Permission denied`가 남는다(장애대응 7.41절). 이름은 꼭 `ca.pem`이다. 기관이 여럿이면 한 파일에 이어 붙인다. 앱이 이 기관을 믿게 된다 — 보안 검사(TLS)는 끄지 않는다.
사내 인증(OIDC)과 사내 메일 API(10-1절)도 같은 파일을 쓴다. `ca` 디렉토리는 묶음을 풀 때 함께 생긴다(안내 파일 `ca/README.md`가 들어 있다).
`cp`가 **`Permission denied`**면 그 디렉토리를 도커가 만든 것이다(묶음에 `ca`가 없던 옛 묶음) — `sudo chown "$(id -un)" ca` 뒤에 다시 한다.

**③ 앱을 다시 만든다** — ①이나 ②를 했을 때만.

```bash
docker compose -f compose.yml --env-file .env up -d --force-recreate api
docker compose -f compose.yml ps
```

`api`가 `healthy`가 될 때까지 기다린다. **`--force-recreate`를 빼지 않는다** — ②만 했으면(파일 하나를 두었을 뿐) 설정이 바뀌지 않아
`up -d`는 아무것도 하지 않고, 앱은 인증 기관을 모르는 채로 남는다. `restart`는 ①의 `.env` 변경을 읽지 않는다.

**④ 등록한다.** 브라우저에서 `root`로 로그인 → 위 막대 **관리** → 왼쪽 칸 관리 묶음의 **LLM 연결**(왼쪽 칸이 접혀 있으면 위 막대 맨 왼쪽의 세 줄 단추로 편다) → 이름·주소·모델·API 키를 넣고 **등록**.
곧바로 연결을 확인해 **"연결됨"**과 모델 목록이 뜬다. "등록한 모델이 목록에 없다"가 함께 뜨면 모델 이름을 목록에 보이는 대로 고쳐
다시 등록한다(지우고 등록).

**⑤ 물어 본다.** 일반 사용자로 로그인 → 위 막대의 **LLM 질문**에서 아무거나 묻는다. 답이 **쓰이는 대로** 나오면 끝이다.

**⑥ (원하면) 관리자에게 맡긴다.** `root`로 **사용자 관리** → 그 관리자 줄의 **"LLM 연결 관리"**를 켠다. 그 관리자에게도 **LLM 연결**
메뉴가 생긴다. 끄면 거둔다. 주고 거두는 것은 `root`만 한다.

| 이렇게 되면 | 까닭과 할 일 |
|---|---|
| "연결 안 됨 — LLM 서버에 닿지 않는다 (ECONNREFUSED)" 등 | 주소·포트가 틀렸거나 망이 막혔다 — 장애대응 7.24절 |
| "연결 안 됨 — … (UNABLE_TO_VERIFY_LEAF_SIGNATURE)"·"(SELF_SIGNED_CERT_IN_CHAIN)" | 앱이 사내 인증 기관을 모른다 — ②를 하고 ③(`--force-recreate`)으로 다시 만든다. 그래도 같으면 `ca/ca.pem`이 **그 기관의** 인증서인지 본다(중간 기관이 있으면 그것까지 이어 붙인다). 앱이 파일을 걸었는지: `docker exec workfluence-api grep -az '^NODE_EXTRA_CA_CERTS=' /proc/1/environ` — 한 줄이 나와야 한다. 나오지 않으면 `ls -ld ca ca/ca.pem`(`drwxr-xr-x`·`-rw-r--r--`여야 한다) → ② → ③ |
| "WF_LLM_MASTER_KEY가 없어 API 키를 저장할 수 없다" | ①을 하지 않았다. ①과 ③을 하고 다시 등록한다 |
| 등록 칸 아래에 "http 주소다 — … 암호화되지 않고 사내망을 지난다" | 알림이다(막지 않는다). LLM 서버가 https를 받으면 https 주소로 등록한다 |
| 답이 끝에 한꺼번에 나온다 | 앞단의 다른 프록시가 모은다 — 장애대응 7.25절 |

**다 되었으면** 날짜·LLM 이름·"연결됨"·답이 흘러나왔는지를 운영 기록에 적는다 — 보류 29(사내 LLM 실연동)를 닫는 근거가 된다.

## 10-1. 사내 메일 연결하기 — 반입 뒤, 메일 API 담당에게 주소를 받은 날

workfluence가 **부른 사람(멘션)에게 메일로도 알리게** 하고, 비밀번호를 잊은 사람이 **내 email로 재설정 링크**를 받게 하는 절차다(Phase 19).
**반입한 날 하지 않아도 된다** — 메일을 켜지 않으면 알림은 앱 안 알림함으로만 가고, 비밀번호 찾기는 관리자에게 초기화 요청만 된다.
순서대로 따라 하면 되고, **`compose.yml`은 고치지 않는다.** 사내 메일은 API로 보내기만 한다 — 설정은 `.env`의 몇 줄이다.

**준비할 것** — 메일 API 담당에게 받는다.

| 무엇 | 예 |
|---|---|
| 보내는 주소 | `https://mail.example.internal/api/v1/email/send` — **끝의 `/send`까지.** 마크다운으로 보내려면 `…/send_markdown` |
| 인증 | 있으면 헤더 이름과 값(예: `Authorization` / `Bearer <토큰>`, `X-API-Key` / `<키>`). 없으면 비워 둔다 |
| 사내 인증 기관 인증서 | **주소가 `https`이고 사내 기관이 서명했을 때만.** 10절 ②와 같은 파일(`ca/ca.pem`) |
| 시험으로 받을 주소 | 내 메일 주소 |

**① `.env`에 적는다.** 편집기(`vi .env` 등)로 열어 아래 줄을 채운다 — 없는 줄은 끝에 더한다. **아직 켜지 않는다**(`WF_MAIL_ENABLED`는 ③ 뒤에).

```
WF_MAIL_API_URL=https://mail.example.internal/api/v1/email/send
WF_MAIL_FORMAT=text
WF_MAIL_SENDER_NAME=위키
WF_MAIL_AUTH_HEADER=
WF_MAIL_AUTH_VALUE=
WF_PUBLIC_URL=https://<호스트>:8443
```

- `WF_MAIL_FORMAT`은 `text`(평문) 또는 `markdown`이다. `markdown`이면 주소도 `…/send_markdown`으로 적는다.
- `WF_MAIL_SENDER_NAME`은 받는 사람에게 보이는 보내는 이름이다. 비우면 `위키`다.
- 인증이 있으면 헤더 이름과 **값 전체**(`Bearer `까지)를 적는다. 둘 중 하나만 적으면 앱이 뜨지 않는다. 값에 `$`가 있으면 홑따옴표로 감싼다(`WF_MAIL_AUTH_VALUE='…'`) —
  compose가 `$`를 변수로 읽는다(3절).
- `WF_PUBLIC_URL`은 메일 속 링크의 주소다(사람들이 브라우저에 치는 주소 — 7절). **`https://`부터 호스트와 포트까지만** 적는다(`https://<호스트>:8443`) — `https://`를 빼거나
  경로(`/wiki` 등)를 붙이면 앱이 뜨지 않는다(열리지 않는 링크를 보내지 않게 — 위키는 그 주소의 맨 위에서 돈다, 장애대응 4절). 비우면 부르기 메일은 링크 없이 보내고, **메일로 비밀번호 재설정은 쓰이지 않는다** — 그 메일은 링크가 전부라 비밀번호 찾기에
  그 단추가 보이지 않는다.
- 메일 API 주소가 `http`면 부르기 메일과 함께 **재설정 링크도 평문으로** 사내망을 지난다. 링크는 30분·한 번이고 쓰면 죽는다. 사내 보안이 문제 삼으면 켠 뒤
  관리 → 운영 설정의 **email로 비밀번호 재설정 (passwordResetMail)** 을 **끔**으로 둔다 — 이미 보낸 링크도 막힌다.

**② 주소가 `https`이고 사내 기관이면** — 10절 ②대로 `ca/ca.pem`을 둔다. `http`면 건너뛴다.

**③ 시험 메일을 한 통 보낸다** — 켜기 전에. 설정(주소·형식·보내는 이름·인증 헤더 이름 — 값은 가린다)을 먼저 말하고 한 통을 보낸다.

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/mail-test.js <내 메일 주소>
```

창에 **`보냈다 — HTTP 200`**이 나오고 메일함에 **`[위키] 시험 메일`**이 오면 된다(안 보이면 스팸함도). 아니면 창이 까닭을 말한다 — 장애대응 7.21절의 표대로 고치고
다시 친다. `.env`를 고치면 이 명령은 곧바로 새 값을 읽는다.

**④ 켠다.** `.env`의 두 줄을 이렇게 바꾸고 앱을 **다시 만든다.**

```
WF_MAIL_ENABLED=true
WF_MAIL_MOCK=false
```

```bash
docker compose -f compose.yml --env-file .env up -d --force-recreate api
docker compose -f compose.yml ps
```

`api`가 `healthy`가 될 때까지 기다린다. **`--force-recreate`를 빼지 않는다** — `restart`는 `.env`를 다시 읽지 않는다. `WF_MAIL_MOCK`을 `true`로 둔 채 켜면 앱이
뜨지 않는다(메일이 나간다고 믿는데 로그로만 남는 상태를 막는다).

**⑤ 불러 본다.** 두 계정이 필요하다 — 다른 사람 계정으로 로그인해 아무 문서의 댓글에 `@<내 아이디>`를 넣어 저장한다. 내 메일함에
**`[위키] <그 사람 이름> 님이 회원님을 불렀습니다`**가 오면 끝이다. **메일은 계정에 email이 있는 사람에게만 간다** — 가입 때 적은 것, 사내 계정은 로그인 때
받은 것이다. 첫 `root` 계정은 email이 없어 알림함으로만 받는다.

**⑥ 재설정 메일을 한 통 받아 본다**(Phase 19) — **email이 있는 일반 사용자나 관리자 계정**으로 한다(root는 이 길을 쓰지 않는다). 로그인하지 않은 창에서
로그인 화면 → **아이디·비밀번호 찾기** → 오른쪽 카드에 그 계정의 **이름**(화면에 보이는 그대로)과 **email**을 넣고 **내 email로 재설정 링크 받기**. 그 메일함에
**`[위키] 비밀번호 재설정`**이 오고, 안의 링크가 **`WF_PUBLIC_URL`의 주소로 시작하면** 된다. 링크를 열어 새 비밀번호를 정하고 그 비밀번호로 로그인되는지 본다
(시험 계정이 아니면 링크를 열지 않고 메일을 지워도 된다 — 비밀번호는 바뀌지 않는다). 한 계정에 5분에 한 통이라 곧바로 다시 눌러도 새 메일은 오지 않는다.

| 이렇게 되면 | 까닭과 할 일 |
|---|---|
| ③이 `받지 않았다 — HTTP 400`·`401`·`404` 등 | 창의 까닭과 `응답:` 줄을 본다 — 장애대응 7.21절 |
| ③이 `보내지 못했다 — … 인증서를 믿지 못했다` | ②를 하고 ③을 다시 친다 |
| ④ 뒤 `api`가 뜨지 않는다(`환경변수 검증 실패`) | 그 줄이 말하는 `WF_MAIL_` 키를 고친다 — 장애대응 7.21절 "앱이 뜨지 않는다" |
| ③은 되는데 ⑤의 메일이 안 온다 | 알림함에는 왔는지, `--force-recreate`로 다시 만들었는지 — 장애대응 7.21절 |
| ⑥의 **내 email로 재설정 링크 받기** 단추가 없다 | `WF_PUBLIC_URL`이 비었거나, 메일이 켜지지 않았거나, 운영 설정에서 꺼져 있다 — 장애대응 7.39절 |
| ⑥의 메일이 안 온다 · 링크가 다른 주소로 시작한다 | 감사로그의 `auth.password.reset.request` 상세(`result`)로 까닭을 본다. 주소는 `WF_PUBLIC_URL`을 고치고 ④처럼 다시 만든다 — 장애대응 7.39절 |

**다 되었으면** 날짜·메일 API 주소의 호스트·③의 결과·⑤와 ⑥의 메일이 닿았는지를 운영 기록에 적는다 — 보류 18(사내 메일 API 실연동)을 닫는 근거가 된다.

## 11. 새 버전을 들여온다 — 두 번째 반입부터

한 번 설치한 서버에 **새 묶음**을 올리는 순서다. 표 구조는 앞으로만 바뀐다 — 새 판을 올린 뒤에는 옛 판으로 그냥 돌아갈 수 없고,
⑤의 백업이 되돌리는 유일한 길이다. 옛 묶음의 tar도 지우지 않고 둔다.

**① 묶음이 온전한지 먼저 본다** — 지금 설치를 건드리기 전에. 묶음 tar 옆에 같은 이름의 `.sha256` 파일이 함께 온다.

```bash
cd /media/반입
cat workfluence-<날짜>.tar.sha256
sha256sum -c workfluence-<날짜>.tar.sha256
```

`cat`의 앞 64자가 따로 간 기록(0.1절)과 같고 `OK`여야 한다. 아니면 여기서 멈춘다 — 지금 설치는 그대로다.

**② 지금 버전을 적는다.**

```bash
cd ~/workfluence/deploy
cat MANIFEST.txt
```

**③ 새 묶음을 같은 자리에 푼다.** `.env`·`certs/`·`ca/ca.pem`은 묶음에 없어서 그대로 남는다. **`nginx.conf`는 새 것으로 바뀐다** —
고쳐 썼으면(운영이관 5절 — 업로드 상한) 먼저 복사해 두고, 푼 뒤에 같은 줄을 다시 고친다.

```bash
cp nginx.conf nginx.conf.before-update
tar -xf /media/반입/workfluence-<날짜>.tar -C ~/workfluence/deploy --strip-components=1
sha256sum -c SHA256SUMS
cat MANIFEST.txt
diff nginx.conf.before-update nginx.conf
```

`sha256sum`의 모든 줄이 `OK`여야 한다. `diff`가 무언가를 내면 그 줄이 옛 판에서 고쳤거나 새 판이 바꾼 것이다 — 고쳐 썼던 값이면 다시 넣는다.

**④ `.env`에 새 키가 있는지 본다.** 새 판이 읽는 키 가운데 `.env`에 없는 것을 뽑는다.

```bash
comm -23 <(grep -o '^WF_[A-Z0-9_]*' env.template | sort) <(grep -o '^WF_[A-Z0-9_]*' .env | sort)
```

아무것도 안 나오면 넘어간다. 나온 키 가운데 3절 표의 필수 키가 있으면 3절의 두 줄(줄 만들기 `for` 줄과 그 키의 `sed` 줄)로 채운다.
나머지는 비워 두면 기본값이다.

거꾸로 **새 판이 읽지 않는 키**도 본다 — 나온 줄은 아무 일도 하지 않는다(compose가 앱에 넘기지 않는다).

```bash
comm -13 <(grep -o '^WF_[A-Z0-9_]*' env.template | sort) <(grep -o '^WF_[A-Z0-9_]*' .env | sort)
```

> **Phase 18부터 메일 설정이 틀리면 `tools`도 멈춘다** — ⑦의 표 만들기가 `환경변수 검증 실패 … WF_MAIL_…`로 멈추면 그 키부터 고친다(장애대응 7.21절). 옛 판에서
> 운영(`production`)인데 `WF_MAIL_ENABLED=true`이고 `WF_MAIL_MOCK`을 적지 않았다면(기본 `true` — 보내지 않고 로그로만 남겼다) 새 판은 뜨지 않는다: 메일을 쓸 거면
> `WF_MAIL_MOCK=false`와 10-1절의 설정을, 아니면 `WF_MAIL_ENABLED=false`를 적는다.
>
> **Phase 18 전의 판에서 메일을 썼다면** `WF_MAIL_FROM`·`WF_MAIL_API_TOKEN`이 나온다 — 두 키는 없어졌다. 보내는 이름은 `WF_MAIL_SENDER_NAME`, 토큰은
> `WF_MAIL_AUTH_HEADER=Authorization`·`WF_MAIL_AUTH_VALUE=Bearer <토큰>`으로 옮기고 옛 줄을 지운다. 요청 모양도 사내 메일 API 설명대로 바뀌었다 — 10-1절 ③의
> 시험 메일로 확인한다.

> **Phase 13 전에 설치한 서버**(앱이 소유 계정으로 붙던 판)라면 `WF_PG_APP_PASSWORD`가 나온다. 반드시 채운다:
>
> ```bash
> grep -q '^WF_PG_APP_PASSWORD=' .env || echo 'WF_PG_APP_PASSWORD=' >> .env
> sed -i "s/^WF_PG_APP_PASSWORD=.*/WF_PG_APP_PASSWORD=$(openssl rand -hex 16)/" .env
> ```
>
> 이 값이 없으면 ⑤부터 compose가 `WF_PG_APP_PASSWORD를 .env에 설정`이라며 아무것도 하지 않는다. 계정은 ⑦의 표 만들기가 만든다 —
> **⑦을 ⑧보다 먼저 한다.** 거꾸로 하면 앱이 아직 없는 계정으로 붙으려다 데이터베이스에 붙지 못한다(장애대응 7.31절).

**⑤ 사람들에게 알리고, 앱을 멈추고, 백업을 뜬다.** 멈춘 뒤에 떠야 그 뒤의 글이 섞이지 않는다. 명령은 8절과 같다 — 디렉토리만 오늘
날짜로 둔다. 이 백업은 아직 옛 이미지로 뜬다(`tar`는 어느 판에나 있다).

```bash
docker compose -f compose.yml --env-file .env stop api nginx
B=~/workfluence/backups/$(date +%Y%m%d)-before-update
mkdir -p "$B"
docker exec workfluence-postgres pg_dump -U workfluence -Fc workfluence > "$B/db.dump"
docker compose -f compose.yml --env-file .env run --rm --no-deps -T --entrypoint tar tools -czf - -C /data/attachments . > "$B/attachments.tar.gz"
ls -lh "$B"
tar -tzf "$B/attachments.tar.gz" | wc -l
```

`db.dump`가 0바이트가 아닌지, 마지막 줄이 숫자만 내는지 본다(8절). 첨부가 있는 서버인데 `1`이면 엉뚱한 볼륨을 떴다 — 1절의
디렉토리에서 쳤는지 본다.

**⑥ 새 이미지를 올린다.**

```bash
docker load -i images.tar
docker images | grep -E 'workfluence-app|postgres|nginx'
```

**⑦ 표를 만든다** — 새 판의 표 구조로 바꾸고, 앱 계정과 권한을 맞춘다.

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/db/migrate.js
```

5절과 같이 `앱 계정 workfluence_app: 권한 적용`이 나와야 한다.

**⑧ 다시 띄운다.**

```bash
docker compose -f compose.yml --env-file .env up -d
docker compose -f compose.yml --env-file .env ps
```

`up -d`가 이미지가 바뀐 것을 알아채고 컨테이너를 새로 만든다. 셋이 `healthy`가 될 때까지 기다린다.

**⑨ 사후 검증** — 7절 표를 다시 본다. 적어도 앱이 산다·로그인된다·문서를 만든다·파일이 붙는다·7.2절 두 가지. 그리고 새 `MANIFEST.txt`의
버전과 git sha를 작업 기록에 적는다.

새 판이 뜨지 않으면 먼저 `docker compose -f compose.yml --env-file .env logs api --tail 50`의 첫 오류 줄을 보고 장애대응 가이드로 간다.
옛 판으로 되돌리는 것은 **혼자 하지 않는다** — 옛 묶음의 tar와 ⑤의 백업을 들고 개발 담당과 함께 한다. 표 구조가 이미 새 판으로
바뀌었으므로 옛 이미지만 다시 올려서는 안 되고, ⑤의 백업으로 되살려야 한다.
