## 0. 어떤 순서로 보는가

세 가지를 이 순서로 확인한다. 순서를 바꾸면 엉뚱한 곳을 고친다.

```
① 켜져 있는가        docker compose ps          — 컨테이너가 도는지, healthy인지
② 창고가 붙었는가     /api/health 의 db 값        — ok가 아니면 데이터베이스 문제다
③ 무슨 말을 하는가    docker compose logs        — 앱이 남긴 기록. event 코드와 요청 번호로 찾는다 (7.28절)
```

**코드를 의심하기 전에 서비스가 떠 있는지 본다.** 내려간 서비스를 코드 문제로 오진하는 것이 가장 흔한 낭비다.

> **명령은 묶음을 푼 디렉토리에서 친다** — 운영 서버는 `~/workfluence/deploy`(반입 가이드 1절), 개발 서버는 저장소의 `deploy`.
> 거기서는 `docker compose -f compose.yml --env-file .env …`와 `-f`를 뺀 `docker compose …`가 같은 것을 가리킨다.
> **`pnpm`으로 시작하는 명령은 저장소가 있는 곳(개발·빌드 서버)에서만 된다.** 폐쇄망에서는 옆에 적은 `tools` 명령을 쓴다 —
> 앱 이미지로 한 번 돌고 끝나는 작업 칸이다(운영이관 0절).

## 2. 데이터베이스를 못 쓰는 상태

앱은 살아 있고 데이터베이스만 안 될 때가 가장 흔하다. 이 시스템은 그 상태를 **정상으로 보고하지 않도록** 만들었다.

앱 컨테이너 **안에서** 묻는다. 앱의 포트(3000)는 바깥에 열지 않아 호스트에서 `127.0.0.1:3000`으로는 닿지 않고, 이미지에 `curl`이 없어
안에 있는 Node로 묻는다.

```bash
docker exec workfluence-api node -e "fetch('http://127.0.0.1:3000/api/health').then(async r=>console.log(r.status, await r.text())).catch(e=>console.log('응답 없음', e.cause?.code ?? e.message))"
```

nginx를 거쳐 물어도 된다: `curl -sk https://localhost:8443/api/health`(`8443`은 `.env`의 `WF_HTTPS_PORT`).

| 응답 | 뜻 |
|---|---|
| `200 {"status":"ok","db":"ok",...}` | 앱과 데이터베이스 모두 정상 |
| `503 {"status":"degraded","db":"unreachable"}` | 앱은 살아 있고 데이터베이스가 안 된다 |
| `응답 없음 …` 또는 `container … is not running` | 앱 자체가 죽었다. 4절로 |

`degraded`가 나오면 순서대로 본다.

```bash
docker compose -f compose.yml --env-file .env ps                        # postgres가 healthy인가
docker compose -f compose.yml --env-file .env logs postgres --tail 50
docker compose -f compose.yml --env-file .env logs api --tail 50 | grep health.db_failed   # 앱이 본 까닭(error)
df -h /                                                                 # 디스크가 찼는가
```

`health.db_failed` 줄의 `error`가 `28P01 password authentication failed for user "workfluence_app"`이면 데이터베이스는 멀쩡하고 **앱 계정으로
붙지 못한 것**이다 — 7.31절.

**디스크 부족을 먼저 확인한다.** 디스크가 차면 데이터베이스가 쓰기에 실패하고, 그 증상은 연결 오류처럼 보인다. 원인과 증상이 달라 추적이 어렵다.

컨테이너 헬스체크가 실패를 인식하면 자동으로 다시 시작한다. 반복해서 죽고 살아나면 자동 복구에 맡기지 않고 로그를 본다.

## 3. 화면이 전부 404인데 상태는 정상

**이 유형을 먼저 알아 두어야 한다.** 화면 파일의 위치 설정이 어긋나면 모든 화면이 404가 되는데, 상태 확인은 API만 보므로 정상이라고 답한다. 로그에도 아무것도 남지 않는다.

Phase 0에서 이 결함을 실제로 한 번 만들었고, 그래서 **위치가 어긋나면 프로그램이 켜지지 않도록** 고쳤다. 지금은 아래 메시지를 내고 멈춘다.

```
Error: WF_SERVE_WEB=true인데 SPA 산출물이 없다: <기대한 경로>
  WF_WEB_DIST=<설정값> (기준 <기준 경로>)
  개발이면 'pnpm build'를, 컨테이너면 이미지 레이아웃과 WF_WEB_DIST를 확인한다.
```

즉 **이제는 404가 아니라 기동 실패로 나타난다.** 만약 그래도 404가 보이면 안내 데스크가 잘못된 곳으로 넘기고 있는 것이니 nginx 설정을 본다. 경위는 트러블슈팅 T-013.

## 4. 켜지다가 바로 죽는다

기동 로그의 **첫 오류 줄**을 본다. 뒤쪽 줄은 그 결과일 뿐이다.

```bash
docker compose -f compose.yml --env-file .env logs api --tail 80
```

| 메시지에 있는 말 | 뜻 | 조치 |
|---|---|---|
| 스키마에 없는 키 / unrecognized key | **개발 실행(`pnpm dev`·`pnpm start`)에서** 설정 이름이 틀렸거나 이 버전이 모르는 항목이다. compose로 띄운 앱에서는 나오지 않는다(아래) | `.env`에서 그 항목을 지우거나 이름을 고친다 |
| 운영에서 자동 마이그레이션 거부 | 운영에 자동 구조 변경이 켜져 있다 | `.env`의 `WF_DB_AUTO_MIGRATE`를 `false`로 |
| SPA 산출물이 없다 | 화면 파일 위치 설정 | 3절 |
| 테스트 DB가 없다 | 운영에 시험용 설정이 섞였다 | `WF_ENV`가 `production`인지 확인 |
| `WF_DATABASE_URL`을 말하며 멈춘다 | 비밀번호에 `/ ? # %` 같은 글자가 있어 접속 주소가 깨졌다 | 7.31절 |

**개발 실행에서는 설정 항목을 모르면 일부러 켜지지 않는다.** 이름이 한 글자 틀렸을 때 조용히 무시되고 값이 안 먹는 상태가 훨씬 찾기 어렵기 때문이다. 기동 실패는 불편하지만 정직한 실패다.

**compose로 띄운 운영에서는 다르다.** 앱에는 `compose.yml`의 `environment:`에 적힌 키만 넘어간다. `.env`에 이름을 틀리게 적은 키는
**앱까지 가지 않아 조용히 무시되고**, 그 설정은 기본값으로 돈다 — 켜지는데 값이 안 먹는 쪽이다(`WF_PG_APP_PASSWORD`처럼 compose가
반드시 요구하는 키만 빠지면 알려 준다 — 7.31절). 바꾼 값이 안 먹으면 이름을 대조한다(묶음을 푼 디렉토리에서):

```bash
comm -13 <(grep -o '^WF_[A-Z0-9_]*' env.template | sort) <(grep -o '^WF_[A-Z0-9_]*' .env | sort)
```

나오는 키는 이 배포가 읽지 않는다 — 오타이거나 옛 키다. `env.template`에 있는 이름으로 고치고 `docker compose -f compose.yml --env-file .env up -d`로
다시 만든다.

## 5. 느려졌다

| 확인 | 명령 | 판단 |
|---|---|---|
| 디스크 여유 | `df -h /` | 5GB 미만이면 먼저 정리한다 |
| 컨테이너 자원 | `docker stats --no-stream` | 메모리가 한계에 붙어 있는지 |
| 데이터베이스 연결 수 | postgres 로그 | 연결 고갈 메시지 |
| 안 쓰는 이미지·캐시 | `docker system df` | 쌓인 것이 디스크를 먹는다 |

디스크가 차면 **옆 컨테이너의 쓰기 실패로 번진다.** 먼저 지워야 할 것은 안 쓰는 이미지와 빌드 캐시다. 데이터 볼륨은 손대지 않는다.

## 6. 재부팅 후 안 올라온다

모든 서비스는 자동 재시작으로 설정돼 있다. 그래도 안 올라오면 순서대로 본다.

```bash
systemctl is-active docker                                  # 도커 자체가 떴는가
docker compose -f compose.yml --env-file .env ps            # 컨테이너 상태
docker compose -f compose.yml --env-file .env up -d         # 수동 기동
```

**재부팅 후 자동 기동은 반드시 실제로 한 번 확인해야 한다.** 설정만 보고 넘기면 정작 필요한 날에 안 올라온다. 이 확인은 Phase 0 완료 기준에 들어 있다.

## 7. 데이터를 잃었다

되돌리는 스크립트는 두지 않았다. **되돌림은 백업 복원으로 처리한다.** 잘못된 되돌리기가 데이터를 더 잃게 만들기 때문이다.

| 잃은 것 | 복원 대상 |
|---|---|
| 문서·계정·기록 | 데이터베이스 덤프 |
| 첨부 파일 | 첨부 디렉토리 |

두 가지를 **같은 시점의 것으로 함께** 복원해야 한다. 한쪽만 되돌리면 문서는 있는데 첨부가 없는 상태가 된다.

**복원 절차는 7.18절에 있고, 연습은 실제로 했다** (Phase 5). 볼륨 둘을 지우고 백업에서
되살려 모든 테이블의 행 수가 맞는 것을 확인했다 — 기록은 `P5_검증기록_Release` 3.1절이다.
순서를 건너뛰면 되살릴 수 있었던 것까지 잃으므로 **7.18절의 번호를 그대로 따른다.**

## 7.1 로그인이 안 된다 (Phase 1)

로그인 실패는 **응답만 보고 원인을 알 수 없게** 되어 있다. 없는 계정·틀린 비밀번호·승인
대기·잠김·정지가 모두 같은 401 문구를 낸다 (계정 열거 방지). **원인은 감사로그에 있다.**

```bash
docker exec workfluence-api node -e "fetch('http://127.0.0.1:3000/api/health').then(async r=>console.log(await r.text()))"
```

관리자로 로그인해 감사로그 화면을 열거나, DB에서 직접 본다.

| 기록의 `reason` | 뜻 | 조치 |
|---|---|---|
| `unknown` | 그런 아이디가 없다 | 아이디를 확인한다 |
| `wrong` | 비밀번호가 틀렸다 | 5회까지 |
| `pending` | 승인 대기다 | 관리자가 사용자 관리에서 승인한다 |
| `locked` | 잠겼다 | 15분 기다리거나 관리자가 잠금 해제 |
| `suspended` | 관리자가 **정지**했다 (Phase 13) | 7.32절 |
| `changed` | 비밀번호를 확인하는 사이 **관리자가 그 비밀번호를 초기화했다** — 옛 비밀번호로 들어온 것이 되어 들이지 않았다 (Phase 13). 본인의 비밀번호 변경은 로그인과 같은 줄에 서서 이렇게 되지 않는다 | 관리자에게 받은 임시 비밀번호로 들어간다. 초기화를 부탁한 적이 없는데 보이면 관리자에게 알린다 — 누가 옛 비밀번호를 쓰고 있었다 |
| `no_role_mapped` | IdP 그룹이 역할로 매핑되지 않는다 | `WF_OIDC_ROLE_MAP`을 본다 |

관리자가 아무도 없어 감사로그 화면을 열 수 없으면(설치 직후) 7.29절이다.

## 7.2 모두가 로그아웃됐다

세션은 데이터베이스에 있다 (`sessions` 테이블). **데이터베이스가 끊기면 전원이 로그아웃된다.**
2절을 먼저 본다. `WF_SESSION_SECRET`을 바꿔도 기존 세션이 전부 무효가 된다 — 바꿀
이유가 없으면 바꾸지 않는다.

## 7.3 사내 계정 로그인 버튼이 없다 / 눌러도 안 된다

| 증상 | 원인 | 조치 |
|---|---|---|
| 버튼이 아예 없다 | `WF_OIDC_ENABLED=false` | 켜야 하면 설정을 바꾸고 다시 기동한다 |
| 켰는데 기동이 안 된다 | issuer·client·redirect 중 비어 있는 값이 있다 | 기동 로그가 어느 키인지 알려 준다. **일부러 멈춘다** — 버튼만 있고 안 눌리는 상태를 만들지 않는다 |
| `state가 일치하지 않는다` | 로그인 도중 세션이 끊겼거나 링크를 재사용했다 | 로그인 화면에서 다시 시작한다 |
| `이 계정은 정지돼 있다 — 관리자에게 문의한다` (Phase 13) | 관리자가 그 사내 계정을 **정지**했다. 회사 로그인은 됐지만 이 위키가 거절한다 | 7.32절 |
| `이 계정에 부여할 역할이 없다` | 그 사람의 IdP 그룹이 매핑표에 없다 | `WF_OIDC_ROLE_MAP`에 그룹을 넣는다. 매핑 안 되면 **기본 거부**다 |
| `사내 인증 서버와 처리하지 못했다` (Phase 11) | 앱이 사내 IdP와의 처리에 실패했다. 앱 로그의 **`auth.oidc_failed`** 줄(`step`·`error`)이 까닭을 말한다: `UNABLE_TO_VERIFY_LEAF_SIGNATURE`·`SELF_SIGNED_CERT_IN_CHAIN`이면 사내 인증 기관을 모른다 · `ENOTFOUND`·`ECONNREFUSED`·`ETIMEDOUT`이면 주소나 망 · `OIDC Discovery 실패: HTTP 404`면 `WF_OIDC_ISSUER`가 틀렸다 | 인증 기관이면 [반입 가이드](운영가이드_반입.md) 10절 ②·③(`ca/ca.pem`을 두고 `--force-recreate`로 다시 띄운다). 주소·망이면 IdP 담당과 확인. 줄 찾기: `docker compose -f compose.yml logs api --since 15m \| grep auth.oidc_failed` |
| `토큰 교환 실패: HTTP 401`(또는 400) | IdP가 앱의 client를 받지 않았다 | `WF_OIDC_CLIENT_ID`·`WF_OIDC_CLIENT_SECRET`·`WF_OIDC_REDIRECT_URI`를 IdP 등록값과 맞춘다. 같은 `auth.oidc_failed` 줄이 남는다 |
| `사내 인증이 보낸 토큰을 받아들이지 못했다` (401) | 앱이 IdP가 준 토큰(id_token)을 검증하다 거절했다 — **다시 해도 같다.** `auth.oidc_failed` 줄의 `error`: `JWTClaimValidationFailed: unexpected "aud" claim value`면 `WF_OIDC_CLIENT_ID`가 IdP의 것과 다르다 · `unexpected "iss"`면 `WF_OIDC_ISSUER` · `JWTExpired`면 앱 서버나 IdP의 시각이 어긋났다 · `JWSSignatureVerificationFailed`·`JWKSNoMatchingKey`면 IdP의 서명 키 | 설정값을 IdP 담당의 등록값과 대조한다. 시각이면 서버의 시간 동기화를 본다. 실패한 로그인은 감사로그 `auth.login.failure`(`method: oidc`, `reason: idp_rejected` — 닿지 않으면 `idp_unreachable`)로도 남는다 |

> **운영에서 모의 인증은 켜지지 않는다.** `WF_OIDC_MOCK=true`와 `WF_ENV=production`을 함께 주면
> 환경변수 검증이 기동을 거부한다. 운영 이미지에는 그 키를 넘기지도 않는다.

## 7.4 감사로그를 지우고 싶다

지울 수 없다. `audit_events`는 추가만 되도록 데이터베이스가 막고 있다.

```
ERROR: audit_events는 append-only다 (시도: DELETE)
```

위 문장은 소유 계정으로 지우려 할 때의 것이다. 기동 중인 앱의 계정(`workfluence_app`)에는 **고치고 지우는 권한 자체가 없어**
`permission denied for table audit_events`가 먼저 막는다 (Phase 13 — 두 겹이다).

보존 기간이 지난 기록은 월간 정리가 지운다 (Phase 4, FR-540) — 운영 서버에서는
`docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/audit-purge.js`, 저장소가 있는 곳에서는 `pnpm audit:purge`.
**보존 기간보다 최근 것은 지워지지 않고**, 기록을 고치는 것은 어떤 경우에도 막혀 있다 — 데이터베이스가
막는다. 보존 기간은 관리 화면에서 바꿀 수 있고 **90일보다 짧게는 내려가지 않는다.**
주기와 실행 방법은 [`docs/운영가이드_운영이관.md`](운영가이드_운영이관.md) 4.2절에 있다.

## 7.5 스페이스가 안 보인다 (Phase 2)

**Crew가 아니면 목록에 나오지 않고 주소로 들어가도 404다.** 일부러 그렇게 했다 — 403을 주면
"그 스페이스는 있다"가 새어 나간다. 로그에도 404로 남는다.

| 확인 | 방법 |
|---|---|
| Crew에 있나 | 그 스페이스의 owner나 관리자에게 확인. `space_members` 표 |
| 지워졌나 | `spaces.deleted_at`이 차 있으면 삭제된 것이다. **관리자가 휴지통 화면에서 되살린다**(Phase 15부터 **스페이스 관리 전체**를 맡겨 받은 사람도) |
| 중지됐나 | 보이긴 하는데 쓰기가 안 된다면 `status='suspended'`다 |

## 7.6 저장이 409로 막힌다

> **먼저 볼 것: 실시간 편집이 켜져 있으면 화면에서는 이 증상이 나오지 않는다** (Phase 6).
> 두 사람이 같은 페이지를 열면 서로의 글자가 바로 보이고 충돌 자체가 생기지 않는다.
> 그래도 409를 봤다면 ① `WF_COLLAB_ENABLED=false`로 꺼 두었거나 ② 화면이 아니라 API를
> 직접 호출했거나 ③ 실시간 편집 연결이 끊긴 채(편집 화면 아래가 빨갛다) 저장을 눌렀거나 셋 중 하나다.
> 7.19절을 먼저 본다.

정상 동작이다 (`P2_설계서_Page` 3.1절). 다른 사람이 먼저 저장했다는 뜻이고, 응답에 현재
버전과 내가 편집을 시작한 버전이 함께 온다.

```json
{"message":"다른 사용자가 먼저 저장했다...","currentVersionNo":5,"baseVersionNo":3}
```

**덮어쓰는 방법은 없다.** 최신을 불러와 다시 편집해야 한다. 쓰던 내용이 아깝다면 화면에서
복사해 둔 뒤 "최신 내용 불러오기"를 누른다.

혼자 쓰는데도 이 오류가 난다면 같은 페이지를 **다른 탭에서 열어 둔 것**이다 (실시간 편집이 꺼진 경우).

## 7.7 페이지를 지울 수 없다

하위 페이지가 있으면 막는다 — 고아 페이지를 만들지 않기 위해서다. 하위를 먼저 문서 보기의 **옮기기**로 다른 곳에
옮기거나(사용자 가이드 3.3절, 7.35절) 지운다.

## 7.8 페이지를 옮길 수 없다

| 메시지 | 뜻 |
|---|---|
| `페이지를 자기 자신이나 자손 아래로 옮길 수 없다` | 트리가 고리가 된다 |
| `부모 페이지를 찾을 수 없다` | 부모가 없거나 지워졌거나 **다른 스페이스**의 페이지다. 스페이스를 넘나드는 이동은 없다 — 새로 만들어 옮긴다. 다른 스페이스의 페이지도 없는 것과 같게 답한다(Phase 14 — 따로 답하면 아는 페이지가 살아 있는지를 알려 준다) |
| `페이지 트리 깊이는 10를 넘을 수 없다` | 옮기는 가지의 **자손까지** 세서 판정한다 |

화면에서 옮기는 법과 그 밖의 거절(차례를 기다리다 돌려보냄 등)은 7.35절이다.

## 7.9 파일 첨부가 안 된다 (Phase 3)

먼저 **화면에 뜬 숫자**를 본다. 숫자마다 원인이 다르다.

| 화면 안내 | 뜻 | 조치 |
|---|---|---|
| `허용하지 않는 확장자다: exe` | 올릴 수 없는 종류다 | 정상 동작이다. **관리자가 "운영 설정"에서 켤 수 있는 종류인지 먼저 본다.** 그 목록에도 없으면 우리가 내용을 검사할 규칙이 없는 종류다 — 담당자에게 요청한다 |
| `확장자(.pdf)와 형식(text/html)이 맞지 않는다` | 파일 이름과 브라우저가 밝힌 종류가 다르다 | 정상 동작이다 |
| `내용이 .pdf 형식이 아니다` | 이름은 맞는데 **파일 앞부분 바이트가 그 형식이 아니다.** 이름만 바꾼 파일이다 | 정상 동작이다. 진짜 그 형식으로 다시 저장해 올린다 |
| `파일이 너무 크다 (상한 20MB)` | 앱이 막았다 | 상한을 늘리려면 `WF_UPLOAD_MAX_MB`와 nginx의 `client_max_body_size`를 **둘 다** 바꾸고 다시 띄운다(운영이관 5절) |
| 첨부 칸에 빨간 글씨로 **`HTTP 413`**만 뜬다 | **안내 데스크(nginx)가 막았다.** 앱까지 오지도 않았다 — 그래서 앱의 문장이 없고, 첨부 칸은 받은 번호만 보인다 | 위와 같다. 둘 중 nginx 쪽만 작으면 이렇게 나온다. 앱 로그에는 아무것도 없고 nginx 로그에 `"status":413` 줄이 있다 |
| `500` 또는 아무 안내 없이 실패 | 저장 공간 문제일 수 있다 | 아래를 본다 |

**저장 공간 확인**

```bash
docker compose -f compose.yml --env-file .env exec api sh -lc 'id; ls -ld /data/attachments; df -h /data'
```

읽는 법:

- `uid=1000(node)`이고 폴더 주인이 `node`여야 한다. 주인이 `root`로 나오면 **볼륨이 잘못 만들어진 것**이다. 이때는 첫 업로드부터 전부 실패한다.
  - 고치기: `docker compose -f compose.yml --env-file .env exec -u root api chown -R node:node /data/attachments`
  - 왜 생기나: 이미지 안에 그 폴더가 없는 채로 볼륨이 붙으면 도커가 `root` 것으로 만든다. 지금 이미지는 미리 만들어 두었으므로 옛 볼륨에서만 나타난다.
- `df -h /data`의 여유가 없으면 그것이 원인이다. 첨부를 지워도 **파일 자체는 바로 남는다**(같은 파일을 여러 문서가 쓸 수 있어서다). 보존 기간이 지난 뒤 휴지통 정리가 **아무도 안 쓰는 파일만** 지운다 — 운영 서버에서는 `docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/trash-purge.js`, 저장소가 있는 곳에서는 `pnpm trash:purge`. 자동으로 돌지는 않는다 — 사람이 부르는 명령이다(운영이관 4.2절).

**올라간 파일이 어디 있나**

`/data/attachments/<앞 두 글자>/<긴 숫자>`에 있다. 이름이 사람이 읽을 수 있는 형태가 아닌 것이 정상이다 — 원래 이름은 데이터베이스에 따로 있다.

## 7.10 검색해도 안 나온다 (Phase 3)

순서대로 본다.

1. **그 사람이 그 공간을 볼 수 있는가.** 못 보는 공간의 문서는 검색 결과에 **아예 나오지 않는다.** 이것은 고장이 아니라 설계다. 공간 화면에서 Crew에 들어 있는지 먼저 확인한다 (7.5절).
2. **문서가 지워지지 않았는가.** 휴지통에 있는 문서는 결과에 없다.
3. **찾는 말이 본문에 실제로 있는가.** 제목과 본문 글자만 찾는다. 첨부 **파일 안의 내용은 찾지 않는다.**
4. 위가 다 맞는데 안 나오면 **색인이 빠진 것**이다. 아래로 다시 만든다(운영 서버).

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/reindex.js
```

저장소가 있는 곳에서는 `pnpm search:reindex`가 같은 코드다. 이 명령은 문서 본문에서 검색용 글자를 다시 뽑아 채운다. 원본을 건드리지 않으므로 **몇 번 돌려도 안전하다.** 문서가 많으면 시간이 걸린다. `재색인 완료: <N>개 페이지`가 나오면 끝이다.

> **검색은 감사 기록에 남지 않는다.** "누가 무엇을 검색했나"는 기록에 없다. 기록이 검색량만큼 불어나는 것을 피하기 위한 결정이다. 첨부를 **내려받은 것**은 남는다.

## 7.10-1 휴지통을 비우기 전에 알아야 할 것 (Phase 4)

휴지통 정리(운영 서버는 `tools`의 `trash-purge.js`, 저장소가 있는 곳은 `pnpm trash:purge` — 운영이관 4.2절)는 **보존 기간을 넘긴 것을 영구히 지운다.** 되돌릴 수 없다.

지우는 것이 두 갈래라는 점을 꼭 보고 실행한다.

| 무엇 | 설명 |
|---|---|
| 직접 지운 문서·첨부·댓글 | 보존 기간(기본 30일)을 넘긴 것 |
| **지워진 공간에 딸린 문서 전부** | 그 공간 안에서 **지우지 않았던 문서까지** 함께 지워진다 |

두 번째가 중요하다. **공간을 되살리면 안에 있던 문서도 함께 돌아온다** — 즉 공간이
휴지통에 있는 동안 그 문서들은 아직 살아 있는 것이다. 보존 기간이 지나 정리를 돌리면
그것들이 같이 없어진다.

명령이 실행 전에 몇 건인지 알려 준다. 숫자를 보고 판단한다.

```
[purge] 주의: 지워진 스페이스에 딸린 **살아 있던** 페이지 12건도 함께 지운다
```

감사로그 정리(`tools`의 `audit-purge.js`, 저장소에서는 `pnpm audit:purge`)는 보존 기간이 **최소 90일**로 묶여 있다. 그보다 짧게
설정할 수 없고, 설정값이 어떤 경로로 낮아졌더라도 명령이 90일 아래로는 지우지 않는다.

## 7.11 로그인이 "요청이 너무 잦다"로 막힌다 (Phase 4)

같은 주소에서 **실패한** 로그인이 1분에 20번을 넘으면 그 주소를 잠시 막는다. 무차별 대입 방어다.

**성공한 로그인은 세지 않는다.** 그래서 정상적으로 쓰는 사람이 많다고 막히지는 않는다. 다만 **끝나기 전에는 센다** —
한 주소에서 아직 끝나지 않은 로그인이 한꺼번에 20건을 넘으면 그 순간의 나머지는 막힌다(사내 NAT 뒤에서 여럿이 동시에 — 7.34절).

> 이 문장은 **한동안 사실이 아니었다.** 성공을 세지 않도록 고친 것이 2026-09-22이지만
> (T-023) 그 수정이 실제로는 동작하지 않아 **성공 로그인 스물한 번째부터 막혔다.**
> 같은 날 부하 측정에서 드러나 고쳤다 (T-027). 지금은 성공 로그인 50회를 연속으로 해도
> 막히지 않는 것을 컨테이너에서 확인했다.

| 상황 | 뜻 | 조치 |
|---|---|---|
| 한 사람만 막힌다 | 그 사람이 비밀번호를 여러 번 틀렸다 | **계정 잠금**일 수 있다 (7.1절). 관리자가 잠금 해제 |
| 같은 사무실 여러 명이 동시에 막힌다 | 그 주소에서 실패가 몰렸다 | 1분 기다린다. 반복되면 누가 잘못된 비밀번호로 계속 시도하는지 감사로그의 `auth.login.failure`를 본다 |
| 계속 막힌다 | 자동화된 시도일 수 있다 | 감사로그에서 실패가 오는 주소를 확인하고 망 담당자에게 알린다 |
| **비밀번호 변경**에서 막힌다 (Phase 13) | 같은 주소에서 지금 비밀번호를 **틀린** 변경이 1분에 5번을 넘었다. 성공한 변경은 세지 않는다 | 1분 기다린다. 본인이 아닌데 보이면 그 사람의 세션을 누가 쥐고 있을 수 있다 — 사용자 관리에서 **세션 강제 종료** 뒤 **비밀번호 초기화** |

## 7.12 알림이 안 온다 (Phase 4)

순서대로 본다. **대개 고장이 아니라 설계다.**

1. **부른 사람이 그 공간을 볼 수 있는가.** Crew가 아니면 이름을 적어도 알림이 가지 않는다. 알림이 "그런 문서가 있다"를 알려 주는 통로가 되지 않게 한 것이다.
2. **아이디를 정확히 적었는가.** 없는 아이디는 그냥 글자로 남는다.
3. **자기 자신을 부른 것은 아닌가.** 자기 알림은 만들지 않는다. 같이 쓴 문서에서는 **스스로 부른 것이 확실할 때만** 그렇게 판정한다 (7.22절).
4. **메일 주소를 적은 것은 아닌가.** `kim@example.internal`의 `@example`은 멘션이 아니다.
5. **불린 사람이 정지돼 있지는 않은가** (Phase 13). 정지된 계정에는 알림함에도 메일로도 가지 않는다 — 7.32절. 사용자 관리에서 상태 칸을 본다.
6. 위가 다 맞는데 안 오면 그때가 고장이다. `docker compose logs api`에서 그 시각의 오류를 본다.

알림은 **앱 안 알림함과 메일 둘 다로** 간다 (Phase 6). 메일이 안 오는 경우는 7.21절을 본다. 사내 메신저로는 가지 않는다.

### 7.12-1 비밀번호 초기화 요청이 관리자의 알림에 안 온다 (Phase 17)

사용자가 로그인 화면의 **비밀번호 찾기**로 요청하면, 맞는 계정일 때 그 사람을 **관리할 수 있는** 관리자·시스템 관리자의 알림(모든 화면 맨 위 오른쪽의 **알림**)에 간다. 순서대로 본다.

1. **넣은 아이디와 email이 계정과 맞았는가.** 맞지 않으면 아무에게도 가지 않는다(화면은 같은 말을 한다 — 계정이 있는지 새지 않게). 감사로그에서 행위 `auth.password.recover`의 상세 `found`가 `false`면 맞지 않은 것이다.
2. **요청한 계정이 활성인가.** 승인 대기·정지된 계정의 요청은 맞아도 가지 않는다(`found`도 `false`다). **사내 계정(회사 로그인 — 비밀번호가 없다)의 요청**은 `found`가 `true`여도 알리지 않는다 — 관리자가 초기화할 수 없고 회사 로그인 시스템에서 바꾼다(7.3절). `users.password_hash`가 비어 있으면 사내 계정이다.
3. **그 사람을 관리할 수 있는가.** 관리자는 시스템 관리자를 관리하지 못하고, 자기가 할 수 없는 위임(예: LLM 연결 관리)을 가진 사람도 관리하지 못한다 — 그런 요청은 할 수 있는 사람(시스템 관리자)에게만 간다. 받는 사람도 활성이어야 한다.
4. **이미 같은 요청의 알림이 읽지 않은 채 있는가.** 그때는 새로 만들지 않는다. 누가 그 사람의 비밀번호를 초기화하면 받은 사람 모두에게서 읽음이 된다.
5. 위가 다 맞는데 안 오면 앱 로그에서 `auth.recover_notify_failed`(error)를 찾는다 — 알림을 만들다 우리 쪽에서 실패했다(개발 담당). 요청 자체는 감사로그에 남아 있으니 그것으로 처리한다(사용자가이드 16.5절).

## 7.13 설정을 바꿨는데 안 먹는다 (Phase 4)

| 무엇을 바꿨나 | 확인 |
|---|---|
| 첨부 크기 상한 | **서버 천장이 따로 있다.** 화면에 "이 서버의 천장 NMB"라고 적혀 있고 그보다 크게는 저장이 안 된다. 올리려면 `WF_UPLOAD_MAX_MB`와 nginx의 `client_max_body_size`를 **둘 다** 올리고 다시 띄운다 |
| 그 밖의 값 | **다시 띄울 필요가 없다.** 저장 즉시 다음 요청부터 먹는다. 안 먹으면 저장이 실패한 것이므로 화면의 빨간 글씨를 본다 |
| 무엇이 언제 바뀌었는지 모르겠다 | 감사로그의 `settings.update`를 본다. **바뀐 키의 이전·이후 값이 함께 남는다** |

설정을 되돌리려면 감사로그의 "이전 값"을 보고 그 값을 다시 넣는다.

## 7.14 반입한 묶음이 이상하다 (Phase 5)

폐쇄망에는 저장소의 검사 도구(`pnpm release:verify`)가 없다. **`sha256sum -c SHA256SUMS`**(반입 가이드 1절)가 같은 지문을 본다.

| 증상 | 확인 | 조치 |
|---|---|---|
| `sha256sum -c SHA256SUMS`에 `FAILED` 줄이 있다(끝에 `WARNING: … computed checksum did NOT match`) | 그 줄의 파일 이름 | **그 묶음을 쓰지 않는다.** 옮기는 도중에 상했다. 다시 받는다 |
| `FAILED open or read` · `No such file or directory` | 묶음이 덜 풀렸다 — `--strip-components=1`을 빼먹으면 한 겹 아래(`workfluence-<날짜>/`)에 풀린다 | 반입 가이드 1절대로 다시 푼다. 그래도 없으면 빌드 쪽에 다시 요청한다 |
| 묶음 tar의 `.sha256`이 `FAILED`다 (새 버전 — 반입 가이드 11절 ①) | 매체의 tar | 풀지 않는다. 지금 설치는 그대로 두고 다시 받는다 |
| `docker load`가 "no space left" | `df -h /` | 5GB 미만이면 그 자리에서 멈춘다. 오래된 이미지를 **이름을 보고** 지운다 |
| 이미지는 올라갔는데 컨테이너가 안 뜬다 | `docker compose logs api` | 대개 `.env`다. 7.15절 |
| (빌드 서버) `pnpm release:verify`가 실패한다 | 출력의 파일 이름 | 묶음을 다시 만든다(빌드 가이드 12절) |

## 7.15 컨테이너가 뜨자마자 죽는다 (Phase 5)

앱은 **설정이 틀리면 일부러 기동을 거부한다.** 잘못된 설정으로 절반만 동작하는 것보다
안 뜨는 것이 낫다는 판단이다. 그래서 이 증상은 대개 고장이 아니라 **설정 오류**다.

```bash
docker compose -f compose.yml --env-file .env logs api | tail -30
```

| 로그에 나오는 말 | 뜻 | 조치 |
|---|---|---|
| 모르는 `WF_` 키가 있다 | **개발 실행(`pnpm dev`·`pnpm start`)에서만** 난다 — 저장소의 `.env`에 오타가 있거나 이 버전이 모르는 키다. compose로 띄운 앱에는 `compose.yml`에 적힌 키만 가므로 이 말이 나오지 않고, `.env`의 오타는 조용히 무시된다(4절) | 그 줄을 지우거나 이름을 고친다 |
| 값의 형식이 맞지 않다 | 숫자 자리에 글자가 들어갔다 | 해당 키를 고친다 |
| `WF_SESSION_SECRET` 관련 | 너무 짧다 (32자 이상) | 새로 길게 만든다 |
| 데이터베이스에 붙지 못한다 | postgres가 아직 안 떴거나 비밀번호가 다르다. `28P01 … "workfluence_app"`이면 앱 계정이다 | `docker compose ps`로 postgres가 `healthy`인지 먼저 본다. 앱 계정이면 7.31절 |

**환경 파일이 둘이라는 것을 기억한다** (개발 서버). 개발 실행용(저장소의 `.env`)과 compose용(`deploy/.env`)이 다르다.
compose 전용 키(`WF_PG_PASSWORD`·`WF_PG_APP_PASSWORD`)를 개발용 `.env`에 적으면 개발 실행이 "모르는 키"라며 거부한다(T-015).
반대로 개발용 키를 compose용 `.env`에 적으면 **아무 말 없이 무시된다** — compose가 앱에 넘기지 않는다. 운영 서버에는 compose용
`.env` 하나뿐이다.

## 7.16 접속이 안 된다 — 인증서 (Phase 5)

| 증상 | 뜻 | 조치 |
|---|---|---|
| 브라우저가 "이 사이트는 안전하지 않습니다"를 넘어갈 수 없게 막는다 | 인증서에 **SAN이 없다.** 요즘 브라우저는 경고가 아니라 오류로 처리한다 | `openssl x509 -in certs/cert.pem -noout -ext subjectAltName`로 확인하고, 없으면 재발급 |
| 며칠 전까지 됐는데 갑자기 전부 안 된다 | 인증서 만료 | `openssl x509 -in certs/cert.pem -noout -enddate`. 만료됐으면 재발급 |
| nginx 컨테이너가 `unhealthy` | 인증서 파일이 없거나 읽을 수 없다 | `docker compose logs nginx`. nginx는 **자기 자신에게 HTTPS로 물어보므로** 인증서 문제가 여기서 먼저 빨개진다 |

## 7.17 전부 느리거나 아예 응답이 없다 (Phase 5)

**느린 것과 멈춘 것은 다르다.** 먼저 어느 쪽인지 가린다.

```bash
curl -sk -m 5 https://localhost:8443/api/health
```

| 결과 | 뜻 | 조치 |
|---|---|---|
| 5초 안에 `status: ok` | 앱은 정상이다. 특정 화면만 느린 것 | 어느 화면인지 확인. 문서가 많이 쌓였으면 색인을 다시 만든다 (7.10절 — 운영 서버는 `tools`의 `reindex.js`, 저장소에서는 `pnpm search:reindex`). 로그인만 느리면 7.34절 |
| `db`가 `ok`가 아니다 | 앱은 살아 있고 데이터베이스가 문제 | postgres 컨테이너 로그와 `df -h /`를 본다. 디스크가 차면 데이터베이스가 먼저 쓰기를 실패한다 |
| **아무 응답 없이 시간만 흐른다** | 아래를 본다 | ↓ |

응답이 아예 없을 때, 데이터베이스 연결이 묶여 있는지 본다.

```bash
docker exec workfluence-postgres psql -U workfluence -d workfluence   -c "select state, count(*) from pg_stat_activity where datname='workfluence' group by state"
```

`idle in transaction`이 여럿 쌓여 있으면 **연결이 새는 것**이다. 2026-09-22에 이 증상으로
앱 전체가 멈춘 적이 있다 (T-026). 그때 두 가지를 고쳤다.

- 원인이 된 코드를 고쳤다.
- **기다림에 상한을 뒀다.** 이제는 같은 일이 생겨도 30초 안에 데이터베이스가 그 연결을
  끊고, 앱은 멈추는 대신 오류를 낸다. 오류는 로그에 남으므로 찾을 수 있다.

그래도 응답이 없으면 앱만 다시 띄운다. **데이터는 앱 컨테이너에 없다.**

```bash
docker compose -f compose.yml --env-file .env restart api
```

## 7.18 되살려야 한다 (Phase 5)

**순서를 지킨다.** 급할 때 순서를 건너뛰면 되살릴 수 있었던 것까지 잃는다. 운영 서버(저장소 없음)의 명령은
[운영이관](운영가이드_운영이관.md) 10절에 있다 — 아래의 `pnpm` 명령 자리에 그것을 쓴다.

1. **멈춘다.** 사람들이 계속 쓰면 되살린 시점 이후의 글이 섞인다.
   `docker compose -f compose.yml --env-file .env stop api nginx`
2. **지금 상태를 먼저 뜬다.** 망가진 상태라도 뜬다 — 백업이 더 오래된 것일 수 있고,
   그러면 **지금 것에만 있는 글**이 있다. 운영 서버는 운영이관 10.1절, 저장소가 있는 곳은 `pnpm backup:create`
3. **어느 백업으로 갈지 정한다.** `ls -lh ~/workfluence/backups/` (저장소에서 뜬 것은 `.local/backups/`)
4. **되살린다.** 운영 서버는 운영이관 10.3절. 저장소가 있는 곳은 `pnpm backup:restore .local/backups/<시각>` —
   빈 볼륨에만 되살리고, 마이그레이션 수를 대조한 다음 앱 계정과 권한을 맞춘다(`앱 계정 workfluence_app: 권한 적용` — 그 뒤에 행 수·첨부 대조가 이어진다, Phase 13).
   **두 경로의 백업은 서로 바꿔 쓰지 못한다** — `pnpm backup:restore`는 `pnpm backup:create`가 뜬 것(`dump.pgc`·`attachments.tar`·`BACKUP.json`)만
   읽고, 운영 서버의 백업(`db.dump`·`attachments.tar.gz`, 운영이관 10.1절)은 10.3절로 되살린다.
   - "대상이 비어 있지 않다"며 거절하면 **그게 안전장치다.** 정말 덮어쓸 것인지
     한 번 더 확인한 뒤에만 진행한다. 이 판단은 혼자 하지 않는다.
5. **개수를 대조한다.** 되살린 뒤 문서 수·사용자 수·첨부 수가 백업 시점과 맞는지 본다.
   `pnpm backup:restore`는 그 숫자를 출력한다. 운영이관 10.3절로 되살렸으면 화면에서 문서·사용자·첨부를 몇 개 열어 본다.
   - 5-1. **앱 계정의 권한을 맞춘다** (Phase 13). 되살린 데이터베이스에는 백업을 뜬 때의 권한이 들어온다 — 앱 계정이 없던 때의 백업이면
     비어 있다. `docker compose -f compose.yml --env-file .env run --rm tools node dist/db/migrate.js` → `앱 계정 workfluence_app: 권한 적용`
     (7.30절). 여러 번 쳐도 같다.
6. **띄운다.** `docker compose -f compose.yml --env-file .env up -d`
7. **사람들에게 언제로 되돌아갔는지 알린다.** 그 시점 이후에 쓴 글은 없어졌다.
   알리지 않으면 "내가 쓴 글이 사라졌다"가 따로 신고로 들어온다.


## 7.19 "연결이 끊겼다"가 뜬다 — 실시간 편집 (Phase 6)

편집 화면 아래에 **빨간 글씨로** 뜬다. 뜬 동안 쓴 것은 **저장되지 않는다.**

| 확인 | 뜻 | 조치 |
|---|---|---|
| 다른 화면은 되는가 | 앱은 살아 있고 WebSocket만 끊겼다 | nginx가 `Upgrade`를 넘기는지 본다 (묶음의 `nginx.conf` — 저장소의 `deploy/nginx.conf`) |
| 여러 사람이 동시에 | 서버 쪽 문제 | `docker compose logs api`에서 `Collab`을 찾는다 |
| 한 사람만 | 그 사람 망이나 프록시 | 새로고침. 사내 프록시가 WebSocket을 막는 경우가 있다 |

**사람에게 먼저 알린다: 지금 쓰고 있는 것을 다른 곳에 복사한 뒤 새로고침하라고.**
새로고침하면 서버에 남아 있는 마지막 상태부터 다시 시작한다.

> **실시간 편집을 통째로 끌 수 있다.** `WF_COLLAB_ENABLED=false`로 두고 다시 띄우면
> Phase 2의 단독 편집으로 돌아간다 — 한 사람씩 고치고 저장하며, 겹치면 "먼저
> 저장했다" 안내가 나온다. 원인을 찾는 동안 서비스를 세우지 않는 길이다.

## 7.19-1 편집하다 갑자기 끊겼다 — 끊은 쪽이 서버다 (Phase 7)

7.19절과 증상은 같지만 **원인이 다르다.** 서버가 일부러 끊은 경우다.

```
docker compose logs api | grep -E '"event":"collab\.(closed|revoked)"'
```

| 로그 (event와 `reason` 필드) | 뜻 | 조치 |
|---|---|---|
| `collab.revoked` · `reason: 세션 파기` · `count` | 비밀번호를 바꿨거나 관리자가 세션을 강제 종료했거나 계정을 **정지**했다(`sessionOnly: true`면 그 세션에서 로그아웃했다) | **정상이다.** 다시 로그인하면 된다. 정지였으면 로그인도 안 된다 — 7.32절 |
| `collab.closed` · `reason: 세션 없음` | 세션이 만료됐거나(유휴 30분·절대 12시간) 그 세션으로 **다른 탭에서 로그아웃**했다 | 정상. 다시 로그인 |
| `collab.closed` · `reason: 계정 비활성` | 그 계정이 활성이 아니다 — 관리자가 **정지**했다. 정지는 보통 위의 `collab.revoked`로 곧바로 끊고, 이 줄은 주기 점검이 잡은 것이다 | 정상 (7.32절) |
| `collab.closed` · `reason: 쓰기 권한 없음` | Crew에서 빠졌거나 viewer로 바뀌었거나 공간이 중지됐다 | 정상. 권한을 돌려주려면 관리 화면에서 |
| `collab.closed` · `reason: 비밀번호 변경 필요` | 임시 비밀번호 상태다 | 비밀번호를 바꾸게 한다 |
| `collab.recheck_failed` | 주기 재판정이 DB에 닿지 못했다 — 다음 주기에 다시 한다 | 반복되면 2절 |
| `session.revoke_failed` | 세션을 끊은 뒤 편집 연결을 끊는 데 실패했다 | 그 사람의 세션을 한 번 더 강제 종료한다. 반복되면 개발 담당 |
| 아무 로그도 없다 | 서버가 끊은 것이 아니다 | 7.19절로 간다 |

> **권한을 잃은 사람이 최대 5분까지 계속 쓸 수 있다.** 세션을 끊는 동작(비밀번호 변경·강제
> 종료)은 즉시 닿지만, Crew 제거·viewer로 바꾸기·공간 중지처럼 **부를 자리가 없는 변화**는 주기 점검이 잡는다.
> 급하면 그 사람의 세션을 강제 종료하면 즉시 끊긴다. 주기는 `WF_COLLAB_RECHECK_MS`다.

## 7.19-2 실시간 편집이 **컨테이너에서만** 안 붙는다 (Phase 7)

화면도 뜨고 `/api/health`도 `ok`인데 두 브라우저가 서로 안 보인다. 개발에서는 됐다.

| 확인 | 명령 | 기준 |
|---|---|---|
| nginx가 `Host`를 포트까지 넘기는가 | `grep 'proxy_set_header Host' nginx.conf` (묶음을 푼 디렉토리에서 — 저장소라면 `deploy/nginx.conf`) | **`$http_host`**여야 한다. `$host`면 포트가 떨어져 업그레이드가 401이 된다 (T-032) |
| 업그레이드가 401인가 | `docker compose logs nginx \| grep ' 401 '` | 401이 줄줄이 찍히면 위 항목이다 |

앞단에 사내 장비가 하나 더 있으면 그쪽도 `Origin`과 `Host`를 바꾸지 않고 넘겨야 한다.

## 7.19-3 연결됨인데 한 페이지에서 **남의 편집이 안 보인다** (Phase 8)

그 페이지를 연 사람 모두에게 같은 증상이고, 다른 페이지는 된다. 브라우저 콘솔에 편집기(y-tiptap) 렌더 오류가 찍힌다.

Phase 9 이전에는 조작한 클라이언트가 **편집기가 만들지 않는 것**(특수한 문서 조각)을 문서에 넣으면 생겼다. 서버는 그것을 저장에서
빼고 중계를 이어 갔지만(설계서 FR-909), 각자의 화면은 그것을 그리다 멈췄다.

> **Phase 9부터 서버가 그런 편집을 받지 않는다**(보류 23 닫음 — 7.23). 그래서 이 증상은 Phase 9 이전에 서버에 들어간 실시간 상태에서만
> 생길 수 있다. 새로 생겼다면 7.23의 기록을 먼저 보고 개발 담당에게 알린다 — 관문의 틈이다.

| 조치 | 뜻 |
|---|---|
| 그 페이지를 편집 중인 사람 중 **한 명이 아무 글자나 한 번 친다** | 그 사람의 편집기가 문서를 다시 쓰면서 그 조각을 지우고, 그 지움이 모두에게 간다 |
| 그래도 안 되면 모두 나간 뒤 실시간 상태를 지운다 | 마지막 버전에서 다시 시작한다(저장되지 않은 협업 편집은 잃는다). 명령은 7.20절 3번 |
| 누가 넣었는지 | Phase 9부터의 시도는 감사로그의 `page.collab.reject`가 누가·어느 페이지·까닭을 직접 남긴다(7.23). Phase 9 이전에 들어간 것은 그 시각의 `page.collab.save`·접속 기록과 맞춰 본다. 반복되면 보안 담당에게 알린다 |

## 7.19-4 내가 친 글이 **남에게 안 보인다** — 내 화면에는 있다 (Phase 8)

한 사람에게만 생긴다. 그 사람 화면에는 글이 있는데 다른 사람 화면과 저장된 버전에는 없고, 그 자리에 **다른 글**이 보이기도 한다.
대개 **페이지를 연 직후**에 친 글이다.

실시간 편집에서 화면마다 식별 번호가 하나씩 있고, 화면은 페이지를 열자마자 그 번호를 (커서를 보여 주려고) 알린다.
Phase 9 이전에는 서버가 그 알림을 모두에게 그대로 퍼뜨렸고, 조작한 클라이언트가 그 번호로 **먼저** 편집을 보내면 서버는 그 번호의
글을 이미 받은 것으로 알고 진짜 주인이 그 사이 친 글을 버렸다(Phase 6부터).

> **Phase 9부터 서버가 막는다**(보류 24 닫음). 화면이 번호를 알리는 순간 서버가 그 번호의 주인을 적어 두고, 남이 그 번호로 쓰면
> 받지 않고 끊는다(7.23). 아래는 Phase 9 이전의 설명이다 — 새로 생겼다면 관문의 틈이니 개발 담당에게 알린다.

주인의 화면이 그 편집을 받아 스스로 번호를 바꾸면 그 뒤에 친 글은 정상으로 갔지만, 이미 친 글이 더 많으면 번호를 바꾸지 않아
**그 뒤에 친 글도 어긋났다** — 새로고침이 확실하다. 부른 사람의 이름은 틀리지 않았다 — 먼저 보낸 사람이 그 번호로 쓴 부름은 그
사람의 이름으로 나가고, 어긋난 채 친 부름은 이름을 비웠다.

| 조치 | 뜻 |
|---|---|
| **새로고침하기 전에** 그 사람이 자기 화면의 그 글을 복사해 둔다 | 새로고침하면 화면이 서버의 문서로 바뀌어 화면에만 있던 글이 사라진다 |
| 새로고침한 뒤 붙여 넣는다 | 새 번호로 다시 들어가 모두에게 간다 |
| 누가 보냈는지 | Phase 9부터의 시도는 감사로그의 `page.collab.reject`(규칙 `owner`)가 직접 남긴다(7.23). Phase 9 이전의 것은 그 시각의 접속 기록과 `page.collab.save`를 맞춰 본다. 반복되면 보안 담당에게 알린다 |

## 7.20 실시간 편집인데 버전이 안 생긴다 (Phase 6)

**대개 고장이 아니라 설계다.** 순서대로 본다.

1. **아직 타이핑 중인가.** 잠깐 멈춰야 남긴다 (기본 5초, `WF_COLLAB_IDLE_SAVE_MS`).
2. **내용이 정말 바뀌었는가.** 커서만 움직인 것은 바뀐 것이 아니다 — 그것까지 세면
   가만히 보고만 있어도 버전이 쌓인다.
3. **문서가 검증을 통과하는가.** 통과하지 못하면 **버전을 만들지 않는다.** Phase 9부터는 그 페이지를 편집하는 화면에
   **"자동 저장이 멈췄다: <까닭>"**이 뜬다(뒤에 들어온 사람에게도, 서버가 다시 뜬 뒤에 연 사람에게도). 로그는 `docker compose logs api`의
   `collab.save_invalid`(검증 실패로 저장하지 않았다 — `errors` 필드에 까닭 셋까지)다. 실시간 상태는 살아 있으므로 화면에서 고치면 다음 유휴에 저장되고 그 알림이 사라진다.
   까닭이 `노드 수 50000 초과`면 문서가 너무 길다 — 내용을 나눠 다른 페이지로 옮긴다. 까닭에 `textAlign`이 있으면 Phase 9 이전에
   들어간 정렬이다 — **그 문단을 한 번 고치면** 편집기가 그 속성을 지워 다시 저장된다.
   까닭이 **`서버가 버전을 남기지 못했다 — 잠시 뒤 다시 한다`**면 문서는 멀쩡하고 **저장하는 순간 DB가 실패했다**. 다음 유휴에 저절로
   다시 하고, 되면 알림이 사라진다. 계속 뜨면 `docker compose logs api`에서 `collab.save_failed`(`trigger: idle`)를 찾아 그 `error`로
   DB부터 본다(2절).
   **다만 로그의 검증 오류가 화면에 보이지 않는 것**(편집기에 없는 노드나 속성 — 조작한 클라이언트가 넣을 수 있다)이면
   화면에서 고칠 수 없다. **Phase 9부터는 서버가 그런 편집을 문 앞에서 받지 않는다**(보류 22 닫음 — 7.23). 그래도 이렇게
   되었다면(Phase 9 이전에 들어간 상태) 그 페이지를 편집하는 사람이 모두 나간 뒤 그 페이지의 실시간 상태를 지우면 마지막
   버전에서 다시 시작한다. **저장되지 않은 협업 편집은 잃는다.**

   ```
   docker exec workfluence-postgres psql -U workfluence -d workfluence -c "DELETE FROM page_realtime WHERE page_id = '<페이지 id>'"
   ```
4. **빈 문서로 만들지 않았는가.** 전부 지운 상태는 저장하지 않는다 — 연결이 끊기며
   빈 상태가 올라오면 내용이 사라지기 때문이다. 일부러 비우려면 **저장 버튼**을 누른다.

## 7.21 메일이 안 온다 (Phase 6 · 사내 메일 API 설정 Phase 18)

**먼저 시험 메일을 한 통 보낸다** — 설정이 맞는지, 메일 API가 받는지를 한 번에 본다(반입 가이드 10-1절). 앱이 메일을 켰는지와 무관하게 보낸다.

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/cli/mail-test.js <받을 주소>
```

창이 설정(주소·형식·보내는 이름·인증 헤더 이름 — 값은 가린다)과 결과를 말하고, 보냈으면 0, 아니면 1로 끝난다. 그 까닭대로 고친다:

| 창의 말 | 까닭과 조치 |
|---|---|
| `보냈다 — HTTP 200` 인데 메일함에 없다 | 메일 API는 받았다 — 받는 쪽(스팸함, 사내 메일 서버의 전달)을 메일 담당에게 묻는다. 시험 메일의 "보낸 때"로 찾는다 |
| `받지 않았다 — HTTP 400. 필수 값이 빠졌거나…` | 받는 주소·`WF_MAIL_SENDER_NAME`을 본다. 형식이 `markdown`이면 주소가 `…/send_markdown`인지. 창의 `응답:` 줄이 메일 API의 말이다 |
| `HTTP 401`·`403` | 인증 — `WF_MAIL_AUTH_HEADER`(헤더 이름)와 `WF_MAIL_AUTH_VALUE`(값 **전체** — `Bearer `까지)를 메일 API 담당에게 받은 대로 |
| `HTTP 404`·`405` | 주소가 틀렸다 — `WF_MAIL_API_URL`을 끝의 `/api/v1/email/send`까지 적는다 |
| `HTTP 500` 등 | 메일 서버가 보내지 못했다 — 메일 API 담당에게 그 시각을 알린다 |
| `보내지 못했다 — … (ECONNREFUSED)`·`(ENOTFOUND)`·`10초 안에 답이 없다` | 주소·포트·방화벽 |
| `보내지 못했다 — 인증서를 믿지 못했다 (…)` | 사내 인증 기관 — `ca/ca.pem`에 두고 다시 친다(반입 가이드 10절 ②). 앱에도 쓰려면 `--force-recreate api` |
| `보내지 못했다 — 메일 API가 다른 주소로 넘겼다` | 넘겨주기는 따르지 않는다(인증 값이 다른 곳으로 가지 않게) — 넘겨 준 곳의 주소를 적는다 |
| `WF_MAIL_API_URL이 비었다` | `.env`에 적지 않았다 |
| 명령이 `환경변수 검증 실패`로 멈춘다 | 설정이 틀렸다 — 그 줄이 말하는 키를 고친다(아래 "앱이 뜨지 않는다") |

시험 메일은 되는데 멘션 메일이 안 오면:

| 확인 | 조치 |
|---|---|
| 앱 안 알림함에는 왔는가 | 왔으면 메일만 문제다. 안 왔으면 7.12절(알림) |
| `WF_MAIL_ENABLED`가 `true`인가 | 기본은 꺼짐이다. 시험 명령의 `지금 앱은 …` 줄이 말한다 |
| `WF_MAIL_MOCK`이 `false`인가 | `true`면 **일부러 안 보낸다.** 로그에 `mail.mock_sent`(모의 발송)가 찍힌다. 운영에서 켜고 모의면 앱이 아예 뜨지 않는다(Phase 18) |
| `.env`를 고친 뒤 앱을 **다시 만들었는가** | `docker compose -f compose.yml --env-file .env up -d --force-recreate api` — `restart`는 `.env`를 다시 읽지 않는다 |
| 감사로그에 `mail.send`가 있는가 | 있으면 우리 쪽은 보냈다. `mail.fail`이면 메일 API가 거절했다(상세 `kind`가 `test`면 시험 명령의 것). 감사 기록 단계가 1이면 성공(`mail.send`)은 남지 않는다 — 로그의 `mail.rejected`·`mail.failed`로 본다(7.38절) |
| 로그에 `mail.rejected`·`mail.failed`·`mail.mention_failed`·`mail.unconfigured`가 있는가 | `mail.rejected`는 메일 API가 받지 않았다(`status` 필드 — 응답 본문은 싣지 않는다, 시험 명령으로 본다), `mail.failed`는 닿지 않았다(`error` 필드), `mail.mention_failed`(error)는 멘션 메일을 처리하다 우리 쪽에서 실패했다(감사 기록까지 — 개발 담당), `mail.unconfigured`는 주소가 비었다 — 알림함은 그대로다 |

**앱이 뜨지 않는다 — `환경변수 검증 실패`에 `WF_MAIL_`이 보인다** (Phase 18). 메일 설정이 틀리면 기동에서 막는다:
`WF_MAIL_API_URL`(http(s)가 아니다·사용자 정보나 `?…`가 섞였다 — 키는 인증 헤더로), `WF_MAIL_AUTH_HEADER`·`WF_MAIL_AUTH_VALUE`(하나만 있다·헤더 이름에 빈칸이나 콜론·값에 줄바꿈),
`WF_MAIL_MOCK`(운영에서 켰는데 모의다 — `false`로), `WF_MAIL_API_URL`(켰는데 비었다), `WF_MAIL_SENDER_NAME`(100자를 넘는다). **`WF_MAIL_FROM`·`WF_MAIL_API_TOKEN`은 Phase 18에 없어졌다** —
개발 서버의 `.env`에 남아 있으면 "모르는 키"로 뜨지 않는다. 보내는 이름은 `WF_MAIL_SENDER_NAME`, 토큰은 `WF_MAIL_AUTH_HEADER=Authorization`·`WF_MAIL_AUTH_VALUE=Bearer <토큰>`으로 옮긴다
(compose는 새 키만 넘기므로 `deploy/.env`의 옛 줄은 앱에 닿지 않고 아무 일도 하지 않는다 — 지운다).

**메일이 실패해도 글은 정상으로 저장된다.** 그렇게 만들어 두었다 — 메일 서버가
죽었다고 댓글이 안 써지면 안 된다.

> 요청 형식은 사용자가 준 사내 메일 API 설명 그대로다(`POST …/api/v1/email/send`, `subject`·`content`·`receivers`·`sender_name` — P18 설계서 C절). 실제 사내 API로
> 보낸 것은 **폐쇄망 현장에서** 한다(보류 18). 현장의 API가 다르면 `apps/api/src/mail/domain/request.ts` 한 파일을 고친다.


## 7.22 알림에 부른 사람 이름이 없다 — "문서에서 불렸다" (Phase 8)

**대개 고장이 아니라 설계다.** 같이 쓴 문서(실시간 편집)에서 서버는 **누구의 창이 어떤 글자를 들여왔는지**와
**누구의 편집으로 부름이 새로 생겼는지**를 적어 둔다. 부름의 글자를 전부 들여온 사람과 그 부름을 생기게 한 사람이
**같을 때만** 그 사람의 이름을 적는다. 확실하지 않으면 **틀린 이름을 적는 대신 비운다.**

| 확인 | 뜻 |
|---|---|
| 누가 **남의 글자를 지우거나 끼워 넣어** 부름이 새로 생겼는가 (예: `@kim.lee`에서 `.lee`를 지워 `@kim`) | 글자는 한 사람이, 부름을 생기게 한 것은 다른 사람이다. 설계대로 비운다 |
| 두 사람이 `@아이디`를 **나눠서** 쳤는가 (한 사람이 `@ki`, 다른 사람이 `m`) | 설계대로 비운다 |
| 누가 **남의 부름을 옮겼는가** — 잘라 붙이기, 지웠다 되돌리기, 문단을 제목·목록으로 바꾸기, **그 부름 앞에서 Enter로 문단을 나누거나 Backspace로 합치기** | 옮긴 부름은 비운다(그 이름이 이미 저장된 버전에 있으면 새 알림이 가지 않는다). 옮긴 사람이 부른 것도 아니고 원래 사람의 이름을 옮겨 붙이지도 않는다. **처음부터 저장돼 있던 부름**(누가 만들었는지 모른다)을 지웠다가 붙여 넣기·되돌리기로 다시 만든 것도, 지운 사람 자신이 했어도 비운다 |
| `docker compose logs api`에 `collab.makers_failed`(멘션 장부를 고치지 못했다)가 있는가 | 그 방의 멘션은 그 뒤로 모두 "모름"이다(편집은 계속된다). 그 줄의 `pageId`와 시각을 적어 개발 담당에게 넘긴다 — 장부가 예상하지 못한 문서 모양을 만났다 |
| `docker compose logs api`에 `collab.makers_unsure`(변경이 보낸 것보다 문서를 더 바꿨다)가 있는가 | **Phase 9부터는 나오지 않아야 한다** — 미리 보내 두는 조작한 편집을 서버가 문 앞에서 받지 않는다(7.23). 나왔다면 관문의 틈이다: 그 페이지와 시각을 개발 담당에게 넘긴다. 그 줄의 `userId`는 **섞여 들어간 쪽(피해자)**의 사용자 id다 |

**이름이 "틀렸다"는 신고라면 고장일 수 있다.** 이름이 붙는 것은 그 부름의 글자를 전부 자기 창으로 들여오고 자기 편집으로
그 부름을 생기게 한 사람뿐이다. 두 가지를 먼저 확인한다 — ① 남의 글을 **복사해 붙여 넣은 사람**은 그 안의 부름을 만든 사람이
된다(붙여 넣은 글자는 그 사람의 창이 새로 들여온 것이다). ② 잘라낸 남의 부름을 **두 번에 나눠** 붙여 넣은 사람도 그렇다 — 한 글자씩
다시 친 것과 서버가 가릴 수 없다(설계대로). 둘 다 아니면 페이지 id와 그 시각을 적어 개발 담당에게 넘긴다.

> 부른 사람을 기억하는 장부는 실시간 편집 상태 옆(`page_realtime.authors`)에 있다.
> **지워도 된다** — 지우면 그 문서에서 아직 저장되지 않은 부름이 "모름"이 될 뿐이고, 정본 문서와
> 이미 간 알림은 그대로다.

## 7.23 "서버가 이 편집을 받지 않았다"가 뜬다 (Phase 9)

편집 화면 아래에 **빨간 글씨로** 뜨고, 그 사람의 실시간 편집 연결이 끊긴다. 같이 쓰던 다른 사람은 아무 일도 겪지 않는다.

서버는 같이 쓰는 문서의 편집을 **받아들이기 전에** 본다 — 우리 편집기가 만들 수 있는 모양인가, 아직 없는 글자에 기대지 않는가,
남의 식별 번호로 쓰지 않는가. 아니면 받지 않고 끊는다(설계서 `P9_설계서_Gate`). **평소에는 일어나지 않는다.**

**먼저 까닭을 본다.** 관리 화면 → **감사로그**에서 행위를 `page.collab.reject`로 고른다. 누가(사용자), 어느 페이지(대상), 어느
규칙(`detail.rule`)에 무슨 까닭(`detail.reason`)으로 걸렸는지가 있다. 같은 내용이 `docker compose logs api`에
`collab.gate_refused`(`pageId`·`userId`·`rule`·`reason` 필드)로도 남는다. 글의 내용은 어디에도 남지 않는다.

| 누가·어떻게 | 뜻 | 조치 |
|---|---|---|
| **평범하게 쓰던 사람**이 무언가를 붙여 넣거나 새 기능을 쓰다가 끊겼다. 까닭이 `허용되지 않는 속성·노드·마크`, `… 안에 올 수 없는 …`, `속성 '…' 값은 …`, `중첩 깊이 64 초과` | **우리 편집기와 서버 규칙이 어긋났다**(개발 결함). 그 사람이 한 일은 정상이다 | 무엇을 하다 끊겼는지(어디서 무엇을 붙여 넣었는지) 묻고, 페이지 id·시각·까닭을 개발 담당에게 넘긴다. 여러 사람이 같은 일로 막히면 **실시간 편집을 끈다**(7.19 끝의 `WF_COLLAB_ENABLED=false` — 한 사람씩 저장하는 방식으로 돌아간다) |
| 평범하게 쓰던 사람이 **한 번**, 까닭이 `목록 항목의 첫 자식이 문단이 아니게 되는 변경`이고 같은 페이지를 **다른 사람도 그 무렵 고치고 있었다** (Phase 12) | 두 사람이 같은 목록 항목의 첫 줄을 동시에 바꿨다 — 드물다. 둘 다 받으면 그 항목이 통째로 지워지므로 뒤에 닿은 사람의 편집만 받지 않았다 | 그 사람에게 새로고침한 뒤 다시 하라고 알린다. 같은 사람이 되풀이하면 아래 줄이다 |
| 한 사용자가 **여러 번**, 까닭이 `목록 항목의 첫 자식이 문단이 아니게 되는 변경` (Phase 12), `편집기가 만들지 않는 타입·내용`, `남의 클라이언트 ID로 쓴 조각`, `서버에서 보류될 조각`, `아직 없는 글자를 지우는 삭제`, `같은 클라이언트가 두 번 나온 변경`, `앞 조각과 다른 자리에 이어 쓴 조각` | 우리 편집기로는 나오지 않는 편집이다 — **조작한 프로그램**일 가능성이 크다 | 보안 담당에게 알린다. 계속되면 관리자가 그 사람의 세션을 끊고(관리 화면의 **사용자 관리** → 그 사람 줄의 **세션 강제 종료**) 그 공간의 권한을 거둔다 |
| 까닭이 `읽을 수 없는 변경`·`읽을 수 없는 사람 표시` | 망에서 깨졌거나 조작이다 | 한 번이면 그 사람에게 새로고침을 권한다. 반복되면 위와 같다 |
| **아주 큰 것**(수만 문단·큰 표)을 한꺼번에 붙여 넣다가 끊겼다. 감사로그의 `detail.rule`이 **`size`**, 앱 로그에 **`collab.frame_too_large`**(`pageId`·`userId`·`limitBytes`) (Phase 12) | 편집 하나가 한 번에 보낼 수 있는 크기(16MiB)를 넘었다. 정상 문서 하나(저장 상한 2MB)의 8배라 평소에는 나오지 않는다 | 나눠 붙여 넣으라고 알린다. 그 문서가 이미 아주 크면(실시간 상태가 커지는 것 — 보류 19) 개발 담당에게 페이지 id를 넘긴다 |
| 링크를 붙여 넣다가 끊겼고 까닭이 `속성 'rel' 값에 'opener'를 둘 수 없다` | 다른 곳에서 복사한 링크에 새 창이 이 위키 창을 옮길 수 있게 하는 표시가 붙어 있었다. 편집기는 붙여 넣을 때 그 표시를 뺀다 — 그래도 이렇게 끊겼다면 그 사람의 화면이 **업데이트 전의 옛 화면**이다. 결함이 아니다 | 새로고침하고 다시 붙여 넣으라고 알린다. 새로고침한 뒤에도 같은 까닭으로 끊기면 위의 "조작한 프로그램" 줄과 같다 |

`중첩 깊이 64 초과`는 인용·목록을 아주 깊게 겹친 것이다 — 정상 편집기로도 만들 수 있지만 저장할 수 없는 문서라 문 앞에서
돌려보낸다. 그 사람에게 겹침을 줄여 다시 쓰라고 알리면 되고, 개발 결함이 아니다.

**같이 보는 사람 목록에 내가 안 보인다**(동료 화면에 내 이름·커서가 없다)는 이 절의 끊김과 다르다 — 편집은 오간다. 같은 페이지를
아주 여러 번(16번 넘게) 새로 열었는데 그 페이지를 누군가 늘 열어 두고 있었거나 자동 저장이 멈춰 있으면 그렇다. **한 글자를 치면**
그 뒤로 보인다. 모두가 그 페이지에서 나가 저장이 끝나면 저절로 풀린다 — 자동 저장이 멈춘 페이지는 그 까닭(7.20절 3번)을 먼저 푼다(설계서 `P9_설계서_Gate` D.5).

**끊긴 사람에게는** 쓰던 내용을 다른 곳에 복사한 뒤 새로고침하라고 알린다. 새로고침하면 서버에 남은 마지막 상태부터 다시
시작한다. 같은 것을 다시 붙여 넣어 또 끊기면 그 내용이 원인이다 — 그 내용을 개발 담당에게 함께 넘긴다.

## 7.24 LLM 연결 확인이 "연결 안 됨"이다 (Phase 10)

관리 화면 → **LLM 연결**에서 **연결 확인**을 누르면 까닭이 뜬다. 앱 서버가 등록한 주소의 `/models`를 불러 본 결과다(설계서 `P10_설계서_Llm` D.2).

| 까닭 | 뜻 | 조치 |
|---|---|---|
| `LLM 서버에 닿지 않는다 (ECONNREFUSED)`·`(ENOTFOUND)`·`(ETIMEDOUT)` | 주소(호스트·포트)가 틀렸거나, 앱 서버에서 그 서버로 가는 길이 막혔다(방화벽) | 앱 컨테이너 안에서 직접 불러 본다: `docker compose -f compose.yml exec api node -e "fetch('http://llm.example.internal:8000/v1/models').then(r=>console.log(r.status)).catch(e=>console.log(e.cause?.code))"`(주소는 등록한 것으로). 여기서도 안 되면 망 담당에게 그 주소·포트를 열어 달라고 한다 |
| `LLM 서버에 닿지 않는다 (UNABLE_TO_VERIFY_LEAF_SIGNATURE)`·`(SELF_SIGNED_CERT_IN_CHAIN)` 등 인증서 코드 | 주소가 `https`이고 **사내 인증 기관(CA)이 서명한 인증서**다. 앱이 그 기관을 모른다 | TLS 검증을 끄지 않는다(`CLAUDE.md` 7절). 앱이 그 기관을 믿게 한다 — [반입 가이드](운영가이드_반입.md) 10절 ②·③: compose 옆 `ca/ca.pem`에 그 기관의 인증서를 두고 `docker compose -f compose.yml --env-file .env up -d --force-recreate api`로 **다시 만든다**(`up -d`만으로는 파일을 알아채지 못한다 — T-049). 붙었는지: `docker exec workfluence-api sh -c 'tr "\0" "\n" < /proc/1/environ \| grep NODE_EXTRA_CA_CERTS'`가 한 줄. 그래도 같으면 중간 기관까지 이어 붙였는지 본다 |
| `LLM 서버가 다른 주소로 넘겼다 — 넘겨주기는 따르지 않는다` | 등록한 주소가 다른 곳으로 넘긴다(`http`→`https` 등). 넘겨주기를 따르면 API 키가 등록하지 않은 곳으로 가므로 따르지 않는다 | 넘겨진 **최종 주소**로 다시 등록한다(지우고 등록) |
| "모델 목록을 읽을 수 없다 — 주소가 OpenAI 호환 API의 /v1까지인지 확인한다" | 주소에 `/v1`이 빠졌거나, vLLM이 아닌 곳이다 | `http://호스트:포트/v1` 모양으로 다시 등록한다 |
| `invalid api key`·`HTTP 401` 같은 거절 | API 키가 틀렸거나 없다. LLM 서버의 문장이 키를 되읊으면 그 자리는 `***`로 가려져 나온다 | 지우고 맞는 키로 다시 등록한다. 키는 다시 볼 수 없으므로 고쳐 넣는 화면은 없다 — 지워도 대화는 남는다 |
| `10초 안에 답이 없다` | LLM 서버가 바쁘거나 멈췄다 | LLM 서버 담당에게 알린다 |
| `연결됨` + **"등록한 모델이 목록에 없다"** | 주소·키는 맞고 **모델 이름**이 틀렸다 | 목록에 보이는 이름 그대로 다시 등록한다 |
| `이 LLM의 API 키를 풀 수 없다 — …` | 앱의 마스터 키가 바뀌었거나 없다. 또는 데이터베이스에서 그 LLM의 **주소가 바뀌었다**(키는 주소와 묶여 잠겨 있다 — 화면에는 주소를 고치는 길이 없다) | 7.26절 |

**목록의 주소 옆에 "(암호화 안 됨)"** — `http` 주소다. 질문과 답(키가 있으면 키도)이 사내망을 평문으로 지난다. 사내 LLM이 `https`를 받으면 지우고 `https` 주소로 다시 등록한다.

**"LLM 연결" 메뉴가 안 보인다** — 시스템 관리자(`root`)와, 시스템 관리자가 **사용자 관리**에서 "LLM 연결 관리"를 준 관리자에게 보인다.
그 관리자에게 맡기려면 root로 사용자 관리 → 그 사람 줄의 "LLM 연결 관리"를 켠다(다음 요청부터 먹는다 — 새로고침). 거두면 끈다.
관리자가 member가 되면 저절로 사라진다. 누가 언제 주고 거뒀는지는 감사로그 `user.grants.change`에 있다.

## 7.25 LLM 답이 안 온다·끊긴다·한꺼번에 온다 (Phase 10)

답 아래에 빨간 글씨로 까닭이 뜬다. 저장되지 않은 질문은 입력칸에 되돌아온다.

| 화면의 까닭 | 뜻 | 조치 |
|---|---|---|
| `등록된 LLM이 없다` | 시스템 관리자가 등록하지 않았거나 지웠다 | 관리 화면에서 등록한다 |
| `LLM 서버에 닿지 않는다 (…)` | 7.24절과 같다 | 7.24절 |
| `시간 상한(10분)을 넘었다` | 답 하나가 `WF_LLM_TIMEOUT_MS`(기본 10분)를 넘었다. 거기까지는 "끊김"으로 저장된다 | LLM 서버가 느린지 본다. 늘 긴 답이 필요하면 `WF_LLM_TIMEOUT_MS`를 올리고 다시 띄운다(1시간까지) |
| `답이 상한(200,000자)을 넘어 끊었다` · `생각 과정이 상한을 넘어 끊었다` | 한 답의 설계 상한이다 | 질문을 나눠 묻는다 |
| `LLM 서버가 5분 동안 아무것도 보내지 않았다 (UND_ERR_HEADERS_TIMEOUT)`·`(UND_ERR_BODY_TIMEOUT)` | LLM 서버가 5분 동안 첫 글자도, 다음 글자도 보내지 않았다 — 붐벼서 줄을 섰거나 멈췄다. `WF_LLM_TIMEOUT_MS`와 다른 상한이라 그 값을 올려도 바뀌지 않는다(설계서 D.2) | LLM 서버 담당에게 그 시각을 알린다. 자주 나면 보류 29의 판정(첫 조각까지의 시간)에 적는다 |
| `대화가 모델이 한 번에 읽을 수 있는 길이를 넘었다 — 새 대화를 시작한다 (LLM 서버: This model's maximum context length is …)` | 대화가 **모델이 한 번에 읽을 수 있는 길이**보다 길어졌다. 앞 대화를 몰래 잘라 보내지 않는다(설계서 D.3) | **새 대화**를 시작한다. 앞 대화의 요점을 붙여 넣으면 된다 |
| `답이 모델의 길이 상한에서 잘렸다 — 대화가 길면 새 대화를 시작한다` | 모델이 쓸 수 있는 만큼 쓰고 멈췄다(`finish_reason: length`). 거기까지는 "끊김"으로 저장된다 | 대화가 길면 새 대화로, 아니면 "이어서 써 줘"로 묻는다 |
| `LLM 서버가 흘려보내지 않았다 — 흘려보내기(stream)를 지원하는 OpenAI 호환 주소인지 확인한다` | 등록한 주소가 답을 한꺼번에(흘려보내지 않고) 준다 — vLLM 앞의 게이트웨이가 `stream`을 모른다 | vLLM의 주소를 직접 등록하거나, 게이트웨이 담당에게 흘려보내기를 켜 달라고 한다 |
| `LLM 응답의 한 줄이 너무 길다 — …` | LLM 서버(또는 그 앞의 장비)가 줄바꿈 없이 끝없이 보낸다. 앱 메모리를 지키려고 끊었다 | LLM 서버 담당에게 알린다 — 정상 vLLM은 이렇게 보내지 않는다 |
| `LLM 응답을 읽을 수 없다` | 흐름 안에 OpenAI 호환 모양이 아닌 조각이 왔다(HTML 오류 쪽 등). 거절이 아니라 응답의 모양이 틀렸다 — 감사의 `failure`는 `protocol`이다 | 등록한 주소가 vLLM의 `/v1`인지, 그 앞의 게이트웨이가 흐름을 고쳐 쓰는지 본다 |
| `세션이 끝나 답을 멈췄다 — 다시 로그인한다` | 답을 받는 사이 그 사람의 세션이 끝났다 — 비밀번호를 바꿨거나, 관리자가 세션을 강제 종료했거나, 같은 세션의 다른 탭에서 로그아웃했다. 거기까지는 "중지됨"으로 저장된다 | 다시 로그인해 묻는다. 감사로그의 그 `llm.ask`에 `detail.failure = revoked`가 남는다 |
| `대화 하나에 메시지는 200개까지다 — 새 대화를 시작한다` | 대화 하나의 상한이다 | 새 대화를 시작한다 |
| `이미 답을 받고 있다 — 끝나거나 중지한 뒤에 묻는다` | 한 사람은 한 번에 하나만 묻는다. **다른 탭·다른 창**에서 답을 받는 중이다 | 그 탭에서 중지하거나 끝나기를 기다린다. 창을 닫았거나 그 화면을 떠났으면(다른 메뉴·뒤로 가기) 받던 답이 멈추고 곧 풀린다 |
| `연결이 끊겼다 — 답이 저장됐는지 목록을 다시 본다` | 브라우저와 서버 사이가 끊겼다 | 목록을 다시 본다. 서버는 거기까지를 저장했을 수 있다 |
| `그 사이에 대화가 지워져 이 답을 저장하지 않았다` | 답을 받는 사이 그 대화가 지워졌다(다른 탭에서 지움, 보존 기간) | 새 대화로 다시 묻는다 |
| `답을 저장하지 못했다` | 데이터베이스가 거절했다 | `docker compose logs api`에서 `llm.save_failed` 줄의 `error`(PostgreSQL 코드와 문장)를 본다. 연결이 끊긴 것이면 2절. 질문·답 내용은 로그에 없다(drizzle 문장은 "DB 질의 실패 — 문장은 싣지 않는다"로만 나온다) |

**어떤 까닭으로 실패하는지 모아 보려면** — 로그에는 종류와 HTTP 상태만 남는다(LLM 서버의 문장은 남의 응답이라 싣지 않는다):
`docker compose -f compose.yml logs api | grep '"event":"llm.ask_failed"'` → 줄마다 `kind`(`rejected`·`timeout`·`unreachable`·`protocol`)와
`httpStatus`, `providerId`가 있다. `llm.ask_error`는 우리 쪽 결함이다(개발 담당에게 그 줄의 `requestId`와 함께).
감사로그의 `llm.ask`에도 `detail.failure`(`unreachable`·`rejected`·`protocol`·`timeout`·`length`·`revoked` …)와 `detail.httpStatus`가 있다. 감사 기록 단계가 1이면 `llm.ask`는 남지 않는다 — 이 절의 감사로그 확인은 로그의 event 코드로 대신한다(7.38절).

**답이 흘러나오지 않고 끝에 한꺼번에 나온다** — 중간의 누군가가 응답을 모았다가 보낸다. 우리 nginx는 앱이 붙이는 `X-Accel-Buffering: no`를 따라 모으지 않는다(설계서 D.1). nginx 앞에 **다른 프록시**(사내 L7 장비 등)가 있으면 그쪽에서 이 경로(`/api/llm/ask`)의 버퍼링을 끄게 한다.

## 7.25-1 "답변이 늦어지고 있습니다."가 뜬다 (Phase 12)

질문을 보내면 답 자리에 **`답변을 기다리고 있습니다 · 12s`**처럼 기다린 초가 보이고, 5초를 넘으면 **`답변이 늦어지고 있습니다.`**가
함께 뜬다. 첫 답 조각(생각 과정 포함)이 오면 사라진다. **질문 수를 막는 장치는 없다** — 사내 LLM 서버가 붐비면 스스로 느려진다(사용자 결정,
보류 30).

| 이렇게 되면 | 뜻 | 조치 |
|---|---|---|
| 몇 초~몇십 초 뒤에 답이 나오기 시작한다 | 사내 LLM 서버가 앞의 질문들을 처리하는 중이다 | 기다린다. 자주 그러면 LLM 서버 담당에게 붐비는 시각을 알린다 |
| 초가 계속 올라가고 5분쯤에 `LLM 서버가 5분 동안 아무것도 보내지 않았다`로 끝난다 | 서버가 첫 글자를 보내지 못했다 — 7.25절의 그 줄 | 7.25절 |
| 초가 멈춰 있다(올라가지 않는다) | 화면이 멈췄다 — 브라우저 문제다 | 새로고침한다. 보낸 질문은 서버가 받았으면 목록에 남는다 |

## 7.26 "API 키를 풀 수 없다" (Phase 10)

LLM API 키는 **`WF_LLM_MASTER_KEY`로 잠가서**(암호화) 데이터베이스에 있다. 그 값이 바뀌거나 비면 저장된 키를 풀 수 없다.

- **이전 값으로 되돌리면** 다시 풀린다 — 백업과 따로 보관해 둔 값을 `.env`에 넣고 다시 띄운다
- 값을 잃었으면 관리 화면에서 그 LLM을 **지우고 키를 다시 넣어 등록**한다. 대화는 남고, 사람들은 새로 등록한 LLM으로 이어 묻는다
- `WF_LLM_MASTER_KEY: 32바이트를 base64(url)로 적은 것이어야 한다`로 **앱이 뜨지 않으면** 값의 모양이 틀렸다 — `openssl rand -base64 32`의 출력을 그대로 넣는다(7.15절과 같은 종류)
- **백업에는 마스터 키가 들어가지 않는다**(데이터베이스와 첨부만). 백업으로 다른 서버에 되살리면 그 서버에도 **같은 마스터 키**가 있어야 키가 풀린다

## 7.27 LLM 대화가 사라졌다 (Phase 10)

**되살릴 수 없다** — LLM 대화는 휴지통에 가지 않는다(`CLAUDE.md` 6절). 왜 사라졌는지만 확인한다.

| 확인 | 뜻 |
|---|---|
| 고정하지 않은 대화이고 마지막으로 물은 지 7일(운영 설정 `llmRetentionDays`)이 지났다 | 보존 기간이다. 앱이 한 시간마다 지운다. 감사로그 `llm.conversation.purge`에 지운 수가 남는다 |
| 그 사람의 대화가 100개(`llmConversationMax`)를 넘었다 | 새 대화를 저장할 때 **고정하지 않은 것 중 가장 오래된 것**이 지워졌다. 그때 화면이 "오래된 대화 n개를 지웠다"고 말했고, 감사로그 그 사람의 `llm.ask`에 `detail.evicted`가 있다 |
| 관리자가 운영 설정에서 기간·개수를 줄였다 | 감사로그 `settings.update`의 이전·이후 값 |
| 로그에 `llm.sweep_failed` · `error: 42P01 relation "llm_conversations" does not exist` | 반대로 **지워지지 않는다** — 표가 없다. 반입 가이드 5절의 표 만들기(`migrate.js`)를 빠뜨렸다. 지운 날에는 `llm.sweep_done`(`count`)이 남는다 |

고정한 대화는 풀 때까지 지워지지 않는다. 오래 남겨야 하는 대화는 **고정**하라고 알린다(20개까지).

**"보관 105/100"처럼 상한을 넘어 보인다** — 관리자가 운영 설정에서 대화 수(`llmConversationMax`)를 그 사람의 **고정 수 아래로** 내렸다.
고정은 관리 작업이 풀지 않는다(사람이 한 설정을 조용히 되돌리지 않는다, 설계서 D.5). 새 질문은 그대로 되고 고정하지 않은 앞 대화만
지워진다. 그 사람이 고정을 풀어야 줄어든다.


## 7.28 앱 로그 읽기 — 요청 번호와 event 코드 (Phase 11)

앱 로그는 **한 줄에 JSON 하나**다. 줄마다 **`event`**(무슨 일인가 — 아래 표)가 있고, 요청 안에서 남긴 줄에는 **`requestId`**(그 요청의
번호)와 로그인한 사람의 `userId`가 있다. 문장(`msg`)은 사람을 위한 설명이다 — **찾을 때는 event와 번호로 찾는다.** 문장은 고쳐질 수
있지만 event 코드는 그대로다(설계서 `P11_설계서_Ops` D.4).

### 한 요청을 끝까지 잇기

"방금 오류가 났다"는 신고를 받으면:

1. 그 시각 근처의 실패한 요청을 찾는다 — 앱 접근 로그(`http.request`)의 `status`가 500번대인 줄:
   ```
   docker compose -f compose.yml logs api --since 15m | grep '"event":"http.request"' | grep '"status":5'
   ```
   사용자를 알면 그 사람의 id로 좁힌다(`SELECT id FROM users WHERE username = '<아이디>'`를 postgres 컨테이너에서).
2. 그 줄의 `requestId`로 **같은 요청의 모든 줄**을 모은다 — nginx 줄(들어온 요청), 앱 접근 로그, 오류 줄(`http.unhandled` 등):
   ```
   docker compose -f compose.yml logs api nginx --since 15m | grep '<requestId>'
   ```
3. 그 요청이 남긴 **감사 행** — 관리 화면의 **감사로그 → "요청 번호"** 칸에 붙이고 **거르기**. 목록 끝 칸에도 번호가 보인다.
   관리 화면을 열 수 없으면 데이터베이스에서:
   ```
   docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT created_at, action, target_type, target_id FROM audit_events WHERE request_id = '<requestId>'"
   ```

화면을 연 사람도 번호를 볼 수 있다 — 브라우저 개발자 도구 → 네트워크 → 그 요청의 응답 머리말 `X-Request-Id`.
개발 담당에게 넘길 때는 **요청 번호와 시각**을 함께 준다.

- **앱 접근 로그**(`http.request`): `method`·`route`(경로 틀 — `/api/pages/:id`)·`status`·`durationMs`·`userId`, 받는 쪽이 먼저 끊었으면
  `aborted`. 없는 주소를 부른 요청(404)은 `route`가 비고 `path`(받은 경로, 200자까지)가 있다. 주소의 대소문자는 가리지 않는다(`/API/…`도
  남는다). **질의 문자열(검색어)은 싣지 않는다.** 헬스체크와 화면 파일, 그리고 배경 표시(`x-wf-background: 1`)가 붙은 알림 수 물음(`GET /api/notifications/unread-count` — 30초마다)은 남기지 않는다(nginx 접근 로그도 같다). 그 밖의 경로는 표시가 붙어도 남는다. 5xx는 `warn`이다.
- `userId`는 **그 요청을 보낸 사람**이다. 세션을 끊는 요청(관리자의 강제 종료·비밀번호 변경) 안에서 남은 줄은 끊긴 사람을
  **`targetUserId`**로 따로 적는다(`collab.revoked`·`session.revoke_failed`).
- **nginx 로그**도 JSON 한 줄이다: `requestId`·`method`·`uri`(질의 없음)·`status`·`requestTime`·`upstreamTime`. referer는 싣지 않는다.
- 실시간 편집(WebSocket)의 줄에는 `requestId`가 없다 — `pageId`·`userId`로 찾는다.

### 로그는 얼마나 남나

서비스마다 **20MB 파일 5개**(최대 100MB)까지 남고 넘으면 오래된 것부터 지워진다. 오래 두어야 하는 로그는 그 전에 옮겨 둔다:
`docker compose -f compose.yml logs --no-color api > api-날짜.log`. 크기와 개수는 `.env`의 `WF_LOG_MAX_SIZE`·`WF_LOG_MAX_FILES`로
바꾸고 **컨테이너를 다시 만들어야 먹는다**(`docker compose -f compose.yml up -d`).

## 7.29 설치 직후 root로 로그인이 안 된다 (Phase 13)

새로 설치한 서버에서 첫 계정의 아이디(`.env`의 `WF_ROOT_USERNAME`, 비어 있으면 `root`)와 `WF_ROOT_PASSWORD`로 로그인하면 **아이디 또는
비밀번호가 올바르지 않다**만 뜬다. 관리자가 아무도 없으니 감사로그 화면도 열 수 없다 — 데이터베이스에서 직접 본다. 아이디를 바꿨으면 둘째
명령의 끝 `'root'`를 그 아이디로 바꿔 친다 — 그대로 치면 남이 그 아이디로 가입해 둔 행(아래 표의 첫 줄)을 찾지 못한다.

```bash
grep '^WF_ROOT_USERNAME=' .env
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT username, role, status, locked_until FROM users WHERE role = 'root' OR username = 'root'"
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT created_at, target_id, detail->>'reason' AS reason FROM audit_events WHERE action = 'auth.login.failure' ORDER BY created_at DESC LIMIT 5"
```

| 보이는 것 | 뜻 | 조치 |
|---|---|---|
| 그 아이디(`WF_ROOT_USERNAME`, 기본 `root`)인 행이 있는데 `role`이 `root`가 아니다(흔히 `member`·`pending`) | **누가 그 아이디로 가입해 두었다** — 첫 계정을 만들기 전에 앱이 떠 있었다. 시드는 그 계정을 root로 올리지 않고 `… root가 아니다 …`로 멈춘다(그 사람의 비밀번호로 root가 되는 길이다) | 그 가입 요청을 승인하지 않는다. `.env`의 `WF_ROOT_USERNAME`을 다른 아이디로 바꾸고 반입 가이드 5-1절을 다시 친다. 새 root로 들어가 그 계정을 확인한다 |
| 둘째 명령이 `(0 rows)` | **첫 계정을 만들지 않았다** — 반입 가이드 5-1절을 건너뛰었다. 이 시스템에는 계정을 만드는 화면이 없고, 가입 요청은 승인할 관리자가 있어야 한다 | 반입 가이드 5-1절: `docker compose -f compose.yml --env-file .env run --rm tools node dist/db/seed.js` → `root 계정 생성`. `WF_ROOT_PASSWORD가 없다`로 멈추면 반입 가이드 3절대로 `.env`에 값을 넣고 다시 친다 |
| `reason`이 `unknown` | 그 아이디가 없다 | 둘째 명령의 `username`으로 들어간다(`WF_ROOT_USERNAME`을 바꿨으면 그 이름이다) |
| `reason`이 `wrong` | 비밀번호가 다르다. **시드는 이미 있는 계정의 비밀번호를 바꾸지 않는다** — 계정을 만든 뒤 `.env`의 값을 바꿨으면 먹지 않는다 | 처음 시드를 친 때의 값으로 들어간다. 모르면: 다른 root가 있으면 그 사람이 사용자 관리에서 **비밀번호 초기화**를 한다. 없으면 개발 담당에게 |
| `reason`이 `locked`이고 `locked_until`이 지금보다 뒤 | 여러 번 틀려 잠겼다(기본 5회·15분) | 그 시각이 지나면 다시 한다 |
| `status`가 `suspended` | 정지돼 있다 — 시드는 정지된 root를 되살리지 않는다(`root 계정이 정지돼 있다 … 되살리지 않는다`) | 다른 root가 **정지 해제**한다(7.32절) |

## 7.30 화면이 500이고 앱 로그에 `permission denied` — 앱 계정의 권한이 비었다 (Phase 13)

앱은 **앱 계정**(`workfluence_app`)으로 데이터베이스에 붙는다 — 표를 읽고 쓰기만 하고, 표를 만들거나 감사기록을 고치지 못한다. 그 권한은
표 만들기(`tools`의 `migrate.js`)가 준다. 그 단계가 빠지면 아래처럼 보인다. **`/api/health`는 `ok`다** — 헬스체크는 데이터베이스에 붙는지만
보고 표를 읽지 않는다. 조용한 유형이다.

| 보이는 것 | 뜻 |
|---|---|
| 화면의 저장·조회가 500을 내고, 앱 로그의 `http.unhandled` 줄 `error`가 `42501 permission denied for table <표>`(또는 `for sequence <이름>`) | 앱 계정에 그 표의 권한이 없다. 흔히 **백업을 되살린 뒤**다 — 되살린 데이터베이스에는 백업을 뜬 때의 권한이 들어온다. 앱 계정이 없던 Phase 13 전의 백업이면 비어 있다 |
| 표 만들기의 출력에 `앱 계정 workfluence_app: 권한 적용`이 없다, 또는 표 만들기가 `42501 permission denied …`로 멈췄다 | 표 만들기를 `api`로 쳤다(`run --rm api node dist/db/migrate.js` — Phase 13 전 가이드의 명령). `api`는 앱 계정이라 표를 만들 수 없고 권한도 주지 않는다 |
| 감사로그 정리가 `permission denied for table audit_events`로 멈췄다 | 정리를 `api`로 돌렸다. 앱 계정은 감사기록을 지우지 못한다 — **일부러 그렇다.** `tools`로 한다(운영이관 4.2절) |

확인 — 앱 계정이 가진 권한을 표마다 본다.

```bash
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT table_name, string_agg(privilege_type, ',' ORDER BY privilege_type) AS privileges FROM information_schema.role_table_grants WHERE grantee = 'workfluence_app' GROUP BY table_name ORDER BY table_name"
```

모든 표가 나오고 `audit_events`만 `INSERT,SELECT`, 나머지는 `DELETE,INSERT,SELECT,UPDATE`여야 한다. 표가 빠졌거나 아무 줄도 없으면
권한이 빈 것이다.

조치 — 표 만들기를 `tools`로 다시 친다. 여러 번 쳐도 같다.

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/db/migrate.js
```

`앱 계정 workfluence_app: 권한 적용`이 나오면 된다. 앱을 다시 띄울 필요는 없다 — 권한은 다음 요청부터 먹는다. 그래도 500이 이어지면
`docker compose -f compose.yml --env-file .env restart api`.

## 7.31 `WF_PG_APP_PASSWORD`가 없다며 멈춘다 · 앱이 앱 계정으로 붙지 못한다 (Phase 13)

| 보이는 것 | 뜻 |
|---|---|
| compose 명령이 아무것도 하지 않고 `… WF_PG_APP_PASSWORD를 .env에 설정`을 낸다(`up`도 `run --rm tools`도) | `.env`에 앱 계정 비밀번호가 없다 — Phase 13 전에 만든 `.env`이거나, `--env-file`이 다른 파일을 가리킨다 |
| `/api/health`가 `degraded`이고 앱 로그의 `health.db_failed` 줄 `error`가 `28P01 password authentication failed for user "workfluence_app"` | 앱 계정이 아직 없거나 비밀번호가 `.env`와 다르다 — 표 만들기보다 앱을 먼저 띄웠거나, `WF_PG_APP_PASSWORD`를 바꾸고 표 만들기를 치지 않았다 |
| 앱이 `WF_DATABASE_URL`을 말하며 켜지다 죽는다 · `tools`가 접속 주소를 읽지 못한다 | 비밀번호에 `/ ? # %` 같은 글자가 있어 접속 주소가 깨졌다. `$`가 든 값은 compose가 변수로 읽어 다른 값이 된다 |

조치 — 셋 다 같은 순서다. **순서를 바꾸지 않는다.**

① `.env`에 새 값을 넣는다 — 줄이 없으면 더하고, 있으면 바꾼다. 숫자와 a~f만 나오는 값이다.

```bash
grep -q '^WF_PG_APP_PASSWORD=' .env || echo 'WF_PG_APP_PASSWORD=' >> .env
sed -i "s/^WF_PG_APP_PASSWORD=.*/WF_PG_APP_PASSWORD=$(openssl rand -hex 16)/" .env
```

② 표 만들기 — 앱 계정을 만들거나 비밀번호를 새 값으로 맞춘다.

```bash
docker compose -f compose.yml --env-file .env run --rm tools node dist/db/migrate.js
```

③ 앱을 새 값으로 다시 만든다.

```bash
docker compose -f compose.yml --env-file .env up -d
```

`up -d`는 `.env`가 바뀐 것을 알아채고 앱을 새로 만든다. ③을 ②보다 먼저 하면 앱이 아직 없는(또는 옛 비밀번호의) 계정으로 붙으려다
위의 `28P01`이 난다. 앱 계정의 비밀번호는 언제 바꿔도 된다 — 이 세 단계가 전부다.

**소유 계정(`WF_PG_PASSWORD`)의 값이 깨졌으면 다르다.** 그 비밀번호는 데이터베이스를 처음 만들 때 정해져, `.env`만 바꿔서는 맞지
않는다 — 개발 담당과 함께 고친다.

## 7.32 정지된 사람이 로그인이 안 된다고 한다 (Phase 13)

관리자가 **사용자 관리**에서 **정지**한 계정은 로그인하지 못한다 — 퇴사자를 막는 장치다. 정지하는 순간 그 사람의 로그인이 모두 풀리고,
열어 둔 편집 창도 그 자리에서 끊긴다(앱 로그 `collab.revoked` · `reason: 세션 파기`).

| 확인 | 방법 |
|---|---|
| 정지됐는가 | 사용자 관리 → **찾기**에 아이디를 넣거나 **상태**에서 **정지**를 고른다. 상태 칸이 **정지**다 |
| 로그인 화면에 뜨는 말 | 아이디·비밀번호 계정은 다른 실패와 같은 **아이디 또는 비밀번호가 올바르지 않다**다 — 비밀번호가 맞아도 그렇다(계정이 있는지 새지 않게). 사내 계정은 **이 계정은 정지돼 있다 — 관리자에게 문의한다** |
| 누가 언제 정지했나 | 감사로그 `user.suspend`(푼 것은 `user.unsuspend`). 정지된 사람의 로그인 시도는 `auth.login.failure`의 `reason: suspended` |

**조치.** 퇴사자라면 그대로 둔다. 잘못 정지했으면 관리자가 그 줄의 **정지 해제**를 누른다 — 곧바로 **활성**이 되고, 비밀번호·Crew 소속·쓴
문서는 그대로다. 그 사람은 다시 로그인하면 된다(정지할 때 로그인이 모두 풀렸다). 화면의 순서는 사용자 가이드 16.10절이다.

- 정지할 수 없는 경우 — 단추가 눌리지 않거나, 눌러도 화면이 빨간 글씨로 까닭을 말한다: 자기 자신(`자기 자신은 정지할 수 없다`),
  마지막 root(`마지막 root는 정지할 수 없다`), 승인 대기 계정(`활성 계정만 정지할 수 있다` — 승인하지 않고 두면 어차피 로그인하지 못한다),
  관리할 권한이 없는 사람(`이 사용자를 관리할 권한이 없다` — admin에게 root, 위임받지 않은 admin에게 위임받은 admin).
- 사내 계정도 회사 로그인이 된 뒤 이 위키가 거절한다. 정지를 풀기 전에는 로그인할 때마다 되살아나지 않는다.
- 정지된 사람은 불러도(`@아이디`) 알림이 가지 않는다 — 승인 대기 계정과 같다.

## 7.33 (빌드 서버) 묶기가 이미지나 작업 폴더 때문에 멈춘다 (Phase 13)

`pnpm release:bundle`(빌드 가이드 12절)은 이미지를 저장하기 전에 셋을 보고, 하나라도 어긋나면 묶지 않고 멈춘다.

| 멈추며 하는 말 | 뜻 | 조치 |
|---|---|---|
| `앱 이미지가 <이름>다 — 폐쇄망의 compose는 workfluence-app:latest를 찾는다 …` | `WF_APP_IMAGE`로 다른 태그를 가리켰다(셸이나 `deploy/.env`). 그대로 묶으면 폐쇄망의 `up -d`가 "이미지 없음"으로 죽는다 | 셸의 `WF_APP_IMAGE`를 비우고(`unset WF_APP_IMAGE`), `deploy/.env`에 그 줄이 있으면 지운 뒤 다시 한다 |
| `커밋하지 않은 변경이 있다 — 커밋한 뒤 다시 빌드하고 묶는다:` 뒤에 파일 목록 | 작업 폴더에 커밋하지 않은 변경이 있다. 이미지는 작업 폴더 그대로 만들어지는데 라벨은 커밋 번호만 적는다 — 내용이 다른 이미지가 같은 라벨을 단다 | 그 변경을 커밋하거나 되돌린 뒤 **빌드부터** 다시 한다(빌드 가이드 5절). 되돌리기만 하고 빌드하지 않으면 이 검사는 지나지만 이미지는 그 변경을 담고 있다 |
| 아래 문장 — 라벨이 HEAD와 다르다 | 아래 표 | 아래 표 |

셋째는 이렇게 말한다.

```text
앱 이미지(workfluence-app:latest)는 커밋 <라벨>로 빌드됐다 — 지금은 <HEAD>다. 지금 커밋으로 다시 빌드한다: GIT_SHA=$(git rev-parse HEAD) docker compose -f deploy/compose.yml --env-file deploy/.env build api
```

묶음은 **지금 커밋으로 빌드한 앱 이미지만** 담는다 — 다른 커밋의 이미지가 반입되면 `MANIFEST.txt`의 커밋과 실제 내용이 어긋나고,
폐쇄망에서 "무엇이 들어갔나"를 답할 수 없다.

| `<라벨>` 자리 | 뜻 | 조치 |
|---|---|---|
| `(라벨 없음)` 또는 `unknown` | `GIT_SHA` 없이 빌드했다(옛 빌드 명령) | 빌드 가이드 5절의 명령으로 다시 빌드한다 |
| 다른 커밋 번호 | 빌드한 뒤에 커밋이 바뀌었다(`git pull`·새 커밋) | 같다 |

다시 빌드한 뒤 빌드 가이드 12절을 처음부터 한다. **`GIT_SHA`에 지금 커밋이 아닌 값을 넣어 맞추지 않는다** — 라벨이 묶음의 유일한 근거다.
작업 폴더 검사는 **묶는 순간**만 본다 — 고친 채로 빌드하고 되돌린 뒤 묶으면 지나간다. 그래서 빌드 전에도 `git status --short`가 비어 있는지 본다(빌드 가이드 3절).

## 7.34 로그인이 몰리면 느려진다 (Phase 13)

비밀번호 확인은 **일부러 무거운 계산**이다(한 번에 CPU로 0.1~0.2초) — 비밀번호를 훔쳐도 하나씩 맞춰 보기 어렵게 하려는 것이다.
Phase 13부터 그 계산이 남에게 번지지 않게 했다(보류 16).

- 확인하는 동안 **데이터베이스 연결을 쥐지 않는다.** 전에는 로그인이 몰리면 연결 10개가 모두 확인을 기다리며 묶여, 남의 조회까지 2~4초씩
  기다렸다.
- 한 서버에서 동시에 도는 확인은 **CPU 코어 수까지, 많아도 셋**이다 — 앱의 작업 스레드 넷 가운데 하나는 파일 읽기·쓰기에 남긴다. 넘는 로그인은 줄을 선다.
- **한 계정의 로그인은 차례로** 확인한다 — 같은 아이디로 동시에 여러 번 들어오면 하나씩 처리된다. 동시에 틀려도 잠금이 걸리게 하려는 것이다.

그래서 몰리면 **로그인은** 차례를 기다려 몇 초씩 걸릴 수 있지만 **남의 화면은 늦어지지 않는 것이** 정상이다(고치기 전과 뒤를 잰 값은
`docs/P13_검증기록_Readiness.md` 2절). 그렇지 않을 때 본다.

```bash
docker compose -f compose.yml --env-file .env logs api --since 15m | grep '"route":"/api/auth/login"'
docker compose -f compose.yml --env-file .env logs api --since 15m | grep 'timeout exceeded when trying to connect'
docker stats --no-stream workfluence-api
```

| 보이는 것 | 뜻 | 조치 |
|---|---|---|
| 로그인 줄의 `durationMs`가 몰린 때만 길고 곧 돌아온다. 같은 시각의 다른 `http.request` 줄은 짧다 | 확인이 줄을 섰다 — 정상 | 없다 |
| 같은 시각의 다른 `http.request` 줄도 `durationMs`가 길다 | 남에게 번졌다 | 아래 둘을 본다 |
| 둘째 명령에 줄이 나온다 | 데이터베이스 연결을 기다리다 10초에서 실패했다 | 7.17절(`pg_stat_activity`의 `idle in transaction`). 그 시각과 줄을 개발 담당에게 |
| `docker stats`의 CPU가 로그인이 몰린 동안 내내 높다(확인 한 건이 코어 하나 남짓을 쓴다 — 2코어 서버면 200% 가까이) | 확인 계산이 CPU를 쓴다 | 로그인이 끝나면 내려온다. 몰릴 때마다 그러면 그 시각과 로그인 수(감사로그 `auth.login.success`·`auth.login.failure`)를 개발 담당에게 |
| 한 아이디의 로그인만 오래 걸린다 | 그 아이디로 동시에 여러 번 들어온다(자동 로그인하는 프로그램 등) — 차례로 처리된다 | 그 프로그램을 확인한다. 틀린 비밀번호가 몰리면 그 계정이 잠긴다(7.1·7.11절) |
| 여럿이 한꺼번에 로그인하는데 일부가 **요청이 너무 잦다. 1분 후 다시 시도한다**를 받는다 | 사내 NAT 뒤라 모두가 한 주소로 보이면, 한 주소에서 **아직 끝나지 않은** 로그인이 20건을 넘는 순간 막힌다 — 성공한 로그인은 끝난 뒤에야 세지 않게 된다(7.11절). 로그인이 줄을 서 오래 걸릴수록 잘 생긴다 | 1분 뒤 다시 하게 한다. 다 같이 로그인하는 행사(교육 등)라면 미리 개발 담당과 본다 — 여러 주소에서 한꺼번에 몰리는 모양은 아직 재지 못했다(보류 31) |

## 7.35 문서를 옮길 수 없다 · 옮겼는데 순서가 다르다 (Phase 14)

문서는 문서 보기 화면의 **옮기기**로 옮긴다(사용자 가이드 3.3절). 판정은 서버가 한다 — 화면은 까닭을 그대로 보인다.

| 화면에 뜬 말 | 뜻 | 조치 |
|---|---|---|
| **페이지 트리 깊이는 10를 넘을 수 없다** | 옮길 문서 **아래에 달린 문서까지** 세어 10단계를 넘는다 | 더 얕은 자리를 고른다. 깊이 한도는 설계 고정값이라 바꾸지 않는다 |
| **페이지를 자기 자신이나 자손 아래로 옮길 수 없다** | 옮기기 칸을 연 사이 누가 트리를 바꿨다(칸은 자기와 그 아래를 목록에서 뺀다) | 새로고침하고 다시 고른다 |
| **부모 페이지를 찾을 수 없다** | 고른 부모가 그 사이 지워졌다 | 새로고침하고 다시 고른다 |
| **이 스페이스의 페이지 트리를 다른 사람이 바꾸는 중이다 — 잠시 뒤 다시 한다** | 같은 공간의 옮기기·만들기·지우기·되살리기는 차례로 한다. 앞의 것을 2초 넘게 기다리게 되어 돌려보냈다 — 끝없이 기다리면 기다리는 요청들이 데이터베이스 연결을 다 쥔다(7.17절) | 잠시 뒤 다시 한다. 한가한 때도 자주 뜨면 그 시각과 공간을 개발 담당에게 — 느린 요청은 7.17절로 본다 |
| **이 스페이스에 쓸 권한이 없다** | viewer이거나 공간이 중지됐다 | 7.36절 |

"어느 문서 다음"으로 옮겼는데 순서가 다르다 — 까닭은 둘이다.

1. **칸을 연 뒤 누가 같은 부모 아래를 바꿨다.** 자리는 칸을 연 때의 "형제 가운데 몇 번째"로 보내므로 한 칸 어긋날 수 있다. 한 번 더 옮긴다.
2. **자리 값이 겹쳐 있다.** 같은 값이면 만든 순서로 갈린다. 겹침은 Phase 14 전의 옮기기(받은 값을 그대로 적었다)와 동시 만들기(둘이 같은
   맨 뒤를 읽었다), 그리고 지금도 휴지통 **되살리기**(부모 아래로 되살리면 지울 때의 자리 값을 그대로 쓴다)로 생긴다. 옮긴 문서는 이웃 둘 사이의
   빈 값을 받고, **이웃 둘의 값이 같아** 빈 값이 없을 때만 형제 전부가 다시 매겨진다. 그래서 **겹친 두 문서 사이로 한 문서를 옮기면** 풀린다
   (예: A·B·C가 겹쳤으면 C를 **A 다음**으로). 겹친 것이 둘뿐이면 그 가운데 하나를 아무 자리로나 옮겨도 풀린다. 옮긴 뒤 아래 질의를 한 번 더
   쳐서 줄이 없는지 본다.

자리가 겹쳤는지는 이렇게 본다(공간과 부모마다 묶는다 — 지운 문서와 휴지통의 공간은 뺀다).

```bash
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT s.name AS space, p.parent_id, p.position, count(*) FROM pages p JOIN spaces s ON s.id = p.space_id WHERE p.deleted_at IS NULL AND s.deleted_at IS NULL GROUP BY s.id, s.name, p.parent_id, p.position HAVING count(*) > 1 ORDER BY 1"
```

`(0 rows)`면 겹친 곳이 없다. 줄이 나오면 그 공간(`space`)의 그 부모(`parent_id` — 맨 위면 빈칸) 아래에서 겹친 문서 하나를 옮긴다. 누가 언제
어디서 어디로 옮겼는지는 감사로그 `page.move`에 남는다(옛 부모·자리와 새 부모·자리).

## 7.36 공간·분류를 지울 수 없다 · 중지된 공간을 바꿀 수 없다 (Phase 14)

공간의 관리 칸(스페이스 정보·분류 관리·위험 구역 — 사용자 가이드 2.6절)과 관리자의 **스페이스 관리** 화면(같은 가이드 17.1절)은 서버의 규칙대로 단추를 보인다.

| 보이는 것 | 뜻 | 조치 |
|---|---|---|
| **지우기**가 없다(주인 — 팀 공간의 owner, 개인 공간을 만든 사람) | Crew가 본인 말고도 있거나, 공간이 **중지**됐다. 남이 쓰는 공간을 주인 혼자 지우지 못하고, 중지된 공간은 관리자(와 **스페이스 관리 전체**를 맡겨 받은 사람)만 지운다 | Crew를 먼저 뺀다. 중지됐으면 관리자에게 맡긴다 |
| **지우기**가 없다(관리자) | 공간이 쓰는 중이다(활성) | 먼저 **중지**한다. 중지된 줄에 **지우기**가 보인다. 관리자가 주인이고 Crew가 본인뿐인 공간은 주인으로서 활성일 때도 지운다 |
| **중지된 스페이스는 바꿀 수 없다** | 관리 칸을 연 사이 누가 공간을 중지했다. 중지된 공간에서는 칸이 잠기고 **중지된 스페이스는 이름·설명·분류를 바꿀 수 없다. 먼저 다시 쓸 수 있게 한다.**가 보인다 | **다시 쓰기** → 바꾸기 → 필요하면 다시 **중지**. **관리자가 건 중지**면 주인에게는 **다시 쓰기**가 없다 — 관리자에게 부탁한다(7.37절). 관리자가 **주인이 건 중지**에서 이 순서를 밟으면 다시 건 중지는 **관리자가 건 것**이 된다 — 주인이 풀지 못하고 Crew도 바꾸지 못하게 된다(Phase 16). 주인이 풀 수 있게 두려면 관리자는 다시 쓰기만 하고 주인에게 알린다 |
| 관리자가 중지한 공간을 주인이 **다시 쓰기**로 풀었다 | Phase 14까지는 주인도 풀었다 — 누가 걸었는지 가리지 않았다(보류 32). **Phase 15부터는 막는다** — 푼 사람이 주인이면 **관리자가 건 중지 풀기**를 맡겨 받은 것이다 | 7.37절. 감사로그 `space.status.change`로 누가 풀었는지 본다 |
| (Phase 14까지) **이 분류를 쓰는 스페이스가 N개 있다(휴지통 포함). 먼저 옮긴 뒤 지운다** | 그 분류를 쓰는 공간이 있어 지우지 못했다. **Phase 15부터는 지우면 쓰던 공간이 분류 없음이 된다** — 이 말은 나오지 않는다 | 7.37절 |
| **남의 공간이 쓰는 분류는 관리자나 '분류 관리'를 받은 사람이 지운다** (또는 **이름을 바꾼다**) | 만든 사람이 지우려 했는데 만든 사람이 주인이 아닌 공간(휴지통 포함)이 그 분류를 쓴다 | 관리자가 지우거나, 관리자가 그 사람에게 **분류 관리**를 맡긴다(사용자 가이드 16.7절) |
| **분류는 만든 사람과 관리자가 지운다** | 만든 사람도 관리자도 아니다 | 만든 사람이나 관리자에게 부탁한다 |
| **스페이스 관리** 메뉴가 없다 | 그 계정이 관리자(admin·root)도, **스페이스 관리 전체**·**분류 관리**를 맡겨 받은 member도 아니다 | 사용자 관리에서 역할과 위임을 본다(7.37절) |

어느 공간이 그 분류를 쓰는지는 이렇게 본다 — 쓰이는 분류 **전부**를 보이고, 지우려는 분류의 줄을 찾는다(휴지통의 공간은 `deleted_at`이 찍혀
있다). **명령에 분류 이름을 넣지 않는다** — 분류 이름은 사용자가 지은 글자라, 붙여 넣으면 따옴표 등이 명령과 질의를 바꿀 수 있다.

```bash
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT c.name AS category, s.name AS space, s.status, s.deleted_at FROM space_categories c JOIN spaces s ON s.category_id = c.id ORDER BY c.name, s.name"
```

지운 공간은 휴지통의 **지운 스페이스**에서 관리자(와 **스페이스 관리 전체**를 맡겨 받은 사람)가 되살린다(7.5절).

## 7.37 주인이 다시 쓰기를 못 한다 · 주인이 Crew를 바꾸지 못한다 · 맡긴 권한이 먹지 않는다 · 분류를 지웠더니 공간의 분류가 없어졌다 (Phase 15·16)

Phase 15부터 **관리자가 member 한 사람에게 일을 맡긴다**(분류 관리·관리자가 건 중지 풀기·스페이스 관리 전체 — 사용자 가이드 16.7절). 관리자가 건
중지는 권한을 받은 주인만 풀고(Phase 16부터 그동안 Crew는 관리자만 바꾼다), 분류를 지우면 쓰던 공간은 분류 없음이 된다. 아래는 그 규칙대로 동작하는 것이다 — 고장이 아니면 설명하고, 바꿔야
하면 위임을 켜고 끈다.

| 증상 | 확인 | 원인 | 조치 |
|---|---|---|---|
| 주인의 관리 칸에 **관리자가 중지한 스페이스다.**가 보이고 **다시 쓰기**가 없다. 누르던 화면에서는 **관리자가 중지한 스페이스다 — 다시 쓰기는 관리자나 '관리자가 건 중지 풀기'를 받은 주인이 한다**(403) | 아래 첫 명령 — 그 공간의 `suspended_by_owner`가 `f`다 | 주인이 아닌 사람(관리자, 스페이스 관리 전체를 받은 사람)이 중지했다. Phase 15 전에 이미 중지돼 있던 공간은 건 사람을 모르면 관리자가 건 것으로 쳤다 | 관리자가 **스페이스 관리**에서 **다시 쓰기**를 누르거나, 그 주인에게 **관리자가 건 중지 풀기**를 켠다 |
| 위임을 켰는데 그 사람에게 메뉴·단추가 안 보인다 | 아래 둘째 명령 — 그 사람의 `role`과 `grants` | 화면을 새로 고치지 않았다(권한은 **다음 요청부터** 먹는다). 또는 역할이 바뀌어 사라졌다 — 셋은 member만, LLM 연결 관리는 admin만 받는다. member가 admin이 되면 셋이 사라진다(admin은 셋을 원래 한다) | 새로 고치게 한다. 역할이 바뀌었으면 다시 켠다 |
| **스페이스 관리 전체**를 받은 사람이 목록의 공간을 누르면 **스페이스를 찾을 수 없다** | 그 사람이 그 공간의 Crew인가 | 스페이스 관리 전체는 중지·다시 쓰기·지우기·되살리기만 맡긴다 — Crew가 아닌 공간의 문서는 읽지 못한다(설명도 비어 보인다) | 고장이 아니다. 읽어야 하면 Crew로 넣는다 — 쓰는 중이거나 주인이 건 중지면 주인이, **관리자가 건 중지**(스페이스 관리 전체를 받은 사람이 건 것도 그렇다)면 관리자가 넣는다(아래 Phase 16 줄) |
| 사용자 관리에서 위임 칸이 눌리지 않는다 | 마우스를 올려 까닭을 본다 | **LLM 연결 관리**는 root만 켜고 끈다. 그 줄 자체를 관리할 수 없는 사람(자기에게 없는 위임을 가진 관리자)이다 | root에게 맡긴다 |
| 분류를 지웠더니 공간들의 분류가 **분류 없음**이 됐다 | 아래 셋째 명령 — 지운 분류와 분류 없음이 된 공간들(`cleared`) | 그렇게 만들었다(사용자 결정 — 지우기 전에 몇 개가 분류 없음이 되는지 묻는다) | 되돌리려면 같은 이름으로 분류를 다시 만들고, `cleared`의 공간들에 붙인다(공간의 관리 칸) |
| **그 사이 누가 상태를 바꿨다 — 다시 본다**(409) · **그 사이 누가 이 스페이스를 바꿨다 — 다시 본다**(409, 지우기) | — | 두 사람이 같은 공간을 거의 동시에 중지하거나 풀거나 지웠다(누가 건 중지인지가 바뀐 것도). 뒤의 요청은 앞의 결과를 판정하지 않고 덮지 않는다 | 화면이 다시 읽는다. 지금 상태를 보고 다시 한다 |
| 관리자가 중지했다고 믿었는데 주인이 **다시 쓰기**로 풀었다 | 감사 `space.status.change`의 중지 줄 — `byOwner`가 `true`면 주인이 건 중지다 | 관리자가 중지를 눌렀을 때 이미 주인이 중지해 두어 아무것도 바뀌지 않았다. 주인이 건 중지는 주인이 푼다 | **스페이스 관리**나 그 공간의 관리 칸에서 **관리자가 건 중지로 바꾸기**(넘겨받기 — 감사에 `takeover`). 그 뒤로는 주인도 권한이 있어야 푼다 |
| **그 사이 누가 이 사람의 위임을 바꿨다 — 목록을 다시 본다**(409) | — | 사용자 관리를 연 사이 다른 관리자가 그 사람의 위임을 바꿨다. 화면이 본 목록과 서버의 목록이 달라 받지 않았다 — 옛 화면이 방금 거둔 위임을 되살리지 않게 | 화면이 목록을 다시 읽는다. 지금 칸을 보고 다시 누른다 |
| **역할을 바꾸면 사라지는 위임을 거둘 권한이 없다: llm.manage**(403) — 화면에서는 그 역할이 골라지지 않는다 | — | LLM 연결 관리를 가진 관리자를 member로 내리면 그 위임이 사라진다 — 그것을 거두는 것은 root다 | root가 역할을 바꾼다 |
| 주인이 Crew를 넣지·빼지·바꾸지 못한다 — **관리자가 중지한 스페이스다 — Crew는 관리자가 바꾼다**(403), Crew 칸에 **추가**가 없다 (Phase 16) | 아래 첫 명령 — 그 공간의 `suspended_by_owner`가 `f`다 | 관리자가 건 중지 동안 Crew는 관리자만 바꾼다(사용자 결정 — 조사하려고 멈춘 공간을 주인이 남에게 열지 못하게). 관리자가 건 중지 풀기를 받은 주인도 먼저 풀어야 한다 | 관리자가 대신 바꾸거나 다시 쓰게 한다. 권한을 받은 주인은 **다시 쓰기**로 먼저 푼다. 퇴사자는 관리자가 빼거나 계정을 정지한다 |
| **주인이 건 중지가 아니다 — 그 사이 누가 바꿨다. 다시 본다**(409) | 감사 `space.status.change` — 그 사이 주인이 다시 쓰기(`wasByOwner: true`)를 했나 | 관리자가 넘겨받기를 누르기 전에 주인이 풀었다. 넘겨받기는 화면이 본 상태(주인이 건 중지)를 싣는다 — 쓰는 중인 공간을 모르고 멈추지 않게 | 화면이 다시 읽는다. 멈춰야 하면 **중지**를 누른다 |
| **없는 분류다**(400) | — | 공간에 분류를 붙이는 사이 누가 그 분류를 지웠다 | 새로 고치고 다른 분류를 고른다 |
| (새 버전 들여오기) 표 만들기(`tools … migrate.js`)가 `users_grants_holder_chk`로 멈춘다 | 아래 넷째 명령 — 관리자가 아닌 사람의 위임 | Phase 15 전의 규칙(위임은 관리자만)을 거스른 행이 있다 — 손으로 고친 데이터가 아니면 생기지 않는다 | 그 행의 위임을 비운 뒤(`UPDATE users SET grants = '{}' WHERE username = '…'` — 소유 계정으로) 표 만들기를 다시 친다. 마이그레이션은 한 트랜잭션이라 멈춘 것은 반쯤 적용되지 않는다 |

명령은 반입한 서버의 compose 폴더에서 친다(운영 이관 가이드). **명령에 공간·분류 이름을 넣지 않는다** — 사용자가 지은 글자라, 붙여 넣으면 따옴표
등이 명령과 질의를 바꿀 수 있다(7.36절과 같은 까닭). 넷째 명령의 결과에서 사람을 확인하고, 조치의 `UPDATE`에만 그 아이디를 넣는다.

```bash
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT s.name, s.kind, s.suspended_at, s.suspended_by_owner, u.username AS suspended_by FROM spaces s LEFT JOIN users u ON u.id = s.suspended_by WHERE s.status = 'suspended' AND s.deleted_at IS NULL ORDER BY s.suspended_at DESC LIMIT 20"
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT username, role, grants FROM users WHERE cardinality(grants) > 0 ORDER BY username"
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT created_at, detail FROM audit_events WHERE action = 'category.delete' ORDER BY created_at DESC LIMIT 5"
docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT username, role, grants FROM users WHERE cardinality(grants) > 0 AND role <> 'admin'"
```

누가 언제 맡기고 거뒀는지는 감사 `user.grants.change`(이전·이후), 누가 중지하고 풀었는지는 `space.status.change`(중지는 `byOwner` — 건 사람이
주인이었나)에 남는다.

## 7.38 감사로그에 자동 저장·첨부 받기·내보내기·LLM 질문이 안 보인다 (Phase 17)

대개 고장이 아니라 **감사 기록 단계**다. 감사로그 화면 제목 아래의 접힌 **기록 단계:** 줄을 본다 — 지금 단계가 적혀 있고, 누르면 펼쳐진다(사용자가이드 18.3절).

| 지금 단계 | 남기지 않는 것 |
|---|---|
| 2 · 줄임 | `page.collab.save`(실시간 편집의 자동 저장 — 사람이 누른 저장 `page.collab.flush`와 제목 바꾸기 `page.collab.title`은 늘 남는다) |
| 1 · 최소 | 위에 더해 `attachment.download`·`page.export`·`mail.send`·`llm.ask` |

- 누가 언제 바꿨는지는 감사로그에서 행위 `settings.update`의 상세(`before`·`after`의 `auditLevel`)로 본다 — 그 기록은 단계와 무관하게 남는다.
- 다시 남기려면 시스템 관리자가 **3 · 전체**로 고른다. 낮춘 동안의 기록은 되살릴 수 없다.
- 단계가 3인데도 안 보이면 그때가 고장이다. 7.12-1절처럼 `docker compose logs api`에서 그 시각의 오류를 본다.

## 8. 기록은 어디에 있는가

| 무엇 | 어디 | 성격 |
|---|---|---|
| 앱이 남긴 운영 기록 | 컨테이너 표준 출력 (`docker compose logs`) | 한 줄에 JSON 하나 — `event` 코드와 요청 번호(`requestId`)가 있다(7.28절). 서비스마다 20MB × 5개에서 순환한다 |
| 누가 무엇을 했는지 | 데이터베이스의 감사 기록 테이블 | **수정·삭제 불가**. Phase 1부터 채워진다. Phase 11부터 행마다 그 요청의 번호(`request_id`)가 있다 |
| 들어온 요청 | nginx 컨테이너 로그 | JSON 한 줄 — 요청 번호가 앱 로그와 같다. 질의 문자열(검색어)은 없다 |
| 데이터베이스 자체 기록 | postgres 컨테이너 로그 | 연결·디스크 오류가 여기 나온다 |

앱 기록에는 **비밀번호·토큰·세션 값·문서 본문·LLM 질문과 답·지시문·LLM API 키가 들어가지 않는다.** 데이터베이스 오류도 PostgreSQL의 코드와 문장만 — 문장 속 값은 가린다. 로그를 보고 사용자 개인정보나 문서 내용을 알 수는 없다. 사용자는 불투명한 식별자로만 나온다.
