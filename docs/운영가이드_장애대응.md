- 읽는 사람: **운영 담당자.** 증상에서 시작해 확인, 조치로 간다

- 현재 반영 범위: **Phase 12까지** (2026-09-26). 앱 기동·DB·화면 서빙·설정(2~6절), 로그인·세션(7.1~7.4), 스페이스·페이지(7.5~7.8), 첨부·검색(7.9~7.10), 휴지통·로그인 제한·알림·운영 설정(7.10-1~7.13), 반입·기동·인증서·느림과 멈춤·되살리기(7.14~7.18), 실시간 편집·메일(7.19~7.21), 살아 있는 연결의 권한·프록시(7.19-1·7.19-2), 남의 편집이 안 보임(7.19-3), 내 글이 남에게 안 보임(7.19-4), 알림의 부른 사람(7.22), 서버가 편집을 받지 않음(7.23), 사내 LLM(7.24~7.27, 답을 기다리는 표시 7.25-1), 앱 로그 읽기 — 요청 번호·event 코드(7.28), 사내 IdP 실패(7.3)

> 개발 중에 겪은 문제는 [`docs/internal/검토서_트러블슈팅.md`](internal/검토서_트러블슈팅.md)에 있다. 이 문서는 **운영에서 일어나는 일**만 다룬다.

## 0. 어떤 순서로 보는가

세 가지를 이 순서로 확인한다. 순서를 바꾸면 엉뚱한 곳을 고친다.

```
① 켜져 있는가        docker compose ps          — 컨테이너가 도는지, healthy인지
② 창고가 붙었는가     /api/health 의 db 값        — ok가 아니면 데이터베이스 문제다
③ 무슨 말을 하는가    docker compose logs        — 앱이 남긴 기록. event 코드와 요청 번호로 찾는다 (7.28절)
```

**코드를 의심하기 전에 서비스가 떠 있는지 본다.** 내려간 서비스를 코드 문제로 오진하는 것이 가장 흔한 낭비다.

## 2. 데이터베이스를 못 쓰는 상태

앱은 살아 있고 데이터베이스만 안 될 때가 가장 흔하다. 이 시스템은 그 상태를 **정상으로 보고하지 않도록** 만들었다.

```bash
curl -s http://127.0.0.1:3000/api/health
```

| 응답 | 뜻 |
|---|---|
| `{"status":"ok","db":"ok",...}` | 앱과 데이터베이스 모두 정상 |
| `{"status":"degraded","db":"unreachable"}` + HTTP 503 | 앱은 살아 있고 데이터베이스가 안 된다 |
| 응답 없음 | 앱 자체가 죽었다. 4절로 |

`degraded`가 나오면 순서대로 본다.

```bash
docker compose -f deploy/compose.yml ps          # postgres가 healthy인가
docker compose -f deploy/compose.yml logs postgres --tail 50
df -h /                                          # 디스크가 찼는가
```

**디스크 부족을 먼저 확인한다.** 디스크가 차면 데이터베이스가 쓰기에 실패하고, 그 증상은 연결 오류처럼 보인다. 원인과 증상이 달라 추적이 어렵다.

컨테이너 헬스체크가 실패를 인식하면 자동으로 다시 시작한다. 반복해서 죽고 살아나면 자동 복구에 맡기지 않고 로그를 본다.

## 3. 화면이 전부 404인데 상태는 정상

**이 유형을 먼저 알아 두어야 한다.** 화면 파일의 위치 설정이 어긋나면 모든 화면이 404가 되는데, 상태 확인은 API만 보므로 정상이라고 답한다. 로그에도 아무것도 남지 않는다.

Phase 0에서 이 결함을 실제로 한 번 만들었고, 그래서 **위치가 어긋나면 프로그램이 켜지지 않도록** 고쳤다. 지금은 아래 메시지를 내고 멈춘다.

```
Error: WF_SERVE_WEB=true인데 SPA 산출물이 없다: <기대한 경로>
  WF_WEB_DIST=<설정값> (기준 <기준 경로>)
  개발이면 'pnpm build'를, 컨테이너면 이미지 레이아웃과 WF_WEB_DIST를 확인한다.
```

즉 **이제는 404가 아니라 기동 실패로 나타난다.** 만약 그래도 404가 보이면 안내 데스크가 잘못된 곳으로 넘기고 있는 것이니 nginx 설정을 본다. 경위는 트러블슈팅 T-013.

## 4. 켜지다가 바로 죽는다

기동 로그의 **첫 오류 줄**을 본다. 뒤쪽 줄은 그 결과일 뿐이다.

```bash
docker compose -f deploy/compose.yml logs api --tail 80
```

| 메시지에 있는 말 | 뜻 | 조치 |
|---|---|---|
| 스키마에 없는 키 / unrecognized key | 설정 이름이 틀렸거나 이 버전이 모르는 항목이다 | `.env`에서 그 항목을 지우거나 이름을 고친다 |
| 운영에서 자동 마이그레이션 거부 | 운영에 자동 구조 변경이 켜져 있다 | `.env`의 `WF_DB_AUTO_MIGRATE`를 `false`로 |
| SPA 산출물이 없다 | 화면 파일 위치 설정 | 3절 |
| 테스트 DB가 없다 | 운영에 시험용 설정이 섞였다 | `WF_ENV`가 `production`인지 확인 |

**설정 항목을 모르면 일부러 켜지지 않는다.** 이름이 한 글자 틀렸을 때 조용히 무시되고 값이 안 먹는 상태가 훨씬 찾기 어렵기 때문이다. 기동 실패는 불편하지만 정직한 실패다.

## 5. 느려졌다

| 확인 | 명령 | 판단 |
|---|---|---|
| 디스크 여유 | `df -h /` | 5GB 미만이면 먼저 정리한다 |
| 컨테이너 자원 | `docker stats --no-stream` | 메모리가 한계에 붙어 있는지 |
| 데이터베이스 연결 수 | postgres 로그 | 연결 고갈 메시지 |
| 안 쓰는 이미지·캐시 | `docker system df` | 쌓인 것이 디스크를 먹는다 |

디스크가 차면 **옆 컨테이너의 쓰기 실패로 번진다.** 먼저 지워야 할 것은 안 쓰는 이미지와 빌드 캐시다. 데이터 볼륨은 손대지 않는다.

## 6. 재부팅 후 안 올라온다

모든 서비스는 자동 재시작으로 설정돼 있다. 그래도 안 올라오면 순서대로 본다.

```bash
systemctl is-active docker                       # 도커 자체가 떴는가
docker compose -f deploy/compose.yml ps          # 컨테이너 상태
docker compose -f deploy/compose.yml up -d       # 수동 기동
```

**재부팅 후 자동 기동은 반드시 실제로 한 번 확인해야 한다.** 설정만 보고 넘기면 정작 필요한 날에 안 올라온다. 이 확인은 Phase 0 완료 기준에 들어 있다.

## 7. 데이터를 잃었다

되돌리는 스크립트는 두지 않았다. **되돌림은 백업 복원으로 처리한다.** 잘못된 되돌리기가 데이터를 더 잃게 만들기 때문이다.

| 잃은 것 | 복원 대상 |
|---|---|
| 문서·계정·기록 | 데이터베이스 덤프 |
| 첨부 파일 | 첨부 디렉토리 |

두 가지를 **같은 시점의 것으로 함께** 복원해야 한다. 한쪽만 되돌리면 문서는 있는데 첨부가 없는 상태가 된다.

**복원 절차는 7.18절에 있고, 연습은 실제로 했다** (Phase 5). 볼륨 둘을 지우고 백업에서
되살려 모든 테이블의 행 수가 맞는 것을 확인했다 — 기록은 `P5_검증기록_Release` 3.1절이다.
순서를 건너뛰면 되살릴 수 있었던 것까지 잃으므로 **7.18절의 번호를 그대로 따른다.**

## 7.1 로그인이 안 된다 (Phase 1)

로그인 실패는 **응답만 보고 원인을 알 수 없게** 되어 있다. 없는 계정·틀린 비밀번호·승인
대기·잠김이 모두 같은 401 문구를 낸다 (계정 열거 방지). **원인은 감사로그에 있다.**

```bash
docker exec workfluence-api node -e "fetch('http://127.0.0.1:3000/api/health').then(async r=>console.log(await r.text()))"
```

관리자로 로그인해 감사로그 화면을 열거나, DB에서 직접 본다.

| 기록의 `reason` | 뜻 | 조치 |
|---|---|---|
| `unknown` | 그런 아이디가 없다 | 아이디를 확인한다 |
| `wrong` | 비밀번호가 틀렸다 | 5회까지 |
| `pending` | 승인 대기다 | 관리자가 사용자 관리에서 승인한다 |
| `locked` | 잠겼다 | 15분 기다리거나 관리자가 잠금 해제 |
| `no_role_mapped` | IdP 그룹이 역할로 매핑되지 않는다 | `WF_OIDC_ROLE_MAP`을 본다 |

## 7.2 모두가 로그아웃됐다

세션은 데이터베이스에 있다 (`sessions` 테이블). **데이터베이스가 끊기면 전원이 로그아웃된다.**
2절을 먼저 본다. `WF_SESSION_SECRET`을 바꿔도 기존 세션이 전부 무효가 된다 — 바꿀
이유가 없으면 바꾸지 않는다.

## 7.3 사내 계정 로그인 버튼이 없다 / 눌러도 안 된다

| 증상 | 원인 | 조치 |
|---|---|---|
| 버튼이 아예 없다 | `WF_OIDC_ENABLED=false` | 켜야 하면 설정을 바꾸고 다시 기동한다 |
| 켰는데 기동이 안 된다 | issuer·client·redirect 중 비어 있는 값이 있다 | 기동 로그가 어느 키인지 알려 준다. **일부러 멈춘다** — 버튼만 있고 안 눌리는 상태를 만들지 않는다 |
| `state가 일치하지 않는다` | 로그인 도중 세션이 끊겼거나 링크를 재사용했다 | 로그인 화면에서 다시 시작한다 |
| `이 계정에 부여할 역할이 없다` | 그 사람의 IdP 그룹이 매핑표에 없다 | `WF_OIDC_ROLE_MAP`에 그룹을 넣는다. 매핑 안 되면 **기본 거부**다 |
| `사내 인증 서버와 처리하지 못했다` (Phase 11) | 앱이 사내 IdP와의 처리에 실패했다. 앱 로그의 **`auth.oidc_failed`** 줄(`step`·`error`)이 까닭을 말한다: `UNABLE_TO_VERIFY_LEAF_SIGNATURE`·`SELF_SIGNED_CERT_IN_CHAIN`이면 사내 인증 기관을 모른다 · `ENOTFOUND`·`ECONNREFUSED`·`ETIMEDOUT`이면 주소나 망 · `OIDC Discovery 실패: HTTP 404`면 `WF_OIDC_ISSUER`가 틀렸다 | 인증 기관이면 [반입 가이드](운영가이드_반입.md) 10절 ②·③(`ca/ca.pem`을 두고 `--force-recreate`로 다시 띄운다). 주소·망이면 IdP 담당과 확인. 줄 찾기: `docker compose -f compose.yml logs api --since 15m \| grep auth.oidc_failed` |
| `토큰 교환 실패: HTTP 401`(또는 400) | IdP가 앱의 client를 받지 않았다 | `WF_OIDC_CLIENT_ID`·`WF_OIDC_CLIENT_SECRET`·`WF_OIDC_REDIRECT_URI`를 IdP 등록값과 맞춘다. 같은 `auth.oidc_failed` 줄이 남는다 |
| `사내 인증이 보낸 토큰을 받아들이지 못했다` (401) | 앱이 IdP가 준 토큰(id_token)을 검증하다 거절했다 — **다시 해도 같다.** `auth.oidc_failed` 줄의 `error`: `JWTClaimValidationFailed: unexpected "aud" claim value`면 `WF_OIDC_CLIENT_ID`가 IdP의 것과 다르다 · `unexpected "iss"`면 `WF_OIDC_ISSUER` · `JWTExpired`면 앱 서버나 IdP의 시각이 어긋났다 · `JWSSignatureVerificationFailed`·`JWKSNoMatchingKey`면 IdP의 서명 키 | 설정값을 IdP 담당의 등록값과 대조한다. 시각이면 서버의 시간 동기화를 본다. 실패한 로그인은 감사로그 `auth.login.failure`(`method: oidc`, `reason: idp_rejected` — 닿지 않으면 `idp_unreachable`)로도 남는다 |

> **운영에서 모의 인증은 켜지지 않는다.** `WF_OIDC_MOCK=true`와 `WF_ENV=production`을 함께 주면
> 환경변수 검증이 기동을 거부한다. 운영 이미지에는 그 키를 넘기지도 않는다.

## 7.4 감사로그를 지우고 싶다

지울 수 없다. `audit_events`는 추가만 되도록 데이터베이스가 막고 있다.

```
ERROR: audit_events는 append-only다 (시도: DELETE)
```

보존 기간이 지난 기록은 `pnpm audit:purge`가 지운다 (Phase 4, FR-540). **보존 기간보다
최근 것은 지워지지 않고**, 기록을 고치는 것은 어떤 경우에도 막혀 있다 — 데이터베이스가
막는다. 보존 기간은 관리 화면에서 바꿀 수 있고 **90일보다 짧게는 내려가지 않는다.**
주기와 실행 방법은 [`docs/운영가이드_운영이관.md`](운영가이드_운영이관.md) 4.2절에 있다.

## 7.5 스페이스가 안 보인다 (Phase 2)

**Crew가 아니면 목록에 나오지 않고 주소로 들어가도 404다.** 일부러 그렇게 했다 — 403을 주면
"그 스페이스는 있다"가 새어 나간다. 로그에도 404로 남는다.

| 확인 | 방법 |
|---|---|
| Crew에 있나 | 그 스페이스의 owner나 관리자에게 확인. `space_members` 표 |
| 지워졌나 | `spaces.deleted_at`이 차 있으면 삭제된 것이다. **관리자가 휴지통 화면에서 되살린다** |
| 중지됐나 | 보이긴 하는데 쓰기가 안 된다면 `status='suspended'`다 |

## 7.6 저장이 409로 막힌다

> **먼저 볼 것: 실시간 편집이 켜져 있으면 화면에서는 이 증상이 나오지 않는다** (Phase 6).
> 두 사람이 같은 페이지를 열면 서로의 글자가 바로 보이고 충돌 자체가 생기지 않는다.
> 그래도 409를 봤다면 ① `WF_COLLAB_ENABLED=false`로 꺼 두었거나 ② 화면이 아니라 API를
> 직접 호출했거나 ③ 실시간 편집 연결이 끊긴 채(편집 화면 아래가 빨갛다) 저장을 눌렀거나 셋 중 하나다.
> 7.19절을 먼저 본다.

정상 동작이다 (`P2_설계서_Page` 3.1절). 다른 사람이 먼저 저장했다는 뜻이고, 응답에 현재
버전과 내가 편집을 시작한 버전이 함께 온다.

```json
{"message":"다른 사용자가 먼저 저장했다...","currentVersionNo":5,"baseVersionNo":3}
```

**덮어쓰는 방법은 없다.** 최신을 불러와 다시 편집해야 한다. 쓰던 내용이 아깝다면 화면에서
복사해 둔 뒤 "최신 내용 불러오기"를 누른다.

혼자 쓰는데도 이 오류가 난다면 같은 페이지를 **다른 탭에서 열어 둔 것**이다 (실시간 편집이 꺼진 경우).

## 7.7 페이지를 지울 수 없다

하위 페이지가 있으면 막는다 — 고아 페이지를 만들지 않기 위해서다. 하위를 먼저 다른 곳으로
옮기거나 지운다.

## 7.8 페이지를 옮길 수 없다

| 메시지 | 뜻 |
|---|---|
| `자기 자신이나 자손 아래로 옮길 수 없다` | 트리가 고리가 된다 |
| `다른 스페이스의 페이지를 부모로 둘 수 없다` | 스페이스를 넘나드는 이동은 없다. 새로 만들어 옮긴다 |
| `페이지 트리 깊이는 10을 넘을 수 없다` | 옮기는 가지의 **자손까지** 세서 판정한다 |

## 7.9 파일 첨부가 안 된다 (Phase 3)

먼저 **화면에 뜬 숫자**를 본다. 숫자마다 원인이 다르다.

| 화면 안내 | 뜻 | 조치 |
|---|---|---|
| `허용하지 않는 확장자다: exe` | 올릴 수 없는 종류다 | 정상 동작이다. **관리자가 "운영 설정"에서 켤 수 있는 종류인지 먼저 본다.** 그 목록에도 없으면 우리가 내용을 검사할 규칙이 없는 종류다 — 담당자에게 요청한다 |
| `확장자(.pdf)와 형식(text/html)이 맞지 않는다` | 파일 이름과 브라우저가 밝힌 종류가 다르다 | 정상 동작이다 |
| `내용이 .pdf 형식이 아니다` | 이름은 맞는데 **파일 앞부분 바이트가 그 형식이 아니다.** 이름만 바꾼 파일이다 | 정상 동작이다. 진짜 그 형식으로 다시 저장해 올린다 |
| `파일이 너무 크다 (상한 20MB)` | 앱이 막았다 | 상한을 늘리려면 `WF_UPLOAD_MAX_MB`와 nginx의 `client_max_body_size`를 **둘 다** 바꾸고 다시 띄운다 |
| `413 Request Entity Too Large` (nginx 글씨체의 흰 화면) | **안내 데스크가 막았다.** 앱까지 오지도 않았다 | 위와 같다. 둘 중 nginx 쪽만 작으면 이 화면이 나온다 |
| `500` 또는 아무 안내 없이 실패 | 저장 공간 문제일 수 있다 | 아래를 본다 |

**저장 공간 확인**

```bash
docker compose -f deploy/compose.yml exec api sh -lc 'id; ls -ld /data/attachments; df -h /data'
```

읽는 법:

- `uid=1000(node)`이고 폴더 주인이 `node`여야 한다. 주인이 `root`로 나오면 **볼륨이 잘못 만들어진 것**이다. 이때는 첫 업로드부터 전부 실패한다.
  - 고치기: `docker compose exec -u root api chown -R node:node /data/attachments`
  - 왜 생기나: 이미지 안에 그 폴더가 없는 채로 볼륨이 붙으면 도커가 `root` 것으로 만든다. 지금 이미지는 미리 만들어 두었으므로 옛 볼륨에서만 나타난다.
- `df -h /data`의 여유가 없으면 그것이 원인이다. 첨부를 지워도 **파일 자체는 바로 남는다**(같은 파일을 여러 문서가 쓸 수 있어서다). 보존 기간이 지난 뒤 `pnpm trash:purge`가 **아무도 안 쓰는 파일만** 지운다. 자동으로 돌지는 않는다 — 사람이 부르는 명령이다.

**올라간 파일이 어디 있나**

`/data/attachments/<앞 두 글자>/<긴 숫자>`에 있다. 이름이 사람이 읽을 수 있는 형태가 아닌 것이 정상이다 — 원래 이름은 데이터베이스에 따로 있다.

## 7.10 검색해도 안 나온다 (Phase 3)

순서대로 본다.

1. **그 사람이 그 공간을 볼 수 있는가.** 못 보는 공간의 문서는 검색 결과에 **아예 나오지 않는다.** 이것은 고장이 아니라 설계다. 공간 화면에서 Crew에 들어 있는지 먼저 확인한다 (7.5절).
2. **문서가 지워지지 않았는가.** 휴지통에 있는 문서는 결과에 없다.
3. **찾는 말이 본문에 실제로 있는가.** 제목과 본문 글자만 찾는다. 첨부 **파일 안의 내용은 찾지 않는다.**
4. 위가 다 맞는데 안 나오면 **색인이 빠진 것**이다. 아래로 다시 만든다.

```bash
pnpm search:reindex
```

이 명령은 문서 본문에서 검색용 글자를 다시 뽑아 채운다. 원본을 건드리지 않으므로 **몇 번 돌려도 안전하다.** 문서가 많으면 시간이 걸린다.

> **검색은 감사 기록에 남지 않는다.** "누가 무엇을 검색했나"는 기록에 없다. 기록이 검색량만큼 불어나는 것을 피하기 위한 결정이다. 첨부를 **내려받은 것**은 남는다.

## 7.10-1 휴지통을 비우기 전에 알아야 할 것 (Phase 4)

`pnpm trash:purge`는 **보존 기간을 넘긴 것을 영구히 지운다.** 되돌릴 수 없다.

지우는 것이 두 갈래라는 점을 꼭 보고 실행한다.

| 무엇 | 설명 |
|---|---|
| 직접 지운 문서·첨부·댓글 | 보존 기간(기본 30일)을 넘긴 것 |
| **지워진 공간에 딸린 문서 전부** | 그 공간 안에서 **지우지 않았던 문서까지** 함께 지워진다 |

두 번째가 중요하다. **공간을 되살리면 안에 있던 문서도 함께 돌아온다** — 즉 공간이
휴지통에 있는 동안 그 문서들은 아직 살아 있는 것이다. 보존 기간이 지나 정리를 돌리면
그것들이 같이 없어진다.

명령이 실행 전에 몇 건인지 알려 준다. 숫자를 보고 판단한다.

```
[purge] 주의: 지워진 스페이스에 딸린 **살아 있던** 페이지 12건도 함께 지운다
```

감사로그 정리(`pnpm audit:purge`)는 보존 기간이 **최소 90일**로 묶여 있다. 그보다 짧게
설정할 수 없고, 설정값이 어떤 경로로 낮아졌더라도 명령이 90일 아래로는 지우지 않는다.

## 7.11 로그인이 "요청이 너무 잦다"로 막힌다 (Phase 4)

같은 주소에서 **실패한** 로그인이 1분에 20번을 넘으면 그 주소를 잠시 막는다. 무차별 대입 방어다.

**성공한 로그인은 세지 않는다.** 그래서 정상적으로 쓰는 사람이 많다고 막히지는 않는다.

> 이 문장은 **한동안 사실이 아니었다.** 성공을 세지 않도록 고친 것이 2026-09-22이지만
> (T-023) 그 수정이 실제로는 동작하지 않아 **성공 로그인 스물한 번째부터 막혔다.**
> 같은 날 부하 측정에서 드러나 고쳤다 (T-027). 지금은 성공 로그인 50회를 연속으로 해도
> 막히지 않는 것을 컨테이너에서 확인했다.

| 상황 | 뜻 | 조치 |
|---|---|---|
| 한 사람만 막힌다 | 그 사람이 비밀번호를 여러 번 틀렸다 | **계정 잠금**일 수 있다 (7.1절). 관리자가 잠금 해제 |
| 같은 사무실 여러 명이 동시에 막힌다 | 그 주소에서 실패가 몰렸다 | 1분 기다린다. 반복되면 누가 잘못된 비밀번호로 계속 시도하는지 감사로그의 `auth.login.failure`를 본다 |
| 계속 막힌다 | 자동화된 시도일 수 있다 | 감사로그에서 실패가 오는 주소를 확인하고 망 담당자에게 알린다 |

## 7.12 알림이 안 온다 (Phase 4)

순서대로 본다. **대개 고장이 아니라 설계다.**

1. **부른 사람이 그 공간을 볼 수 있는가.** Crew가 아니면 이름을 적어도 알림이 가지 않는다. 알림이 "그런 문서가 있다"를 알려 주는 통로가 되지 않게 한 것이다.
2. **아이디를 정확히 적었는가.** 없는 아이디는 그냥 글자로 남는다.
3. **자기 자신을 부른 것은 아닌가.** 자기 알림은 만들지 않는다. 같이 쓴 문서에서는 **스스로 부른 것이 확실할 때만** 그렇게 판정한다 (7.22절).
4. **메일 주소를 적은 것은 아닌가.** `kim@example.internal`의 `@example`은 멘션이 아니다.
5. 위가 다 맞는데 안 오면 그때가 고장이다. `docker compose logs api`에서 그 시각의 오류를 본다.

알림은 **앱 안 알림함과 메일 둘 다로** 간다 (Phase 6). 메일이 안 오는 경우는 7.21절을 본다. 사내 메신저로는 가지 않는다.

## 7.13 설정을 바꿨는데 안 먹는다 (Phase 4)

| 무엇을 바꿨나 | 확인 |
|---|---|
| 첨부 크기 상한 | **서버 천장이 따로 있다.** 화면에 "이 서버의 천장 NMB"라고 적혀 있고 그보다 크게는 저장이 안 된다. 올리려면 `WF_UPLOAD_MAX_MB`와 nginx의 `client_max_body_size`를 **둘 다** 올리고 다시 띄운다 |
| 그 밖의 값 | **다시 띄울 필요가 없다.** 저장 즉시 다음 요청부터 먹는다. 안 먹으면 저장이 실패한 것이므로 화면의 빨간 글씨를 본다 |
| 무엇이 언제 바뀌었는지 모르겠다 | 감사로그의 `settings.update`를 본다. **바뀐 키의 이전·이후 값이 함께 남는다** |

설정을 되돌리려면 감사로그의 "이전 값"을 보고 그 값을 다시 넣는다.

## 7.14 반입한 묶음이 이상하다 (Phase 5)

| 증상 | 확인 | 조치 |
|---|---|---|
| `pnpm release:verify`가 "체크섬이 다르다" | 어느 파일인지 출력에 나온다 | **그 묶음을 쓰지 않는다.** 옮기는 도중에 상했다. 다시 받는다 |
| `pnpm release:verify`가 "필수 파일 없음" | 묶음이 덜 풀렸거나 만들 때 빠졌다 | 압축을 다시 푼다. 그래도 없으면 빌드 쪽에 다시 요청한다 |
| `docker load`가 "no space left" | `df -h /` | 5GB 미만이면 그 자리에서 멈춘다. 오래된 이미지를 **이름을 보고** 지운다 |
| 이미지는 올라갔는데 컨테이너가 안 뜬다 | `docker compose logs api` | 대개 `.env`다. 7.15절 |

## 7.15 컨테이너가 뜨자마자 죽는다 (Phase 5)

앱은 **설정이 틀리면 일부러 기동을 거부한다.** 잘못된 설정으로 절반만 동작하는 것보다
안 뜨는 것이 낫다는 판단이다. 그래서 이 증상은 대개 고장이 아니라 **설정 오류**다.

```bash
docker compose -f deploy/compose.yml --env-file deploy/.env logs api | tail -30
```

| 로그에 나오는 말 | 뜻 | 조치 |
|---|---|---|
| 모르는 `WF_` 키가 있다 | `.env`에 오타가 있거나 이 버전이 모르는 키다 | 그 줄을 지우거나 이름을 고친다 |
| 값의 형식이 맞지 않다 | 숫자 자리에 글자가 들어갔다 | 해당 키를 고친다 |
| `WF_SESSION_SECRET` 관련 | 너무 짧다 (32자 이상) | 새로 길게 만든다 |
| 데이터베이스에 붙지 못한다 | postgres가 아직 안 떴거나 비밀번호가 다르다 | `docker compose ps`로 postgres가 `healthy`인지 먼저 본다 |

**환경 파일이 둘이라는 것을 기억한다.** 앱용(`.env`)과 컨테이너 구성용(`deploy/.env`)이
다르다. 한쪽에 적어야 할 것을 다른 쪽에 적으면 앱이 "모르는 키"라며 거부한다.

## 7.16 접속이 안 된다 — 인증서 (Phase 5)

| 증상 | 뜻 | 조치 |
|---|---|---|
| 브라우저가 "이 사이트는 안전하지 않습니다"를 넘어갈 수 없게 막는다 | 인증서에 **SAN이 없다.** 요즘 브라우저는 경고가 아니라 오류로 처리한다 | `openssl x509 -in deploy/certs/cert.pem -noout -ext subjectAltName`로 확인하고, 없으면 재발급 |
| 며칠 전까지 됐는데 갑자기 전부 안 된다 | 인증서 만료 | `openssl x509 -in deploy/certs/cert.pem -noout -enddate`. 만료됐으면 재발급 |
| nginx 컨테이너가 `unhealthy` | 인증서 파일이 없거나 읽을 수 없다 | `docker compose logs nginx`. nginx는 **자기 자신에게 HTTPS로 물어보므로** 인증서 문제가 여기서 먼저 빨개진다 |

## 7.17 전부 느리거나 아예 응답이 없다 (Phase 5)

**느린 것과 멈춘 것은 다르다.** 먼저 어느 쪽인지 가린다.

```bash
curl -sk -m 5 https://localhost:8443/api/health
```

| 결과 | 뜻 | 조치 |
|---|---|---|
| 5초 안에 `status: ok` | 앱은 정상이다. 특정 화면만 느린 것 | 어느 화면인지 확인. 문서가 많이 쌓였으면 색인을 다시 만든다 (`pnpm search:reindex`) |
| `db`가 `ok`가 아니다 | 앱은 살아 있고 데이터베이스가 문제 | postgres 컨테이너 로그와 `df -h /`를 본다. 디스크가 차면 데이터베이스가 먼저 쓰기를 실패한다 |
| **아무 응답 없이 시간만 흐른다** | 아래를 본다 | ↓ |

응답이 아예 없을 때, 데이터베이스 연결이 묶여 있는지 본다.

```bash
docker exec workfluence-postgres psql -U workfluence -d workfluence   -c "select state, count(*) from pg_stat_activity where datname='workfluence' group by state"
```

`idle in transaction`이 여럿 쌓여 있으면 **연결이 새는 것**이다. 2026-09-22에 이 증상으로
앱 전체가 멈춘 적이 있다 (T-026). 그때 두 가지를 고쳤다.

- 원인이 된 코드를 고쳤다.
- **기다림에 상한을 뒀다.** 이제는 같은 일이 생겨도 30초 안에 데이터베이스가 그 연결을
  끊고, 앱은 멈추는 대신 오류를 낸다. 오류는 로그에 남으므로 찾을 수 있다.

그래도 응답이 없으면 앱만 다시 띄운다. **데이터는 앱 컨테이너에 없다.**

```bash
docker compose -f deploy/compose.yml --env-file deploy/.env restart api
```

## 7.18 되살려야 한다 (Phase 5)

**순서를 지킨다.** 급할 때 순서를 건너뛰면 되살릴 수 있었던 것까지 잃는다.

1. **멈춘다.** 사람들이 계속 쓰면 되살린 시점 이후의 글이 섞인다.
   `docker compose -f deploy/compose.yml --env-file deploy/.env stop api nginx`
2. **지금 상태를 먼저 뜬다.** 망가진 상태라도 뜬다 — 백업이 더 오래된 것일 수 있고,
   그러면 **지금 것에만 있는 글**이 있다. `pnpm backup:create`
3. **어느 백업으로 갈지 정한다.** `ls -lh .local/backups/`
4. **되살린다.** `pnpm backup:restore .local/backups/<시각>`
   - "대상이 비어 있지 않다"며 거절하면 **그게 안전장치다.** 정말 덮어쓸 것인지
     한 번 더 확인한 뒤에만 진행한다. 이 판단은 혼자 하지 않는다.
5. **개수를 대조한다.** 되살린 뒤 문서 수·사용자 수·첨부 수가 백업 시점과 맞는지 본다.
   명령이 그 숫자를 출력한다.
6. **띄운다.** `docker compose -f deploy/compose.yml --env-file deploy/.env up -d`
7. **사람들에게 언제로 되돌아갔는지 알린다.** 그 시점 이후에 쓴 글은 없어졌다.
   알리지 않으면 "내가 쓴 글이 사라졌다"가 따로 신고로 들어온다.


## 7.19 "연결이 끊겼다"가 뜬다 — 실시간 편집 (Phase 6)

편집 화면 아래에 **빨간 글씨로** 뜬다. 뜬 동안 쓴 것은 **저장되지 않는다.**

| 확인 | 뜻 | 조치 |
|---|---|---|
| 다른 화면은 되는가 | 앱은 살아 있고 WebSocket만 끊겼다 | nginx가 `Upgrade`를 넘기는지 본다 (`deploy/nginx.conf`) |
| 여러 사람이 동시에 | 서버 쪽 문제 | `docker compose logs api`에서 `Collab`을 찾는다 |
| 한 사람만 | 그 사람 망이나 프록시 | 새로고침. 사내 프록시가 WebSocket을 막는 경우가 있다 |

**사람에게 먼저 알린다: 지금 쓰고 있는 것을 다른 곳에 복사한 뒤 새로고침하라고.**
새로고침하면 서버에 남아 있는 마지막 상태부터 다시 시작한다.

> **실시간 편집을 통째로 끌 수 있다.** `WF_COLLAB_ENABLED=false`로 두고 다시 띄우면
> Phase 2의 단독 편집으로 돌아간다 — 한 사람씩 고치고 저장하며, 겹치면 "먼저
> 저장했다" 안내가 나온다. 원인을 찾는 동안 서비스를 세우지 않는 길이다.

## 7.19-1 편집하다 갑자기 끊겼다 — 끊은 쪽이 서버다 (Phase 7)

7.19절과 증상은 같지만 **원인이 다르다.** 서버가 일부러 끊은 경우다.

```
docker compose logs api | grep -E '"event":"collab\.(closed|revoked)"'
```

| 로그 (event와 `reason` 필드) | 뜻 | 조치 |
|---|---|---|
| `collab.revoked` · `reason: 세션 파기` · `count` | 비밀번호를 바꿨거나 관리자가 세션을 강제 종료했다(`sessionOnly: true`면 그 세션에서 로그아웃했다) | **정상이다.** 다시 로그인하면 된다 |
| `collab.closed` · `reason: 세션 없음` | 세션이 만료됐거나(유휴 30분·절대 12시간) 그 세션으로 **다른 탭에서 로그아웃**했다 | 정상. 다시 로그인 |
| `collab.closed` · `reason: 계정 비활성` | 관리자가 그 계정을 멈췄다 | 정상 |
| `collab.closed` · `reason: 쓰기 권한 없음` | Crew에서 빠졌거나 공간이 중지됐다 | 정상. 권한을 돌려주려면 관리 화면에서 |
| `collab.closed` · `reason: 비밀번호 변경 필요` | 임시 비밀번호 상태다 | 비밀번호를 바꾸게 한다 |
| `collab.recheck_failed` | 주기 재판정이 DB에 닿지 못했다 — 다음 주기에 다시 한다 | 반복되면 2절 |
| `session.revoke_failed` | 세션을 끊은 뒤 편집 연결을 끊는 데 실패했다 | 그 사람의 세션을 한 번 더 강제 종료한다. 반복되면 개발 담당 |
| 아무 로그도 없다 | 서버가 끊은 것이 아니다 | 7.19절로 간다 |

> **권한을 잃은 사람이 최대 5분까지 계속 쓸 수 있다.** 세션을 끊는 동작(비밀번호 변경·강제
> 종료)은 즉시 닿지만, Crew 제거·공간 중지처럼 **부를 자리가 없는 변화**는 주기 점검이 잡는다.
> 급하면 그 사람의 세션을 강제 종료하면 즉시 끊긴다. 주기는 `WF_COLLAB_RECHECK_MS`다.

## 7.19-2 실시간 편집이 **컨테이너에서만** 안 붙는다 (Phase 7)

화면도 뜨고 `/api/health`도 `ok`인데 두 브라우저가 서로 안 보인다. 개발에서는 됐다.

| 확인 | 명령 | 기준 |
|---|---|---|
| nginx가 `Host`를 포트까지 넘기는가 | `grep 'proxy_set_header Host' deploy/nginx.conf` | **`$http_host`**여야 한다. `$host`면 포트가 떨어져 업그레이드가 401이 된다 (T-032) |
| 업그레이드가 401인가 | `docker compose logs nginx \| grep ' 401 '` | 401이 줄줄이 찍히면 위 항목이다 |

앞단에 사내 장비가 하나 더 있으면 그쪽도 `Origin`과 `Host`를 바꾸지 않고 넘겨야 한다.

## 7.19-3 연결됨인데 한 페이지에서 **남의 편집이 안 보인다** (Phase 8)

그 페이지를 연 사람 모두에게 같은 증상이고, 다른 페이지는 된다. 브라우저 콘솔에 편집기(y-tiptap) 렌더 오류가 찍힌다.

Phase 9 이전에는 조작한 클라이언트가 **편집기가 만들지 않는 것**(특수한 문서 조각)을 문서에 넣으면 생겼다. 서버는 그것을 저장에서
빼고 중계를 이어 갔지만(설계서 FR-909), 각자의 화면은 그것을 그리다 멈췄다.

> **Phase 9부터 서버가 그런 편집을 받지 않는다**(보류 23 닫음 — 7.23). 그래서 이 증상은 Phase 9 이전에 서버에 들어간 실시간 상태에서만
> 생길 수 있다. 새로 생겼다면 7.23의 기록을 먼저 보고 개발 담당에게 알린다 — 관문의 틈이다.

| 조치 | 뜻 |
|---|---|
| 그 페이지를 편집 중인 사람 중 **한 명이 아무 글자나 한 번 친다** | 그 사람의 편집기가 문서를 다시 쓰면서 그 조각을 지우고, 그 지움이 모두에게 간다 |
| 그래도 안 되면 모두 나간 뒤 실시간 상태를 지운다 | 마지막 버전에서 다시 시작한다(저장되지 않은 협업 편집은 잃는다). 명령은 7.20절 3번 |
| 누가 넣었는지 | Phase 9부터의 시도는 감사로그의 `page.collab.reject`가 누가·어느 페이지·까닭을 직접 남긴다(7.23). Phase 9 이전에 들어간 것은 그 시각의 `page.collab.save`·접속 기록과 맞춰 본다. 반복되면 보안 담당에게 알린다 |

## 7.19-4 내가 친 글이 **남에게 안 보인다** — 내 화면에는 있다 (Phase 8)

한 사람에게만 생긴다. 그 사람 화면에는 글이 있는데 다른 사람 화면과 저장된 버전에는 없고, 그 자리에 **다른 글**이 보이기도 한다.
대개 **페이지를 연 직후**에 친 글이다.

실시간 편집에서 화면마다 식별 번호가 하나씩 있고, 화면은 페이지를 열자마자 그 번호를 (커서를 보여 주려고) 알린다.
Phase 9 이전에는 서버가 그 알림을 모두에게 그대로 퍼뜨렸고, 조작한 클라이언트가 그 번호로 **먼저** 편집을 보내면 서버는 그 번호의
글을 이미 받은 것으로 알고 진짜 주인이 그 사이 친 글을 버렸다(Phase 6부터).

> **Phase 9부터 서버가 막는다**(보류 24 닫음). 화면이 번호를 알리는 순간 서버가 그 번호의 주인을 적어 두고, 남이 그 번호로 쓰면
> 받지 않고 끊는다(7.23). 아래는 Phase 9 이전의 설명이다 — 새로 생겼다면 관문의 틈이니 개발 담당에게 알린다.

주인의 화면이 그 편집을 받아 스스로 번호를 바꾸면 그 뒤에 친 글은 정상으로 갔지만, 이미 친 글이 더 많으면 번호를 바꾸지 않아
**그 뒤에 친 글도 어긋났다** — 새로고침이 확실하다. 부른 사람의 이름은 틀리지 않았다 — 먼저 보낸 사람이 그 번호로 쓴 부름은 그
사람의 이름으로 나가고, 어긋난 채 친 부름은 이름을 비웠다.

| 조치 | 뜻 |
|---|---|
| **새로고침하기 전에** 그 사람이 자기 화면의 그 글을 복사해 둔다 | 새로고침하면 화면이 서버의 문서로 바뀌어 화면에만 있던 글이 사라진다 |
| 새로고침한 뒤 붙여 넣는다 | 새 번호로 다시 들어가 모두에게 간다 |
| 누가 보냈는지 | Phase 9부터의 시도는 감사로그의 `page.collab.reject`(규칙 `owner`)가 직접 남긴다(7.23). Phase 9 이전의 것은 그 시각의 접속 기록과 `page.collab.save`를 맞춰 본다. 반복되면 보안 담당에게 알린다 |

## 7.20 실시간 편집인데 버전이 안 생긴다 (Phase 6)

**대개 고장이 아니라 설계다.** 순서대로 본다.

1. **아직 타이핑 중인가.** 잠깐 멈춰야 남긴다 (기본 5초, `WF_COLLAB_IDLE_SAVE_MS`).
2. **내용이 정말 바뀌었는가.** 커서만 움직인 것은 바뀐 것이 아니다 — 그것까지 세면
   가만히 보고만 있어도 버전이 쌓인다.
3. **문서가 검증을 통과하는가.** 통과하지 못하면 **버전을 만들지 않는다.** Phase 9부터는 그 페이지를 편집하는 화면에
   **"자동 저장이 멈췄다: <까닭>"**이 뜬다(뒤에 들어온 사람에게도, 서버가 다시 뜬 뒤에 연 사람에게도). 로그는 `docker compose logs api`의
   `collab.save_invalid`(검증 실패로 저장하지 않았다 — `errors` 필드에 까닭 셋까지)다. 실시간 상태는 살아 있으므로 화면에서 고치면 다음 유휴에 저장되고 그 알림이 사라진다.
   까닭이 `노드 수 50000 초과`면 문서가 너무 길다 — 내용을 나눠 다른 페이지로 옮긴다. 까닭에 `textAlign`이 있으면 Phase 9 이전에
   들어간 정렬이다 — **그 문단을 한 번 고치면** 편집기가 그 속성을 지워 다시 저장된다.
   까닭이 **`서버가 버전을 남기지 못했다 — 잠시 뒤 다시 한다`**면 문서는 멀쩡하고 **저장하는 순간 DB가 실패했다**. 다음 유휴에 저절로
   다시 하고, 되면 알림이 사라진다. 계속 뜨면 `docker compose logs api`에서 `collab.save_failed`(`trigger: idle`)를 찾아 그 `error`로
   DB부터 본다(2절).
   **다만 로그의 검증 오류가 화면에 보이지 않는 것**(편집기에 없는 노드나 속성 — 조작한 클라이언트가 넣을 수 있다)이면
   화면에서 고칠 수 없다. **Phase 9부터는 서버가 그런 편집을 문 앞에서 받지 않는다**(보류 22 닫음 — 7.23). 그래도 이렇게
   되었다면(Phase 9 이전에 들어간 상태) 그 페이지를 편집하는 사람이 모두 나간 뒤 그 페이지의 실시간 상태를 지우면 마지막
   버전에서 다시 시작한다. **저장되지 않은 협업 편집은 잃는다.**

   ```
   docker exec workfluence-postgres psql -U workfluence -d workfluence -c "DELETE FROM page_realtime WHERE page_id = '<페이지 id>'"
   ```
4. **빈 문서로 만들지 않았는가.** 전부 지운 상태는 저장하지 않는다 — 연결이 끊기며
   빈 상태가 올라오면 내용이 사라지기 때문이다. 일부러 비우려면 **저장 버튼**을 누른다.

## 7.21 메일이 안 온다 (Phase 6)

| 확인 | 조치 |
|---|---|
| 앱 안 알림함에는 왔는가 | 왔으면 메일만 문제다. 안 왔으면 7.12절(알림) |
| `WF_MAIL_ENABLED`가 `true`인가 | 기본은 꺼짐이다 |
| `WF_MAIL_MOCK`이 `false`인가 | `true`면 **일부러 안 보낸다.** 로그에 `mail.mock_sent`(모의 발송)가 찍힌다 |
| 감사로그에 `mail.send`가 있는가 | 있으면 우리 쪽은 보냈다. `mail.fail`이면 메일 API가 거절했다 |
| `WF_MAIL_API_URL`·`WF_MAIL_FROM`이 비지 않았는가 | 비면 로그에 `mail.unconfigured`가 찍히고 보내지 않는다 |
| 로그에 `mail.rejected`·`mail.failed`·`mail.mention_failed`가 있는가 | `mail.rejected`는 메일 API가 받지 않았다(`status` 필드), `mail.failed`는 닿지 않았다(`error` 필드), `mail.mention_failed`(error)는 멘션 메일을 처리하다 우리 쪽에서 실패했다(감사 기록까지 — 개발 담당) — 알림함은 그대로다 |

**메일이 실패해도 글은 정상으로 저장된다.** 그렇게 만들어 두었다 — 메일 서버가
죽었다고 댓글이 안 써지면 안 된다.

> 사내 메일 API의 요청 형식은 **아직 실제로 확인하지 않았다** (보류 18). 형식이
> 다르면 `apps/api/src/mail/http.sender.ts` 한 파일을 고친다.


## 7.22 알림에 부른 사람 이름이 없다 — "문서에서 불렸다" (Phase 8)

**대개 고장이 아니라 설계다.** 같이 쓴 문서(실시간 편집)에서 서버는 **누구의 창이 어떤 글자를 들여왔는지**와
**누구의 편집으로 부름이 새로 생겼는지**를 적어 둔다. 부름의 글자를 전부 들여온 사람과 그 부름을 생기게 한 사람이
**같을 때만** 그 사람의 이름을 적는다. 확실하지 않으면 **틀린 이름을 적는 대신 비운다.**

| 확인 | 뜻 |
|---|---|
| 누가 **남의 글자를 지우거나 끼워 넣어** 부름이 새로 생겼는가 (예: `@kim.lee`에서 `.lee`를 지워 `@kim`) | 글자는 한 사람이, 부름을 생기게 한 것은 다른 사람이다. 설계대로 비운다 |
| 두 사람이 `@아이디`를 **나눠서** 쳤는가 (한 사람이 `@ki`, 다른 사람이 `m`) | 설계대로 비운다 |
| 누가 **남의 부름을 옮겼는가** — 잘라 붙이기, 지웠다 되돌리기, 문단을 제목·목록으로 바꾸기, **그 부름 앞에서 Enter로 문단을 나누거나 Backspace로 합치기** | 옮긴 부름은 비운다(그 이름이 이미 저장된 버전에 있으면 새 알림이 가지 않는다). 옮긴 사람이 부른 것도 아니고 원래 사람의 이름을 옮겨 붙이지도 않는다. **처음부터 저장돼 있던 부름**(누가 만들었는지 모른다)을 지웠다가 붙여 넣기·되돌리기로 다시 만든 것도, 지운 사람 자신이 했어도 비운다 |
| `docker compose logs api`에 `collab.makers_failed`(멘션 장부를 고치지 못했다)가 있는가 | 그 방의 멘션은 그 뒤로 모두 "모름"이다(편집은 계속된다). 그 줄의 `pageId`와 시각을 적어 개발 담당에게 넘긴다 — 장부가 예상하지 못한 문서 모양을 만났다 |
| `docker compose logs api`에 `collab.makers_unsure`(변경이 보낸 것보다 문서를 더 바꿨다)가 있는가 | **Phase 9부터는 나오지 않아야 한다** — 미리 보내 두는 조작한 편집을 서버가 문 앞에서 받지 않는다(7.23). 나왔다면 관문의 틈이다: 그 페이지와 시각을 개발 담당에게 넘긴다. 그 줄의 `userId`는 **섞여 들어간 쪽(피해자)**의 사용자 id다 |

**이름이 "틀렸다"는 신고라면 고장일 수 있다.** 이름이 붙는 것은 그 부름의 글자를 전부 자기 창으로 들여오고 자기 편집으로
그 부름을 생기게 한 사람뿐이다. 두 가지를 먼저 확인한다 — ① 남의 글을 **복사해 붙여 넣은 사람**은 그 안의 부름을 만든 사람이
된다(붙여 넣은 글자는 그 사람의 창이 새로 들여온 것이다). ② 잘라낸 남의 부름을 **두 번에 나눠** 붙여 넣은 사람도 그렇다 — 한 글자씩
다시 친 것과 서버가 가릴 수 없다(설계대로). 둘 다 아니면 페이지 id와 그 시각을 적어 개발 담당에게 넘긴다.

> 부른 사람을 기억하는 장부는 실시간 편집 상태 옆(`page_realtime.authors`)에 있다.
> **지워도 된다** — 지우면 그 문서에서 아직 저장되지 않은 부름이 "모름"이 될 뿐이고, 정본 문서와
> 이미 간 알림은 그대로다.

## 7.23 "서버가 이 편집을 받지 않았다"가 뜬다 (Phase 9)

편집 화면 아래에 **빨간 글씨로** 뜨고, 그 사람의 실시간 편집 연결이 끊긴다. 같이 쓰던 다른 사람은 아무 일도 겪지 않는다.

서버는 같이 쓰는 문서의 편집을 **받아들이기 전에** 본다 — 우리 편집기가 만들 수 있는 모양인가, 아직 없는 글자에 기대지 않는가,
남의 식별 번호로 쓰지 않는가. 아니면 받지 않고 끊는다(설계서 `P9_설계서_Gate`). **평소에는 일어나지 않는다.**

**먼저 까닭을 본다.** 관리 화면 → **감사로그**에서 행위를 `page.collab.reject`로 고른다. 누가(사용자), 어느 페이지(대상), 어느
규칙(`detail.rule`)에 무슨 까닭(`detail.reason`)으로 걸렸는지가 있다. 같은 내용이 `docker compose logs api`에
`collab.gate_refused`(`pageId`·`userId`·`rule`·`reason` 필드)로도 남는다. 글의 내용은 어디에도 남지 않는다.

| 누가·어떻게 | 뜻 | 조치 |
|---|---|---|
| **평범하게 쓰던 사람**이 무언가를 붙여 넣거나 새 기능을 쓰다가 끊겼다. 까닭이 `허용되지 않는 속성·노드·마크`, `… 안에 올 수 없는 …`, `속성 '…' 값은 …`, `중첩 깊이 64 초과` | **우리 편집기와 서버 규칙이 어긋났다**(개발 결함). 그 사람이 한 일은 정상이다 | 무엇을 하다 끊겼는지(어디서 무엇을 붙여 넣었는지) 묻고, 페이지 id·시각·까닭을 개발 담당에게 넘긴다. 여러 사람이 같은 일로 막히면 **실시간 편집을 끈다**(7.19 끝의 `WF_COLLAB_ENABLED=false` — 한 사람씩 저장하는 방식으로 돌아간다) |
| 한 사용자가 **여러 번**, 까닭이 `편집기가 만들지 않는 타입·내용`, `남의 클라이언트 ID로 쓴 조각`, `서버에서 보류될 조각`, `아직 없는 글자를 지우는 삭제`, `같은 클라이언트가 두 번 나온 변경`, `앞 조각과 다른 자리에 이어 쓴 조각` | 우리 편집기로는 나오지 않는 편집이다 — **조작한 프로그램**일 가능성이 크다 | 보안 담당에게 알린다. 계속되면 관리자가 그 사람의 세션을 끊고(관리 화면의 **사용자 관리** → 그 사람 줄의 **세션 강제 종료**) 그 공간의 권한을 거둔다 |
| 까닭이 `읽을 수 없는 변경`·`읽을 수 없는 사람 표시` | 망에서 깨졌거나 조작이다 | 한 번이면 그 사람에게 새로고침을 권한다. 반복되면 위와 같다 |
| **아주 큰 것**(수만 문단·큰 표)을 한꺼번에 붙여 넣다가 끊겼다. 감사로그에는 없고 앱 로그에 **`collab.frame_too_large`**(`pageId`·`userId`·`limitBytes`) (Phase 12) | 편집 하나가 한 번에 보낼 수 있는 크기(16MiB)를 넘었다. 정상 문서 하나(저장 상한 2MB)의 8배라 평소에는 나오지 않는다 | 나눠 붙여 넣으라고 알린다. 그 문서가 이미 아주 크면(실시간 상태가 커지는 것 — 보류 19) 개발 담당에게 페이지 id를 넘긴다 |
| 링크를 붙여 넣다가 끊겼고 까닭이 `속성 'rel' 값에 'opener'를 둘 수 없다` | 다른 곳에서 복사한 링크에 새 창이 이 위키 창을 옮길 수 있게 하는 표시가 붙어 있었다. 편집기는 붙여 넣을 때 그 표시를 뺀다 — 그래도 이렇게 끊겼다면 그 사람의 화면이 **업데이트 전의 옛 화면**이다. 결함이 아니다 | 새로고침하고 다시 붙여 넣으라고 알린다. 새로고침한 뒤에도 같은 까닭으로 끊기면 위의 "조작한 프로그램" 줄과 같다 |

`중첩 깊이 64 초과`는 인용·목록을 아주 깊게 겹친 것이다 — 정상 편집기로도 만들 수 있지만 저장할 수 없는 문서라 문 앞에서
돌려보낸다. 그 사람에게 겹침을 줄여 다시 쓰라고 알리면 되고, 개발 결함이 아니다.

**같이 보는 사람 목록에 내가 안 보인다**(동료 화면에 내 이름·커서가 없다)는 이 절의 끊김과 다르다 — 편집은 오간다. 같은 페이지를
아주 여러 번(16번 넘게) 새로 열었는데 그 페이지를 누군가 늘 열어 두고 있었거나 자동 저장이 멈춰 있으면 그렇다. **한 글자를 치면**
그 뒤로 보인다. 모두가 그 페이지에서 나가 저장이 끝나면 저절로 풀린다 — 자동 저장이 멈춘 페이지는 그 까닭(7.20절 3번)을 먼저 푼다(설계서 `P9_설계서_Gate` D.5).

**끊긴 사람에게는** 쓰던 내용을 다른 곳에 복사한 뒤 새로고침하라고 알린다. 새로고침하면 서버에 남은 마지막 상태부터 다시
시작한다. 같은 것을 다시 붙여 넣어 또 끊기면 그 내용이 원인이다 — 그 내용을 개발 담당에게 함께 넘긴다.

## 7.24 LLM 연결 확인이 "연결 안 됨"이다 (Phase 10)

관리 화면 → **LLM 연결**에서 **연결 확인**을 누르면 까닭이 뜬다. 앱 서버가 등록한 주소의 `/models`를 불러 본 결과다(설계서 `P10_설계서_Llm` D.2).

| 까닭 | 뜻 | 조치 |
|---|---|---|
| `LLM 서버에 닿지 않는다 (ECONNREFUSED)`·`(ENOTFOUND)`·`(ETIMEDOUT)` | 주소(호스트·포트)가 틀렸거나, 앱 서버에서 그 서버로 가는 길이 막혔다(방화벽) | 앱 컨테이너 안에서 직접 불러 본다: `docker compose -f compose.yml exec api node -e "fetch('http://llm.example.internal:8000/v1/models').then(r=>console.log(r.status)).catch(e=>console.log(e.cause?.code))"`(주소는 등록한 것으로). 여기서도 안 되면 망 담당에게 그 주소·포트를 열어 달라고 한다 |
| `LLM 서버에 닿지 않는다 (UNABLE_TO_VERIFY_LEAF_SIGNATURE)`·`(SELF_SIGNED_CERT_IN_CHAIN)` 등 인증서 코드 | 주소가 `https`이고 **사내 인증 기관(CA)이 서명한 인증서**다. 앱이 그 기관을 모른다 | TLS 검증을 끄지 않는다(`CLAUDE.md` 7절). 앱이 그 기관을 믿게 한다 — [반입 가이드](운영가이드_반입.md) 10절 ②·③: compose 옆 `ca/ca.pem`에 그 기관의 인증서를 두고 `docker compose -f compose.yml --env-file .env up -d --force-recreate api`로 **다시 만든다**(`up -d`만으로는 파일을 알아채지 못한다 — T-049). 붙었는지: `docker exec workfluence-api sh -c 'tr "\0" "\n" < /proc/1/environ \| grep NODE_EXTRA_CA_CERTS'`가 한 줄. 그래도 같으면 중간 기관까지 이어 붙였는지 본다 |
| `LLM 서버가 다른 주소로 넘겼다 — 넘겨주기는 따르지 않는다` | 등록한 주소가 다른 곳으로 넘긴다(`http`→`https` 등). 넘겨주기를 따르면 API 키가 등록하지 않은 곳으로 가므로 따르지 않는다 | 넘겨진 **최종 주소**로 다시 등록한다(지우고 등록) |
| "모델 목록을 읽을 수 없다 — 주소가 OpenAI 호환 API의 /v1까지인지 확인한다" | 주소에 `/v1`이 빠졌거나, vLLM이 아닌 곳이다 | `http://호스트:포트/v1` 모양으로 다시 등록한다 |
| `invalid api key`·`HTTP 401` 같은 거절 | API 키가 틀렸거나 없다. LLM 서버의 문장이 키를 되읊으면 그 자리는 `***`로 가려져 나온다 | 지우고 맞는 키로 다시 등록한다. 키는 다시 볼 수 없으므로 고쳐 넣는 화면은 없다 — 지워도 대화는 남는다 |
| `10초 안에 답이 없다` | LLM 서버가 바쁘거나 멈췄다 | LLM 서버 담당에게 알린다 |
| `연결됨` + **"등록한 모델이 목록에 없다"** | 주소·키는 맞고 **모델 이름**이 틀렸다 | 목록에 보이는 이름 그대로 다시 등록한다 |
| `이 LLM의 API 키를 풀 수 없다 — …` | 앱의 마스터 키가 바뀌었거나 없다. 또는 데이터베이스에서 그 LLM의 **주소가 바뀌었다**(키는 주소와 묶여 잠겨 있다 — 화면에는 주소를 고치는 길이 없다) | 7.26절 |

**목록의 주소 옆에 "(암호화 안 됨)"** — `http` 주소다. 질문과 답(키가 있으면 키도)이 사내망을 평문으로 지난다. 사내 LLM이 `https`를 받으면 지우고 `https` 주소로 다시 등록한다.

**"LLM 연결" 메뉴가 안 보인다** — 시스템 관리자(`root`)와, 시스템 관리자가 **사용자 관리**에서 "LLM 연결 관리"를 준 관리자에게 보인다.
그 관리자에게 맡기려면 root로 사용자 관리 → 그 사람 줄의 "LLM 연결 관리"를 켠다(다음 요청부터 먹는다 — 새로고침). 거두면 끈다.
관리자가 member가 되면 저절로 사라진다. 누가 언제 주고 거뒀는지는 감사로그 `user.grants.change`에 있다.

## 7.25 LLM 답이 안 온다·끊긴다·한꺼번에 온다 (Phase 10)

답 아래에 빨간 글씨로 까닭이 뜬다. 저장되지 않은 질문은 입력칸에 되돌아온다.

| 화면의 까닭 | 뜻 | 조치 |
|---|---|---|
| `등록된 LLM이 없다` | 시스템 관리자가 등록하지 않았거나 지웠다 | 관리 화면에서 등록한다 |
| `LLM 서버에 닿지 않는다 (…)` | 7.24절과 같다 | 7.24절 |
| `시간 상한(10분)을 넘었다` | 답 하나가 `WF_LLM_TIMEOUT_MS`(기본 10분)를 넘었다. 거기까지는 "끊김"으로 저장된다 | LLM 서버가 느린지 본다. 늘 긴 답이 필요하면 `WF_LLM_TIMEOUT_MS`를 올리고 다시 띄운다(1시간까지) |
| `답이 상한(200,000자)을 넘어 끊었다` · `생각 과정이 상한을 넘어 끊었다` | 한 답의 설계 상한이다 | 질문을 나눠 묻는다 |
| `LLM 서버가 5분 동안 아무것도 보내지 않았다 (UND_ERR_HEADERS_TIMEOUT)`·`(UND_ERR_BODY_TIMEOUT)` | LLM 서버가 5분 동안 첫 글자도, 다음 글자도 보내지 않았다 — 붐벼서 줄을 섰거나 멈췄다. `WF_LLM_TIMEOUT_MS`와 다른 상한이라 그 값을 올려도 바뀌지 않는다(설계서 D.2) | LLM 서버 담당에게 그 시각을 알린다. 자주 나면 보류 29의 판정(첫 조각까지의 시간)에 적는다 |
| `대화가 모델이 한 번에 읽을 수 있는 길이를 넘었다 — 새 대화를 시작한다 (LLM 서버: This model's maximum context length is …)` | 대화가 **모델이 한 번에 읽을 수 있는 길이**보다 길어졌다. 앞 대화를 몰래 잘라 보내지 않는다(설계서 D.3) | **새 대화**를 시작한다. 앞 대화의 요점을 붙여 넣으면 된다 |
| `답이 모델의 길이 상한에서 잘렸다 — 대화가 길면 새 대화를 시작한다` | 모델이 쓸 수 있는 만큼 쓰고 멈췄다(`finish_reason: length`). 거기까지는 "끊김"으로 저장된다 | 대화가 길면 새 대화로, 아니면 "이어서 써 줘"로 묻는다 |
| `LLM 서버가 흘려보내지 않았다 — 흘려보내기(stream)를 지원하는 OpenAI 호환 주소인지 확인한다` | 등록한 주소가 답을 한꺼번에(흘려보내지 않고) 준다 — vLLM 앞의 게이트웨이가 `stream`을 모른다 | vLLM의 주소를 직접 등록하거나, 게이트웨이 담당에게 흘려보내기를 켜 달라고 한다 |
| `LLM 응답의 한 줄이 너무 길다 — …` | LLM 서버(또는 그 앞의 장비)가 줄바꿈 없이 끝없이 보낸다. 앱 메모리를 지키려고 끊었다 | LLM 서버 담당에게 알린다 — 정상 vLLM은 이렇게 보내지 않는다 |
| `LLM 응답을 읽을 수 없다` | 흐름 안에 OpenAI 호환 모양이 아닌 조각이 왔다(HTML 오류 쪽 등). 거절이 아니라 응답의 모양이 틀렸다 — 감사의 `failure`는 `protocol`이다 | 등록한 주소가 vLLM의 `/v1`인지, 그 앞의 게이트웨이가 흐름을 고쳐 쓰는지 본다 |
| `세션이 끝나 답을 멈췄다 — 다시 로그인한다` | 답을 받는 사이 그 사람의 세션이 끝났다 — 비밀번호를 바꿨거나, 관리자가 세션을 강제 종료했거나, 같은 세션의 다른 탭에서 로그아웃했다. 거기까지는 "중지됨"으로 저장된다 | 다시 로그인해 묻는다. 감사로그의 그 `llm.ask`에 `detail.failure = revoked`가 남는다 |
| `대화 하나에 메시지는 200개까지다 — 새 대화를 시작한다` | 대화 하나의 상한이다 | 새 대화를 시작한다 |
| `이미 답을 받고 있다 — 끝나거나 중지한 뒤에 묻는다` | 한 사람은 한 번에 하나만 묻는다. **다른 탭·다른 창**에서 답을 받는 중이다 | 그 탭에서 중지하거나 끝나기를 기다린다. 창을 닫았거나 그 화면을 떠났으면(다른 메뉴·뒤로 가기) 받던 답이 멈추고 곧 풀린다 |
| `연결이 끊겼다 — 답이 저장됐는지 목록을 다시 본다` | 브라우저와 서버 사이가 끊겼다 | 목록을 다시 본다. 서버는 거기까지를 저장했을 수 있다 |
| `그 사이에 대화가 지워져 이 답을 저장하지 않았다` | 답을 받는 사이 그 대화가 지워졌다(다른 탭에서 지움, 보존 기간) | 새 대화로 다시 묻는다 |
| `답을 저장하지 못했다` | 데이터베이스가 거절했다 | `docker compose logs api`에서 `llm.save_failed` 줄의 `error`(PostgreSQL 코드와 문장)를 본다. 연결이 끊긴 것이면 2절. 질문·답 내용은 로그에 없다(drizzle 문장은 "DB 질의 실패 — 문장은 싣지 않는다"로만 나온다) |

**어떤 까닭으로 실패하는지 모아 보려면** — 로그에는 종류와 HTTP 상태만 남는다(LLM 서버의 문장은 남의 응답이라 싣지 않는다):
`docker compose -f compose.yml logs api | grep '"event":"llm.ask_failed"'` → 줄마다 `kind`(`rejected`·`timeout`·`unreachable`·`protocol`)와
`httpStatus`, `providerId`가 있다. `llm.ask_error`는 우리 쪽 결함이다(개발 담당에게 그 줄의 `requestId`와 함께).
감사로그의 `llm.ask`에도 `detail.failure`(`unreachable`·`rejected`·`protocol`·`timeout`·`length`·`revoked` …)와 `detail.httpStatus`가 있다.

**답이 흘러나오지 않고 끝에 한꺼번에 나온다** — 중간의 누군가가 응답을 모았다가 보낸다. 우리 nginx는 앱이 붙이는 `X-Accel-Buffering: no`를 따라 모으지 않는다(설계서 D.1). nginx 앞에 **다른 프록시**(사내 L7 장비 등)가 있으면 그쪽에서 이 경로(`/api/llm/ask`)의 버퍼링을 끄게 한다.

## 7.25-1 "답변이 늦어지고 있습니다."가 뜬다 (Phase 12)

질문을 보내면 답 자리에 **`답변을 기다리고 있습니다 · 12s`**처럼 기다린 초가 보이고, 5초를 넘으면 **`답변이 늦어지고 있습니다.`**가
함께 뜬다. 첫 답 조각(생각 과정 포함)이 오면 사라진다. **질문 수를 막는 장치는 없다** — 사내 LLM 서버가 붐비면 스스로 느려진다(사용자 결정,
보류 30).

| 이렇게 되면 | 뜻 | 조치 |
|---|---|---|
| 몇 초~몇십 초 뒤에 답이 나오기 시작한다 | 사내 LLM 서버가 앞의 질문들을 처리하는 중이다 | 기다린다. 자주 그러면 LLM 서버 담당에게 붐비는 시각을 알린다 |
| 초가 계속 올라가고 5분쯤에 `LLM 서버가 5분 동안 아무것도 보내지 않았다`로 끝난다 | 서버가 첫 글자를 보내지 못했다 — 7.25절의 그 줄 | 7.25절 |
| 초가 멈춰 있다(올라가지 않는다) | 화면이 멈췄다 — 브라우저 문제다 | 새로고침한다. 보낸 질문은 서버가 받았으면 목록에 남는다 |

## 7.26 "API 키를 풀 수 없다" (Phase 10)

LLM API 키는 **`WF_LLM_MASTER_KEY`로 잠가서**(암호화) 데이터베이스에 있다. 그 값이 바뀌거나 비면 저장된 키를 풀 수 없다.

- **이전 값으로 되돌리면** 다시 풀린다 — 백업과 따로 보관해 둔 값을 `.env`에 넣고 다시 띄운다
- 값을 잃었으면 관리 화면에서 그 LLM을 **지우고 키를 다시 넣어 등록**한다. 대화는 남고, 사람들은 새로 등록한 LLM으로 이어 묻는다
- `WF_LLM_MASTER_KEY: 32바이트를 base64(url)로 적은 것이어야 한다`로 **앱이 뜨지 않으면** 값의 모양이 틀렸다 — `openssl rand -base64 32`의 출력을 그대로 넣는다(7.15절과 같은 종류)
- **백업에는 마스터 키가 들어가지 않는다**(데이터베이스와 첨부만). 백업으로 다른 서버에 되살리면 그 서버에도 **같은 마스터 키**가 있어야 키가 풀린다

## 7.27 LLM 대화가 사라졌다 (Phase 10)

**되살릴 수 없다** — LLM 대화는 휴지통에 가지 않는다(`CLAUDE.md` 6절). 왜 사라졌는지만 확인한다.

| 확인 | 뜻 |
|---|---|
| 고정하지 않은 대화이고 마지막으로 물은 지 7일(운영 설정 `llmRetentionDays`)이 지났다 | 보존 기간이다. 앱이 한 시간마다 지운다. 감사로그 `llm.conversation.purge`에 지운 수가 남는다 |
| 그 사람의 대화가 100개(`llmConversationMax`)를 넘었다 | 새 대화를 저장할 때 **고정하지 않은 것 중 가장 오래된 것**이 지워졌다. 그때 화면이 "오래된 대화 n개를 지웠다"고 말했고, 감사로그 그 사람의 `llm.ask`에 `detail.evicted`가 있다 |
| 관리자가 운영 설정에서 기간·개수를 줄였다 | 감사로그 `settings.update`의 이전·이후 값 |
| 로그에 `llm.sweep_failed` · `error: 42P01 relation "llm_conversations" does not exist` | 반대로 **지워지지 않는다** — 표가 없다. 반입 가이드 5절의 표 만들기(`migrate.js`)를 빠뜨렸다. 지운 날에는 `llm.sweep_done`(`count`)이 남는다 |

고정한 대화는 풀 때까지 지워지지 않는다. 오래 남겨야 하는 대화는 **고정**하라고 알린다(20개까지).

**"보관 105/100"처럼 상한을 넘어 보인다** — 관리자가 운영 설정에서 대화 수(`llmConversationMax`)를 그 사람의 **고정 수 아래로** 내렸다.
고정은 관리 작업이 풀지 않는다(사람이 한 설정을 조용히 되돌리지 않는다, 설계서 D.5). 새 질문은 그대로 되고 고정하지 않은 앞 대화만
지워진다. 그 사람이 고정을 풀어야 줄어든다.


## 7.28 앱 로그 읽기 — 요청 번호와 event 코드 (Phase 11)

앱 로그는 **한 줄에 JSON 하나**다. 줄마다 **`event`**(무슨 일인가 — 아래 표)가 있고, 요청 안에서 남긴 줄에는 **`requestId`**(그 요청의
번호)와 로그인한 사람의 `userId`가 있다. 문장(`msg`)은 사람을 위한 설명이다 — **찾을 때는 event와 번호로 찾는다.** 문장은 고쳐질 수
있지만 event 코드는 그대로다(설계서 `P11_설계서_Ops` D.4).

### 한 요청을 끝까지 잇기

"방금 오류가 났다"는 신고를 받으면:

1. 그 시각 근처의 실패한 요청을 찾는다 — 앱 접근 로그(`http.request`)의 `status`가 500번대인 줄:
   ```
   docker compose -f compose.yml logs api --since 15m | grep '"event":"http.request"' | grep '"status":5'
   ```
   사용자를 알면 그 사람의 id로 좁힌다(`SELECT id FROM users WHERE username = '<아이디>'`를 postgres 컨테이너에서).
2. 그 줄의 `requestId`로 **같은 요청의 모든 줄**을 모은다 — nginx 줄(들어온 요청), 앱 접근 로그, 오류 줄(`http.unhandled` 등):
   ```
   docker compose -f compose.yml logs api nginx --since 15m | grep '<requestId>'
   ```
3. 그 요청이 남긴 **감사 행** — 관리 화면의 **감사로그 → "요청 번호"** 칸에 붙이고 **거르기**. 목록 끝 칸에도 번호가 보인다.
   관리 화면을 열 수 없으면 데이터베이스에서:
   ```
   docker exec workfluence-postgres psql -U workfluence -d workfluence -c "SELECT created_at, action, target_type, target_id FROM audit_events WHERE request_id = '<requestId>'"
   ```

화면을 연 사람도 번호를 볼 수 있다 — 브라우저 개발자 도구 → 네트워크 → 그 요청의 응답 머리말 `X-Request-Id`.
개발 담당에게 넘길 때는 **요청 번호와 시각**을 함께 준다.

- **앱 접근 로그**(`http.request`): `method`·`route`(경로 틀 — `/api/pages/:id`)·`status`·`durationMs`·`userId`, 받는 쪽이 먼저 끊었으면
  `aborted`. 없는 주소를 부른 요청(404)은 `route`가 비고 `path`(받은 경로, 200자까지)가 있다. 주소의 대소문자는 가리지 않는다(`/API/…`도
  남는다). **질의 문자열(검색어)은 싣지 않는다.** 헬스체크와 화면 파일은 남기지 않는다. 5xx는 `warn`이다.
- `userId`는 **그 요청을 보낸 사람**이다. 세션을 끊는 요청(관리자의 강제 종료·비밀번호 변경) 안에서 남은 줄은 끊긴 사람을
  **`targetUserId`**로 따로 적는다(`collab.revoked`·`session.revoke_failed`).
- **nginx 로그**도 JSON 한 줄이다: `requestId`·`method`·`uri`(질의 없음)·`status`·`requestTime`·`upstreamTime`. referer는 싣지 않는다.
- 실시간 편집(WebSocket)의 줄에는 `requestId`가 없다 — `pageId`·`userId`로 찾는다.

### 로그는 얼마나 남나

서비스마다 **20MB 파일 5개**(최대 100MB)까지 남고 넘으면 오래된 것부터 지워진다. 오래 두어야 하는 로그는 그 전에 옮겨 둔다:
`docker compose -f compose.yml logs --no-color api > api-날짜.log`. 크기와 개수는 `.env`의 `WF_LOG_MAX_SIZE`·`WF_LOG_MAX_FILES`로
바꾸고 **컨테이너를 다시 만들어야 먹는다**(`docker compose -f compose.yml up -d`).

## 8. 기록은 어디에 있는가

| 무엇 | 어디 | 성격 |
|---|---|---|
| 앱이 남긴 운영 기록 | 컨테이너 표준 출력 (`docker compose logs`) | 한 줄에 JSON 하나 — `event` 코드와 요청 번호(`requestId`)가 있다(7.28절). 서비스마다 20MB × 5개에서 순환한다 |
| 누가 무엇을 했는지 | 데이터베이스의 감사 기록 테이블 | **수정·삭제 불가**. Phase 1부터 채워진다. Phase 11부터 행마다 그 요청의 번호(`request_id`)가 있다 |
| 들어온 요청 | nginx 컨테이너 로그 | JSON 한 줄 — 요청 번호가 앱 로그와 같다. 질의 문자열(검색어)은 없다 |
| 데이터베이스 자체 기록 | postgres 컨테이너 로그 | 연결·디스크 오류가 여기 나온다 |

앱 기록에는 **비밀번호·토큰·세션 값·문서 본문·LLM 질문과 답·지시문·LLM API 키가 들어가지 않는다.** 데이터베이스 오류도 PostgreSQL의 코드와 문장만 — 문장 속 값은 가린다. 로그를 보고 사용자 개인정보나 문서 내용을 알 수는 없다. 사용자는 불투명한 식별자로만 나온다.
