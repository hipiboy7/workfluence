## 1. 프로젝트 개요

**금융 폐쇄망 안에서 쓰는 위키·문서 협업 시스템**을 만든다. 팀이 업무 문서를 함께 쓰고, 고쳐 온 이력을 잃지 않으며, 누가 무엇을 언제 바꿨는지 추적할 수 있어야 한다.

### 1.1 왜 직접 만드는가

상용 위키를 도입하는 대신 자체 구축하는 이유는 세 가지다.

| 이유 | 내용 |
|---|---|
| **반입 제약** | 폐쇄망은 인터넷이 없다. 상용 제품은 설치·갱신·라이선스 확인 경로가 전부 반입 절차를 타야 하고, 보안 패치 주기를 우리가 통제할 수 없다 |
| **감사 요구** | 금융기관은 누가 무엇을 조회·변경했는지 증적이 필요하다. 감사 항목과 보존 정책을 제품 기능에 맞추는 것이 아니라 우리 정책에 맞춰야 한다 |
| **인증 연동** | 사내 IdP(OIDC)와 로컬 계정을 함께 쓴다. 상용 제품의 연동 방식에 사내 IdP를 맞추는 것보다 우리가 IdP에 맞추는 편이 현실적이다 |

### 1.2 대상과 규모

- 사용자 약 **300명**. 동시 접속은 수십 명 수준으로 가정한다.
- 단일 앱 서버 + PostgreSQL 1대로 시작한다. 이중화는 부하 실측 후 판단한다 (`CLAUDE.md` 보류 6).
- 문서량은 초기 수천 건, 첨부 포함 수십 GB 이내로 가정한다.

### 1.3 제품 기준

기능의 기준점은 **Confluence의 실제 동작**이다. 다만 그대로 베끼지 않는다. 기능이 있는 Phase에서는 그 기능을 Confluence와 대조해 채택·변형·제외를 **그 Phase 설계서의 대조 절**에 남기고, 본문에는 우리 판단의 근거만 쓴다 (`CLAUDE.md` 1.3절·4절).

## 2. 용어

| 용어 | 뜻 |
|---|---|
| **스페이스** | 페이지를 담는 최상위 구획. **개인**(만든 사람만)과 **팀**(Crew만) 두 종류 |
| **카테고리(분류)** | 스페이스를 묶는 이름표. 사용자가 만든다 |
| **Crew** | 팀 스페이스를 함께 쓰는 사람들. `owner`(생성자) · `editor`(편집) · `viewer`(보기) |
| **페이지** | 스페이스 안의 문서. 부모-자식 트리를 이룬다 |
| **버전** | 페이지를 저장할 때마다 쌓이는 스냅샷. 지워지지 않는다 |
| **역할** | 시스템 권한. `root`(시스템) ⊃ `admin`(사용자·스페이스 관리) ⊃ `member`(일반) |
| **사용자 상태** | `승인 대기` → `활성`. 로그인 실패가 쌓이면 `잠김` |
| **스페이스 상태** | `활성` / `중지`. 중지되면 읽기 전용 |

## 3. 제약

| 구분 | 제약 | 영향 |
|---|---|---|
| 망 | 운영은 인터넷 차단 | 런타임에 외부 자원을 **하나도** 쓰지 않는다. 폰트·아이콘·문서 UI 자산 전부 번들 |
| 반입 | 파일 반입 절차를 거친다 | 이미지 tar + 체크섬 + SBOM·라이선스 목록을 묶음으로 전달. 이미지 크기를 작게 유지한다 |
| 개발 | 개발·빌드가 사내 Linux 서버 한 대 (2026-09-21 통합). 다른 프로젝트와 공유 | 명령은 OS 무관한 `pnpm` 스크립트로만. 남의 컨테이너·볼륨을 건드리지 않고, 프록시 뒤라 빌드에 프록시를 넘긴다 |
| 보안 | 금융기관 내부 시스템 | 기본 거부 권한, 감사로그 append-only, 세션 서버측 통제, 의존성 라이선스·시크릿 검사 |
| 저장소 | GitHub **공개** | 사내 호스트명·IP·계정·IdP 등록값·실데이터를 커밋하지 않는다 (`CLAUDE.md` 12.3절) |

## 5. Phase 로드맵과 인수 기준

각 Phase는 **브라우저에서 동작하는 증분**으로 끝난다. 인수 기준은 사람이 화면에서 확인할 수 있는 문장으로 쓴다.

| Phase | 명칭 | 인수 기준 (이것이 되면 그 Phase는 끝났다) |
|---|---|---|
| **0** | 범위·아키텍처·공통 기반 | Linux 서버에서 pull → 이미지 빌드 → compose 기동 → 브라우저에서 앱이 뜨고 `/api/health`가 `db: ok`를 반환한다. `pnpm check`가 통과한다 |
| **1** | 인증·사용자·권한 골격 | 가입 요청한 계정을 관리자가 승인하면 로그인된다. IdP 계정으로 로그인하면 그룹이 역할로 매핑된다. 두 경로 모두 감사로그에 남는다 |
| **2** | 스페이스·페이지·편집기 | 팀 스페이스를 만들고 Crew를 넣고, 페이지를 작성·편집·이동하고, 이전 버전을 복원할 수 있다. 두 사람이 같은 버전을 저장하면 뒤가 충돌 안내를 받는다 |
| **3** | 검색·첨부·댓글 | 한글 두 글자로 페이지가 검색되고, 내가 볼 수 없는 스페이스는 결과에 없다. 파일을 첨부·다운로드하고 댓글을 단다 |
| **4** | 권한 세분화·관리·알림 | 관리자가 사용자·스페이스를 관리하고 감사로그로 추적한다. 삭제한 페이지를 휴지통에서 되살린다. 멘션이 알림함에 뜬다 |
| **5** | 운영화·반입 | 반입 리허설: 이미지 tar를 옮겨 기동하고, 백업본으로 복원하며, 300명 기준 부하에서 목표 지연을 만족한다 |
| **6** | 2단계 | 착수 시 세부화 |

## 7. 확정된 결정과 근거

프로토타입(`exp/prototype`)에서 화면으로 확인한 뒤 확정한 것들이다. 프로토타입은 결정의 **계기**이고, 아래는 우리가 그 결정을 유지하는 **이유**다.

### 7.1 계정

| 결정 | 이유 |
|---|---|
| 비밀번호 **8자 이상·2종 조합**, 5회 실패 시 15분 잠금 | 사내망 안에서만 접근되는 문서 시스템이다. 길이·복잡도를 과하게 올리면 사용자가 메모에 적어 두는 쪽이 더 큰 위험이 된다. 잠금은 유지해 무차별 대입을 막는다. 사내 정책 문서가 확인되면 그 값으로 바꾼다 (`CLAUDE.md` 확인 필요 B) |
| 가입은 **요청 → 관리자 승인** | 누가 시스템에 들어오는지를 관리자가 통제해야 한다. 자동 가입은 폐쇄망이라도 퇴직자·외부 인력 문제를 남긴다 |
| 승인 시 **개인 스페이스 자동 생성** | 첫 로그인에 아무것도 없으면 무엇을 해야 할지 모른다. 바로 쓸 공간을 하나 준다 |
| ID 찾기는 **email + 이름** 둘 다 요구하고 **마스킹된 ID**만 보여준다 | email만으로 ID를 돌려주면 email 목록을 가진 사람이 계정을 열거할 수 있다. 두 정보를 요구하고 결과를 가려 노출 범위를 줄인다 |
| PWD 찾기는 **임시 비밀번호를 화면에 1회 표시**하고 다음 로그인에서 변경을 강제한다 | 폐쇄망이라 메일 발송 경로가 없다. 화면 표시가 유일한 전달 수단이고, 변경 강제로 노출 창을 닫는다 |
| 담당자 확인에 **email을 노출하지 않는다** | 로그인 전 화면이다. 연락처는 사내 다른 경로로 이미 알 수 있고, 여기 두면 수집 대상이 된다 |
| 비밀번호 입력에 **눈 아이콘**(기본 가림) | 오타로 인한 실패·잠금을 줄인다. 기본이 가림이어야 어깨너머 노출을 막는다 |

### 7.2 스페이스

| 결정 | 이유 |
|---|---|
| **개인 / 팀** 두 종류 | 혼자 쓰는 메모와 함께 쓰는 문서는 접근 통제가 다르다. 한 종류로 두면 "나만 보는 공간"을 만들 방법이 없다 |
| 팀 스페이스는 **Crew만** 접근 | 사내 전체 공개가 기본이면 부서 문서가 의도치 않게 퍼진다. 필요한 사람을 명시적으로 넣는다 |
| Crew 역할 **owner / editor / viewer** | "함께 작업하는 사람"과 "볼 수만 있는 사람"이 실제로 나뉜다. owner는 구성원을 관리한다 |
| 관리자는 **모든 스페이스를 본다** | 사용자 이탈·분쟁·감사 시 관리자가 접근하지 못하면 운영이 막힌다. 접근은 감사로그에 남는다 |
| 화면에서 **키(식별자)를 없애고 분류(카테고리)를 쓴다** | 사용자가 키를 정하면 중복·의미 없는 문자열이 쌓인다. 식별자는 시스템이 만들고, 사람은 분류로 찾는다 |
| 카테고리는 **모든 활성 사용자가 생성** | 스페이스를 만드는 사람이 분류도 만들 수 있어야 흐름이 끊기지 않는다. 남용되면 Phase 4에서 관리 기능을 붙인다 |
| 상태 **활성 / 중지**, 중지는 읽기 전용 | 쓰지 않는 스페이스를 지우기 전에 얼려 둘 단계가 필요하다. 문서는 남기고 편집만 막는다 |
| 삭제는 **생성자는 Crew가 본인뿐일 때**, **관리자는 중지 상태일 때** | 여러 사람이 쓰는 공간을 한 사람이 지울 수 있으면 안 된다. 관리자 삭제도 "중지"라는 예고 단계를 거친다 |

### 7.3 역할

| 결정 | 이유 |
|---|---|
| **root ⊃ admin ⊃ member** 3단계 | 시스템 운영(설정·버전·기반)과 업무 관리(사용자·스페이스)는 책임이 다르다. 한 역할로 묶으면 업무 관리자에게 시스템 권한까지 준다 |
| root만 root를 부여한다. admin은 root를 관리할 수 없다 | 권한 상승 경로를 막는다 |
| 권한 판정은 **공유 패키지의 순수 함수 한 곳** | 화면·API·가드가 각자 판단하면 언젠가 어긋난다. 한 곳에서 판정하고 테스트로 고정한다 |

### 7.4 문서

| 결정 | 이유 |
|---|---|
| 본문은 **구조화 JSON만** 받는다. HTML을 받지 않는다 | HTML을 받으면 서버가 정화(sanitize)해야 하고, 정화 규칙의 구멍이 그대로 XSS가 된다. 허용 노드·마크 목록 밖은 거부하는 편이 확실하다 |
| 버전은 **append-only**, 복원도 새 버전 | 이력이 지워지면 감사가 불가능하다. 복원조차 "되돌린 사실"을 남긴다 |
| 저장 시 **기준 버전 불일치는 거부(409)** | 마지막 저장이 이기면 앞사람 작업이 조용히 사라진다. 사용자에게 알리고 선택하게 한다 |
| 삭제는 **soft delete** | 실수로 지운 문서를 복구할 수 있어야 한다 |

### 7.5 정정 이력

- 없음 (v1 최초 작성).

## 8. 위험과 대응

| # | 위험 | 대응 |
|---|---|---|
| 1 | 폐쇄망 반입 단계에서 이미지·의존성 문제가 드러나 설계가 뒤집힌다 | **Phase 0의 완료 기준을 Linux 빌드·기동으로 둔다.** 마지막이 아니라 처음에 뚫는다 |
| 2 | 한글 2글자 검색이 느리거나 결과가 빠진다 | Phase 3에서 재현율·p95를 실측하고, 미달이면 확장(pg_bigm) 반입을 판단한다 (보류 2) |
| 3 | IdP 실연동이 개발 PC에서 불가능해 늦게 터진다 | 모의 서버로 개발하되 **Linux 서버에서 실호출 검증**을 Phase 1 완료 기준에 넣는다. 모의 통과는 완료가 아니다 |
| 4 | 공개 저장소에 사내 정보가 섞인다 | CI에 gitleaks. 문서·예시는 placeholder만. 커밋 전 검사를 습관으로 |
| 5 | 프로토타입 코드를 근거 없이 승격해 품질 부채가 남는다 | 모듈 단위로 4단계 문서를 밟으며 승격. 근거를 쓸 수 없는 코드는 가져오지 않는다 |
| 6 | 문서가 실제 동작과 어긋난다 | `pnpm verify:docs`(기계 검사) + `doc-consistency` 에이전트(뜻 검사) 두 층 |
| 7 | 감사로그가 비대해져 성능·용량 문제를 만든다 | 보존 기간을 설정값으로 두고 Phase 4에서 정리 배치를 설계한다 |
