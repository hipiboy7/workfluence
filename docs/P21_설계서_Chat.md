# P21 설계서 — Chat (독립 메뉴의 채팅과 headless 접속 — F-016)

새 메뉴에 **방 단위 채팅**을 만든다. 사람은 화면으로, 사람 없이 도는 클라이언트(headless — 예: AI 에이전트)는 **API 토큰으로** 같은 방에 들어와 같은 메시지를 주고받는다.
새 메시지는 WebSocket으로 받는다. 위키 문서·스페이스와는 독립이다(방은 스페이스에 속하지 않는다).

- 요청 원문: `docs/prompts/phase21/scope.md` · 백로그 F-016
- 요구사항 번호: **FR-2400**, 비기능 **NFR-240**부터
- 선행: [`docs/P6_설계서_Collab.md`](P6_설계서_Collab.md)(실시간 편집의 WebSocket — 연결 수명·재판정 방식) · 공개 API(`docs/spinoff/public-api/설계서_PublicApi.md` — 토큰·scope·빈도 제한)
- 브랜치: `impl-phase21` (사용자 지시로 `tanminkwan-rest-api`에서 분기 — PR의 기준 브랜치도 그쪽이다)

## A. 착수 쟁점 (2026-10-12)

| # | 쟁점 | 사용자 답 | 이 설계가 한 것 |
|---|---|---|---|
| 1 | 채팅의 범위 | **"방 단위"** | 방 목록 · 방 만들기·초대 · 메시지 보내기·읽기. 스페이스·페이지에 붙은 채팅은 하지 않는다 |
| 2 | 새 메시지 수신 방식 | **"WebSocket"** | 사람 한 명(또는 headless 한 개)이 연결 **하나**를 열면 참여한 모든 방의 새 메시지가 온다 |
| 3 | 공개 API에 넣는가 | "api라기보다 headless 또는 background chat에 가까운거지?" → **이번 Phase에 함께 만든다** | 화면과 headless가 **같은 채팅 유스케이스**를 부른다. headless는 토큰(`Authorization: Bearer`)으로 WebSocket·REST에 닿는다 (C절) |
| 4 | 보존·삭제·감사 | **"나중에"** | 보류 39로 등재했다. 이번에는 메시지를 지우지 않고 보존 기간도 없다 — 단 **남기는 모양은 나중에 정책을 얹을 수 있게** 둔다 (F절) |

## A.1 묻지 않고 정한 것 — 근거와 되돌릴 조건

| # | 정한 것 | 근거 | 되돌릴 조건 |
|---|---|---|---|
| 1 | 방은 둘이다 — 1:1(`direct`, 두 사람 사이에 하나)과 여럿(`group`, 이름 있음) | 방 단위라는 답을 가장 작게 담는 모양이다. 1:1은 쌍마다 하나로 고정해 같은 두 사람이 방을 여럿 만들지 못하게 한다 | 1:1도 여러 개가 필요하다는 요청 |
| 2 | 방은 **활성 사용자 누구나** 만든다. 여럿 방은 **참여자 누구나** 초대하고(2026-10-15 개정 — 처음에는 만든 사람만이었다. 사용자: "상식적으로 초대된 사람도 다른 사람을 초대할 수 있는것이 맞지"), 참여자는 스스로 나갈 수 있다 | 권한 체계(스페이스 Crew)를 새로 만들지 않는다 — 참여자인지 하나만 본다. 만든 사람이 나가도 방이 멈추지 않는다 | 관리자가 방을 막거나 초대 권한을 나눠야 할 때 |
| 3 | 메시지는 **평문**이다. 길이 상한은 설정(`WF_CHAT_MAX_MESSAGE_CHARS`). HTML로 그리지 않는다 | LLM 답을 평문으로 그린 것(CLAUDE.md 7절)과 같다 — 입력이 화면을 깨는 길을 막는다 | 서식(마크다운)을 원할 때 |
| 4 | 참여자가 아니면 방은 **없는 것과 같은 404**다 | 방이 있는지 드러내지 않는다(보류 34의 같은 결) | — |
| 5 | 정지된 사용자·세션 만료·토큰 폐기는 **그 연결을 그 자리에서 끊는다** | 실시간 편집과 같은 규칙(Phase 7) | — |
| 6 | 보내는 쪽이 **`clientMsgId`**(그 연결이 정하는 임의 문자열)를 붙이면 서버가 같은 값의 되풀이를 한 번만 받는다 | headless는 연결이 끊겼다 다시 보낼 때 같은 메시지를 두 번 보내기 쉽다 | — |
| 7 | **새로 초대된 사람은 그 방의 지난 메시지도 읽는다**(참여한 시각으로 거르지 않는다). 읽음 번호는 초대 시점의 마지막 번호로 시작해 안 읽은 수가 지난 메시지로 부풀지 않는다 | 방 단위 채팅의 흔한 기대("맥락을 보고 들어온다")이고 거르려면 표가 더 필요하다 | 초대받기 전의 대화를 숨겨야 한다는 요청(보류 39와 함께 정한다) |
| 8 | 사람 찾기(`GET /chat/users`)는 활성 사용자의 **표시 이름과 id만** 준다. 아이디·메일은 싣지 않는다 | 방에 부르려면 이름으로 찾아야 하고, 300명 규모의 사내 사용자 이름은 이미 위키 곳곳(작성자·Crew)에 보인다 | 이름 목록의 노출이 문제가 되면 같은 스페이스·같은 방을 쓴 사람으로 좁힌다. **같은 방 참여자의 아이디는 방 정보에 싣는다**(FR-2409, 2026-10-16 — 사람 찾기는 그대로) |

## C. 연결과 인증

### C.1 한 연결, 두 입구

| | 사람(화면) | headless |
|---|---|---|
| 주소 | `wss://…/api/chat/ws` | `wss://…/api/v1/chat/ws` |
| 인증 | 세션 쿠키 | `Authorization: Bearer <토큰>` (업그레이드 요청의 헤더) |
| 출처 확인 | `Origin`이 같은 출처 | 하지 않는다 |
| 권한 | 로그인한 사용자 | 토큰의 scope ∩ 그 사람의 권한 |
| 끊는 때 | 세션 파기·정지 | **토큰** 폐기·만료·정지·세션 파기 |

두 입구는 **인증만 다르고** 인증이 끝나면 같은 `ChatGateway` 코드로 합쳐진다(DIP — 인증 결과는 `{userId, 끊김 열쇠}`).
토큰이 URL의 질의 문자열로 오는 것은 받지 않는다(로그에 남는다 — CLAUDE.md 7절).

### C.2 메시지 모양 (JSON 텍스트 프레임)

| 방향 | `type` | 내용 |
|---|---|---|
| 서버→클라 | `hello` | 연결이 선 직후 — `userId`, 참여한 방 id 목록 |
| 클라→서버 | `send` | `roomId`, `body`, `clientMsgId`(선택) |
| 서버→클라 | `ack` | `clientMsgId`, `roomId`, `seq`, `createdAt` — 보낸 사람에게만 |
| 서버→클라 | `message` | `roomId`, `seq`, `senderId`, `body`, `kind`(`user`·`join`·`leave`), `createdAt` — **보낸 사람 포함** 참여자 모두 |
| 서버→클라 | `room` | 방이 생기거나 초대·나감 — `roomId`, `change`(`joined`·`left`는 당사자에게, `members`는 방에 남은 다른 참여자에게) |
| 서버→클라 | `error` | `code`, `roomId?`, `clientMsgId?` — 그 메시지만 거절하고 연결은 둔다 |
| 양쪽 | 프로토콜 ping/pong | 30초 주기 — 응답이 없으면 끊는다(실시간 편집과 같다) |

모르는 `type`·너무 큰 프레임·JSON이 아닌 것은 **연결을 닫는다**(편집 관문의 규칙과 같다 — 조작한 연결이 서버에 일을 시키지 못하게).

## D. 데이터 모델 (마이그레이션 `0015_chat.sql`, 안내 줄은 `0016_chat_notices.sql`, 나간 사람 조회 인덱스는 `0017_chat_leave_idx.sql` — 손으로 쓴다)

| 표 | 칸 | 비고 |
|---|---|---|
| `chat_rooms` | `id` uuid, `kind` (`direct`/`group`), `name` text null, `created_by` uuid, `created_at`, `last_seq` bigint(기본 0), `last_message_at` timestamptz null(방 목록 정렬) | 1:1은 `name` 없음. `last_seq`는 새 메시지의 번호를 매기는 곳(행 잠금) |
| `chat_members` | `room_id`, `user_id`, `joined_at`, `last_read_seq` bigint(기본 0), 기본키(`room_id`,`user_id`) | 나가면 행을 지운다(되돌리기 없음) |
| `chat_direct_pairs` | `user_a`, `user_b`(`user_a < user_b`), `room_id` | 쌍의 유일성. 1:1 만들기가 두 사람 순서와 무관하게 같은 방을 돌려준다 |
| `chat_messages` | `id` uuid, `room_id`, `seq` bigint, `sender_id`, `body` text, `client_msg_id` text null, `created_at` | 고유(`room_id`,`seq`) · 고유(`room_id`,`sender_id`,`client_msg_id`) — 같은 값의 되풀이를 한 번만 받는다. `kind` text(기본 `user`, 0016 — `user`·`join`·`leave`만): 안내 줄은 `join`·`leave`이고 `sender_id`는 그 일을 한 사람(나간 사람·초대한 사람), `body`는 `chatNoticeText`가 만든 문장이다 |

- 번호 매기기: 보낼 때 `chat_rooms` 행을 `FOR UPDATE`로 잠그고 `last_seq + 1`을 받는다 — 방 안에서 번호가 비지도 겹치지도 않는다.
- **안내 줄(F-019)**: 방 행을 잠근 같은 트랜잭션에서 넣고(`ChatService.insertNotice`·`closeNotices`) 방의 마지막 번호를 올린다. 다 읽어 둔 사람(읽은 번호 = 안내 전의 마지막 번호)은 안내 줄까지 읽은 것으로 옮겨 안 읽은 수가 늘지 않는다 — 이미 밀려 있는 사람은 그대로라 그 사람의 수에는 안내 줄이 끼어 하나 늘 수 있다(번호만으로 세는 FR-2407 때문). 마지막 사람이 나가면 줄을 넣지 않는다. 안내 줄은 사람이 쓴 것이 아니라 **보내기 한도에 들지 않는다**. headless 클라이언트는 `kind`로 사람의 말과 가른다 — 안내 줄에는 답하지 않는다
- 메시지는 **고쳐 쓰지도 지우지도 않는 모양**으로 둔다(보류 39 — 정책이 정해지면 그 위에 얹는다). 앱 DB 계정에는 UPDATE·DELETE를 주지 않는 방안을 보류 39에서 본다.
- 앱 계정의 권한은 마이그레이션 단계가 **모든 표에 한꺼번에** 준다(`apps/api/src/db/app-role.ts` — DML 전부, `audit_events`만 예외). 새 표도 따로 더할 것이 없다. 메시지 표의 UPDATE·DELETE를 앱 계정에서 거두는 것은 보류 39에서 본다.

## E. API

화면용은 세션 + CSRF 머리말, headless용은 토큰이다. **본문과 응답은 같고** 경로 앞머리만 다르다(`/api/chat/…` ↔ `/api/v1/chat/…`).

| 메서드·경로 | 하는 일 | scope |
|---|---|---|
| `GET /rooms` | 내가 참여한 방 — 마지막 메시지 시각 순, `unread` 포함 | read |
| `GET /rooms/{id}` | 참여한 방 하나(목록의 한 항목과 같은 모양) | read |
| `POST /rooms` | `{kind:'direct', userId}` 또는 `{kind:'group', name, userIds[]}` | write |
| `POST /rooms/{id}/members` | 여럿 방에 초대(참여자 누구나 — 1:1 방은 403 `DIRECT_ROOM`) | write |
| `DELETE /rooms/{id}/members/me` | 방에서 나가기 | write |
| `GET /rooms/{id}/messages` | `beforeSeq`·`afterSeq`·`limit`(기본 50, 상한 200) | read |
| `POST /rooms/{id}/messages` | 보내기(`body`, `clientMsgId`) — WebSocket을 못 쓰는 곳용 | write |
| `PUT /rooms/{id}/read` | `{seq}` — 읽음 표시 | write |
| `GET /users` | 방에 부를 사람 찾기(이름) — 활성 사용자만, 이름·id만 | read |

공개 API의 명세(`openapi.yaml`)에는 위 REST를 **설명과 함께** 더한다(칸 설명이 빠지면 시험이 실패한다). **WebSocket은 OpenAPI가 표현하지 못하므로** 명세의 머리말(`info.description`)과 API사용가이드에 연결 방법·프레임 모양·재접속 규칙을 쓴다 — 에이전트가 명세만 읽고 접속할 수 있어야 한다.

## F. 보류 (보류 39로 등재)

보존 기간·메시지 삭제·관리자의 열람·감사 기록 대상 여부는 **나중에 정한다**(사용자 답 4). 이번에 하지 않는 것을 분명히 한다.

- 메시지는 지우지 않는다. 보존 기간이 없다.
- 관리자도 남의 방을 읽는 경로가 없다.
- 감사 기록에 채팅을 더하지 않는다(내용 없이 남길지는 그때 정한다). 다만 **연결 거절·한도 초과는 앱 로그**(`event` 코드, 내용 없이)에 남긴다.
- 트리거: 사내 보안 검토가 채팅의 보존·감사를 묻거나 방 수·메시지 수가 쌓여 정리가 필요할 때.

## I. 만들면서 풀린 것 (2026-10-12)

1. **토큰 단위로 끊기** — `RevocationBus`에 토큰 id를 열쇠로 받는 길(`revokeToken`)을 더했다. 토큰 한 개의 폐기(본인·관리자)는 그 토큰의 연결만 끊고, 세션을 모두 끊는 동작(`revoke(userId)`)은 그 사용자의 화면·headless 연결을 모두, 로그아웃(`sid`)은 그 세션의 연결만 끊는다. 만료·정지는 주기 재판정이 잡는다(`ApiTokensService.isLive`). 시험: `chat.gateway.integration.spec.ts` "끊기".
2. **여러 앱 인스턴스** — 이중화를 하지 않으므로(0.1절) 방 구독은 프로세스 안 메모리(`ChatHub`)다.
3. **업그레이드 분기** — 편집 게이트웨이가 채팅 경로(`readChatWsPath`)를 먼저 가려 건드리지 않고, 채팅 게이트웨이는 **꺼져 있어도** 자기 경로를 직접 404로 닫는다(응답 없이 열려 남는 소켓이 없다). 시험: 편집 게이트웨이의 `upgrade`를 채팅 경로로 불러 소켓에 아무것도 하지 않는지 + 편집 경로가 아닌 것은 여전히 404인지.
4. **빈도 제한** — 사용자 결정("추천대로"): 채팅 쓰기는 공개 API의 분당 30이 아니라 채팅 전용 한도(`WF_CHAT_SEND_PER_MIN`, 기본 60)만 쓴다. WebSocket은 연결마다, REST는 토큰마다(`ChatApiRateGuard`, 공개 API 쓰기 예산과 키가 달라 서로 소진시키지 않는다).
5. **한 연결의 프레임은 받은 순서대로 하나씩 처리한다** — 처음에는 프레임마다 바로 저장을 불러, 연달아 보낸 메시지의 번호가 뒤바뀔 수 있었다(시험이 잡았다). 연결마다 처리 줄(`chain`)을 둔다.
6. **방 목록은 연결과 상관없이 화면이 먼저 받는다** — 처음에는 `hello`를 받은 뒤에야 받아, 연결이 막히면 목록과 지난 메시지가 비어 보였다(컴포넌트 시험이 잡았다).
7. **병합 전 검토(2026-10-12)에서 고친 것** — ① 끊은 연결의 프레임은 처리하지 않는다(`ws.close()`는 핸드셰이크가 끝날 때까지 받기를 멈추지 않고 처리 줄에 쌓인 프레임도 있다) ② 보내기 한도는 사용자마다 한 예산(`SendLimiter` — 연결·토큰마다 세면 곱해지고 화면용 REST에는 한도가 없었다) ③ 연결이 선 직후 한 번 더 판정(인증과 `join` 사이의 폐기 경합) ④ 재접속 때 놓친 메시지는 한 번에 200개씩 이어서 받는다 ⑤ 받기 전인 방의 실시간 메시지를 버리지 않는다 ⑥ 연결 상한으로 밀려난(4409) 화면은 스스로 다시 붙지 않는다(서로 쫓아내는 되풀이) ⑦ 초대·나감을 남은 참여자에게도 알린다(`room` 프레임의 `members`) ⑧ 읽음 표시가 나가기와 겹치면 404 ⑨ 번호 질의의 상한(`CHAT_LIMITS.maxSeq`) ⑩ 채팅을 끄면 위 막대의 메뉴가 사라진다(`/api/auth/config`의 `chatEnabled`, FR-2420) ⑪ 프레임 상한이 글자 상한의 최악(글자당 4바이트)을 담지 못하면 기동을 거부한다(`WF_CHAT_MAX_FRAME_BYTES`) ⑫ `ChatInvite`의 lint 오류(검증기록의 "`pnpm check` 통과"가 그 시점에는 사실이 아니었다 — 초대 화면을 더한 뒤 다시 돌리지 않았다).
8. **알면서 두는 것** — 방 만들기·초대에는 횟수 제한과 상대의 동의·차단이 없다(괴롭힘·스팸 방을 받는 쪽이 없앨 길이 없다 — 1:1은 나갈 수 없다). 보류 39에서 보존·삭제와 함께 정한다. 사람 찾기는 활성 사용자 전원의 id·표시 이름을 연다(A.1-8). 연결 상한은 세션·토큰 구분 없이 사용자 단위라 탈취한 토큰이 그 사람의 화면 연결을 밀어낼 수 있다(가용성). 쓰기 쪽 느린 소비자는 `bufferedAmount`를 보지 않는다(ping에 답하지 못하면 끊긴다).
